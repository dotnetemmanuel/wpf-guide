PART 01

Where WPF stands today

WPF is a retained-mode, vector-based, resolution-independent UI framework. You describe a tree of elements; WPF composes it into a DirectX scene and re-renders what changed. Everything else in the framework follows from that one decision.

It shipped in 2006 on .NET Framework 3.0, moved to .NET Core 3.0 in 2019, and is now open source at dotnet/wpf, shipping yearly with the rest of .NET. Visual Studio's shell is still WPF. So are large parts of Office's add-in surface, most industrial and defence line-of-business tooling on Windows, and a long tail of internal tools nobody is going to rewrite.

What that means practically:

  • It is Windows only. The TFM is net10.0-windows. You need Windows to build and to run. There is no Linux story and there never will be.
  • It is in maintenance-plus mode. Yearly releases contain performance work, accessibility fixes, and incremental Fluent styling. No new layout system, no new binding engine.
  • The core API surface is frozen, which is why a 2013 book still works. Dependency properties, routed events, templates and binding have not changed.
  • Trimming and Native AOT are not supported. WPF leans on reflection everywhere (binding paths, XAML type resolution). Publish self-contained or framework-dependent, not trimmed.

Choosing WPF over the alternatives

PickWhen
WPFWindows-only desktop, rich data-heavy UI, dense forms, custom-drawn controls, an existing WPF codebase, or a team that already knows XAML. The deepest styling/templating system of anything in .NET.

What actually changed since the books were written

Keep this list in your head while reading anything published before 2020:

  • Project format. SDK-style .csproj, no packages.config, no AssemblyInfo.cs, no app.config for settings.
  • MVVM plumbing. CommunityToolkit.Mvvm source generators replace every hand-written INotifyPropertyChanged and ICommand in every old sample.
  • Composition. Microsoft.Extensions.Hosting gives you DI, configuration and logging. The books construct view models with new.
  • Async. async/await existed by 2013 but the idioms didn't. BackgroundWorker is gone from real code.
  • Theming. .NET 9 added a built-in Fluent theme and ThemeMode. The books' chapters on Aero/Luna theming are archaeology.
  • Gone entirely. XBAP and partial trust, WCF-as-default (HttpClient now), BinaryFormatter (removed in .NET 9, which breaks old clipboard and drag-drop code).
GOTCHA

WPF has no x:Bind. Compiled bindings are a UWP/WinUI feature. Every binding in WPF is reflection-based and resolved at runtime, which is why a typo in a Path fails silently instead of failing to build. Part 11 covers how to make those failures loud.

Project setup and startup

The project file

dotnet new wpf -n Tasks gets you this. It is the whole build configuration:

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <ApplicationIcon>app.ico</ApplicationIcon>
    <!-- Treat XAML binding failures as build-visible where possible -->
    <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="CommunityToolkit.Mvvm" Version="8.4.0" />
    <PackageReference Include="Microsoft.Extensions.Hosting" Version="10.0.0" />
    <PackageReference Include="Microsoft.Xaml.Behaviors.Wpf" Version="1.1.135" />
  </ItemGroup>

Notes on the properties that matter:

  • UseWPF pulls in the WPF reference assemblies and turns on the XAML build tasks. Setting UseWindowsForms alongside it is legal and is how you host WinForms controls.
  • net10.0-windows can be pinned to a Windows SDK version — net10.0-windows10.0.19041.0 — if you need WinRT APIs such as toast notifications.
  • Files under the project root ending in .xaml are implicitly Page items; App.xaml is implicitly ApplicationDefinition. You rarely need to declare either.

What the XAML compiler actually does

Each .xaml file with an x:Class produces a generated partial class containing field declarations for every x:Name and an InitializeComponent() method. That method loads a compiled binary form of the markup (BAML) embedded as a resource and walks it, instantiating objects and setting properties.

MainWindow.g.i.cs (generated) 
public partial class MainWindow : System.Windows.Window, IComponentConnector
{
    internal System.Windows.Controls.TextBox DraftBox;   // from x:Name="DraftBox"

    public void InitializeComponent()
    {
        if (_contentLoaded) return;
        _contentLoaded = true;
        var resourceLocater = new Uri("/Tasks;component/mainwindow.xaml", UriKind.Relative);
        System.Windows.Application.LoadComponent(this, resourceLocater);
    }

    void IComponentConnector.Connect(int connectionId, object target) { /* wires names + handlers */ }
}

Two consequences worth internalising. First, anything you do before InitializeComponent() runs will be overwritten by the markup. Set defaults after the call, or in the markup itself. Second, XAML is not interpreted at runtime in the normal case — but it can be, via XamlReader.Parse, which is how plugin skinning works.

That is fine for a toy. For anything real you want the window to come out of a container, so you delete StartupUri and override OnStartup. Part 15 builds this out properly; the shape is:

App.xaml.cs 
public partial class App : Application
{
    private readonly IHost _host;

    public App()
    {
        _host = Host.CreateApplicationBuilder().ConfigureServices().Build();
    }

    protected override async void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);
        await _host.StartAsync();
        _host.Services.GetRequiredService<MainWindow>().Show();
    }

    protected override async void OnExit(ExitEventArgs e)
    {
        using (_host) await _host.StopAsync(TimeSpan.FromSeconds(5));
        base.OnExit(e);
    }
}

Shutdown mode and single instance

ShutdownMode decides when the message loop ends: OnLastWindowClose (default), OnMainWindowClose, or OnExplicitShutdown — the last of which you need for tray applications, paired with a manual Application.Current.Shutdown().

Single-instance has no framework support. Use a named mutex:

C# 
private static Mutex? _single;

protected override void OnStartup(StartupEventArgs e)
{
    _single = new Mutex(initiallyOwned: true, @"Global\Tasks.App.SingleInstance", out bool isFirst);
    if (!isFirst)
    {
        // Optionally signal the running instance over a named pipe, then:
        Shutdown();
        return;
    }
    base.OnStartup(e);
}

Unhandled exceptions

Three separate hooks, and you want all three. DispatcherUnhandledException catches exceptions on the UI thread and lets you mark them handled; TaskScheduler.UnobservedTaskException catches faulted tasks nobody awaited; AppDomain.CurrentDomain.UnhandledException is the last resort and is not recoverable.

C# 
public App()
{
    DispatcherUnhandledException += (_, e) =>
    {
        _logger.LogError(e.Exception, "Unhandled UI exception");
        MessageBox.Show("Something went wrong. The action was cancelled.",
                        "Tasks", MessageBoxButton.OK, MessageBoxImage.Error);
        e.Handled = true;              // keep the app alive
    };

    TaskScheduler.UnobservedTaskException += (_, e) =>
    {
        _logger.LogError(e.Exception, "Unobserved task exception");
        e.SetObserved();
    };

    AppDomain.CurrentDomain.UnhandledException += (_, e) =>
        _logger.LogCritical(e.ExceptionObject as Exception, "Fatal");
}
GOTCHA

async void OnStartup is one of the few places async void is correct — the framework gives you no awaitable override. But an exception thrown after the first await inside it will not hit DispatcherUnhandledException reliably. Wrap the body in a try/catch yourself.

PART 03

XAML, precisely

XAML is an object graph serialisation format. Every element is a type, every attribute is a property or an event, and the whole document is a constructor call tree. Once you see it that way the odd corners stop being odd.

Namespaces

XAML 
<Window
  xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
  xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
  xmlns:sys="clr-namespace:System;assembly=System.Runtime"
  xmlns:vm="clr-namespace:Tasks.ViewModels"
  xmlns:ctrl="clr-namespace:Tasks.Controls"
  xmlns:b="http://schemas.microsoft.com/xaml/behaviors"
  xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
  xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
  mc:Ignorable="d"
  d:DataContext="{d:DesignInstance vm:MainViewModel}">
  • The default namespace maps to every WPF UI assembly at once, via XmlnsDefinition attributes on those assemblies.
  • The x: namespace is the XAML language itself — x:Class, x:Name, x:Key, x:Type, x:Static, x:Array, x:Null.
  • clr-namespace: maps your own types. The ;assembly= part is only needed for types outside the current assembly.
  • d: and mc:Ignorable="d" are design-time only; the compiler strips them. d:DataContext gives the designer and IntelliSense a type to bind against, which is how you get autocomplete on binding paths.

Property syntax, three ways

XAML 
<!-- 1. attribute syntax: value goes through a TypeConverter -->
<Button Background="SteelBlue" Margin="4,8" />

<!-- 2. property element syntax: for values that aren't expressible as a string -->
<Button>
  <Button.Background>
    <LinearGradientBrush StartPoint="0,0" EndPoint="0,1">
      <GradientStop Offset="0" Color="#3B6FD4" />
      <GradientStop Offset="1" Color="#22458A" />
    </LinearGradientBrush>
  </Button.Background>
</Button>

<!-- 3. content syntax: the type's [ContentProperty] takes the children implicitly -->
<Button>                         <!-- Button's ContentProperty is Content -->
  <StackPanel Orientation="Horizontal">
    <Path Data="M0,0 L8,4 L0,8 Z" Fill="White" Width="8" Height="8" />
    <TextBlock Text="Run" Margin="6,0,0,0" />
  </StackPanel>
</Button>

"4,8" becoming a Thickness and "SteelBlue" becoming a SolidColorBrush are both TypeConverter work. Your own types get the same treatment if you attribute them with [TypeConverter(typeof(MyConverter))].

Markup extensions

Anything in braces is a markup extension: an object that is constructed at parse time and asked to provide a value for the property. They are not string interpolation.

x:Name versus Name, and escaping

Name is a real CLR property on FrameworkElement; x:Name is the XAML-level directive. On a FrameworkElement they do the same thing and you cannot set both. On anything that isn't a FrameworkElement — a Storyboard, a converter in a resource dictionary — only x:Name works. Default to x:Name and stop thinking about it.

Escapes you will hit:

XAML 
<!-- literal braces: escape with an empty pair -->
<TextBlock Text="{}{not a binding}" />

<!-- comma inside a markup extension parameter: quote it -->
<TextBlock Text="{Binding Total, StringFormat='{}{0:N2} kr'}" />

<!-- whitespace preservation -->
<TextBlock xml:space="preserve">  indented  </TextBlock>

<!-- a null-safe empty string -->
<TextBlock Text="{x:Null}" />
GOTCHA

StringFormat needs a leading {} whenever the format string itself starts with {, otherwise the parser sees a markup extension. StringFormat='{}{0:N2}' works; StringFormat='{0:N2}' throws at load.

PART 04

Layout

Layout is a two-pass recursive negotiation. Understand the two passes and every panel's behaviour becomes predictable.

Measure, then arrange

Measure. A parent calls child.Measure(availableSize), saying "here is the space I could give you". The child measures its own children, then reports DesiredSize — what it wants. Available size can be double.PositiveInfinity in a dimension, which means "ask for whatever you like"; a StackPanel passes infinity along its orientation, a ScrollViewer passes infinity in its scrolling direction.

Arrange. The parent decides and calls child.Arrange(finalRect), saying "here is what you actually get". The child may be given less than it asked for, and must cope. This is where HorizontalAlignment, VerticalAlignment and Margin are applied.

The rules that follow from this:

  • A child inside a StackPanel with Orientation="Vertical" gets infinite height at measure, so Height="Auto" means "as tall as I want" and vertical alignment does nothing.
  • A ScrollViewer only scrolls if its content asked for more than it got, which is why putting a ListBox inside a vertical StackPanel produces an infinitely tall list that never scrolls. Use a Grid or DockPanel instead.
  • Width/Height constrain the measure pass. MinWidth/MaxWidth clamp it. ActualWidth/ActualHeight are the arrange results and are zero until the first layout pass completes.

Writing a custom panel

Override two methods. This one lays children out on a circle — the shape of the code is the same for any layout algorithm you need:

C# 
public sealed class RadialPanel : Panel
{
    public static readonly DependencyProperty RadiusProperty =
        DependencyProperty.Register(
            nameof(Radius), typeof(double), typeof(RadialPanel),
            new FrameworkPropertyMetadata(100d,
                FrameworkPropertyMetadataOptions.AffectsMeasure |
                FrameworkPropertyMetadataOptions.AffectsArrange));

    public double Radius
    {
        get => (double)GetValue(RadiusProperty);
        set => SetValue(RadiusProperty, value);
    }

    protected override Size MeasureOverride(Size availableSize)
    {
        // Let every child take as much as it likes, then claim a square.
        var loose = new Size(double.PositiveInfinity, double.PositiveInfinity);
        double maxChild = 0;
        foreach (UIElement child in InternalChildren)
        {
            child.Measure(loose);
            maxChild = Math.Max(maxChild,
                Math.Max(child.DesiredSize.Width, child.DesiredSize.Height));
        }
        double side = (Radius + maxChild / 2) * 2;
        return new Size(side, side);
    }

    protected override Size ArrangeOverride(Size finalSize)
    {
        int n = InternalChildren.Count;
        if (n == 0) return finalSize;

        var centre = new Point(finalSize.Width / 2, finalSize.Height / 2);
        for (int i = 0; i < n; i++)
        {
            var child = InternalChildren[i];
            double angle = 2 * Math.PI * i / n - Math.PI / 2;
            var size = child.DesiredSize;
            var topLeft = new Point(
                centre.X + Radius * Math.Cos(angle) - size.Width / 2,
                centre.Y + Radius * Math.Sin(angle) - size.Height / 2);
            child.Arrange(new Rect(topLeft, size));
        }
        return finalSize;
    }
}
RULE

Any dependency property that changes how big something is must declare AffectsMeasure; anything that changes where it sits must declare AffectsArrange. Forget these and your panel simply won't update when the property changes.

Layout rounding and DPI

WPF units are device-independent: 1 unit = 1/96 inch. On a 150% display, 96 units is 144 physical pixels. That is why WPF scales cleanly and why a 1-unit border sometimes renders blurry — it lands between device pixels.

UseLayoutRounding="True" (set it on your window; it inherits) snaps layout results to device pixels and fixes almost all of it. For hairlines inside a shape, SnapsToDevicePixels="True" is the older, cruder sibling — prefer layout rounding.

Per-monitor DPI awareness is on by default for .NET Core-era WPF, but only if the manifest says so. Check app.manifest contains PerMonitorV2 if you have a mixed-DPI setup, which matters immediately for anyone docking a laptop to a 4K display.

PART 05

Dependency properties

The single most important idea in WPF, and the one with no equivalent in the rest of .NET. A dependency property is a property whose value is computed from many possible sources, ranked by precedence, and stored sparsely.

Why they exist

A Button has several hundred properties. Storing a field for each, on every button in a grid of ten thousand rows, would be ruinous. Instead, a dependency property is a static registration shared by the type, and values are stored per-instance in a sparse table — only for properties that were actually set.

Sparse storage is the cheap benefit. The real benefit is that the framework can participate in the value. Styles, templates, animations, inheritance from the parent element, and data bindings all set values without fighting each other, because each is a distinct source at a distinct precedence.

Declaring one

C# 
public class RatingBar : Control
{
    public static readonly DependencyProperty ValueProperty =
        DependencyProperty.Register(
            name:         nameof(Value),
            propertyType: typeof(int),
            ownerType:    typeof(RatingBar),
            typeMetadata: new FrameworkPropertyMetadata(
                defaultValue:     0,
                flags:            FrameworkPropertyMetadataOptions.AffectsRender |
                                  FrameworkPropertyMetadataOptions.BindsTwoWayByDefault,
                propertyChangedCallback: OnValueChanged,
                coerceValueCallback:     CoerceValue),
            validateValueCallback: v => v is int i && i >= 0);

    // The CLR wrapper is a convenience only. WPF NEVER calls it —
    // XAML and binding go straight to SetValue/GetValue.
    public int Value
    {
        get => (int)GetValue(ValueProperty);
        set => SetValue(ValueProperty, value);
    }

    private static void OnValueChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        var bar = (RatingBar)d;
        bar.RaiseEvent(new RoutedEventArgs(ValueChangedEvent, bar));
    }

    private static object CoerceValue(DependencyObject d, object baseValue)
    {
        var bar = (RatingBar)d;
        return Math.Clamp((int)baseValue, 0, bar.Maximum);
    }
}
GOTCHA

Never put logic in the CLR wrapper. Put it in the PropertyChangedCallback. The wrapper is bypassed entirely when the value is set from XAML, from a style, from an animation, or from a binding — which is most of the time.

The three callbacks fire in a fixed order and do different jobs:

  • ValidateValueCallback — static, no instance access, returns bool. Throws ArgumentException on false. Use for "no negative sizes ever".
  • CoerceValueCallback — has the instance, so it can clamp against another property. Use for "Value must not exceed Maximum". Call CoerceValue(ValueProperty) from Maximum's changed callback so the clamp re-runs.
  • PropertyChangedCallback — fires only when the effective value actually changed. Where your side effects go.

Value precedence

When several sources set the same property, this is the order, highest first. Memorise it; almost every "why isn't my style applying" question is answered here.

#Source
1Property system coercion
2Active animations, or a held animation
3Local value — SetValue, an attribute in XAML, or a Binding you wrote directly on the element
4TemplatedParent template properties (triggers in the template, then setters)
5Implicit style setters (from a Style keyed by {x:Type})
6Style triggers
7Template triggers (from the ControlTemplate)
8Style setters
9Theme style triggers
10Theme style setters
11Property value inheritance (FontSize, DataContext, FlowDirection…)
12Default value from metadata

The practical consequences:

  • A local value beats every style and trigger. Set Background="Red" on a button and no IsMouseOver trigger will ever change it. This is the single most common WPF confusion. Fix it by moving the value into the style's setters.
  • An animation beats a local value and keeps beating it after the animation finishes, unless the animation has FillBehavior="Stop". Call BeginAnimation(prop, null) to release the hold.
  • Clearing is not setting to default. ClearValue(prop) removes the local value and lets the next source win; SetValue(prop, default) installs a local value that happens to equal the default and continues to block styles.

Attached properties

An attached property is a dependency property registered by one type and set on instances of another. Grid.Row is the canonical example: the Grid owns it, but you set it on the child.

C# 
public static class Watermark
{
    public static readonly DependencyProperty TextProperty =
        DependencyProperty.RegisterAttached(
            "Text", typeof(string), typeof(Watermark),
            new FrameworkPropertyMetadata(null, OnTextChanged));

    public static void SetText(DependencyObject element, string value)
        => element.SetValue(TextProperty, value);

    public static string GetText(DependencyObject element)
        => (string)element.GetValue(TextProperty);

    private static void OnTextChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not TextBox box) return;
        box.GotFocus  -= Repaint;  box.GotFocus  += Repaint;
        box.LostFocus -= Repaint;  box.LostFocus += Repaint;
        Repaint(box, EventArgs.Empty);
    }

    private static void Repaint(object? sender, EventArgs e) { /* swap an adorner in/out */ }
}
XAML 
<TextBox local:Watermark.Text="Search tasks…" />

The Get/Set static methods are not optional — the XAML parser finds the property by convention from those names. This pattern is how you add behaviour to a sealed framework control without subclassing, and it is the basis of "attached behaviours".

Attached behaviours in practice

A frequent need: give an untouchable third-party control a command-on-double-click. No subclass required.

C# 
public static class DoubleClick
{
    public static readonly DependencyProperty CommandProperty =
        DependencyProperty.RegisterAttached(
            "Command", typeof(ICommand), typeof(DoubleClick),
            new PropertyMetadata(null, OnCommandChanged));

    public static void SetCommand(DependencyObject d, ICommand? v) => d.SetValue(CommandProperty, v);
    public static ICommand? GetCommand(DependencyObject d) => (ICommand?)d.GetValue(CommandProperty);

    private static void OnCommandChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not Control c) return;
        c.MouseDoubleClick -= Handle;
        if (e.NewValue is not null) c.MouseDoubleClick += Handle;
    }

    private static void Handle(object sender, MouseButtonEventArgs e)
    {
        var c = (Control)sender;
        var command = GetCommand(c);
        var parameter = (c as FrameworkElement)?.DataContext;
        if (command?.CanExecute(parameter) == true) command.Execute(parameter);
    }
}

              Value="{Binding DataContext.OpenCommand, RelativeSource={RelativeSource AncestorType=ListBox}}" />
    </Style>
  </ListBox.ItemContainerStyle>
</ListBox>

PART 06

Routed events and commands

Three routing strategies

A routed event travels the visual tree rather than firing on one object:

  • Tunnelling — from the root down to the source. Named PreviewXxx by convention. Fires first.
  • Bubbling — from the source up to the root. Named Xxx. Fires after the tunnel completes.
  • Direct — fires only on the source, like a normal CLR event, but still participates in the event system (so it can be used in an EventSetter).

Bubbling is why you can put one handler on a panel and catch clicks from every button inside it:

XAML + C# 
<StackPanel ButtonBase.Click="OnAnyButtonClick">
  <Button Content="Copy"  Tag="copy"  />
  <Button Content="Paste" Tag="paste" />
</StackPanel>
C# 
private void OnAnyButtonClick(object sender, RoutedEventArgs e)
{
    // sender     = the StackPanel (where the handler is attached)
    // e.Source   = the logical source, usually the Button
    // e.OriginalSource = the deepest visual hit, maybe the TextBlock inside it
    if (e.OriginalSource is not DependencyObject d) return;
    var button = d as Button ?? TreeSearch.FindAncestor<Button>(d);   // Part 07
    Dispatch(button?.Tag as string);
    e.Handled = true;             // stops the bubble here
}
GOTCHA

e.Source and e.OriginalSource differ. OriginalSource is the raw visual hit — often a TextBlock or Border inside a control template. Source is the logical-tree element the event is attributed to. For hit-testing in a list, you almost always want OriginalSource plus a walk up to the container.

Setting e.Handled = true stops further handlers — unless a handler was registered with handledEventsToo:

C# 
// Runs even if something lower already marked the event handled.
myPanel.AddHandler(UIElement.MouseLeftButtonDownEvent,
                   new MouseButtonEventHandler(OnDown),
                   handledEventsToo: true);

You need this more often than you'd like, because several built-in controls mark events handled internally. TextBox handles MouseLeftButtonDown; ListBoxItem handles it too. Tunnelled Preview events are the other escape hatch — they fire before the control gets a chance to swallow anything.

Declaring a routed event

C# 
public static readonly RoutedEvent RatingChangedEvent =
    EventManager.RegisterRoutedEvent(
        nameof(RatingChanged), RoutingStrategy.Bubble,
        typeof(RoutedPropertyChangedEventHandler<int>), typeof(RatingBar));

public event RoutedPropertyChangedEventHandler<int> RatingChanged
{
    add    => AddHandler(RatingChangedEvent, value);
    remove => RemoveHandler(RatingChangedEvent, value);
}

private void Raise(int oldValue, int newValue) =>
    RaiseEvent(new RoutedPropertyChangedEventArgs<int>(oldValue, newValue, RatingChangedEvent));

Commands

A command decouples "what the user asked for" from "which control asked". WPF ships two mechanisms and they are easy to confuse.

RoutedCommand — the built-in one

ApplicationCommands.Save, EditingCommands.ToggleBold and friends are RoutedUICommands. They route through the tree looking for a CommandBinding that handles them, and they come with default key gestures for free.

XAML 
<Window.CommandBindings>
  <CommandBinding Command="ApplicationCommands.Save"
                  Executed="OnSave" CanExecute="OnCanSave" />
</Window.CommandBindings>

<Menu>
  <MenuItem Header="_File">
    <!-- picks up the header text AND Ctrl+S automatically -->
    <MenuItem Command="ApplicationCommands.Save" />
  </MenuItem>
</Menu>

Good for text-editing verbs and anything where the target depends on focus — a cut/copy/paste toolbar that should act on whichever text box is active gets this for free. Bad for view-model logic, because CommandBinding handlers live in code-behind.

ICommand on the view model — what you'll actually use

C# 
public interface ICommand
{
    bool CanExecute(object? parameter);
    void Execute(object? parameter);
    event EventHandler? CanExecuteChanged;
}

Write these by hand exactly once, to understand them, then use [RelayCommand] from the Community Toolkit forever after (Part 14). The one thing worth knowing is how CanExecuteChanged gets raised, because that is where hand-rolled implementations go wrong.

WPF's CommandManager re-queries CanExecute on every focus change, keyboard event and mouse-up. Hooking into it is a one-liner and is what the old RelayCommand samples do:

C# 
public event EventHandler? CanExecuteChanged
{
    add    => CommandManager.RequerySuggested += value;
    remove => CommandManager.RequerySuggested -= value;
}

It works, and it is wasteful: every command in the visual tree is re-evaluated on every keystroke. Prefer explicit notification (command.NotifyCanExecuteChanged()) and reserve CommandManager.InvalidateRequerySuggested() for the cases where something outside your control changed.

Input bindings

XAML 
<Window.InputBindings>
  <KeyBinding Key="S" Modifiers="Ctrl"       Command="{Binding SaveCommand}" />
  <KeyBinding Key="F5"                       Command="{Binding RefreshCommand}" />
  <KeyBinding Key="Delete"                   Command="{Binding DeleteCommand}"
                                             CommandParameter="{Binding SelectedItem}" />
  <MouseBinding MouseAction="MiddleClick"    Command="{Binding CloseTabCommand}" />
</Window.InputBindings>
GOTCHA

InputBindings is not a dependency property, so <KeyBinding Command="{Binding …}" /> inside a Style setter doesn't work, and KeyBinding objects created before the DataContext is set will bind against null. On a Window it's fine. Inside a UserControl or a template, use CommandBindings or a behaviour instead.

ItemsControl and containers

This is the mechanism behind every list in WPF. For each item in ItemsSource, the control:

  1. Checks IsItemItsOwnContainerOverride — if the item is already a ListBoxItem, use it directly.
  2. Otherwise calls GetContainerForItemOverride to create one (ListBoxItem, ComboBoxItem, TreeViewItem, DataGridRow…).
  3. Sets the container's Content to the item and its DataContext to the item.
  4. Applies ItemTemplate as the container's ContentTemplate.

Logical tree versus visual tree

The logical tree is what you wrote in XAML: window → panel → button → string. It carries DataContext, resource lookup, and property value inheritance.

The visual tree is the expansion after templates are applied: window → border → panel → button → chrome border → content presenter → text block. It is what gets rendered and hit-tested, and what routed events travel.

C# 
public static class TreeSearch
{
public static T? FindAncestor<T>(DependencyObject start) where T : DependencyObject
{
    for (var d = start; d is not null; d = VisualTreeHelper.GetParent(d))
        if (d is T match) return match;
    return null;
}

public static IEnumerable<T> FindDescendants<T>(DependencyObject root) where T : DependencyObject
{
    for (int i = 0; i < VisualTreeHelper.GetChildrenCount(root); i++)
    {
        var child = VisualTreeHelper.GetChild(root, i);
        if (child is T match) yield return match;
        foreach (var nested in FindDescendants<T>(child)) yield return nested;
    }
}
}
GOTCHA

The visual tree does not exist until the template has been applied. VisualTreeHelper returns nothing in a constructor. Do this work in OnApplyTemplate for a custom control, or in the Loaded event otherwise. And if you find yourself walking the visual tree in application code rather than control code, there is usually a binding that would do the job instead.

PART 08

Resources

Every FrameworkElement has a ResourceDictionary. Lookup walks up the logical tree, then the application, then the theme dictionaries, then the system.

The lookup order

  1. The element's own Resources.
  2. Each logical-tree ancestor's Resources, in order, up to the window.
  3. Application.Current.Resources (and its merged dictionaries, searched last to first).
  4. The theme dictionary for the current Windows theme, in themes/generic.xaml of each assembly that declares ThemeInfo.
  5. SystemColors, SystemFonts, SystemParameters.
GOTCHA

Merged dictionaries are searched in reverse order, so the last one listed wins. This is the opposite of what almost everyone assumes and the reason your override dictionary has no effect when you put it first.

Static versus dynamic

StaticResourceDynamicResource
ResolvedOnce, at loadOn every change, at runtime
Missing keyThrows at load (loud, good)Silently nothing
CostNear zeroKeeps a live reference; measurable in large trees
TargetAny propertyDependency properties only
Forward refsNo — must be defined earlier in the fileYes

Rule of thumb: StaticResource everywhere, DynamicResource only for values that genuinely change at runtime — theme brushes, system colours, and anything a user can switch in settings.

Organising a dictionary

Themes/Colors.xaml 
<ResourceDictionary
  xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
  xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
  xmlns:sys="clr-namespace:System;assembly=System.Runtime"
  xmlns:po="http://schemas.microsoft.com/winfx/2006/xaml/presentation/options">

  <Color x:Key="Accent"      >#286983</Color>
  <Color x:Key="Danger"      >#B4352C</Color>
  <Color x:Key="SurfaceLow"  >#faf4ed</Color>

  <SolidColorBrush x:Key="AccentBrush" Color="{StaticResource Accent}" po:Freeze="True" />
  <SolidColorBrush x:Key="DangerBrush" Color="{StaticResource Danger}" po:Freeze="True" />

  <CornerRadius x:Key="ControlCornerRadius">4</CornerRadius>
  <sys:Double   x:Key="DenseRowHeight">22</sys:Double>
</ResourceDictionary>

po:Freeze="True" on a brush makes it immutable, which removes change-tracking overhead and lets it be shared across threads. Freeze every brush, pen and geometry in your theme dictionary — it is measurable on large trees.

App.xaml 
<Application.Resources>
  <ResourceDictionary>
    <ResourceDictionary.MergedDictionaries>
      <ResourceDictionary Source="/Tasks;component/Themes/Colors.xaml" />
      <ResourceDictionary Source="/Tasks;component/Themes/Typography.xaml" />
      <ResourceDictionary Source="/Tasks;component/Themes/Controls.xaml" />
      <!-- last wins: project-specific overrides go here -->
      <ResourceDictionary Source="/Tasks;component/Themes/Overrides.xaml" />
    </ResourceDictionary.MergedDictionaries>

    <!-- Converters and shared data templates -->
    <conv:BoolToVisibilityConverter x:Key="BoolToVis" />
  </ResourceDictionary>
</Application.Resources>

The /Assembly;component/Path.xaml form is a pack URI. Use it when the dictionary lives in another assembly; a plain relative path is fine within one project.

Swapping themes at runtime

The pattern: one slot in the merged dictionary list that you replace wholesale, and DynamicResource at every usage site.

C# 
public sealed class ThemeService
{
    private ResourceDictionary? _current;

    public void Apply(AppTheme theme)
    {
        var uri = new Uri($"/Tasks;component/Themes/{theme}.xaml", UriKind.Relative);
        var next = new ResourceDictionary { Source = uri };

        var merged = Application.Current.Resources.MergedDictionaries;
        if (_current is not null) merged.Remove(_current);
        merged.Add(next);          // last wins
        _current = next;
    }
}

PART 09

Styles and triggers

A style is a named bag of property setters plus conditional overrides. It is CSS with type safety and without the cascade.

Keyed and implicit styles

XAML 
<!-- Implicit: applies to every Button in scope, no opt-in -->
<Style TargetType="{x:Type Button}">
  <Setter Property="Padding"    Value="12,6" />
  <Setter Property="MinWidth"   Value="88" />
  <Setter Property="FontFamily" Value="{StaticResource UiFont}" />
</Style>

<!-- Keyed: opt-in by key -->
<Style x:Key="PrimaryButton" TargetType="Button"
       BasedOn="{StaticResource {x:Type Button}}">
  <Setter Property="Background" Value="{StaticResource AccentBrush}" />
  <Setter Property="Foreground" Value="White" />
  <Setter Property="FontWeight" Value="SemiBold" />
</Style>

<Button Style="{StaticResource PrimaryButton}" Content="Save" />

BasedOn="{StaticResource {x:Type Button}}" is the idiom for "inherit from the implicit style". Without it, a keyed style silently replaces the implicit one instead of extending it — including the theme style, which is how people accidentally delete their control's entire appearance.

GOTCHA

Implicit styles do not apply to derived types. A Style TargetType="Button" won't touch a ToggleButton, even though ToggleButton derives from ButtonBase and not the other way round. There is no wildcard. You write one style per concrete type, usually with BasedOn chaining to a shared base.

Trigger types

XAML 
<Style TargetType="Button" x:Key="PrimaryButton">
  <Setter Property="Background" Value="{StaticResource AccentBrush}" />

  <Style.Triggers>

    <!-- Property trigger: one dependency property on THIS element -->
    <Trigger Property="IsMouseOver" Value="True">
      <Setter Property="Background" Value="{StaticResource AccentHoverBrush}" />
    </Trigger>

    <Trigger Property="IsEnabled" Value="False">
      <Setter Property="Opacity" Value="0.45" />
    </Trigger>

    <!-- MultiTrigger: all conditions must hold -->
    <MultiTrigger>
      <MultiTrigger.Conditions>
        <Condition Property="IsMouseOver" Value="True" />
        <Condition Property="IsPressed"   Value="True" />
      </MultiTrigger.Conditions>
      <Setter Property="RenderTransform">
        <Setter.Value><ScaleTransform ScaleX="0.98" ScaleY="0.98" /></Setter.Value>
      </Setter>
    </MultiTrigger>

    <!-- DataTrigger: any BINDING, so any view-model property -->
    <DataTrigger Binding="{Binding IsDirty}" Value="True">
      <Setter Property="Content" Value="Save *" />
    </DataTrigger>

    <!-- MultiDataTrigger: several bindings -->
    <MultiDataTrigger>
      <MultiDataTrigger.Conditions>
        <Condition Binding="{Binding IsDirty}"    Value="True" />
        <Condition Binding="{Binding IsReadOnly}" Value="False" />
      </MultiDataTrigger.Conditions>
      <Setter Property="IsDefault" Value="True" />
    </MultiDataTrigger>

    <!-- EventTrigger: starts a storyboard, cannot set properties -->
    <EventTrigger RoutedEvent="Button.Click">
      <BeginStoryboard>
        <Storyboard>
          <DoubleAnimation Storyboard.TargetProperty="Opacity"
                           From="1" To="0.6" Duration="0:0:0.08" AutoReverse="True" />
        </Storyboard>
      </BeginStoryboard>
    </EventTrigger>

  </Style.Triggers>
</Style>

Triggers are declarative and reversible. When the condition stops holding, the previous value comes back automatically — you never write the "undo". That is the reason to prefer a trigger over an event handler that sets a property.

EventSetter

The one way to attach a handler from a style. It only works in a Style, not a ControlTemplate, and the handler must live in code-behind:

XAML 
<Style TargetType="ListBoxItem">
  <EventSetter Event="MouseDoubleClick" Handler="OnItemDoubleClick" />
</Style>

Conditional styling without triggers

Two alternatives worth knowing, because triggers get verbose:

XAML 
<!-- A. Style selector via DataTemplate DataType — different type, different look -->
<DataTemplate DataType="{x:Type vm:ErrorMessage}">   ... </DataTemplate>
<DataTemplate DataType="{x:Type vm:InfoMessage}">    ... </DataTemplate>

<!-- B. A converter that maps a value to a brush, for many-valued cases -->
<TextBlock Foreground="{Binding Severity, Converter={StaticResource SeverityToBrush}}" />

Rule: two states, use a trigger. Many states driven by an enum, use a converter. Genuinely different shapes of content, use a DataTemplate per type.

PART 10

Templates

A ControlTemplate replaces a control's appearance while keeping its behaviour. A DataTemplate decides how a data object is drawn. Between them they are the reason WPF is still worth using.

ControlTemplate

A Button's behaviour — click detection, keyboard activation, command invocation, IsPressed — lives in ButtonBase. Its appearance is entirely in a replaceable template. Swap the template and you still have a real button.

XAML 
<Style x:Key="PillButton" TargetType="Button">
  <Setter Property="Background"      Value="{StaticResource AccentBrush}" />
  <Setter Property="Foreground"      Value="White" />
  <Setter Property="Padding"         Value="16,7" />
  <Setter Property="BorderThickness" Value="1" />
  <Setter Property="Cursor"          Value="Hand" />

  <Setter Property="Template">
    <Setter.Value>
      <ControlTemplate TargetType="Button">
        <Border x:Name="Root"
                Background="{TemplateBinding Background}"
                BorderBrush="{TemplateBinding BorderBrush}"
                BorderThickness="{TemplateBinding BorderThickness}"
                Padding="{TemplateBinding Padding}"
                CornerRadius="999"
                SnapsToDevicePixels="True">
          <ContentPresenter x:Name="Content"
                            HorizontalAlignment="Center"
                            VerticalAlignment="Center"
                            RecognizesAccessKey="True" />
        </Border>

        <ControlTemplate.Triggers>
          <Trigger Property="IsMouseOver" Value="True">
            <Setter TargetName="Root" Property="Opacity" Value="0.9" />
          </Trigger>
          <Trigger Property="IsPressed" Value="True">
            <Setter TargetName="Content" Property="Margin" Value="0,1,0,-1" />
          </Trigger>
          <Trigger Property="IsKeyboardFocused" Value="True">
            <Setter TargetName="Root" Property="BorderBrush"
                    Value="{StaticResource FocusBrush}" />
          </Trigger>
          <Trigger Property="IsEnabled" Value="False">
            <Setter TargetName="Root" Property="Opacity" Value="0.4" />
          </Trigger>
        </ControlTemplate.Triggers>
      </ControlTemplate>
    </Setter.Value>
  </Setter>
</Style>

Three things carry the weight here:

  • TemplateBinding is a lightweight, one-way, compile-time-resolved binding to the templated control's own property. Use it inside templates; it is meaningfully faster than {Binding RelativeSource={RelativeSource TemplatedParent}}. Use the long form only when you need two-way, a converter, or a nested path.
  • ContentPresenter is where Content lands. It automatically picks up ContentTemplate and ContentStringFormat from the templated parent. For an ItemsControl the equivalent is ItemsPresenter.
  • Setter TargetName is only legal inside ControlTemplate.Triggers, not Style.Triggers. A style trigger cannot reach into the template's named parts.

The parts-and-states contract

When you write a custom control you must publish which named parts your template is expected to contain, and look them up defensively:

C# 
[TemplatePart(Name = PartTrack,  Type = typeof(FrameworkElement))]
[TemplatePart(Name = PartThumb,  Type = typeof(Thumb))]
public class RangeSlider : Control
{
    public const string PartTrack = "PART_Track";
    public const string PartThumb = "PART_Thumb";

    private Thumb? _thumb;

    static RangeSlider()
    {
        // Tells WPF to look for the default template in themes/generic.xaml
        DefaultStyleKeyProperty.OverrideMetadata(
            typeof(RangeSlider), new FrameworkPropertyMetadata(typeof(RangeSlider)));
    }

    public override void OnApplyTemplate()
    {
        base.OnApplyTemplate();

        if (_thumb is not null) _thumb.DragDelta -= OnDrag;

        _thumb = GetTemplateChild(PartThumb) as Thumb;   // may legitimately be null
        if (_thumb is not null) _thumb.DragDelta += OnDrag;
    }

    private void OnDrag(object sender, DragDeltaEventArgs e) { /* … */ }
}

Unhooking before re-hooking matters: OnApplyTemplate runs again every time the template is replaced, and a theme switch does exactly that.

DataTemplate

A DataTemplate keyed by DataType rather than x:Key becomes an implicit template: any time WPF is asked to render an object of that type without an explicit template, it finds this one.

XAML 
<Application.Resources>
  <DataTemplate DataType="{x:Type vm:CustomerViewModel}">
    <views:CustomerView />
  </DataTemplate>
  <DataTemplate DataType="{x:Type vm:InvoiceViewModel}">
    <views:InvoiceView />
  </DataTemplate>
</Application.Resources>

<!-- Anywhere in the app: -->
<ContentControl Content="{Binding CurrentPage}" />

That six-line pattern is view-model-first navigation. Set CurrentPage to an InvoiceViewModel and the invoice view appears. No navigation framework, no view locator, no code. It is the single most valuable thing in WPF's design and the thing most worth building your application architecture around.

DataTemplateSelector

For when the choice isn't by type — say, by a property value:

public sealed class MessageTemplateSelector : DataTemplateSelector

    public DataTemplate? Compact { get; set; }

Data binding

The engine everything else leans on. A binding is an object that watches a source property and pushes values into a target dependency property, with optional conversion, validation and fallbacks.

Anatomy

XAML 
<TextBox Text="{Binding Path=Customer.Name,
                        Mode=TwoWay,
                        UpdateSourceTrigger=PropertyChanged,
                        Converter={StaticResource Trim},
                        ConverterParameter=NFC,
                        StringFormat='{}{0}',
                        FallbackValue='(unavailable)',
                        TargetNullValue='(none)',
                        Delay=300,
                        ValidatesOnDataErrors=True,
                        NotifyOnValidationError=True}" />
PartMeaning
PathDotted property path from the source. Path= is optional in first position.
ModeOneWay, TwoWay, OneWayToSource, OneTime, or Default (per-property metadata; TextBox.Text defaults to two-way).
UpdateSourceTriggerWhen the target pushes back: LostFocus (default for Text), PropertyChanged, Explicit.
FallbackValueUsed when the binding fails to resolve at all.
TargetNullValueUsed when the source resolves to null.
DelayMilliseconds to debounce source updates. Excellent on search boxes.

Where the source comes from

Exactly one of these, or none — in which case it's the inherited DataContext:

XAML 
<!-- 1. DataContext (inherited down the logical tree). The normal case. -->
<TextBlock Text="{Binding Title}" />

<!-- 2. ElementName: another named element in the same name scope -->
<Slider x:Name="Zoom" Minimum="0.5" Maximum="3" />
<TextBlock Text="{Binding Value, ElementName=Zoom, StringFormat={}{0:P0}}" />

<!-- 3. RelativeSource Self: this element -->
<TextBox ToolTip="{Binding Text, RelativeSource={RelativeSource Self}}" />

<!-- 4. RelativeSource AncestorType: walk up the visual tree -->
<Button Command="{Binding DataContext.DeleteCommand,
                          RelativeSource={RelativeSource AncestorType=DataGrid}}"
        CommandParameter="{Binding}" />

<!-- 5. RelativeSource TemplatedParent: inside a ControlTemplate -->
<TextBlock Text="{Binding Header, RelativeSource={RelativeSource TemplatedParent}}" />

<!-- 6. Source: an explicit object, usually a resource or a static -->
<TextBlock Text="{Binding Version, Source={x:Static app:BuildInfo.Current}}" />

AncestorLevel disambiguates nesting — {RelativeSource AncestorType=ListBox, AncestorLevel=2} skips the first ListBox and finds the one above it.

Path syntax

XAML 
{Binding Customer.Address.City}          <!-- nested -->
{Binding Items[0].Title}                 <!-- indexer -->
{Binding Tags[status]}                   <!-- string key, no quotes needed -->
{Binding .}                              <!-- the DataContext itself -->
{Binding}                                <!-- same thing, shorter -->
{Binding (Validation.HasError), RelativeSource={RelativeSource Self}}   <!-- attached prop -->
{Binding Path=(vm:Doc.Title)}            <!-- attached prop, qualified -->
{Binding Items/Title}                    <!-- current item of a collection view -->
GOTCHA

Attached properties in a Path must be parenthesised. {Binding Validation.HasError} looks for a property called Validation and fails silently; {Binding (Validation.HasError)} is correct.

Collections and views

The notification contract

For a bound list to update itself, two interfaces matter and they do different jobs:

  • INotifyCollectionChanged — the collection changed: items added, removed, moved, reset. ObservableCollection<T> implements it.
  • INotifyPropertyChanged — an item changed. Your item type must implement this itself; ObservableCollection does nothing for you here.

A list of plain records inside an ObservableCollection will update when you add or remove, and will never update when you edit a field. This surprises people weekly.

CollectionView: sorting, filtering, grouping

Every ItemsSource binding is silently wrapped in an ICollectionView. You can get at it, or declare your own:

      <scm:SortDescription PropertyName="Title"   Direction="Ascending" />
    </CollectionViewSource.SortDescriptions>
    <CollectionViewSource.GroupDescriptions>
      <PropertyGroupDescription PropertyName="Project" />
    </CollectionViewSource.GroupDescriptions>
  </CollectionViewSource>
</Window.Resources>

<!-- xmlns:scm="clr-namespace:System.ComponentModel;assembly=WindowsBase" -->

<ListBox ItemsSource="{Binding Source={StaticResource SortedTasks}}">

From the view model, the same thing with a live filter:

C# 
public partial class TaskListViewModel : ObservableObject
{
    public ObservableCollection<TaskViewModel> Tasks { get; } = [];
    public ICollectionView View { get; }

    [ObservableProperty]
    public partial string Search { get; set; }

    public TaskListViewModel()
    {
        Search = "";
        View = CollectionViewSource.GetDefaultView(Tasks);
        View.SortDescriptions.Add(new SortDescription(nameof(TaskViewModel.DueDate),
                                                      ListSortDirection.Ascending));
        View.Filter = o => o is TaskViewModel t &&
            (Search.Length == 0 ||
             t.Title.Contains(Search, StringComparison.OrdinalIgnoreCase));
    }

    partial void OnSearchChanged(string value) => View.Refresh();
}
GOTCHA

View.Refresh() re-evaluates the filter over the whole collection and resets selection. On a large list, debounce it — a Delay=300 on the search box binding, or a timer. And note that GetDefaultView returns a shared view: two ListBoxes bound to the same collection share sorting, filtering and current item. Use separate CollectionViewSource instances when you need them independent.

Large lists

Beyond roughly 10,000 items, ObservableCollection plus a filter starts to hurt, because every change notification walks the view. Options, in order of effort:

  • Virtualise properly. Confirm VirtualizationMode="Recycling" and that you have not disabled virtualisation by accident (Part 19 lists the ways).
  • Filter at the source. Query the database or the in-memory index and replace the collection, rather than filtering a view over everything.
  • Batch. ObservableCollection raises one event per Add. Build the list first, then assign, or use a collection that supports range operations.
  • Data virtualisation. Implement IList over a paged, lazily-loaded backing store so only the visible window is materialised. Non-trivial; only do it when you must.

Cross-thread collection updates

Adding to a bound ObservableCollection from a background thread throws. Two fixes:

C# 
// A. Marshal to the UI thread (fine for occasional updates).
await Application.Current.Dispatcher.InvokeAsync(() => Tasks.Add(item));

// B. Enable collection synchronisation (better for high-frequency streams).
private readonly object _lock = new();

public TaskListViewModel()
{
    BindingOperations.EnableCollectionSynchronization(Tasks, _lock);
}

// Then from any thread:
lock (_lock) { Tasks.Add(item); }

Option B lets WPF take the same lock while it reads the collection during layout, so background producers don't have to hop threads for every item. It is the right answer for telemetry feeds and log tails.

MVVM with the Community Toolkit

This is the part that has changed most since the books. Everything below replaces roughly two hundred lines of hand-written boilerplate in every old sample you'll read.

What MVVM actually buys you

Not testability alone — the real payoff is that WPF's binding and templating engine is designed around it. DataTemplate DataType only works if your data is view models. Triggers only reach state that is bound. Fight MVVM and you fight the framework.

The division:

  • Model — domain types and services. Knows nothing about WPF.
  • ViewModel — state and commands for one screen or one item. Knows nothing about WPF types, though it may know about abstractions like IDialogService. No using System.Windows.
  • View — XAML plus, ideally, an empty code-behind. Not zero code-behind as a religion; view-only concerns (focus management, animations, drag adorners) legitimately live there.

Observable properties

The old way 
public class TaskViewModel : INotifyPropertyChanged
{
    private string _title = "";
    public string Title
    {
        get => _title;
        set
        {
            if (_title == value) return;
            _title = value;
            OnPropertyChanged();
            OnPropertyChanged(nameof(DisplayName));
        }
    }

    public event PropertyChangedEventHandler? PropertyChanged;
    protected void OnPropertyChanged([CallerMemberName] string? n = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(n));
}
The current way 
using CommunityToolkit.Mvvm.ComponentModel;

public partial class TaskViewModel : ObservableObject
{
    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayName))]
    public partial string Title { get; set; }

    [ObservableProperty]
    public partial bool IsDone { get; set; }

    public string DisplayName => IsDone ? $"\u2713 {Title}" : Title;

    public TaskViewModel() => Title = "";   // see the note below
}
GOTCHA

A partial property declaration cannot have an initialiser. public partial string Title { get; set; } = ""; does not compile, because the generator supplies the implementing declaration and that is where an auto-property initialiser would have to live. Set defaults in the constructor, or mark the property required. This is the one place the new syntax is less convenient than the old field form, and it catches everyone once.

The source generator writes the backing field, the setter with its equality check, the OnPropertyChanged call, and the dependent notifications. Two optional partial hooks let you intercept:

C# 
partial void OnTitleChanging(string oldValue, string newValue)
{
    // runs before the field is assigned; throw here to veto
}

partial void OnTitleChanged(string value)
{
    _logger.LogDebug("Title is now {Title}", value);
    IsDirty = true;
}
SINCE C# 13 / TOOLKIT 8.4

The public partial string Title { get; set; } form replaces the old [ObservableProperty] private string title; field syntax. Partial properties mean the generated member is the one you declared, so XML docs, attributes, nullability and IntelliSense all work properly. The field form still compiles; new code should use partial properties.

Commands

C# 
using CommunityToolkit.Mvvm.Input;

public partial class TaskListViewModel : ObservableObject
{
    private readonly ITaskRepository _repo;

    public ObservableCollection<TaskViewModel> Items { get; } = [];

    [ObservableProperty]
    [NotifyCanExecuteChangedFor(nameof(AddCommand))]
    public partial string Draft { get; set; }

    [ObservableProperty]
    [NotifyCanExecuteChangedFor(nameof(DeleteCommand))]
    public partial TaskViewModel? Selected { get; set; }

    // Synchronous, with a CanExecute guard
    [RelayCommand(CanExecute = nameof(CanAdd))]
    private void Add()
    {
        Items.Add(new TaskViewModel { Title = Draft.Trim() });
        Draft = "";
    }

    private bool CanAdd() => !string.IsNullOrWhiteSpace(Draft);

    // Async, cancellable, with automatic re-entrancy blocking
    [RelayCommand(IncludeCancelCommand = true, AllowConcurrentExecutions = false)]
    private async Task RefreshAsync(CancellationToken ct)
    {
        var rows = await _repo.GetAllAsync(ct);
        Items.Clear();
        foreach (var r in rows) Items.Add(new TaskViewModel(r));
    }

    // Parameterised
    [RelayCommand(CanExecute = nameof(CanDelete))]
    private async Task DeleteAsync(TaskViewModel item, CancellationToken ct)
    {
        await _repo.DeleteAsync(item.Id, ct);
        Items.Remove(item);
    }

    private bool CanDelete(TaskViewModel? item) => item is not null;
}

The generator produces AddCommand, RefreshCommand, RefreshCancelCommand and DeleteCommand. The async ones are IAsyncRelayCommand, which exposes IsRunning — bind a progress indicator straight to {Binding RefreshCommand.IsRunning} and delete your IsBusy property.

             Visibility="{Binding RefreshCommand.IsRunning,
                          Converter={StaticResource BoolToVis}}" />
GOTCHA

AllowConcurrentExecutions = false is the default and it is what you want — it stops a user double-clicking Refresh into two overlapping requests. But it also means CanExecute returns false while running, so the button greys out. If the button shouldn't grey out, either allow concurrency and guard yourself, or bind IsEnabled separately.

Dependency injection and the host

WPF predates Microsoft.Extensions.* by a decade, so nothing is wired up for you. Fifty lines gets you the same composition root you'd have in an ASP.NET Core app.

The wiring

App.xaml.cs 
public partial class App : Application
{
    private readonly IHost _host;

    public App()
    {
        var builder = Host.CreateApplicationBuilder();

        builder.Configuration
            .AddJsonFile("appsettings.json", optional: false)
            .AddJsonFile($"appsettings.{builder.Environment.EnvironmentName}.json", optional: true)
            .AddEnvironmentVariables("TASKS_")

        builder.Services.AddSingleton<IClock, SystemClock>();
        builder.Services.AddSingleton<ITaskRepository, SqliteTaskRepository>();
        builder.Services.AddHttpClient<ITaskApi, TaskApi>((sp, http) =>

        });

        // UI services
        builder.Services.AddSingleton<IDialogService, DialogService>();
        builder.Services.AddSingleton<INavigationService, NavigationService>();

        builder.Services.AddSingleton<MainWindow>();
        builder.Services.AddSingleton<ShellViewModel>();
        builder.Services.AddTransient<TaskListViewModel>();
        builder.Services.AddTransient<TaskEditorViewModel>();

        _host = builder.Build();
    }

    protected override async void OnStartup(StartupEventArgs e)
    {
        try
        {
            base.OnStartup(e);
            await _host.StartAsync();

            var window = _host.Services.GetRequiredService<MainWindow>();
            window.DataContext = _host.Services.GetRequiredService<ShellViewModel>();
            window.Show();
        }
        catch (Exception ex)
        {
            MessageBox.Show(ex.ToString(), "Startup failed");
            Shutdown(1);
        }
    }

    protected override async void OnExit(ExitEventArgs e)
    {
        using (_host) await _host.StopAsync(TimeSpan.FromSeconds(5));
        base.OnExit(e);
    }
}

            try
            {
                var remote = await _api.GetChangesAsync(stoppingToken);
                await _repo.MergeAsync(remote, stoppingToken);
                WeakReferenceMessenger.Default.Send(new SyncCompleted(remote.Count));
            }
            catch (Exception ex) when (ex is not OperationCanceledException)
            {
                _log.LogWarning(ex, "Sync failed; will retry");
            }
        }
    }
}

Register with builder.Services.AddHostedService<SyncService>(). It starts with _host.StartAsync() and stops cleanly on exit. Note that it runs on a thread-pool thread, so anything touching bound collections needs the marshalling from Part 12.

A navigation service, when you need one

C# 
public interface INavigationService
{
    PageViewModel? Current { get; }
    event EventHandler? CurrentChanged;
    Task<bool> NavigateToAsync<TViewModel>(Action<TViewModel>? configure = null)
        where TViewModel : PageViewModel;
    Task<bool> GoBackAsync();
}

public sealed class NavigationService(IServiceProvider services) : INavigationService
{
    private readonly Stack<PageViewModel> _history = new();

    public PageViewModel? Current { get; private set; }
    public event EventHandler? CurrentChanged;

    public async Task<bool> NavigateToAsync<TViewModel>(Action<TViewModel>? configure = null)
        where TViewModel : PageViewModel
    {
        if (Current is not null && !await Current.CanLeaveAsync()) return false;

        var next = services.GetRequiredService<TViewModel>();
        configure?.Invoke(next);
        await next.LoadAsync(CancellationToken.None);

        if (Current is not null) _history.Push(Current);
        Current = next;
        CurrentChanged?.Invoke(this, EventArgs.Empty);
        return true;
    }

    public async Task<bool> GoBackAsync()
    {
        if (_history.Count == 0) return false;
        if (Current is not null && !await Current.CanLeaveAsync()) return false;
        Current = _history.Pop();
        CurrentChanged?.Invoke(this, EventArgs.Empty);
        return true;
    }
}

Dialogs without breaking testability

A view model must never call MessageBox.Show or new SaveFileDialog() — it becomes untestable and drags System.Windows into your logic layer. Put it behind an interface:

C# 
public interface IDialogService
{
    Task<bool> ConfirmAsync(string title, string message);
    Task AlertAsync(string title, string message);
    string? PickOpenFile(string filter, string? initialDirectory = null);
    string? PickSaveFile(string filter, string suggestedName);
    Task<TResult?> ShowAsync<TViewModel, TResult>(TViewModel viewModel)
        where TViewModel : DialogViewModel<TResult>;
}

public sealed class DialogService(IServiceProvider services) : IDialogService
{
    private Window Active =>
        Application.Current.Windows.OfType<Window>().FirstOrDefault(w => w.IsActive)
        ?? Application.Current.MainWindow;

    public Task<bool> ConfirmAsync(string title, string message) =>
        Task.FromResult(MessageBox.Show(Active, message, title,
            MessageBoxButton.YesNo, MessageBoxImage.Question) == MessageBoxResult.Yes);

    public string? PickOpenFile(string filter, string? initialDirectory = null)
    {
        var dlg = new OpenFileDialog { Filter = filter, InitialDirectory = initialDirectory ?? "" };
        return dlg.ShowDialog(Active) == true ? dlg.FileName : null;
    }

    public async Task<TResult?> ShowAsync<TViewModel, TResult>(TViewModel vm)
        where TViewModel : DialogViewModel<TResult>
    {
        // Resolve the window by convention or by an explicit registration
        var window = services.GetRequiredService<DialogWindow>();
        window.Owner = Active;
        window.DataContext = vm;

        var tcs = new TaskCompletionSource<TResult?>();
        vm.RequestClose += result => { window.DialogResult = true; tcs.TrySetResult(result); };
        window.Closed += (_, _) => tcs.TrySetResult(default);

        window.ShowDialog();
        return await tcs.Task;
    }
}

In tests you substitute a fake that returns scripted answers, and your view model logic is exercisable without a UI thread.

Window details that bite

  • Always set Owner on a dialog. Without it the dialog can end up behind the main window and won't centre correctly. WindowStartupLocation="CenterOwner" needs an owner to mean anything.
  • DialogResult only works on windows shown with ShowDialog(). Setting it on a modeless window throws.
  • Cancelling a close happens in Closing via e.Cancel = true. You cannot await inside that handler usefully — if you need an async confirmation, cancel unconditionally, run the async check, then close again with a flag set.
C# 
private bool _closeConfirmed;

protected override async void OnClosing(CancelEventArgs e)
{
    if (_closeConfirmed) { base.OnClosing(e); return; }

    e.Cancel = true;                       // stop this close
    var vm = (ShellViewModel)DataContext;
    if (!await vm.CanCloseAsync()) return;

    _closeConfirmed = true;
    Close();                               // and start a new one
}
PART 17

Threading and async

WPF is single-threaded-apartment with hard thread affinity. Every DispatcherObject — which is every element, every brush, every animation — remembers the thread that created it and throws if touched from another.

The Dispatcher

One UI thread runs a message loop. The Dispatcher is its work queue, ordered by DispatcherPriority.

C# 
// Are we on the UI thread?
bool onUi = Dispatcher.CheckAccess();

// Post work to it (fire and forget, returns immediately).
// BeginInvoke takes a Delegate, so give the lambda an explicit type.
Dispatcher.BeginInvoke(new Action(() => status.Text = "Done"));
Dispatcher.InvokeAsync(() => status.Text = "Done");   // overload takes Action directly

// Post and await the result
var width = await Dispatcher.InvokeAsync(() => element.ActualWidth);

// Post and block until done — deadlock risk, avoid
Dispatcher.Invoke(() => status.Text = "Done");

// Run after layout has completed
Dispatcher.InvokeAsync(() => box.Focus(), DispatcherPriority.Loaded);

Priority matters more than people expect. DispatcherPriority.Background work runs only when the queue is otherwise idle, which is how you keep a busy UI responsive. DispatcherPriority.Render and Loaded are the hooks for "after this frame has been laid out" — the reliable way to focus a control that doesn't exist yet.

The rule you actually follow

With async/await, almost none of the above is needed day to day. await captures the SynchronizationContext, and WPF installs a DispatcherSynchronizationContext, so continuations come back to the UI thread automatically.

C# 
[RelayCommand]
private async Task LoadAsync(CancellationToken ct)
{
    // UI thread here.
    Status = "Loading…";

    var rows = await _repo.GetAllAsync(ct);          // off to the thread pool and back

    // UI thread again — safe to touch bound collections.
    Items.Clear();
    foreach (var r in rows) Items.Add(new TaskViewModel(r));
    Status = $"{Items.Count} tasks";
}
  • Don't use ConfigureAwait(false) in view models and UI code — you want the context back. Do use it in library and service code that never touches UI.
  • Don't call .Result or .Wait() on the UI thread. The continuation needs the UI thread, which you are blocking. That is a textbook deadlock and it is still the most common hang in WPF applications.
  • Do use Task.Run for genuinely CPU-bound work, and nothing else. Wrapping an already-async I/O call in Task.Run just burns a thread.
C# 
// CPU-bound: correct use of Task.Run
var report = await Task.Run(() => _engine.Recalculate(model), ct);

// I/O-bound: wrong
var rows = await Task.Run(() => _repo.GetAllAsync(ct));   // pointless thread hop
var rows = await _repo.GetAllAsync(ct);                   // correct

Freezables and cross-thread objects

Freezable — brushes, geometries, transforms, animations — can be made immutable with Freeze(). A frozen freezable loses thread affinity and can be created on a background thread and used on the UI thread. That's how you pre-build complex geometry off the UI thread:

C# 
var geometry = await Task.Run(() =>
{
    var g = BuildComplexPath(points);   // StreamGeometry, thousands of segments
    g.Freeze();                          // now thread-agnostic and faster to render
    return g;
});

path.Data = geometry;                    // UI thread, no marshalling needed

A second UI thread

Rarely needed, occasionally the right answer — a splash screen that must animate while the main thread blocks on startup, or a diagnostics window that must stay responsive when the main UI hangs:

C# 
var thread = new Thread(() =>
{
    var window = new SplashWindow();
    window.Show();
    Dispatcher.Run();                      // this thread now has its own message loop
});
thread.SetApartmentState(ApartmentState.STA);
thread.IsBackground = true;
thread.Start();

// To close it later, from anywhere:
window.Dispatcher.InvokeShutdown();

The two windows cannot share element instances, and they cannot be parent and child in the normal sense. Treat them as separate applications that happen to share a process.

GOTCHA

async void is correct for event handlers and for framework overrides like OnStartup, and wrong everywhere else. An unhandled exception in an async void method is rethrown on the synchronization context and takes the process down. Every async void body should be wrapped in try/catch, or be a one-liner delegating to a Task-returning method that handles its own errors.

// From code, with a completion await
static Task AnimateAsync(UIElement target, DependencyProperty prop, double to, TimeSpan duration)
{
    var tcs = new TaskCompletionSource();
    var anim = new DoubleAnimation(to, new Duration(duration))
    {
        EasingFunction = new QuadraticEase { EasingMode = EasingMode.EaseInOut },
        FillBehavior = FillBehavior.HoldEnd,

GOTCHA

An animation with FillBehavior.HoldEnd (the default) keeps the property pinned at precedence level 2 forever — above any local value you subsequently set. Setting element.Opacity = 1 after a fade-out appears to do nothing. Clear the animation with BeginAnimation(prop, null) first, or use FillBehavior.Stop.

Respecting the user's motion setting

RenderCapability.Tier tells you how much is hardware-accelerated: 0 means software rendering (remote desktop, some VMs), 2 means full GPU. Dropping animations at tier 0 makes a remote-desktop session feel dramatically better, which matters if your users are on Citrix or RDP.

PART 19

Performance

WPF is fast until you accidentally turn off the thing making it fast. Most performance work is removing mistakes rather than adding optimisations.

Virtualisation: the six ways to break it

A ListBox virtualises by default — only visible containers exist. Each of these silently disables it:

  1. Putting the list inside a StackPanel (or any container that gives infinite space in the scroll direction). The list gets as tall as its content and never scrolls, so everything is "visible".
  2. Replacing ItemsPanel with a non-virtualising panel — StackPanel, WrapPanel, UniformGrid.
  3. Setting ScrollViewer.CanContentScroll="False", which switches to pixel-based scrolling and materialises everything.
  4. Grouping without VirtualizingPanel.IsVirtualizingWhenGrouping="True".
  5. Binding ItemsSource to an IEnumerable that isn't an IList — the panel can't index into it, so it can't virtualise.
  6. Adding items directly to Items rather than through ItemsSource in some container configurations.
XAML — explicit and correct 
<ListBox ItemsSource="{Binding Rows}"
         VirtualizingPanel.IsVirtualizing="True"
         VirtualizingPanel.VirtualizationMode="Recycling"
         VirtualizingPanel.ScrollUnit="Pixel"
         VirtualizingPanel.CacheLength="1,2"
         VirtualizingPanel.CacheLengthUnit="Page"
         VirtualizingPanel.IsVirtualizingWhenGrouping="True"
         ScrollViewer.IsDeferredScrollingEnabled="False">
  <ListBox.ItemsPanel>
    <ItemsPanelTemplate>
      <VirtualizingStackPanel />
    </ItemsPanelTemplate>
  </ListBox.ItemsPanel>
</ListBox>

VirtualizationMode="Recycling" reuses containers instead of creating and discarding them, which is the single biggest win. It is not the default for historical compatibility reasons, so set it explicitly every time.

The other common costs

  • Unfrozen freezables. Every unfrozen brush carries change tracking. Freeze all static brushes, pens and geometries.
  • Deep visual trees. A template with eight nested Borders multiplied across 5,000 rows is 40,000 elements. Flatten templates used in item containers ruthlessly.
  • Binding to properties without change notification. WPF falls back to PropertyDescriptor subscriptions, which leak and are slow. If the source is a plain CLR object with no INotifyPropertyChanged, either add it or set Mode=OneTime.
  • DynamicResource everywhere. Each one keeps a live lookup. Use it only where the value actually changes.
  • Layout thrash. Changing an inherited property (FontSize) on a root element invalidates the whole tree. Changing Visibility from Collapsed to Visible forces measure on the whole subtree — Opacity and IsHitTestVisible are cheaper if you just want it hidden.
  • Text rendering. TextOptions.TextFormattingMode="Display" makes small text crisper at 100% DPI; Ideal (the default) is better at high DPI. TextRenderingMode="ClearType" vs Grayscale matters over remote desktop.
XAML — caching an expensive static subtree 
<Canvas>
  <Canvas.CacheMode>
    <BitmapCache RenderAtScale="1" SnapsToDevicePixels="True" />
  </Canvas.CacheMode>
  <!-- a complex, rarely-changing diagram -->
</Canvas>

BitmapCache rasterises a subtree once and reuses the bitmap. Excellent for static decoration that is transformed or scrolled; harmful for anything that redraws, since you pay for re-rasterising every frame.

Memory leaks

Three sources, in order of frequency:

  1. Event handlers on long-lived objects. A view model subscribing to a singleton service's event is never collected. Use WeakReferenceMessenger, or unsubscribe in a dispose/deactivate hook.
  2. Bindings to non-INotifyPropertyChanged sources. The PropertyDescriptor fallback roots the source object for the application's lifetime.
  3. DataContext retained by a cached Window. Windows you Hide() instead of Close() keep their whole view model graph alive.
C# 
// The weak event pattern, for when you can't control the publisher's lifetime.
WeakEventManager<ITaskRepository, TaskChangedEventArgs>
    .AddHandler(_repo, nameof(ITaskRepository.TaskChanged), OnTaskChanged);

Measuring

  • Visual Studio's WPF Tree Visualizer and the live visual tree, for element counts and "why is that 400px wide".
  • Snoop — the community tool that has outlived every alternative. Inspect and edit any running WPF app's visual tree, watch binding errors live, profile the visual tree size.
  • PerfView or dotnet-trace for allocation and JIT.
  • RenderCapability.Tier, checked at startup and logged, so you know when a user is on software rendering.

Input, focus and keyboard

Two kinds of focus

This distinction causes more subtle bugs than anything else in WPF input.

  • Keyboard focus — exactly one element in the entire desktop has it. Keyboard.FocusedElement. This is where key events go.
  • Logical focus — one element per focus scope remembers that it was focused. A Window, Menu, ToolBar and ContextMenu are each focus scopes by default.

So when you open a menu, the text box loses keyboard focus but keeps logical focus within the window's scope, which is how the menu's Cut command still knows what to act on.

C# 
// Keyboard focus — returns the element that actually got it (may be null)
IInputElement? got = Keyboard.Focus(myTextBox);

// Or, equivalently for a UIElement:
bool ok = myTextBox.Focus();

// Logical focus within a scope
FocusManager.SetFocusedElement(FocusManager.GetFocusScope(myTextBox), myTextBox);

// Which scope am I in?
DependencyObject scope = FocusManager.GetFocusScope(myTextBox);

// Make a panel its own focus scope (rarely a good idea — it breaks tabbing)
FocusManager.SetIsFocusScope(myPanel, true);
GOTCHA

Focus() silently fails if the element is not yet loaded, is collapsed, or has Focusable="False". Focusing on startup or after a template swap must be deferred: Dispatcher.InvokeAsync(() => box.Focus(), DispatcherPriority.Loaded). A focus call that "does nothing" is nearly always a timing problem, not a focus problem.

An attached property for initial focus

public static class FocusOnLoad
{
    public static readonly DependencyProperty IsEnabledProperty =
        DependencyProperty.RegisterAttached(
            "IsEnabled", typeof(bool), typeof(FocusOnLoad),
            new PropertyMetadata(false, OnChanged));

    public static void SetIsEnabled(DependencyObject d, bool v) => d.SetValue(IsEnabledProperty, v);
    public static bool GetIsEnabled(DependencyObject d) => (bool)d.GetValue(IsEnabledProperty);

    private static void OnChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not FrameworkElement fe || e.NewValue is not true) return;

        void Handler(object s, RoutedEventArgs _)
        {
            fe.Loaded -= Handler;
            fe.Dispatcher.InvokeAsync(() =>
            {
                fe.Focus();

        }

        if (fe.IsLoaded) Handler(fe, new RoutedEventArgs());
        else fe.Loaded += Handler;
    }

The drag source

private Point _dragStart;

private void OnMouseMove(object sender, MouseEventArgs e)
{
    if (e.LeftButton != MouseButtonState.Pressed) return;

    Vector moved = _dragStart - e.GetPosition(null);
    if (Math.Abs(moved.X) < SystemParameters.MinimumHorizontalDragDistance &&
        Math.Abs(moved.Y) < SystemParameters.MinimumVerticalDragDistance) return;

    if (((DependencyObject)e.OriginalSource) is not DependencyObject src) return;
    var container = TreeSearch.FindAncestor<ListBoxItem>(src);
    if (container?.DataContext is not TaskViewModel task) return;

    var data = new DataObject();
    data.SetData(typeof(TaskViewModel).FullName!, task);   // in-process, rich
    data.SetText(task.Title);                              // for other apps

    // Blocks until the drop completes or is cancelled.
    DragDrop.DoDragDrop(container, data, DragDropEffects.Move | DragDropEffects.Copy);
}

            continue;
        Point topLeft = c.TranslatePoint(new Point(0, 0), list);
        if (position.Y < topLeft.Y + c.ActualHeight / 2) return i;
    }
    return list.Items.Count;
}

Draw the line itself with an adorner (Part 24) added on DragOver and removed on DragLeave and Drop. Remember that DragLeave fires when the pointer crosses into a child element too, so debounce it or check e.GetPosition against the bounds.

The clipboard, and what .NET 9 changed

SINCE .NET 9 / .NET 10

.NET 9 removed the BinaryFormatter implementation. WPF used it internally for clipboard and drag-drop of arbitrary objects, so Clipboard.SetData(format, someCustomObject) with a non-primitive type now throws PlatformNotSupportedException unless the type is in WPF's known-safe set. .NET 10 goes further: it unifies the WPF and WinForms clipboard implementations, obsoletes the methods that depended on binary serialisation, and adds JSON-based alternatives. If you are on .NET 9, serialise custom payloads yourself; on .NET 10 you can use the new typed/JSON methods.

Performance rules for large grids

  • Set an explicit RowHeight. Without it, the grid measures every row to find the tallest, defeating virtualisation on first layout.
  • Avoid Width="Auto" and SizeToCells columns. They force every row to be measured. Use * and fixed widths.
  • Leave EnableColumnVirtualization="False" unless you genuinely have 50+ columns; it costs more than it saves below that.
  • Keep CellStyle and templates shallow. Every extra Border is multiplied by rows × columns.
  • Do not bind ItemsSource to a LINQ query. It re-enumerates. Materialise to a list first.
  • Turn off CanUserSortColumns if you sort server-side, and handle Sorting yourself with e.Handled = true.

Triggers or VisualStateManager?

Both are in WPF and they do overlapping jobs. Triggers are older, declarative and reversible; VSM is state-machine shaped, came from Silverlight, and supports transitions between named states.

  • Use triggers for WPF-only controls. Less ceremony, and the value-precedence rules are the ones you already know.
  • Use VSM when states are mutually exclusive and you want animated transitions between them, or when the control will be ported to WinUI/Uno later.

Do not mix them for the same property on the same control. Triggers set values at precedence levels 6–7 and VSM animates at level 2, so VSM always wins and the trigger appears broken.

Deriving from an existing control

Often the cheapest option. You inherit all the behaviour and the default template stays valid:

public class NumericTextBox : TextBox
{
    static NumericTextBox()
    {
        // Keep the TextBox default template rather than looking for our own.
        DefaultStyleKeyProperty.OverrideMetadata(
            typeof(NumericTextBox), new FrameworkPropertyMetadata(typeof(TextBox)));
    }

    protected override void OnPreviewTextInput(TextCompositionEventArgs e)
    {
        // Text input, not key codes — works with any keyboard layout.
        string candidate = string.Concat(Text[..SelectionStart], e.Text,
                                          Text[(SelectionStart + SelectionLength)..]);
        e.Handled = !decimal.TryParse(candidate, NumberStyles.Number,
                                      CultureInfo.CurrentCulture, out _);
        base.OnPreviewTextInput(e);
    }

    protected override void OnPreviewKeyDown(KeyEventArgs e)
    {
        if (e.Key == Key.Space) e.Handled = true;   // space isn't a TextInput event
        base.OnPreviewKeyDown(e);
    }
}

public static void PrintElement(FrameworkElement element, string description)
{
    var dialog = new PrintDialog();
    if (dialog.ShowDialog() != true) return;

    // Fit the element to the printable area before printing.
    var capabilities = dialog.PrintQueue.GetPrintCapabilities(dialog.PrintTicket);
    var area = new Size(capabilities.PageImageableArea!.ExtentWidth,
                        capabilities.PageImageableArea.ExtentHeight);

    double scale = Math.Min(area.Width  / element.ActualWidth,
                            area.Height / element.ActualHeight);

    var original = element.LayoutTransform;
    element.LayoutTransform = new ScaleTransform(scale, scale);
    element.Measure(area);
    element.Arrange(new Rect(
        new Point(capabilities.PageImageableArea.OriginWidth,
                  capabilities.PageImageableArea.OriginHeight), area));

    dialog.PrintVisual(element, description);

    element.LayoutTransform = original;
    element.Measure(new Size(element.ActualWidth, element.ActualHeight));
}

The culture bug everyone hits

GOTCHA

WPF does not use CultureInfo.CurrentCulture for binding conversions. It uses the Language property of the element, which defaults to en-US regardless of the machine's settings. So a Swedish user sees 1,234.50 where they expect 1 234,50, and a date StringFormat produces American ordering. This has been the behaviour since 2006 and it will not change.

protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    var culture = CultureInfo.CurrentCulture;       // or a user preference
    CultureInfo.DefaultThreadCurrentCulture   = culture;

    // Make every FrameworkElement inherit the real culture.
    FrameworkElement.LanguageProperty.OverrideMetadata(

            XmlLanguage.GetLanguage(culture.IetfLanguageTag)));
}

public sealed record WindowPlacement(
    double Left, double Top, double Width, double Height, bool Maximised);

public static void Restore(Window window, WindowPlacement p)
{
    // Reject placements entirely outside the current monitor layout.
    var virt = new Rect(SystemParameters.VirtualScreenLeft,
                        SystemParameters.VirtualScreenTop,
                        SystemParameters.VirtualScreenWidth,
                        SystemParameters.VirtualScreenHeight);

EF Core in a desktop app

Desktop is not web: there is no request boundary, so DbContext lifetime has to be decided by you. The rule that works is one context per unit of work, never a singleton.

C# 
// Registration
builder.Services.AddDbContextFactory<TasksDbContext>(options =>
    options.UseSqlite($"Data Source={AppPaths.Database}"));

// Usage — a short-lived context per operation
public sealed class TaskRepository(IDbContextFactory<TasksDbContext> factory) : ITaskRepository
{
    public async Task<IReadOnlyList<TaskDto>> GetAllAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        return await db.Tasks
            .AsNoTracking()
            .OrderBy(t => t.DueDate)
            .Select(t => new TaskDto(t.Id, t.Title, t.IsDone, t.DueDate))
            .ToListAsync(ct);
    }

    public async Task SaveAsync(TaskDto dto, CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        var entity = await db.Tasks.FindAsync([dto.Id], ct);
        if (entity is null) { db.Tasks.Add(TaskEntity.From(dto)); }
        else { entity.Apply(dto); }
        await db.SaveChangesAsync(ct);
    }
}
GOTCHA

Never bind the UI directly to EF entities. Tracked entities hold a reference to their context; a bound DbSet keeps the context alive for the lifetime of the window, lazy loading fires on the UI thread during layout, and a single SaveChanges can cascade changes you never intended. Project to DTOs or view models at the repository boundary. AsNoTracking() on every read query is the habit to build.

An offline-capable read path

The pattern most desktop line-of-business apps converge on: read local, sync in the background, surface staleness.

C# 
public sealed class TaskService(
    ITaskRepository local, ITaskApi remote, IClock clock, ILogger<TaskService> log)
{
    public async Task<LoadResult<TaskDto>> LoadAsync(CancellationToken ct)
    {
        // 1. Always return local data immediately — the UI never waits on the network.
        var cached = await local.GetAllAsync(ct);

        // 2. Refresh in the background and report the outcome, don't throw.
        try
        {
            var since = await local.GetLastSyncAsync(ct);
            var changes = await remote.GetChangesAsync(since, ct);
            await local.MergeAsync(changes, clock.UtcNow, ct);
            return new LoadResult<TaskDto>(await local.GetAllAsync(ct), IsStale: false, null);
        }
        catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException)
        {
            log.LogWarning(ex, "Working offline");
            return new LoadResult<TaskDto>(cached, IsStale: true, "Showing saved data");
        }
    }
}

public sealed record LoadResult<T>(
    IReadOnlyList<T> Items, bool IsStale, string? Message);

public sealed class SettingsStore(ILogger<SettingsStore> log)
{

        new(JsonSerializerDefaults.Web) { WriteIndented = true };

    public UserSettings Load()
    {
        try
        {
            if (!File.Exists(AppPaths.Settings)) return new UserSettings();
            return JsonSerializer.Deserialize<UserSettings>(
                File.ReadAllText(AppPaths.Settings), Json) ?? new UserSettings();
        }
        catch (Exception ex)
        {
            log.LogWarning(ex, "Settings unreadable; starting from defaults");
            return new UserSettings();

    public void Save(UserSettings settings)
    {
        AppPaths.EnsureCreated();

        File.WriteAllText(temp, JsonSerializer.Serialize(settings, Json));
        File.Move(temp, AppPaths.Settings, overwrite: true);
    }
}

Two rules that turn out to matter more than they look: always recover from an unreadable settings file rather than crashing on startup, and always write atomically. Users' machines lose power mid-save.

Secrets on a user's machine

GOTCHA

Anything shipped to a user's machine is not secret. A client secret in appsettings.json, obfuscated in a resource, or encrypted with a key that also ships, is all equally extractable. Desktop applications are public clients in OAuth terms. Design accordingly: use the authorization code flow with PKCE and no client secret, and put anything that must stay secret behind your own API.

For tokens and passwords the user has entrusted to you, DPAPI ties the ciphertext to the Windows user account:

C# 
// PackageReference: System.Security.Cryptography.ProtectedData
public static class UserSecretStore
{
    private static readonly byte[] Entropy = "Tasks.v1"u8.ToArray();

    public static void Save(string name, string value)
    {
        byte[] cipher = ProtectedData.Protect(
            Encoding.UTF8.GetBytes(value), Entropy, DataProtectionScope.CurrentUser);

        AppPaths.EnsureCreated();
        File.WriteAllBytes(Path.Combine(AppPaths.Secrets, name + ".bin"), cipher);
    }

    public static string? Load(string name)
    {
        string path = Path.Combine(AppPaths.Secrets, name + ".bin");
        if (!File.Exists(path)) return null;
        try
        {
            byte[] plain = ProtectedData.Unprotect(
                File.ReadAllBytes(path), Entropy, DataProtectionScope.CurrentUser);
            return Encoding.UTF8.GetString(plain);
        }
        catch (CryptographicException) { return null; }   // different user or machine
    }
}

Most WPF work in 2026 is not greenfield. The good news is that the migration is mostly mechanical; the surprises are concentrated in a short list.

Order of operations

  1. Get on .NET Framework 4.8 first and make sure everything builds and the tests pass. Never migrate framework version and project format at the same time.

  • System accent colour exposed through SystemColors, as a Color, a SolidColorBrush and a ResourceKey, with light and dark shades. Available with or without the Fluent theme.
  • Hyphen-based ligatures in TextBlock and other text controls — a long-standing gap.
  • BinaryFormatter removed. The single most likely thing to break an existing app on upgrade.

What .NET 10 added on top

  • More Fluent coverage — default styles for Label, Hyperlink, GroupBox, GridSplitter and NavigationWindow.
  • Fluent fixes — Expander animation, high-contrast crashes, missing RecognizesAccessKey, and right-to-left layout in MenuItem, Expander and TreeViewItem.
  • A unified clipboard shared with Windows Forms, plus new methods that use JSON serialisation instead of binary, and obsoletions on the methods that cannot work without BinaryFormatter.
  • Performance — internal data structures replaced with base types such as ReadOnlyCollection<T>, cutting allocations in UI automation and file dialogs and speeding up pixel-format conversion.

Partial properties: the one language-level catch

GOTCHA

The [ObservableProperty] public partial string Title { get; set; } form needs C# 13, which means the .NET 9 SDK or later, plus CommunityToolkit.Mvvm 8.4 or later. It works on both target frameworks. But a partial property declaration cannot have an initialiser — public partial string Title { get; set; } = ""; does not compile, because the generator supplies the implementing declaration. Set defaults in the constructor instead. If you are stuck on an older SDK, fall back to the field form: [ObservableProperty] private string _title = "";

Looking ahead

.NET 11 is in preview as of late 2026. The WPF changes so far are maintenance: a fix so self-contained apps ship ijwhost.dll and don't fail to launch with mixed-mode assemblies, protection against crashes from Desktop Window Manager failures, Fluent backdrop and background fixes on Windows 10, and a weak-event-table enumeration fix. Nothing that changes how you write WPF. Plan on .NET 10 for anything you are shipping now.

A reasonable order to learn in

If you're coming from ASP.NET Core or any other .NET background, the sequence that wastes the least time:

  1. Build one window by hand with a Grid, a TextBox and a Button, wired with code-behind. Twenty minutes. It makes the rest concrete.
  2. Read Part 5 on dependency properties until the precedence list is boring. Everything mysterious about WPF traces back to it.
  3. Read Part 11 on binding, then deliberately break bindings and watch the output window.
  4. Learn ContentControl + implicit DataTemplate (Parts 7 and 10). This is the architectural keystone.
  5. Adopt CommunityToolkit.Mvvm and the host (Parts 14 and 15) before you write your second screen, not after your tenth.
  6. Learn templating (Part 10) when you first want a control to look different — not before.

C# — cursor-anchored zoom 
private void OnMouseWheel(object sender, MouseWheelEventArgs e)
{
    var element = (FrameworkElement)sender;
    var transform = (MatrixTransform)element.RenderTransform;
    Matrix m = transform.Matrix;

    double factor = e.Delta > 0 ? 1.15 : 1 / 1.15;
    Point anchor = e.GetPosition(element);      // in unscaled element space

    m.ScaleAtPrepend(factor, factor, anchor.X, anchor.Y);

    // Clamp so the user can't zoom into oblivion
    double scale = Math.Sqrt(Math.Abs(m.M11 * m.M22 - m.M12 * m.M21));
    if (scale is < 0.1 or > 20) return;

    transform.Matrix = m;
    e.Handled = true;
}

The sync design, because it is the hard part

C# 
// Every local mutation writes an outbox record in the same transaction as the change.
public sealed class OutboxEntry
{
    public long Id { get; set; }
    public required string EntityType { get; set; }
    public required string EntityId { get; set; }
    public required string Operation { get; set; }   // Create | Update | Delete
    public required string PayloadJson { get; set; }
    public DateTimeOffset QueuedAt { get; set; }
    public int Attempts { get; set; }
    public string? LastError { get; set; }
    public string? BaseVersion { get; set; }         // ETag or rowversion seen when editing
}

public async Task<SyncOutcome> PushAsync(CancellationToken ct)
{
    await using var db = await _factory.CreateDbContextAsync(ct);
    var pending = await db.Outbox.OrderBy(o => o.Id).Take(50).ToListAsync(ct);

    var conflicts = new List<Conflict>();

    foreach (var entry in pending)
    {
        try
        {
            var result = await _api.ApplyAsync(entry, ct);
            if (result.IsConflict)
            {
                // Do NOT discard the user's work. Park it and let them decide.
                conflicts.Add(new Conflict(entry, result.ServerState!));
                entry.LastError = "Changed on the server";
                continue;
            }
            db.Outbox.Remove(entry);
        }
        catch (HttpRequestException)
        {
            entry.Attempts++;
            break;                     // stop the batch; we're offline
        }
    }

    await db.SaveChangesAsync(ct);
    return new SyncOutcome(pending.Count, conflicts);
}

Three rules that separate a sync implementation that works from one that loses data:

  • The outbox write is in the same transaction as the change. Otherwise a crash between the two silently drops an edit.
  • Send the version you edited from. Without it the server cannot detect a conflict and last-writer-wins quietly destroys someone's work.
  • Never auto-resolve. Show the user both versions and let them choose. Users forgive a conflict dialog; they do not forgive vanished data.

Where to go after

Having built these, the remaining depth in WPF is in three directions, and each is worth a project of its own:

  • Custom rendering. A node-graph editor or a timeline, built on DrawingVisual with your own hit-testing, virtualisation and spatial index. This is where WPF outperforms every alternative in .NET and where the visual-layer APIs from Part 18 pay off.
  • Extensibility. A plugin host using AssemblyLoadContext, where plugins contribute views, commands and settings pages. Forces you to understand pack URIs, resource dictionaries across assemblies, and isolation.
  • Scale. Take an existing large WPF application and make its slowest screen fast. Profiling, virtualisation, binding audits and template flattening on somebody else's code teaches more about the framework than any amount of greenfield work.
