PART 35

Migrating from .NET Framework

Most WPF work in 2026 is not greenfield. The good news is that the migration is mostly mechanical; the surprises are concentrated in a short list.

Builds on Part 2, project setup and startup, which describes the modern project file you are migrating towards.

.NET Framework is the original, Windows-only .NET, now in maintenance with 4.8.x as its final line. Modern .NET (once called .NET Core, and numbered 5 onwards) is its successor, where all new work happens. WPF exists on both. Migrating means moving an existing app from the first to the second, and it pays off in performance, current C# versions, the Fluent theme, and continued fixes.

IN PLAIN TERMS

Migrating a WPF app is like moving a shop into a new building. The furniture and stock (your XAML, styles, bindings, controls) come across as they are. What changes is the building: the wiring, the plumbing, the post box. Those are the platform services around WPF, such as configuration, serialisation and remote calls, and they are where the work is.

Order of operations

The steps below each change one thing, so that when something breaks you know which change broke it. Two terms first. An SDK-style project is the short, modern .csproj format that lists settings rather than every file. PackageReference records NuGet packages inside the project file, replacing the separate packages.config, and it resolves transitive dependencies (the packages your packages depend on) automatically rather than listing each one.

  1. Get on .NET Framework 4.8 first and make sure everything builds and the tests pass. Never migrate framework version and project format at the same time.
  2. Convert to SDK-style .csproj while still targeting net48. The old try-convert tool was archived in May 2024; the .NET Upgrade Assistant can still do the conversion (see below). Verify, commit.
  3. Move packages.config to PackageReference, and resolve the transitive-dependency differences this exposes.
  4. Retarget to net10.0-windows and fix what breaks.
  5. Modernise (nullable, DI, the toolkit) afterwards, incrementally, not as part of the migration.

The value in step 4 is a target framework moniker (TFM), the short name that tells the build which .NET to compile for; the -windows suffix is what makes Windows-only libraries such as WPF available.

Run the .NET Upgrade Assistant before step 4; it produces a report of API-level incompatibilities per project. Microsoft deprecated it in late 2025 in favour of GitHub Copilot app modernization, which needs a paid Copilot plan. Upgrade Assistant still installs and runs, but it gets no more fixes.

What actually breaks

Each row below is a piece of .NET Framework that modern .NET changed or removed, with the replacement. A few terms used in the table: BinaryFormatter is the old serialiser that turned any object graph into bytes, removed because deserialising untrusted data with it could run attacker code. AppDomains were isolated compartments inside one process. ICU and NLS are the two libraries .NET can use for culture rules (sorting, comparison, casing): NLS is Windows' own, ICU the cross-platform one. A single-file publish bundles the app into one executable.

Things that do not break

Worth stating plainly, because teams overestimate the risk: all of your XAML, all of your styles and templates, all of your bindings, all of your converters, all of your custom controls, and all of your dependency properties carry over unchanged. WPF's API surface on .NET is the same surface. The breakage is in the platform around it, not in the UI framework.

Multi-targeting during the transition DEEPER

A large solution cannot always move in one go. A shared library may still be used by other .NET Framework apps, or you may want the old and new builds side by side for a few weeks. Multi-targeting builds the same project for more than one framework at once.

IN PLAIN TERMS

Multi-targeting is printing two editions of a book from one manuscript. Almost every page is shared. Where the editions must differ, the manuscript marks the passage "first edition only" or "second edition only", and the printer includes the right one. The project file marks which references belong to which edition; #if marks the passages in code.

The project file below targets both net48 and net10.0-windows. Notice TargetFrameworks in the plural, and the two ItemGroup elements whose Condition gives each build only the references it needs.

csproj 
<PropertyGroup>
  <TargetFrameworks>net48;net10.0-windows</TargetFrameworks>
  <UseWPF>true</UseWPF>
</PropertyGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'net48'">
  <Reference Include="System.Configuration" />
</ItemGroup>

<ItemGroup Condition="'$(TargetFramework)' == 'net10.0-windows'">
  <PackageReference Include="Microsoft.Extensions.Hosting" Version="10.0.0" />
</ItemGroup>

In code, the NET symbol is defined when building for modern .NET (5 and later) and not for .NET Framework, so each build compiles only its own branch:

C# 
#if NET
    var settings = _config.GetSection("Api").Get<ApiOptions>()!;
#else
    var settings = new ApiOptions { BaseUrl = ConfigurationManager.AppSettings["ApiUrl"]! };
#endif

Multi-targeting a shared library during migration is very useful. Multi-targeting the application itself rarely is: it doubles your test matrix for a transition that should last weeks.

RECAP
  • Migrate in small steps: reach .NET Framework 4.8, convert the project format, switch to PackageReference, then retarget.
  • Change one thing per step and commit after each, so every break has one cause.
  • Your XAML, styles, bindings and controls carry over unchanged; the breakage is in platform services.
  • The usual casualties are BinaryFormatter, WCF, AppDomains, Remoting, and changed culture and encoding defaults.
  • Multi-target shared libraries during the move, not the application itself.
