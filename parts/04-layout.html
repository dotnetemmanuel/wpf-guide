PART 04

Layout

Layout is a two-pass recursive negotiation. Understand the two passes and every panel's behaviour becomes predictable.

Builds on Part 3, XAML precisely. The custom panel at the end also uses a dependency property, explained in Part 5.

If you placed every control at fixed pixel coordinates, your window would break the first time the user resized it, changed the system text size, or switched to a language whose words are longer. WPF instead lets each element say how big it would like to be, and lets containers called panels decide where each child goes. The result adapts to whatever space exists.

Measure, then arrange

Layout runs in two passes over the element tree: one to find out what everyone wants, one to hand out space. After the first full layout, WPF revisits only the elements marked as needing layout again.

Measure. A parent calls child.Measure(availableSize), saying "here is the space I could give you". The child measures its own children, then reports DesiredSize: what it wants. Available size can be double.PositiveInfinity in a dimension, which means "ask for whatever you like"; a StackPanel passes infinity along its orientation, a ScrollViewer passes infinity in its scrolling direction.

Arrange. The parent decides and calls child.Arrange(finalRect), saying "here is what you actually get". The child may be given less than it asked for, and must cope. This is where HorizontalAlignment and VerticalAlignment are applied, positioning the child inside the slot it was given. Margin counts in both passes: it is added to the size the child asks for and kept clear around it when placed.

IN PLAIN TERMS

Picture a host seating guests at a long table. First the host asks each group "how many chairs would you like, if I have up to this many?" and writes the answers down. Only then, knowing all the requests, does the host hand out the actual chairs. A group can be given fewer than it asked for, and has to squeeze in. The difference from a dinner party is that each group first asks its own members the chair question before answering, and later divides the chairs it receives.

The rules that follow from this:

  • A child inside a StackPanel with Orientation="Vertical" gets infinite height at measure, so Height="Auto" means "as tall as I want" and vertical alignment does nothing: the panel gives each child exactly the height it asked for.
  • A ScrollViewer only scrolls if its content asked for more than it got, which is why putting a ListBox inside a vertical StackPanel produces an infinitely tall list that never scrolls. Use a Grid or DockPanel instead.
  • Width/Height constrain the measure pass. MinWidth/MaxWidth clamp it. ActualWidth/ActualHeight are the arrange results and are zero until the first layout pass completes.
IN PLAIN TERMS

A vertical StackPanel is a roll of paper with no end. Ask a ListBox on that roll how tall it wants to be, and it answers "tall enough for all ten thousand items", and gets exactly that. Its scroll bar never appears, because nothing is hidden: the list simply runs off the bottom of the window. A Grid row is a sheet of fixed size, so the list is told how much room there really is and scrolls within it.

The panels

Each panel is one layout strategy. You nest them: a Grid for the page, a StackPanel for a row of buttons inside one cell, and so on.

PanelUse it for
GridThe default. Rows and columns, star-sizing, spanning. Almost every screen root.
StackPanelShort sequences of items along one axis. Never for a scrolling list.
DockPanelClassic chrome: toolbar top, status bar bottom, content fills. Last child fills by default.
WrapPanelFlowing items that wrap. Tag clouds, toolbars, thumbnail walls.
CanvasAbsolute positioning. Diagram surfaces, designers, charts.
UniformGridEqual cells. Keypads, colour pickers, calendar grids.
VirtualizingStackPanelThe default ItemsPanel of ListBox. Realises only containers near the visible area.

In that last row, to realise a container is to actually create the ListBoxItem element for a data item. A list of ten thousand entries with twenty visible creates those twenty plus a cache of about a page above and below the visible area, which is what keeps long lists fast.

Grid: the useful details

A Grid declares its columns and rows first, then places each child with the Grid.Row and Grid.Column attributes (row and column 0 when omitted). Each column width is one of three kinds:

  • Auto: as wide as the widest content in that column.
  • A number: fixed, in device-independent units (explained at the end of this part).
  • Star sizing, * or 2*: a share of whatever width is left after the Auto and fixed columns are served.

Rows work the same way with Height. Notice the ColumnSpan attributes, which let one child cover several columns:

XAML 
<Grid>
  <Grid.ColumnDefinitions>
    <ColumnDefinition Width="Auto" />        <!-- as wide as content -->
    <ColumnDefinition Width="*"    />        <!-- 1 share of the leftover -->
    <ColumnDefinition Width="2*"   />        <!-- 2 shares of the leftover -->
    <ColumnDefinition Width="120"  MinWidth="80" />
  </Grid.ColumnDefinitions>
  <Grid.RowDefinitions>
    <RowDefinition Height="Auto" />
    <RowDefinition Height="*"    />
  </Grid.RowDefinitions>

  <TextBlock Text="Name" Grid.Row="0" Grid.Column="0" />
  <TextBox   Grid.Row="0" Grid.Column="1" Grid.ColumnSpan="3" />
  <ListBox   Grid.Row="1" Grid.ColumnSpan="4" />
</Grid>
IN PLAIN TERMS

Star sizing is splitting a bill. The fixed-price items (Auto and numeric columns) are paid first, then whatever remains is shared out by the number of stars: a 2* column gets two portions for every one a * column gets. Widen the window and only the shared remainder grows.

Two features people miss. SharedSizeGroup makes columns in separate grids the same width, which lines up forms built from repeated rows. GridSplitter gives the user a draggable divider between columns. Notice that the first needs Grid.IsSharedSizeScope on a common ancestor, and the splitter here sits in a narrow column of its own:

XAML 
<!-- SharedSizeGroup: align label columns across separate Grids -->
<StackPanel Grid.IsSharedSizeScope="True">
  <Grid>
    <Grid.ColumnDefinitions>
      <ColumnDefinition Width="Auto" SharedSizeGroup="Labels" />
      <ColumnDefinition Width="*" />
    </Grid.ColumnDefinitions>
    <TextBlock Text="Registration number" />
    <TextBox Grid.Column="1" />
  </Grid>
  <Grid>
    <Grid.ColumnDefinitions>
      <ColumnDefinition Width="Auto" SharedSizeGroup="Labels" />
      <ColumnDefinition Width="*" />
    </Grid.ColumnDefinitions>
    <TextBlock Text="Owner" />
    <TextBox Grid.Column="1" />
  </Grid>
</StackPanel>

<!-- GridSplitter: user-resizable columns -->
<Grid>
  <Grid.ColumnDefinitions>
    <ColumnDefinition Width="240" MinWidth="160" />
    <ColumnDefinition Width="4" />
    <ColumnDefinition Width="*" MinWidth="300" />
  </Grid.ColumnDefinitions>
  <TreeView />
  <GridSplitter Grid.Column="1" HorizontalAlignment="Stretch"
                ResizeBehavior="PreviousAndNext" />
  <ContentControl Grid.Column="2" />
</Grid>

Writing a custom panel DEEPER

The built-in panels cover nearly every screen. When none fits, such as a radial menu or a timeline, you write your own, and the measure and arrange passes above become two methods you override. This one lays children out on a circle; the shape of the code is the same for any layout algorithm you need:

C# 
public sealed class RadialPanel : Panel
{
    public static readonly DependencyProperty RadiusProperty =
        DependencyProperty.Register(
            nameof(Radius), typeof(double), typeof(RadialPanel),
            new FrameworkPropertyMetadata(100d,
                FrameworkPropertyMetadataOptions.AffectsMeasure |
                FrameworkPropertyMetadataOptions.AffectsArrange));

    public double Radius
    {
        get => (double)GetValue(RadiusProperty);
        set => SetValue(RadiusProperty, value);
    }

    protected override Size MeasureOverride(Size availableSize)
    {
        // Let every child take as much as it likes, then claim a square.
        var loose = new Size(double.PositiveInfinity, double.PositiveInfinity);
        double maxChild = 0;
        foreach (UIElement child in InternalChildren)
        {
            child.Measure(loose);
            maxChild = Math.Max(maxChild,
                Math.Max(child.DesiredSize.Width, child.DesiredSize.Height));
        }
        double side = (Radius + maxChild / 2) * 2;
        return new Size(side, side);
    }

    protected override Size ArrangeOverride(Size finalSize)
    {
        int n = InternalChildren.Count;
        if (n == 0) return finalSize;

        var centre = new Point(finalSize.Width / 2, finalSize.Height / 2);
        for (int i = 0; i < n; i++)
        {
            var child = InternalChildren[i];
            double angle = 2 * Math.PI * i / n - Math.PI / 2;
            var size = child.DesiredSize;
            var topLeft = new Point(
                centre.X + Radius * Math.Cos(angle) - size.Width / 2,
                centre.Y + Radius * Math.Sin(angle) - size.Height / 2);
            child.Arrange(new Rect(topLeft, size));
        }
        return finalSize;
    }
}

Read the two methods against the negotiation described earlier. MeasureOverride measures every child and returns the size the panel wants. ArrangeOverride gives each child a rectangle, here centred on a point of the circle, and returns the size actually used. The Radius declaration at the top is a dependency property (Part 5); its flags are what the rule below is about.

RULE

Any dependency property that changes how big something is must declare AffectsMeasure; anything that changes where it sits must declare AffectsArrange. Forget these and your panel simply won't update when the property changes.

Layout rounding and DPI

Monitors differ in how many pixels they pack into an inch, and Windows lets users scale everything up (125%, 150%, 200%). A framework that counted in raw pixels would draw tiny buttons on a sharp laptop screen.

WPF units are device-independent: 1 unit = 1/96 of a logical inch, and the Windows display scaling setting decides how many physical pixels that is. At 100% one unit is one pixel; on a 150% display, 96 units is 144 physical pixels. The physical size on screen still differs between devices, but a layout keeps its proportions instead of shrinking on a dense screen. That is why WPF scales cleanly and why a 1-unit border sometimes renders blurry: it lands between device pixels, and the edge is smeared across two of them.

IN PLAIN TERMS

Units are the measurements on a drawing, and pixels are the squares of the grid paper you trace it onto. The Windows scaling setting decides how many paper squares each unit covers, so on finer paper at a higher setting the drawing keeps its proportions instead of shrinking. A line that falls halfway between two rows of squares gets shaded across both, which is the blur. Layout rounding nudges each edge onto the nearest grid line.

UseLayoutRounding="True" (set it on your window; it inherits) snaps layout results to device pixels and fixes almost all of it. For hairlines inside a shape, SnapsToDevicePixels="True" is the older, cruder sibling; prefer layout rounding.

Mixed-DPI setups are the other half. Modern WPF can rescale a window as it moves between monitors with different scaling, but only if the application manifest asks for it. Check that app.manifest contains PerMonitorV2 if you have a mixed-DPI setup, which matters immediately for anyone docking a laptop to a 4K display. Without it, the window is stretched as a bitmap on the second monitor and looks soft.

RECAP
  • Layout runs in two passes: children say what size they want, then parents decide what they get.
  • A vertical StackPanel gives unlimited height, so a list inside one never scrolls; put lists in a Grid row instead.
  • Grid is the default panel: Auto fits content, numbers are fixed, and stars share what is left.
  • ActualWidth and ActualHeight stay zero until the first layout pass has run.
  • WPF measures in units of 1/96 of a logical inch, scaled by the Windows display setting, and UseLayoutRounding="True" on the window keeps edges crisp.
