PART 33

Data access and services

Most desktop apps read and write a local database, call a web API, or both. The libraries are the same ones a web app uses; what differs is how long things live, which thread waits, and what happens when the network is gone.

Builds on Part 15, dependency injection and the host, Part 17, threading and async and Part 20, testing, packaging, interop (the AppPaths class).

EF Core in a desktop app

EF Core (Entity Framework Core) is .NET's object-relational mapper: you query and save C# objects, and it writes the SQL. You work through a DbContext, an object that holds a database connection and a change tracker, a record of every entity it has loaded and how each one has changed since, so that SaveChanges knows what to write.

Desktop is not web: there is no request boundary, so DbContext lifetime has to be decided by you. In a web app, a new context is created for each HTTP request and thrown away at the end, and that choice is made for you. A desktop app runs for hours with no such natural end point. If you keep one context for the whole session, its change tracker grows with every query, it keeps returning the copies it already loaded instead of fresh data, and a save can write changes from a screen the user abandoned an hour ago.

The rule that works is one context per unit of work, never a singleton. A unit of work is one self-contained operation: load the list, save this edit.

IN PLAIN TERMS

A DbContext is a shopping basket, not a shop. You take one, put in what this trip needs, pay once at the till (SaveChanges), and hand it back. Keep the same basket all day and it fills with items from earlier trips; at the next till, everything still in it gets paid for, including things you meant to put back.

To create short-lived contexts on demand, register a context factory with the host and inject it where contexts are needed. The repository below asks the factory for a new context in each method and disposes it at the end with await using. Notice the read method: AsNoTracking tells EF not to record the loaded rows in the change tracker, and Select copies the results into plain TaskDto records, so nothing that leaves the method is connected to a context.

C# 
// Registration
builder.Services.AddDbContextFactory<TasksDbContext>(options =>
    options.UseSqlite($"Data Source={AppPaths.Database}"));

// Usage: a short-lived context per operation
public sealed class TaskRepository(IDbContextFactory<TasksDbContext> factory) : ITaskRepository
{
    public async Task<IReadOnlyList<TaskDto>> GetAllAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        return await db.Tasks
            .AsNoTracking()
            .OrderBy(t => t.DueDate)
            .Select(t => new TaskDto(t.Id, t.Title, t.IsDone, t.DueDate))
            .ToListAsync(ct);
    }

    public async Task SaveAsync(TaskDto dto, CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        var entity = await db.Tasks.FindAsync([dto.Id], ct);
        if (entity is null) { db.Tasks.Add(TaskEntity.From(dto)); }
        else { entity.Apply(dto); }
        await db.SaveChangesAsync(ct);
    }
}

A DTO (data transfer object) is a plain class or record that only carries data, with no link to where it came from. Lazy loading is EF fetching a related entity at the moment a property is first read; when that read comes from a binding during layout, the database query runs on the UI thread and the window freezes while it waits.

GOTCHA

Never bind the UI directly to EF entities. The context keeps every entity it tracks, and entities set up for lazy loading hold a reference back to their context. A bound DbSet keeps the context alive for the lifetime of the window, lazy loading fires on the UI thread during layout, and a single SaveChanges can cascade changes you never intended. Project to DTOs or view models at the repository boundary. AsNoTracking() on every read query is the habit to build.

Migrations at startup

When you change your entity classes, EF Core generates a migration: a script that brings an existing database schema up to date. On a server, you run migrations once as part of deployment. On a desktop, every user has their own database file, often SQLite in their profile folder, so the app itself has to apply pending migrations the first time the new version starts.

The class below does that as a hosted service, a service the host starts when the app starts. Notice the order: it asks whether any migrations are pending, returns straight away if not, and otherwise logs them, backs up the database file, and only then migrates.

C# 
public sealed class DatabaseMigrator(
    IDbContextFactory<TasksDbContext> factory,
    ILogger<DatabaseMigrator> log) : IHostedService
{
    public async Task StartAsync(CancellationToken ct)
    {
        await using var db = await factory.CreateDbContextAsync(ct);
        var pending = (await db.Database.GetPendingMigrationsAsync(ct)).ToList();
        if (pending.Count == 0) return;

        log.LogInformation("Applying {Count} migrations: {Names}", pending.Count, pending);
        BackupDatabase();
        await db.Database.MigrateAsync(ct);
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}

Register it with AddHostedService before anything that touches data. Hosted services start in the order they were registered, and because _host.StartAsync() is awaited in OnStartup, migration completes before the first window shows. Back up first: an interrupted migration on a user's local SQLite file is unrecoverable otherwise, and unlike a server, nobody is standing by with last night's backup.

Calling HTTP APIs

Talking to a web API looks simple: create an HttpClient, call it. The trouble is how long the client lives. Create a new one for every call and each leaves a connection behind that the operating system takes minutes to release; under steady use the machine runs out of them, which is called socket exhaustion. Keep one static client for the whole run and, unless you set PooledConnectionLifetime on its handler, it holds its connections forever, so if the server's address changes (a DNS change during a failover, say), the app keeps talking to the old one. That is the stale DNS problem.

IN PLAIN TERMS

A new HttpClient per call is like hiring a van for every parcel and leaving each one parked outside: the street fills up. One static client, with no PooledConnectionLifetime set, is one van that is never serviced and follows an old map forever. IHttpClientFactory runs a small fleet: it hands out vans that share a garage and quietly replaces each one after a while, so vehicles are reused and the maps stay current.

The registration below creates a typed client: your own TaskApi class receives a configured HttpClient through its constructor. Notice the base address and user agent set once here, and AddStandardResilienceHandler, which adds retries, timeouts and a circuit breaker for transient failures.

C# 
builder.Services
    .AddHttpClient<ITaskApi, TaskApi>((sp, http) =>
    {
        var o = sp.GetRequiredService<IOptions<ApiOptions>>().Value;
        http.BaseAddress = new Uri(o.BaseUrl);
        http.Timeout = TimeSpan.FromSeconds(30);
        http.DefaultRequestHeaders.UserAgent.ParseAdd($"Tasks/{BuildInfo.Version}");
    })
    .AddStandardResilienceHandler();      // Microsoft.Extensions.Http.Resilience

The typed client itself then only deals with its own requests. Notice ResponseHeadersRead, which returns as soon as the headers arrive, and DeserializeAsync on the stream, so a large response is parsed as it downloads rather than first being held in memory as one string.

C# 
public sealed class TaskApi(HttpClient http) : ITaskApi
{
    private static readonly JsonSerializerOptions Json =
        new(JsonSerializerDefaults.Web);

    public async Task<IReadOnlyList<TaskDto>> GetChangesAsync(
        DateTimeOffset since, CancellationToken ct)
    {
        using var response = await http.GetAsync(
            $"tasks?since={since:O}", HttpCompletionOption.ResponseHeadersRead, ct);

        response.EnsureSuccessStatusCode();

        await using var stream = await response.Content.ReadAsStreamAsync(ct);
        return await JsonSerializer.DeserializeAsync<List<TaskDto>>(stream, Json, ct) ?? [];
    }
}

AddHttpClient<TInterface, TImplementation> registers the typed client with a managed HttpMessageHandler pool. That avoids both socket exhaustion (from creating clients per call) and the stale-DNS problem you get from a static HttpClient without PooledConnectionLifetime. Never construct HttpClient with new in application code.

An offline-capable read path DEEPER

Laptops lose Wi-Fi, VPNs drop, and servers go down for maintenance. An app that shows nothing, or an error dialog, whenever the network is unavailable is unusable exactly when people are travelling or working from home. The pattern most desktop line-of-business apps converge on: read local, sync in the background, surface staleness.

IN PLAIN TERMS

Think of a printed train timetable with "valid as of Monday" in the corner. You can always read it, even with no signal. When you can get online, you check for changes and reprint it. If you cannot, you still use the old one, and the date tells you how far to trust it. The app keeps a local copy the same way and tells the user when the copy may be out of date.

The service below combines the local repository and the remote API, in two methods. LoadCachedAsync returns what is stored locally, without touching the network. SyncAsync fetches changes since the last sync and merges them. If that succeeds, it returns the fresh list; if the network fails, it logs a warning and returns the local list flagged as stale, with a message for the user. Network failures come back as data rather than as an exception.

C# 
using Polly;

public sealed class TaskService(
    ITaskRepository local, ITaskApi remote, IClock clock, ILogger<TaskService> log)
{
    public Task<IReadOnlyList<TaskDto>> LoadCachedAsync(CancellationToken ct)
        => local.GetAllAsync(ct);

    public async Task<LoadResult<TaskDto>> SyncAsync(CancellationToken ct)
    {
        try
        {
            var since = await local.GetLastSyncAsync(ct);
            var changes = await remote.GetChangesAsync(since, ct);
            await local.MergeAsync(changes, clock.UtcNow, ct);
            return new LoadResult<TaskDto>(await local.GetAllAsync(ct), IsStale: false, null);
        }
        catch (Exception ex) when (!ct.IsCancellationRequested &&
            ex is HttpRequestException or TaskCanceledException or ExecutionRejectedException)
        {
            log.LogWarning(ex, "Working offline");
            return new LoadResult<TaskDto>(await local.GetAllAsync(ct), IsStale: true, "Showing saved data");
        }
    }
}

public sealed record LoadResult<T>(
    IReadOnlyList<T> Items, bool IsStale, string? Message);

The view model calls LoadCachedAsync first and shows that list, so the screen fills at once, then awaits SyncAsync and replaces the list with the result. The UI never waits on the network to show something.

Notice the exception filter. The ct.IsCancellationRequested check lets a user's own cancel escape as a cancellation instead of turning into "Showing saved data". ExecutionRejectedException comes from Polly, the library behind the resilience handler: when that handler times out it throws TimeoutRejectedException, and when its circuit breaker is open it throws BrokenCircuitException. Both derive from ExecutionRejectedException, so a filter without it only appears to work because the 30-second HttpClient.Timeout usually fires first.

Bind IsStale to an info bar. Users tolerate stale data; they do not tolerate a spinner that never resolves or an exception dialog because the VPN dropped.

Where files go

Windows has a designated folder for each kind of file an app writes, and choosing the right one decides whether the data follows the user between machines, is shared between users, or survives an update. The Environment.SpecialFolder values give you the path without hard-coding it.

KindFolder
Per-user data, databases, cachesSpecialFolder.LocalApplicationData (%LOCALAPPDATA%)
Per-user settings that should roamSpecialFolder.ApplicationData (%APPDATA%)
Machine-wide read-only configSpecialFolder.CommonApplicationData (%PROGRAMDATA%)
User documents the user managesSpecialFolder.MyDocuments, in a named subfolder
NeverThe install directory. It is read-only for standard users and you will get access-denied reports.

"Roam" means that in organisations with roaming profiles, the folder is copied to whichever machine the user signs in to. Keep it small: settings, not databases or caches.

RECAP
  • Create a short-lived DbContext for each operation through a context factory, never one for the whole app.
  • Read with AsNoTracking and hand the UI DTOs, never EF entities.
  • Apply migrations in a hosted service at startup, after backing up the user's database file.
  • Get HttpClient instances from AddHttpClient, never with new.
  • Keep a local copy of remote data and tell the user when it may be stale, instead of failing when offline.
  • Write user data under %LOCALAPPDATA%, never into the install directory.
