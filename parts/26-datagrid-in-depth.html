PART 26

DataGrid in depth

The heaviest control in the box and the one most business applications are built on. Worth knowing properly.

Builds on Part 11, data binding, Part 9, styles and triggers, Part 13, validation and Part 19, performance.

IN PLAIN TERMS

A DataGrid looks like a spreadsheet, but it owns no data. Each row is one of your objects and each column is a view onto one property of that object. When the user finishes editing a cell, the value goes into that property through a binding, and when your code changes the property, the cell updates.

Columns

Left alone, a DataGrid generates one column per public property of your row type, with the property name as the header. That is fine for a quick look at data and wrong for anything a person will use: you cannot choose the order, the widths, the formatting or which properties appear at all. So real screens set AutoGenerateColumns="False" and declare every column.

There are five column types. DataGridTextColumn shows text, DataGridCheckBoxColumn a tick box, DataGridComboBoxColumn a pick list, DataGridHyperlinkColumn a clickable link, and DataGridTemplateColumn anything you can put in a DataTemplate. Column widths take a fixed number (in device-independent pixels), Auto, SizeToCells, SizeToHeader, or a star size such as 2*, which means a proportional share of whatever width is left over.

Each cell has two faces. It shows a display element while the user is just looking (a TextBlock for a text column) and swaps in an editing element once they start editing (a TextBox). ElementStyle styles the first and EditingElementStyle the second.

The grid below declares five columns. Notice the settings on the grid itself: SelectionMode="Extended" allows several rows to be selected with Ctrl and Shift, FrozenColumnCount="1" keeps the first column in place when the user scrolls sideways, and the virtualisation settings are covered under performance below. In the columns, notice the red overdue date done with a DataTrigger in ElementStyle, and the delete button, whose command binding has to climb to the DataGrid because each row's DataContext is the row object, not the screen's view model.

XAML 
<DataGrid ItemsSource="{Binding Rows}"
          AutoGenerateColumns="False"
          CanUserAddRows="False"
          CanUserDeleteRows="False"
          CanUserReorderColumns="True"
          SelectionMode="Extended"
          SelectionUnit="FullRow"
          GridLinesVisibility="Horizontal"
          HeadersVisibility="Column"
          EnableRowVirtualization="True"
          EnableColumnVirtualization="False"
          VirtualizingPanel.VirtualizationMode="Recycling"
          RowHeight="26"
          FrozenColumnCount="1">

  <DataGrid.Columns>
    <DataGridTextColumn Header="Title" Width="2*"
                        Binding="{Binding Title}"
                        SortMemberPath="Title" />

    <DataGridTextColumn Header="Due" Width="110"
                        Binding="{Binding DueDate, StringFormat=yyyy-MM-dd}">
      <DataGridTextColumn.ElementStyle>
        <Style TargetType="TextBlock">
          <Setter Property="HorizontalAlignment" Value="Right" />
          <Style.Triggers>
            <DataTrigger Binding="{Binding IsOverdue}" Value="True">
              <Setter Property="Foreground" Value="{DynamicResource DangerBrush}" />
            </DataTrigger>
          </Style.Triggers>
        </Style>
      </DataGridTextColumn.ElementStyle>
    </DataGridTextColumn>

    <DataGridCheckBoxColumn Header="Done" Width="60"
                            Binding="{Binding IsDone, UpdateSourceTrigger=PropertyChanged}" />

    <DataGridComboBoxColumn Header="Assignee" Width="150"
        SelectedValueBinding="{Binding AssigneeId}"
        SelectedValuePath="Id"
        DisplayMemberPath="Name">
      <DataGridComboBoxColumn.ElementStyle>
        <Style TargetType="ComboBox">
          <Setter Property="ItemsSource"
                  Value="{Binding DataContext.People,
                                  RelativeSource={RelativeSource AncestorType=DataGrid}}" />
        </Style>
      </DataGridComboBoxColumn.ElementStyle>
      <DataGridComboBoxColumn.EditingElementStyle>
        <Style TargetType="ComboBox">
          <Setter Property="ItemsSource"
                  Value="{Binding DataContext.People,
                                  RelativeSource={RelativeSource AncestorType=DataGrid}}" />
        </Style>
      </DataGridComboBoxColumn.EditingElementStyle>
    </DataGridComboBoxColumn>

    <DataGridTemplateColumn Header="" Width="40">
      <DataGridTemplateColumn.CellTemplate>
        <DataTemplate>
          <Button Content="×" Width="20" Height="20"
                  Command="{Binding DataContext.DeleteCommand,
                                    RelativeSource={RelativeSource AncestorType=DataGrid}}"
                  CommandParameter="{Binding}" />
        </DataTemplate>
      </DataGridTemplateColumn.CellTemplate>
    </DataGridTemplateColumn>
  </DataGrid.Columns>
</DataGrid>
GOTCHA

DataGridComboBoxColumn is the single most frustrating class in WPF. A column is a recipe, not something on screen: the grid reads it once per row to build that row's cell. The column itself is not part of the visual tree, so it has no parent to inherit the DataGrid's DataContext from. A binding on one of the column's own properties, such as ItemsSource or Header, therefore has nothing to bind against. Binding and SelectedValueBinding are different, because the column passes them to each cell, where the row object is the DataContext.

That is why the ItemsSource has to be pushed in through both ElementStyle and EditingElementStyle: those styles land on the ComboBox generated in each cell, which is on screen and can walk up the tree to the DataGrid. The alternative that many teams settle on is a DataGridTemplateColumn containing a plain ComboBox, which behaves like everything else.

Selection from a view model

Your view model often needs to know which rows the user picked, for example to delete them or to enable a toolbar button. A single selection is easy: SelectedItem is a dependency property and binds like any other. Multiple selection is the problem. SelectedItems is not a dependency property, so it cannot be bound. Three options:

  1. Put an IsSelected property on the row view model and bind it in RowStyle. Cleanest, and it survives virtualisation.
  2. A behaviour that syncs SelectedItems to a collection.
  3. SelectionChanged in code-behind pushing into the view model. Works, but it's the one that gets copied everywhere.

Option 1 uses RowStyle, a style the grid applies to every row container: the DataGridRow element it creates to host each of your objects. The setter binds the row's own IsSelected to the property on your object in both directions, so selecting a row sets the property and setting the property selects the row. The same style shows the other common use of RowStyle, colouring a whole row from a flag on the data.

XAML: option 1 
<DataGrid.RowStyle>
  <Style TargetType="DataGridRow">
    <Setter Property="IsSelected" Value="{Binding IsSelected, Mode=TwoWay}" />
    <Style.Triggers>
      <DataTrigger Binding="{Binding HasConflict}" Value="True">
        <Setter Property="Background" Value="{DynamicResource WarnSurfaceBrush}" />
      </DataTrigger>
    </Style.Triggers>
  </Style>
</DataGrid.RowStyle>

It survives virtualisation because the selection is stored on your objects. Row containers are thrown away or reused as the user scrolls, but when a row comes back into view the binding reads the flag again.

Editing, commit and validation

Picture a user who edits the title, the due date and the assignee of a task, then realises it was the wrong row. They expect to back out of all three changes at once. The grid supports this with a two-level commit model: an edit is committed first at cell level (the value is written to your property when the user leaves the cell) and then at row level (the row edit ends when the user leaves the row).

Your row type can take part in the row level by implementing IEditableObject. That gives you transactional row editing for free:

IN PLAIN TERMS

IEditableObject is the grid telling your object when to take a photocopy. BeginEdit means "the user started changing this row, keep a copy". CancelEdit means "put the copy back". EndEdit means "the changes stand, throw the copy away". The grid only says when; making and restoring the copy is your code, and your properties really do change during the edit, so anything watching them sees the in-between values.

In the sketch below, Snapshot, Restore and TaskSnapshot are your own helpers, not shown. The ??= keeps the first copy if BeginEdit is called again before the row edit ends.

C# 
public partial class TaskRowViewModel : ObservableValidator, IEditableObject
{
    private TaskSnapshot? _backup;

    public void BeginEdit()   => _backup ??= Snapshot();
    public void CancelEdit()  { if (_backup is { } b) { Restore(b); _backup = null; } }
    public void EndEdit()     => _backup = null;
}

Escape once cancels the cell; Escape twice cancels the row and calls CancelEdit.

Some rules span several cells, such as "the due date must not be before the start date". Checking each cell alone cannot catch that. To validate the whole row, use a DataGrid.RowValidationRules entry: a ValidationRule of your own (see Part 13). Give it ValidationStep="UpdatedValue", which runs the rule after the new values have been written to your object, so the rule can look at the row as a whole:

XAML 
<DataGrid.RowValidationRules>
  <rules:TaskRowRule ValidationStep="UpdatedValue" />
</DataGrid.RowValidationRules>

<DataGrid.RowValidationErrorTemplate>
  <ControlTemplate>
    <Grid Margin="0,-2,0,-2" ToolTip="{Binding RelativeSource={RelativeSource
              AncestorType=DataGridRow}, Path=(Validation.Errors)[0].ErrorContent}">
      <Ellipse Width="12" Height="12" Fill="{DynamicResource DangerBrush}" />
      <TextBlock Text="!" Foreground="White" FontWeight="Bold" FontSize="9"
                 HorizontalAlignment="Center" VerticalAlignment="Center" />
    </Grid>
  </ControlTemplate>
</DataGrid.RowValidationErrorTemplate>

RowValidationErrorTemplate decides what a failed row looks like. This one draws a small red circle with an exclamation mark and puts the first error message in its tooltip.

Performance rules for large grids

IN PLAIN TERMS

A grid bound to 10,000 rows stays fast only because it builds rows for what is on screen, perhaps 30 of them, and reuses those as the user scrolls. That is virtualisation, covered in Part 19. Almost every rule below avoids something that makes the grid look at every row, which quietly throws the saving away.

  • Set an explicit RowHeight. Without it, the grid measures every row to find the tallest, defeating virtualisation on first layout.
  • Avoid Width="Auto" and SizeToCells columns. They force every row to be measured. Use * and fixed widths.
  • Leave EnableColumnVirtualization="False" unless you genuinely have 50+ columns; it costs more than it saves below that.
  • Keep CellStyle and templates shallow. Every extra Border is multiplied by rows × columns.
  • Do not bind ItemsSource to a LINQ query. A query is not a list, so it re-enumerates: every time the grid walks it, the query runs again. Materialise to a list first.
  • Sort on the server if the data lives there. Keep CanUserSortColumns on and handle Sorting yourself with e.Handled = true, as below.

Sorting on the server DEEPER

When the grid shows one page of a table with two million rows, its built-in sort would only reorder the page it holds. Clicking a header should instead ask the database for a new page in the new order.

The Sorting event fires when the user clicks a header, before the grid sorts. Setting e.Handled = true stops the built-in sort. Your handler then flips the column's SortDirection itself, so the arrow in the header still shows, clears the arrow from every other column, and asks the view model to reload. The event only fires while CanUserSortColumns (and the column's own CanUserSort) is true; turn it off and header clicks do nothing at all.

C#: server-side sorting 
private async void OnSorting(object sender, DataGridSortingEventArgs e)
{
    e.Handled = true;
    var column = e.Column;

    column.SortDirection = column.SortDirection == ListSortDirection.Ascending
        ? ListSortDirection.Descending
        : ListSortDirection.Ascending;

    foreach (var c in ((DataGrid)sender).Columns)
        if (c != column) c.SortDirection = null;

    await _viewModel.SortAsync(column.SortMemberPath, column.SortDirection.Value);
}
RECAP
  • Turn off automatic columns and declare each column, so you control order, width and formatting.
  • A column is not on screen, so a binding on its own properties, such as ItemsSource, cannot see the grid's data context, while Binding and SelectedValueBinding work because each cell receives them.
  • Bind multiple selection through an IsSelected flag on each row object, set up in RowStyle.
  • Edits commit per cell and then per row, and IEditableObject lets a row be cancelled as a whole.
  • Large grids stay fast only while virtualisation works: fixed row heights, no auto-sized columns, shallow templates.
