PART 06

Routed events and commands

In WPF a click does not belong to a single object. It travels through the elements that make up the window, and any of them can respond. Commands then separate what the user asked for from the control they used to ask.

Builds on Part 3, XAML precisely (elements nested inside elements) and Part 5, dependency properties (the static-field registration pattern). The visual tree gets its full treatment in Part 7.

Three routing strategies

Picture a toolbar with twenty buttons. If every click fired only on the button itself, you would wire twenty handlers. Worse, a WPF button is not one object on screen: its caption, border and icon are separate elements drawn inside it, and the mouse lands on one of those. An event that fired only on the element under the pointer would reach the caption, not the button.

WPF solves both problems by letting the event travel. A routed event is an event that, once raised, visits a chain of elements in the visual tree rather than firing on one object. The visual tree is every element actually drawn, including the pieces inside each control, arranged parent to child. The element where the event starts is its source.

IN PLAIN TERMS

Think of a click as news passing through an organisation chart. First it is announced from the top down to the person it concerns, so each manager on that line can step in early. Then that person reports it back up the same line, and each manager can act on it. Anyone who deals with it can stamp it "handled", and the rest ignore it unless they asked to see everything. Where the analogy stops: only the direct line between the top and that person ever hears about it, never colleagues on other branches.

Every routed event uses one of three routing strategies, which fix the direction of travel:

  • Tunnelling: from the root down to the source. Named PreviewXxx by convention. Fires first.
  • Bubbling: from the source up to the root. Named Xxx. Fires after the tunnel completes.
  • Direct: fires only on the source, like a normal CLR event, but still participates in the event system (so it can be used in an EventSetter, Part 9).

Input events come in tunnelling and bubbling pairs. The figure follows one mouse press on the text inside a button.

Bubbling is why you can put one handler on a panel and catch clicks from every button inside it. StackPanel has no Click event of its own, so the attribute names the class that defines it: ButtonBase.Click means "the Click event of ButtonBase, the base class of every button, arriving here from below".

XAML + C# 
<StackPanel ButtonBase.Click="OnAnyButtonClick">
  <Button Content="Copy"  Tag="copy"  />
  <Button Content="Paste" Tag="paste" />
</StackPanel>

The comments name what the handler receives; for Click, two of them are the same button. Notice the last line: marking the event handled keeps it from reaching the window.

C# 
private void OnAnyButtonClick(object sender, RoutedEventArgs e)
{
    // sender     = the StackPanel (where the handler is attached)
    // e.Source   = the Button that raised Click
    // e.OriginalSource = also the Button for Click; an inner TextBlock only for raw mouse events
    if (e.OriginalSource is not DependencyObject d) return;
    var button = d as Button ?? TreeSearch.FindAncestor<Button>(d);   // Part 07
    Dispatch(button?.Tag as string);
    e.Handled = true;             // stops the bubble here
}

Click Copy and Dispatch receives "copy". TreeSearch.FindAncestor is a small helper that walks up the visual tree; it is listed in Part 7. For raw input such as MouseDown the two sources can differ, which is what the gotcha is about.

GOTCHA

e.Source and e.OriginalSource can differ. OriginalSource is the raw visual hit, often a TextBlock or Border inside a control template. Source is the logical-tree element the event is attributed to. For hit-testing in a list, you almost always want OriginalSource plus a walk up to the container.

Setting e.Handled = true stops further handlers, unless a handler was registered with handledEventsToo. That option exists only in code, through AddHandler:

C# 
// Runs even if something lower already marked the event handled.
myPanel.AddHandler(UIElement.MouseLeftButtonDownEvent,
                   new MouseButtonEventHandler(OnDown),
                   handledEventsToo: true);

You need this more often than you would like, because several built-in controls mark events handled internally. TextBox handles MouseLeftButtonDown; ListBoxItem handles it too. Tunnelled Preview events are the other escape hatch: they fire before the control gets a chance to swallow anything.

Declaring a routed event DEEPER

When you write your own control and want its parents to hear about something, you declare a routed event the way the framework does. The pattern mirrors a dependency property: a static field registered with the system, plus an ordinary-looking CLR event whose add and remove forward to it.

C# 
public static readonly RoutedEvent RatingChangedEvent =
    EventManager.RegisterRoutedEvent(
        nameof(RatingChanged), RoutingStrategy.Bubble,
        typeof(RoutedPropertyChangedEventHandler<int>), typeof(RatingBar));

public event RoutedPropertyChangedEventHandler<int> RatingChanged
{
    add    => AddHandler(RatingChangedEvent, value);
    remove => RemoveHandler(RatingChangedEvent, value);
}

private void Raise(int oldValue, int newValue) =>
    RaiseEvent(new RoutedPropertyChangedEventArgs<int>(oldValue, newValue, RatingChangedEvent));

RaiseEvent sends the event on its way. Because the strategy is Bubble, any ancestor can listen for it in XAML with local:RatingBar.RatingChanged="...", exactly as the panel above listened for ButtonBase.Click.

Commands

A Save action is usually reachable from a menu item, a toolbar button and Ctrl+S. With plain click handlers you write the logic three times, and when there is nothing to save you have to disable three controls yourself.

A command is an object that represents an action: you can execute it, and you can ask whether it can execute right now. Controls such as Button and MenuItem accept a command, run it when activated, and disable themselves when it says it cannot run. A command decouples "what the user asked for" from "which control asked".

IN PLAIN TERMS

A command is a named request slip, "Save", rather than a wire from one button to one piece of code. The menu, the toolbar and the shortcut all hand in the same slip. Whoever owns the slip decides what happens, and also posts a notice saying whether requests are being accepted right now. Every control that uses the slip reads that notice and greys itself out when the answer is no.

WPF ships two mechanisms and they are easy to confuse.

RoutedCommand: the built-in one

ApplicationCommands.Save, EditingCommands.ToggleBold and friends are RoutedUICommands. They route through the tree looking for a CommandBinding that handles them, and they come with default key gestures for free. A CommandBinding attaches the handlers for one command to an element: Executed does the work, CanExecute answers whether it is available.

XAML 
<Window.CommandBindings>
  <CommandBinding Command="ApplicationCommands.Save"
                  Executed="OnSave" CanExecute="OnCanSave" />
</Window.CommandBindings>

<Menu>
  <MenuItem Header="_File">
    <!-- picks up the header text AND Ctrl+S automatically -->
    <MenuItem Command="ApplicationCommands.Save" />
  </MenuItem>
</Menu>

When this runs, the menu shows Save with Ctrl+S beside it, the item greys out whenever OnCanSave sets e.CanExecute to false, and pressing Ctrl+S calls OnSave.

Good for text-editing verbs and anything where the target depends on focus: a cut/copy/paste toolbar that should act on whichever text box is active gets this for free. Bad for view-model logic, because CommandBinding handlers live in code-behind.

ICommand on the view model: what you will actually use

A view model is a plain C# class that holds a screen's state and actions without referring to any control (Part 14 covers the pattern). Its commands implement ICommand, the three-member interface every WPF command source understands:

C# 
public interface ICommand
{
    bool CanExecute(object? parameter);
    void Execute(object? parameter);
    event EventHandler? CanExecuteChanged;
}

A Button or MenuItem calls CanExecute to decide whether it is enabled, Execute when activated, and listens to CanExecuteChanged to know when to ask again. Controls do not poll: a greyed-out Save button stays grey until the command raises that event.

Write these by hand exactly once, to understand them, then use [RelayCommand] from the Community Toolkit forever after (Part 14). The one thing worth knowing is how CanExecuteChanged gets raised, because that is where hand-rolled implementations go wrong.

WPF's CommandManager re-queries CanExecute on every focus change, keyboard event and mouse-up. Hooking into it is a one-liner and is what the old RelayCommand samples do:

C# 
public event EventHandler? CanExecuteChanged
{
    add    => CommandManager.RequerySuggested += value;
    remove => CommandManager.RequerySuggested -= value;
}

It works, and it is wasteful: every command in the visual tree is re-evaluated on every keystroke. Prefer explicit notification (command.NotifyCanExecuteChanged()) and reserve CommandManager.InvalidateRequerySuggested() for the cases where something outside your control changed.

Input bindings

A built-in RoutedUICommand brings its own shortcut; the SaveCommand on your view model does not. An input binding maps a key or mouse gesture to any command, with an optional parameter.

XAML 
<Window.InputBindings>
  <KeyBinding Key="S" Modifiers="Ctrl"       Command="{Binding SaveCommand}" />
  <KeyBinding Key="F5"                       Command="{Binding RefreshCommand}" />
  <KeyBinding Key="Delete"                   Command="{Binding DeleteCommand}"
                                             CommandParameter="{Binding SelectedItem}" />
  <MouseBinding MouseAction="MiddleClick"    Command="{Binding CloseTabCommand}" />
</Window.InputBindings>

These fire when the input reaches the window, so they work wherever focus is inside it. A focused control that handles the key itself gets it first, and then the binding never sees it.

GOTCHA

InputBindings is not a dependency property, so a Style setter cannot fill it. The Command binding on a KeyBinding follows the DataContext like any other binding, so it works whenever the data context arrives. A KeyBinding only fires while keyboard focus is inside the element that owns it: shortcuts on a UserControl do nothing until something inside it has focus, so put window-wide shortcuts on the Window.

RECAP
  • A routed event travels the tree: the Preview event tunnels down from the window to the element, then the plain event bubbles back up.
  • One handler on a container can catch an event from everything inside it.
  • Setting e.Handled makes later handlers skip the event unless they were added with handledEventsToo, and Preview events run before a control can swallow it.
  • e.OriginalSource is the element actually hit, while e.Source is the element the event is attributed to.
  • A command bundles an action with whether it is currently allowed, and controls that use it enable and disable themselves.
  • Put ICommand on the view model and raise CanExecuteChanged explicitly; keep RoutedCommand for editing verbs that follow focus.
