PART 34

Security, settings and secrets

A desktop app runs on a machine you do not control, under an account you did not choose, next to files the user can open in Notepad. That shapes how you store settings, what you can keep secret, and what input you can trust.

Builds on Part 15, dependency injection and the host, Part 20, testing, packaging, interop (the AppPaths class) and Part 32, Windows integration and custom chrome (the WindowPlacement record).

Settings that are not app.config

.NET Framework apps kept user settings in app.config through the Properties.Settings designer. That system still works but is a dead end (Part 20). The modern replacement is simple: a plain class holding the settings, serialised to a JSON file in the user's profile.

The code below has two parts. UserSettings is the data, with a sensible default for every property, so a missing value in the file never leaves you with a null. SettingsStore loads and saves it. Notice that Load catches every exception and falls back to defaults, and that Save never writes to the real settings file directly: it writes a temporary file, forces it onto the disk, then renames it over the old one.

C# 
public sealed class UserSettings
{
    public string Theme { get; set; } = "System";
    public string Culture { get; set; } = "";
    public bool StartMinimised { get; set; }
    public WindowPlacement? MainWindow { get; set; }
    public List<string> RecentFiles { get; set; } = [];
}

public sealed class SettingsStore(ILogger<SettingsStore> log)
{
    private static readonly JsonSerializerOptions Json =
        new(JsonSerializerDefaults.Web) { WriteIndented = true };

    public UserSettings Load()
    {
        try
        {
            if (!File.Exists(AppPaths.Settings)) return new UserSettings();
            return JsonSerializer.Deserialize<UserSettings>(
                File.ReadAllText(AppPaths.Settings), Json) ?? new UserSettings();
        }
        catch (Exception ex)
        {
            log.LogWarning(ex, "Settings unreadable; starting from defaults");
            return new UserSettings();
        }
    }

    public void Save(UserSettings settings)
    {
        AppPaths.EnsureCreated();
        string temp = AppPaths.Settings + ".tmp";
        using (var fs = new FileStream(temp, FileMode.Create, FileAccess.Write, FileShare.None))
        {
            JsonSerializer.Serialize(fs, settings, Json);
            fs.Flush(flushToDisk: true);
        }
        File.Move(temp, AppPaths.Settings, overwrite: true);
    }
}

Two rules that turn out to matter more than they look: always recover from an unreadable settings file rather than crashing on startup, and always write atomically. Users' machines lose power mid-save.

A write is atomic when anyone reading the file afterwards sees either the complete old version or the complete new one, never half of each. Writing straight into settings.json is not: if the machine dies halfway, the file is left truncated, and without the recovery in Load the app would then refuse to start every time. The rename on its own protects against the app crashing mid-save. Against power loss it is only enough if the temporary file's contents have really reached the disk before the rename, because Windows may still be holding them in memory; Flush(flushToDisk: true) is what makes sure of that.

IN PLAIN TERMS

Updating a notice on a board by rubbing out the old text and writing the new text in place leaves a mess if you are interrupted halfway. Writing the new notice on a fresh sheet, letting the ink dry, and then swapping it for the old one in a single move means the board always shows a complete notice. The temporary file is the fresh sheet, flushing to disk is waiting for the ink to dry, and File.Move with overwrite is the swap.

Secrets on a user's machine

Sooner or later an app needs a credential: an API key, a client secret, a user's access token. The instinct is to hide it somewhere in the app. That instinct is the problem this section addresses.

GOTCHA

Anything shipped to a user's machine is not secret. A client secret in appsettings.json, obfuscated in a resource, or encrypted with a key that also ships, is all equally extractable. Desktop applications are public clients in OAuth terms. Design accordingly: use the authorization code flow with PKCE and no client secret, and put anything that must stay secret behind your own API.

IN PLAIN TERMS

Shipping a secret inside your app is like mailing every customer a copy of the office key hidden inside a box. However clever the hiding place, each customer now owns the box and has unlimited time to open it. OAuth's term public client simply means an app in that position: one that cannot keep a secret, so the security has to come from something else, such as the user signing in.

In the authorization code flow with PKCE (Proof Key for Code Exchange), the app sends the user to sign in with the identity provider, gets back a one-time code, and exchanges it for tokens. PKCE ties the exchange to a random value the app generated for this one sign-in, so an intercepted code is useless to anyone else.

Secrets the user has entrusted to you are a different case: a token you received after they signed in, or a password they asked you to remember. You cannot avoid storing those, but you can make sure the stored copy is useless if the file is copied elsewhere. For tokens and passwords the user has entrusted to you, DPAPI (the Windows Data Protection API) ties the ciphertext to the Windows user account:

IN PLAIN TERMS

DPAPI is a safe whose combination is the user's Windows sign-in. You never see or manage the key. Copy the encrypted file to another machine, or open it as another user, and it cannot be decrypted (the exception is a domain account with a roaming profile, which can decrypt it on any machine the same user signs in to). The limit of the analogy: every program running as that same user can open the safe too, so DPAPI protects against a stolen file, not against malware already running in the user's session.

The class below wraps DPAPI in two methods. Save encrypts a string and writes the bytes to a file; Load reads and decrypts it, and returns null when decryption fails. Notice the entropy: an extra value mixed into the encryption, so another app running as the same user cannot decrypt your data without knowing it. It ships inside your app, so it raises the bar rather than closing the door.

C# 
// PackageReference: System.Security.Cryptography.ProtectedData
public static class UserSecretStore
{
    private static readonly byte[] Entropy = "Tasks.v1"u8.ToArray();

    public static void Save(string name, string value)
    {
        byte[] cipher = ProtectedData.Protect(
            Encoding.UTF8.GetBytes(value), Entropy, DataProtectionScope.CurrentUser);

        AppPaths.EnsureCreated();
        File.WriteAllBytes(Path.Combine(AppPaths.Secrets, name + ".bin"), cipher);
    }

    public static string? Load(string name)
    {
        string path = Path.Combine(AppPaths.Secrets, name + ".bin");
        if (!File.Exists(path)) return null;
        try
        {
            byte[] plain = ProtectedData.Unprotect(
                File.ReadAllBytes(path), Entropy, DataProtectionScope.CurrentUser);
            return Encoding.UTF8.GetString(plain);
        }
        catch (CryptographicException) { return null; }   // different user or machine
    }
}

Open one of the .bin files it writes and you see random bytes, not the token. Copy it to a colleague's machine and Load returns null there.

For interactive sign-in, Microsoft.Identity.Client (MSAL) with the WAM broker is the right answer on Windows: it uses the OS account picker, handles token caching and refresh, and never asks you to store a secret. WAM (Web Account Manager) is the Windows component that holds the accounts the user has already signed in to Windows with, which is why the user often does not need to type a password at all.

Input that reaches a shell or a parser

Some user input gets handed to something powerful: the Windows shell, which opens anything it is given, or a parser that decides which objects to create. If you pass that input through unchecked, a crafted link or file can make your app run a program the user never meant to run.

The first function below opens a user-supplied link. Notice that it parses the text as a URI and allows only a short list of schemes before handing it to the shell. The second part runs a command-line tool. Notice ArgumentList: each argument is added separately and quoted for you, so a path containing spaces or quote characters cannot break out and become extra arguments. It does not stop a value that starts with - being read by the tool as an option, though: reject such values, or turn a path into an absolute one with Path.GetFullPath first.

C# 
// Opening a user-supplied path or URL: validate the scheme first.
public static void OpenExternal(string target)
{
    if (!Uri.TryCreate(target, UriKind.Absolute, out var uri)) return;
    if (uri.Scheme is not ("http" or "https" or "file" or "mailto")) return;

    Process.Start(new ProcessStartInfo(uri.AbsoluteUri) { UseShellExecute = true });
}

// Running a tool: use the argument list, never a concatenated command line.
var psi = new ProcessStartInfo("dotnet");
psi.ArgumentList.Add("build");
psi.ArgumentList.Add(userSuppliedPath);   // quoted and escaped for you
psi.UseShellExecute = false;

Be deliberate about file in that scheme list: the shell opens a file with whatever program is registered for it, and for an .exe or a script that means running it. Drop file if the targets can come from anywhere you do not trust.

Two more that bite in WPF specifically. XamlReader.Parse on untrusted markup can instantiate arbitrary types and is a remote code execution primitive, a building block an attacker can use to run their own code in your process: never parse XAML you did not produce. And Json.NET's TypeNameHandling setting, which lets the incoming JSON name the .NET type to create, has the same problem; System.Text.Json's explicit [JsonDerivedType] model is safe because the type set is closed.

IN PLAIN TERMS

XAML and type-naming JSON are not just data, they are instructions: "create an object of this type and set these properties". Accepting them from a stranger is like letting a delivery note decide which machines in your factory to switch on. A closed type set means the note can only choose from a list you wrote in advance.

Signing DEEPER

An unsigned executable triggers SmartScreen, which for most users reads as "this is malware". SmartScreen is the Windows check that runs when a user opens a downloaded file; for a program with no known publisher or download history it shows a "Windows protected your PC" warning. A code-signing certificate proves who published the file and that it has not been altered since, and SmartScreen builds reputation against that publisher identity.

You need an Authenticode certificate. An OV certificate now requires hardware token or cloud HSM storage, and no certificate type buys instant reputation any more: OV, EV and Azure Artifact Signing all earn it through clean downloads over time. Sign the executable and the installer, and time-stamp both so signatures outlive the certificate. A time-stamp is a countersignature from a trusted server recording when you signed; without one, the signature stops validating when your certificate expires.

The PowerShell command below signs Tasks.exe with the certificate identified by its thumbprint, using SHA-256 for the file digest and for the time-stamp:

PowerShell 
signtool sign /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 `
  /sha1 <thumbprint> Tasks.exe
RECAP
  • Store user settings as JSON in the profile, fall back to defaults if the file is unreadable, and write through a temporary file.
  • Nothing you ship is secret: a desktop app is a public client, so sign users in with PKCE and keep real secrets on your server.
  • Protect tokens and passwords the user gives you with DPAPI, which ties them to their Windows account.
  • Check the scheme before opening user-supplied links, and pass tool arguments through ArgumentList.
  • Never parse XAML, or type-naming JSON, from a source you do not control.
  • Sign and time-stamp both; a new publisher still sees warnings until reputation builds.
