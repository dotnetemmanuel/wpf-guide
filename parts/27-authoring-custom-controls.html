PART 27

Authoring custom controls

Sooner or later you need a piece of UI that WPF does not ship: a search box with a placeholder, a count badge, a text box that only accepts numbers. There are three ways to build one, and picking the wrong one costs either flexibility or days.

Builds on Part 5, dependency properties, Part 9, styles and triggers, Part 10, templates and Part 11, data binding.

UserControl or Control: the decision

IN PLAIN TERMS

Every built-in Button is lookless. Its class knows how to be pressed, focused and clicked, but it contains no drawing at all: its appearance comes from a template that a theme, or you, can replace wholesale. A UserControl is the opposite. It is a fixed arrangement of existing controls that you lay out once, like a pre-printed form: people can fill it in, but not redesign it.

Precisely: a UserControl is a composite whose visual tree you author in XAML alongside its code. A lookless control derives from Control and holds only behaviour and properties; its whole look is a ControlTemplate that consumers can swap out.

UserControlControl (lookless)
Defined byA fixed XAML tree you authorA template consumers can replace
RestyleableNo, not meaningfullyYes, completely
EffortMinutesHours
Right forA screen, a panel, a composite specific to one appA control shipped to other teams or reused across apps

The honest default is UserControl. Most "custom controls" in line-of-business apps are screen fragments that will never be restyled, and lookless controls cost real time. Reach for Control when you are building a library. A third route, deriving from an existing control, comes at the end of this part and is often the cheapest of all.

A UserControl with real dependency properties

A UserControl is only reusable if the screens that host it can pass data in and get data out with bindings, as in <local:SearchBox Query="{Binding Filter}" />. A binding can only target a dependency property, so an ordinary C# property on the control will not do. Each value the host should be able to bind needs a registered dependency property with a plain wrapper around it.

The code-behind below declares three. Query is registered with BindsTwoWayByDefault, so a host binding pushes the user's typing back without writing Mode=TwoWay, the same way TextBox.Text behaves. Placeholder has a default of "Search…". SearchCommand lets the host hand in a command; wiring it to a key or button is left out here.

SearchBox.xaml.cs 
public partial class SearchBox : UserControl
{
    public SearchBox() => InitializeComponent();

    public static readonly DependencyProperty QueryProperty =
        DependencyProperty.Register(
            nameof(Query), typeof(string), typeof(SearchBox),
            new FrameworkPropertyMetadata(
                defaultValue: string.Empty,
                flags: FrameworkPropertyMetadataOptions.BindsTwoWayByDefault));

    public string Query
    {
        get => (string)GetValue(QueryProperty);
        set => SetValue(QueryProperty, value);
    }

    public static readonly DependencyProperty PlaceholderProperty =
        DependencyProperty.Register(nameof(Placeholder), typeof(string), typeof(SearchBox),
            new PropertyMetadata("Search…"));

    public string Placeholder
    {
        get => (string)GetValue(PlaceholderProperty);
        set => SetValue(PlaceholderProperty, value);
    }

    public static readonly DependencyProperty SearchCommandProperty =
        DependencyProperty.Register(nameof(SearchCommand), typeof(ICommand), typeof(SearchBox),
            new PropertyMetadata(null));

    public ICommand? SearchCommand
    {
        get => (ICommand?)GetValue(SearchCommandProperty);
        set => SetValue(SearchCommandProperty, value);
    }
}

The XAML names its root Root so inner elements can bind to the control's own properties with ElementName=Root. Notice three details. Delay=250 waits a quarter of a second after the user stops typing before it updates Query, so a filter does not rerun on every keystroke. The placeholder TextBlock sits on top of the TextBox with IsHitTestVisible="False", so clicks pass through to the box underneath. And a DataTrigger shows the placeholder only while the box is empty.

SearchBox.xaml 
<UserControl x:Class="Tasks.Controls.SearchBox"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             x:Name="Root">
  <Grid>
    <TextBox x:Name="Input"
             Text="{Binding Query, ElementName=Root,
                            UpdateSourceTrigger=PropertyChanged, Delay=250}" />
    <TextBlock Text="{Binding Placeholder, ElementName=Root}"
               Margin="6,0,0,0" VerticalAlignment="Center" IsHitTestVisible="False"
               Foreground="{DynamicResource MutedBrush}">
      <TextBlock.Style>
        <Style TargetType="TextBlock">
          <Setter Property="Visibility" Value="Collapsed" />
          <Style.Triggers>
            <DataTrigger Binding="{Binding Text, ElementName=Input}" Value="">
              <Setter Property="Visibility" Value="Visible" />
            </DataTrigger>
          </Style.Triggers>
        </Style>
      </TextBlock.Style>
    </TextBlock>
  </Grid>
</UserControl>
IN PLAIN TERMS

DataContext is passed down the element tree like a family's home address: every child uses its parent's unless it is given its own. The binding a host writes on your control's tag is evaluated at your control's address. If your control sets its own DataContext, it has moved house, and {Binding Filter} now looks for Filter in your internal object instead of in the host's view model.

GOTCHA

Never set DataContext on a UserControl's root. It breaks the consumer's inherited context, so <local:SearchBox Query="{Binding Filter}" /> would bind against your internal object instead of theirs. Bind to your own properties with ElementName pointing at a named root, as above, or RelativeSource AncestorType=UserControl.

A lookless control

Write a lookless control when the same behaviour must look different in different places: another team's brand, a dark theme, a compact variant. The example is a Badge that shows a count and fades out at zero.

Three pieces: the class, a default style in Themes/Generic.xaml, and an assembly-level ThemeInfo.

ThemeInfo tells WPF where to look for a control's default style. The first argument covers dictionaries per Windows theme, which almost nobody writes any more, so it is None. The second says the generic dictionary, the fallback used for every theme, lives in this assembly. WPF finds it by a fixed path, so the file must be called Themes/Generic.xaml exactly.

AssemblyInfo.cs 
[assembly: ThemeInfo(
    ResourceDictionaryLocation.None,            // theme-specific dictionaries
    ResourceDictionaryLocation.SourceAssembly)] // generic dictionary

In the class, notice four things:

  • The static constructor overrides DefaultStyleKey with typeof(Badge). That is the key WPF uses to look up the default style. A new control deriving from Control requires this: without it, the control keeps the key it inherits, which is not typeof(Badge) and WPF never finds the style you write in Generic.xaml.
  • TemplatePart and TemplateVisualState are documentation for template authors and design tools: they list the named parts and states a replacement template should provide. WPF does not enforce them.
  • The Count property has a change callback that moves the control to the matching visual state.
  • OnApplyTemplate runs whenever a template is applied, and sets the state again without animation, so a fresh template starts in the right state instead of fading into it.
Badge.cs 
[TemplatePart(Name = PartHost, Type = typeof(FrameworkElement))]
[TemplateVisualState(GroupName = "CountStates", Name = "HasCount")]
[TemplateVisualState(GroupName = "CountStates", Name = "Empty")]
public class Badge : Control
{
    public const string PartHost = "PART_Host";

    static Badge() => DefaultStyleKeyProperty.OverrideMetadata(
        typeof(Badge), new FrameworkPropertyMetadata(typeof(Badge)));

    public static readonly DependencyProperty CountProperty =
        DependencyProperty.Register(nameof(Count), typeof(int), typeof(Badge),
            new FrameworkPropertyMetadata(0, OnCountChanged));

    public int Count
    {
        get => (int)GetValue(CountProperty);
        set => SetValue(CountProperty, value);
    }

    private static void OnCountChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
        => ((Badge)d).UpdateStates(useTransitions: true);

    public override void OnApplyTemplate()
    {
        base.OnApplyTemplate();
        UpdateStates(useTransitions: false);
    }

    private void UpdateStates(bool useTransitions)
        => VisualStateManager.GoToState(this, Count > 0 ? "HasCount" : "Empty", useTransitions);
}
IN PLAIN TERMS

Visual states are like the labelled positions on a dial. The control's code only ever says "go to HasCount" or "go to Empty". What each position looks like, and how the control moves between them, is written in the template. A different template can make HasCount a bounce instead of a fade, and the C# never changes.

The default style has no x:Key, only a TargetType, which is what makes it the default (theme) style for every Badge. A consumer's own style does not replace it: it applies on top, and anything the consumer's style leaves unset, including the template, still comes from this one. Inside the template, {TemplateBinding} copies the Badge's own Background, Foreground and FontSize onto the template's elements, so a consumer setting Background="Green" on a Badge still works. Count uses a full Binding with RelativeSource TemplatedParent instead, because the number has to become text and the lighter TemplateBinding does not convert types. The VisualStateManager block defines the two states and a 0.15-second transition between them.

Themes/Generic.xaml 
<ResourceDictionary xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
                    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
                    xmlns:local="clr-namespace:Tasks.Controls">

  <Style TargetType="{x:Type local:Badge}">
    <Setter Property="Background"  Value="#B4352C" />
    <Setter Property="Foreground"  Value="White" />
    <Setter Property="MinWidth"    Value="18" />
    <Setter Property="Height"      Value="18" />
    <Setter Property="FontSize"    Value="10" />

    <Setter Property="Template">
      <Setter.Value>
        <ControlTemplate TargetType="{x:Type local:Badge}">
          <Border x:Name="PART_Host"
                  Background="{TemplateBinding Background}"
                  CornerRadius="9" Padding="5,0">
            <VisualStateManager.VisualStateGroups>
              <VisualStateGroup x:Name="CountStates">
                <VisualStateGroup.Transitions>
                  <VisualTransition GeneratedDuration="0:0:0.15" />
                </VisualStateGroup.Transitions>
                <VisualState x:Name="Empty">
                  <Storyboard>
                    <DoubleAnimation Storyboard.TargetName="PART_Host"
                                     Storyboard.TargetProperty="Opacity" To="0" />
                  </Storyboard>
                </VisualState>
                <VisualState x:Name="HasCount">
                  <Storyboard>
                    <DoubleAnimation Storyboard.TargetName="PART_Host"
                                     Storyboard.TargetProperty="Opacity" To="1" />
                  </Storyboard>
                </VisualState>
              </VisualStateGroup>
            </VisualStateManager.VisualStateGroups>

            <TextBlock Text="{Binding Count, RelativeSource={RelativeSource TemplatedParent}}"
                       Foreground="{TemplateBinding Foreground}"
                       FontSize="{TemplateBinding FontSize}"
                       HorizontalAlignment="Center" VerticalAlignment="Center" />
          </Border>
        </ControlTemplate>
      </Setter.Value>
    </Setter>
  </Style>
</ResourceDictionary>

Triggers or VisualStateManager? DEEPER

Both are in WPF and they do overlapping jobs. Triggers are older, declarative and reversible: when the condition stops being true, the value goes back by itself. The VisualStateManager (VSM) is state-machine shaped, came from Silverlight, and supports transitions between named states.

  • Use triggers for WPF-only controls. Less ceremony, and the value-precedence rules are the ones you already know.
  • Use VSM when states are mutually exclusive and you want animated transitions between them, or when the control will be ported to WinUI/Uno later.

Do not mix them for the same property on the same control. Triggers set values at precedence levels 4 to 7, depending on where they are declared, and VSM animates at level 2 (see the table in Part 5), so VSM always wins and the trigger appears broken. In practice: a hover trigger that sets PART_Host's Opacity to 0.5 never shows, because whichever state is current holds PART_Host's Opacity with an animation (0 in Empty, 1 in HasCount). The trigger's value is there; it is simply outranked.

Deriving from an existing control

Often the cheapest option. Suppose you need a text box that accepts only numbers. Caret, selection, undo, clipboard and the default look should all stay exactly as they are. Deriving from TextBox keeps every bit of that behaviour, and the default template stays valid.

There is no static constructor. A subclass inherits TextBox's DefaultStyleKey, so it gets the TextBox default style and template without asking. The real work happens in OnPreviewTextInput. Preview events run before the control itself handles the input (see Part 23), so marking one handled stops the character from ever arriving. The override builds the text as it would be after the keystroke, replacing any selection, and rejects the character if the result would not parse as a number in the user's culture.

C# 
public class NumericTextBox : TextBox
{
    protected override void OnPreviewTextInput(TextCompositionEventArgs e)
    {
        // Text input, not key codes: works with any keyboard layout.
        string candidate = string.Concat(Text[..SelectionStart], e.Text,
                                          Text[(SelectionStart + SelectionLength)..]);
        e.Handled = !decimal.TryParse(candidate, NumberStyles.Number,
                                      CultureInfo.CurrentCulture, out _);
        base.OnPreviewTextInput(e);
    }

    protected override void OnPreviewKeyDown(KeyEventArgs e)
    {
        if (e.Key == Key.Space) e.Handled = true;   // space isn't a TextInput event
        base.OnPreviewKeyDown(e);
    }
}

One consequence to know: a character is accepted only if the whole text would then parse as a number, so typing - or the decimal separator into an empty box is rejected, because neither is a number on its own. The decimal separator follows the user's culture: in sv-SE the , key is accepted after digits, while . is always rejected.

One catch with styles: an unkeyed style matches its exact target type only. An app-wide implicit TextBox style, including the Fluent styles that .NET 9 and 10 add to app resources, does not apply to NumericTextBox. Opt in with Style="{StaticResource {x:Type TextBox}}" where you use it, or give NumericTextBox its own implicit style with BasedOn set to the TextBox one.

Paste still bypasses PreviewTextInput. Handle it with DataObject.AddPastingHandler(this, OnPaste) in the constructor.

RECAP
  • Start with a UserControl; build a lookless Control only when others must be able to restyle it.
  • Anything a host should bind must be a dependency property on your control.
  • Never set DataContext on the UserControl itself; bind to your own properties by element name instead.
  • A lookless control needs a class, a default style in Themes/Generic.xaml, and ThemeInfo pointing at it.
  • Deriving from an existing control keeps all its behaviour and is often the quickest route.
