PART 23

Input, focus and keyboard

Every key press, click and touch goes to one particular element. Knowing which element, and why input sometimes does not arrive where you expect, is most of what input work in WPF comes down to.

Builds on Part 5, dependency properties (attached properties) and Part 6, routed events and commands.

Two kinds of focus

You are typing in a text box, then choose Edit, Cut from the menu. The menu now has the keyboard, yet Cut still has to know which text box to cut from. WPF solves this by tracking focus in two ways at once. This distinction causes more subtle bugs than anything else in WPF input.

  • Keyboard focus: exactly one element in the entire desktop has it. Keyboard.FocusedElement. This is where key events go.
  • Logical focus: one element per focus scope remembers that it was focused. A focus scope is a region that keeps its own record of focus. A Window, Menu, ToolBar and ContextMenu are each focus scopes by default.

So when you open a menu, the text box loses keyboard focus but keeps logical focus within the window's scope, which is how the menu's Cut command still knows what to act on.

IN PLAIN TERMS

Imagine reading two books with a finger kept in each. Your eyes can only be on one page at a time: that is keyboard focus. Each finger marks your place in its own book: that is logical focus, one per focus scope. Glance at the menu and your eyes move, but the finger in the window still marks the text box, so Cut knows where to act.

The calls below set and query both kinds. Most of the time Focus() on the element is all you need; the FocusManager calls matter when you work across scopes.

C# 
// Keyboard focus: returns the element that actually got it (may be null)
IInputElement? got = Keyboard.Focus(myTextBox);

// Or, equivalently for a UIElement:
bool ok = myTextBox.Focus();

// Logical focus within a scope
FocusManager.SetFocusedElement(FocusManager.GetFocusScope(myTextBox), myTextBox);

// Which scope am I in?
DependencyObject scope = FocusManager.GetFocusScope(myTextBox);

// Make a panel its own focus scope (rarely a good idea: it breaks tabbing)
FocusManager.SetIsFocusScope(myPanel, true);
GOTCHA

Focus() silently fails if the element is not yet loaded, is collapsed, or has Focusable="False". Focusing on startup or after a template swap must be deferred: Dispatcher.InvokeAsync(() => box.Focus(), DispatcherPriority.Loaded). A focus call that "does nothing" is nearly always a timing problem, not a focus problem.

An attached property for initial focus

A dialog should open with the cursor in its first field. Writing that in the code-behind of every window is repetitive and easy to get wrong because of the timing above. An attached property packages it once, so any element can opt in from XAML with local:FocusOnLoad.IsEnabled="True".

When the property is set, it waits for the element's Loaded event (or runs at once if that has already happened), then queues the focus call on the dispatcher so it runs after loading has finished. A text box also gets its contents selected, so typing replaces them.

C# 
public static class FocusOnLoad
{
    public static readonly DependencyProperty IsEnabledProperty =
        DependencyProperty.RegisterAttached(
            "IsEnabled", typeof(bool), typeof(FocusOnLoad),
            new PropertyMetadata(false, OnChanged));

    public static void SetIsEnabled(DependencyObject d, bool v) => d.SetValue(IsEnabledProperty, v);
    public static bool GetIsEnabled(DependencyObject d) => (bool)d.GetValue(IsEnabledProperty);

    private static void OnChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not FrameworkElement fe || e.NewValue is not true) return;

        void Handler(object s, RoutedEventArgs _)
        {
            fe.Loaded -= Handler;
            fe.Dispatcher.InvokeAsync(() =>
            {
                fe.Focus();
                if (fe is TextBox tb) tb.SelectAll();
            }, DispatcherPriority.Input);
        }

        if (fe.IsLoaded) Handler(fe, new RoutedEventArgs());
        else fe.Loaded += Handler;
    }
}

Tab navigation

Keyboard users move through a form with Tab. By default the order follows the element tree, which is usually right. When it is not, or when Tab should stay inside a region, you change it per container.

Each element Tab stops on is a tab stop. TabIndex sets the order explicitly, and the attached property KeyboardNavigation.TabNavigation decides how a container's children take part.

XAML 
<Grid KeyboardNavigation.TabNavigation="Local">
  <TextBox TabIndex="0" />
  <TextBox TabIndex="1" />
  <Button  TabIndex="2" IsDefault="True"  Content="OK" />
  <Button  TabIndex="3" IsCancel="True"   Content="Cancel" />
</Grid>
TabNavigationBehaviour
ContinueDefault. Tab flows in and out of the container freely.
LocalTabIndex values are scoped to this container.
CycleTab wraps inside the container and never leaves. Correct for a modal dialog's content.
OnceThe whole container is a single tab stop. Right for a radio-button group or a toolbar.
NoneSkipped entirely.

IsDefault="True" makes Enter fire the button from anywhere in the window. IsCancel="True" wires Escape and, in a dialog, sets DialogResult = false. Both come free and both are routinely forgotten.

Keyboard and mouse events

Fixed shortcuts belong in key bindings (Part 6). Keys whose meaning depends on state, like Escape to revert only while editing, and dragging on a canvas need the raw events. Keyboard events are routed: handle PreviewKeyDown on a window or panel and you see the key before the focused control does, so you can claim it by setting e.Handled.

Two details in the handler below. When Alt is held, e.Key reports Key.System and the real key moves to e.SystemKey. Modifier keys can be read from Keyboard.Modifiers or, equivalently, e.KeyboardDevice.Modifiers.

C# 
private void OnPreviewKeyDown(object sender, KeyEventArgs e)
{
    // Same as e.KeyboardDevice.Modifiers
    bool ctrl  = (Keyboard.Modifiers & ModifierKeys.Control) != 0;
    bool shift = (Keyboard.Modifiers & ModifierKeys.Shift) != 0;

    // e.Key is the "logical" key; e.SystemKey holds it when Alt is down
    Key key = e.Key == Key.System ? e.SystemKey : e.Key;

    if (ctrl && key == Key.Enter) { Commit(); e.Handled = true; }
    if (key == Key.Escape)        { Revert(); e.Handled = true; }
}

private void OnMouseMove(object sender, MouseEventArgs e)
{
    Point local  = e.GetPosition((IInputElement)sender);
    Point screen = ((UIElement)sender).PointToScreen(local);

    if (e.LeftButton == MouseButtonState.Pressed) Drag(local);
}

In the mouse handler, GetPosition returns the pointer position relative to whichever element you pass, and PointToScreen converts it to screen coordinates, in physical pixels.

The last bullet below depends on hit testing: how WPF decides which element is under the pointer. It only counts areas that are actually painted.

  • Text input: use PreviewTextInput and TextInput, not KeyDown. Key events tell you which key was pressed; text events give you the actual characters after IME, dead keys and keyboard layout have been applied. Filtering a numeric field with KeyDown breaks for anyone using a non-US layout.
  • Mouse capture: element.CaptureMouse() routes all mouse input to that element until ReleaseMouseCapture(), even when the pointer leaves it. Essential for drag operations; leaking capture freezes the UI, because nothing else receives the mouse.
  • IsHitTestVisible="False" makes an element transparent to input without hiding it. Background="{x:Null}" on a panel makes it un-hittable too: set Background="Transparent" if you want a panel to receive mouse events over its empty area. This one catches everybody.
IN PLAIN TERMS

A panel with no background is like a window frame with no glass in it: you see through it and your hand goes straight through, so the click lands on whatever is behind. Transparent is clear glass. It looks exactly the same, but there is now something there to touch, so the panel gets the click.

Here is a drag done properly. Capture the mouse on button down so moves keep arriving even if the pointer leaves the element, release it on button up, and reset your state when capture is lost. Capture can be taken away without a button-up, for example when another window opens or the user switches apps.

C#: a correct drag with capture 
private Point _origin;
private bool _dragging;

protected override void OnMouseLeftButtonDown(MouseButtonEventArgs e)
{
    _origin = e.GetPosition(this);
    _dragging = true;
    CaptureMouse();
    e.Handled = true;
}

protected override void OnMouseMove(MouseEventArgs e)
{
    if (!_dragging) return;
    var p = e.GetPosition(this);
    Offset = new Vector(p.X - _origin.X, p.Y - _origin.Y);
}

protected override void OnMouseLeftButtonUp(MouseButtonEventArgs e)
{
    if (!_dragging) return;
    _dragging = false;
    ReleaseMouseCapture();
    e.Handled = true;
}

protected override void OnLostMouseCapture(MouseEventArgs e)
{
    _dragging = false;      // always reset here: capture can be stolen
}

Touch and manipulation DEEPER

On a touch screen people expect to drag, pinch to zoom and twist with two fingers. Tracking each finger yourself is tedious. A manipulation is WPF doing it for you: it combines one or more touch points into a single stream of changes, a translation, a scale and a rotation, which you apply to a transform.

Setting IsManipulationEnabled="True" turns manipulation events on for the element. The element's RenderTransform is a MatrixTransform so each change can be folded into one matrix.

XAML + C# 
<Border IsManipulationEnabled="True"
        ManipulationStarting="OnStarting"
        ManipulationDelta="OnDelta"
        ManipulationInertiaStarting="OnInertia">
  <Border.RenderTransform><MatrixTransform /></Border.RenderTransform>
</Border>

The handlers do three jobs. OnStarting picks the coordinate space and which kinds of movement to allow. OnDelta applies each change around the point between the fingers. OnInertia sets inertia, the coasting after the fingers lift: decelerations are in device-independent pixels per millisecond squared, so the expressions convert from inches per second squared.

C# 
private void OnStarting(object sender, ManipulationStartingEventArgs e)
{
    e.ManipulationContainer = canvas;     // coordinate space for the deltas
    e.Mode = ManipulationModes.All;       // translate + scale + rotate
}

private void OnDelta(object sender, ManipulationDeltaEventArgs e)
{
    var element = (FrameworkElement)e.Source;
    var transform = (MatrixTransform)element.RenderTransform;
    Matrix m = transform.Matrix;

    Point centre = e.ManipulationOrigin;
    m.ScaleAt(e.DeltaManipulation.Scale.X, e.DeltaManipulation.Scale.Y, centre.X, centre.Y);
    m.RotateAt(e.DeltaManipulation.Rotation, centre.X, centre.Y);
    m.Translate(e.DeltaManipulation.Translation.X, e.DeltaManipulation.Translation.Y);

    transform.Matrix = m;
    e.Handled = true;
}

private void OnInertia(object sender, ManipulationInertiaStartingEventArgs e)
{
    e.TranslationBehavior.DesiredDeceleration = 10.0 * 96 / (1000.0 * 1000.0);
    e.ExpansionBehavior.DesiredDeceleration   = 0.1 * 96 / (1000.0 * 1000.0);
}

By default WPF promotes unhandled touch to mouse events, so a touch-unaware app still works. Set Stylus.IsPressAndHoldEnabled="False" on elements where the press-and-hold-to-right-click delay makes dragging feel laggy.

RECAP
  • Keyboard focus is the one element receiving keys now; logical focus is the element each focus scope remembers.
  • A Focus() call that does nothing is almost always made too early; defer it with the dispatcher.
  • Use TabNavigation, IsDefault and IsCancel to make forms work from the keyboard.
  • Filter typed characters with PreviewTextInput, not KeyDown.
  • A panel needs a Transparent background, not none, to receive clicks on its empty area.
  • Capture the mouse while dragging and always reset your state when capture is lost.
