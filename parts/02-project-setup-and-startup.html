PART 02

Project setup and startup

Before any window appears, three things have to be right: the project file that tells the build what kind of app this is, the code that runs at startup, and the safety net that catches errors nobody anticipated. Get these right once and every later part builds on them.

The project file

A project file tells the .NET SDK what to build: which framework, what kind of executable, which packages. dotnet new wpf -n Tasks gets you most of this. The icon, the warnings setting and the three packages are additions you make yourself, shown here because later parts rely on this file. It is the whole build configuration:

Tasks.csproj 
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net10.0-windows</TargetFramework>
    <UseWPF>true</UseWPF>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <ApplicationIcon>app.ico</ApplicationIcon>
    <!-- Treat XAML binding failures as build-visible where possible -->
    <TreatWarningsAsErrors>false</TreatWarningsAsErrors>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="CommunityToolkit.Mvvm" Version="8.4.0" />
    <PackageReference Include="Microsoft.Extensions.Hosting" Version="10.0.0" />
    <PackageReference Include="Microsoft.Xaml.Behaviors.Wpf" Version="1.1.135" />
  </ItemGroup>

</Project>

Notes on the properties that matter:

  • OutputType of WinExe produces a Windows GUI executable, so no console window opens behind your app.
  • UseWPF pulls in the WPF reference assemblies and turns on the XAML build tasks. Setting UseWindowsForms alongside it is legal and is how you host WinForms controls.
  • net10.0-windows can be pinned to a Windows SDK version, as in net10.0-windows10.0.19041.0, if you need WinRT APIs such as toast notifications.
  • Files under the project root ending in .xaml are implicitly Page items; App.xaml is implicitly ApplicationDefinition. You rarely need to declare either.

What the XAML compiler actually does

You write a window in two files: MainWindow.xaml for the markup and MainWindow.xaml.cs for your code. Something has to join them so that a control named in the markup is a field you can use in C#. That is the XAML compiler's job.

Each .xaml file with an x:Class produces a generated partial class. It contains a field declaration for every x:Name and an InitializeComponent() method. That method loads BAML, a compiled binary form of the markup embedded in your assembly as a resource, and walks it, instantiating objects and setting properties. Visual Studio shows the generated file if you go to the definition of InitializeComponent; the part to notice is the field and the one call to LoadComponent:

MainWindow.g.i.cs (generated) 
public partial class MainWindow : System.Windows.Window, IComponentConnector
{
    internal System.Windows.Controls.TextBox DraftBox;   // from x:Name="DraftBox"

    public void InitializeComponent()
    {
        if (_contentLoaded) return;
        _contentLoaded = true;
        var resourceLocater = new Uri("/Tasks;component/mainwindow.xaml", UriKind.Relative);
        System.Windows.Application.LoadComponent(this, resourceLocater);
    }

    void IComponentConnector.Connect(int connectionId, object target) { /* wires names + handlers */ }
}
IN PLAIN TERMS

Your .xaml file is a flat-pack instruction sheet, and InitializeComponent() is the moment someone follows it: every part is created and every setting applied, in order. Your constructor is the rest of your code around that moment. Anything you set before anyone follows the sheet is overwritten wherever the sheet says otherwise, and the named parts do not exist yet.

Two consequences worth internalising. First, anything you do before InitializeComponent() runs will be overwritten by the markup wherever the markup sets the same property, and fields named with x:Name are still null at that point. Set defaults after the call, or in the markup itself. Second, XAML is not interpreted at runtime in the normal case. It can be, via XamlReader.Parse, which is how plugin skinning works (Part 3 shows it).

Startup: the default, and the one you want

The App class (from App.xaml and App.xaml.cs) is where your application starts: the build generates the real Main method, which creates an App and runs it. The template gives you StartupUri, which constructs the first window for you. The resource dictionaries merged here make shared colours and styles available to every window (Part 8):

App.xaml: template default 
<Application x:Class="Tasks.App"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             StartupUri="MainWindow.xaml">
  <Application.Resources>
    <ResourceDictionary>
      <ResourceDictionary.MergedDictionaries>
        <ResourceDictionary Source="Themes/Colors.xaml" />
        <ResourceDictionary Source="Themes/Controls.xaml" />
      </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
  </Application.Resources>
</Application>

That is fine for a toy. The catch is that WPF creates the window itself, with a parameterless constructor, so you cannot hand it the services it needs (a database, a logger, settings). For anything real you want the window to come out of a container, an object that knows how to build each class along with everything that class depends on. So you delete StartupUri and override OnStartup. The container lives inside a host, an object from Microsoft.Extensions.Hosting that also owns configuration, logging and background services (long-running tasks, such as a periodic sync, that start and stop with the app). Part 15 builds this out properly; the shape is:

App.xaml.cs 
public partial class App : Application
{
    private readonly IHost _host;

    public App()
    {
        var builder = Host.CreateApplicationBuilder();
        builder.Services.AddSingleton<MainWindow>();
        _host = builder.Build();
    }

    protected override async void OnStartup(StartupEventArgs e)
    {
        base.OnStartup(e);
        await _host.StartAsync();
        _host.Services.GetRequiredService<MainWindow>().Show();
    }

    protected override void OnExit(ExitEventArgs e)
    {
        using (_host)
        {
            Task.Run(() => _host.StopAsync(TimeSpan.FromSeconds(5))).GetAwaiter().GetResult();
        }
        base.OnExit(e);
    }
}

When this runs, the constructor builds the host and registers MainWindow with its container. OnStartup starts the host's background services, then asks the container for MainWindow, which arrives with its dependencies already supplied. OnExit waits for the host to stop, giving it up to five seconds, before the app finishes closing. The stop runs on a thread-pool thread through Task.Run, so blocking the UI thread while it waits cannot deadlock.

Shutdown mode

A WPF app runs as long as its message loop runs: the loop on the UI thread that receives clicks, key presses and repaint requests from Windows. Closing a window does not necessarily end it. ShutdownMode decides when the loop ends:

  • OnLastWindowClose (the default): when the last open window closes.
  • OnMainWindowClose: when the window in Application.MainWindow closes, even if others are open.
  • OnExplicitShutdown: only when your code calls Application.Current.Shutdown(). You need this for tray applications, which must keep running with no window open.

Single instance DEEPER

Some apps must not run twice: a second copy would fight the first over the same files or tray icon. Single-instance has no framework support. Use a named mutex, an operating-system lock that any process can ask for by name. The first process creates and owns it; a second process finds the name already taken and quits:

C# 
private static Mutex? _single;

protected override void OnStartup(StartupEventArgs e)
{
    _single = new Mutex(initiallyOwned: true, @"Global\Tasks.App.SingleInstance", out bool isFirst);
    if (!isFirst)
    {
        // Optionally signal the running instance over a named pipe, then:
        Shutdown();
        return;
    }
    base.OnStartup(e);
}

The Global\ prefix makes the name visible across all user sessions on the machine; without it, each signed-in user could run one copy. The mutex is kept in a static field so it lives, and stays owned, for as long as the process does.

Unhandled exceptions

An exception nobody catches normally ends the process: the window vanishes and the user loses their work without a word. You cannot catch everything at the source, so WPF and .NET give you last-chance hooks where you can at least log the error and, in some cases, keep the app alive.

There are three separate hooks, and you want all three, because each sees a different kind of failure:

  • DispatcherUnhandledException catches exceptions on the UI thread and lets you mark them handled, so the app keeps running.
  • TaskScheduler.UnobservedTaskException catches faulted tasks nobody awaited. It fires late, when the garbage collector finalises the abandoned task, and may never fire at all if no collection happens before the app exits.
  • AppDomain.CurrentDomain.UnhandledException is the last resort. It sees exceptions escaping any thread, including UI-thread errors the first hook left unhandled. It is not recoverable: you can log, but the process ends afterwards. A failed task nobody awaited never reaches it.

Subscribe to all three in the App constructor, before anything else can fail. Notice that only the first one can stop the crash, with e.Handled = true:

C# 
public App()
{
    DispatcherUnhandledException += (_, e) =>
    {
        _logger.LogError(e.Exception, "Unhandled UI exception");
        MessageBox.Show("Something went wrong. The action was cancelled.",
                        "Tasks", MessageBoxButton.OK, MessageBoxImage.Error);
        e.Handled = true;              // keep the app alive
    };

    TaskScheduler.UnobservedTaskException += (_, e) =>
    {
        _logger.LogError(e.Exception, "Unobserved task exception");
        e.SetObserved();
    };

    AppDomain.CurrentDomain.UnhandledException += (_, e) =>
        _logger.LogCritical(e.ExceptionObject as Exception, "Fatal");
}
IN PLAIN TERMS

Think of three smoke alarms in different rooms. The UI-thread alarm has an extinguisher next to it: you can put the fire out and carry on. The task alarm only goes off when the rubbish is collected, long after the fire. The process-wide alarm can only tell you the building is coming down, so write the log entry and accept the loss.

GOTCHA

async void OnStartup is one of the few places async void is correct, because the framework gives you no awaitable override. An exception anywhere inside it does reach DispatcherUnhandledException, but only after OnStartup has returned, so marking it handled abandons startup half-way. If no window was shown yet, the default shutdown mode never fires and the process keeps running with no window at all. Wrap the body in a try/catch yourself, and on failure log it, tell the user and call Shutdown().

RECAP
  • The .csproj is the whole build configuration, and UseWPF is the switch that makes it a WPF project.
  • InitializeComponent() builds the objects described in your XAML and overwrites any property the markup also sets, so set your defaults after it.
  • Replace StartupUri with an OnStartup override once windows need services passed to them.
  • ShutdownMode decides whether closing windows ends the app; tray apps need OnExplicitShutdown.
  • Hook all three unhandled-exception events, and remember only the UI-thread one can keep the app alive.
