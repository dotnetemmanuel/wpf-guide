PART 17

Threading and async

WPF is single-threaded-apartment with hard thread affinity. Every DispatcherObject — which is every element, every brush, every animation — remembers the thread that created it and throws if touched from another.

The Dispatcher

One UI thread runs a message loop. The Dispatcher is its work queue, ordered by DispatcherPriority.

C# 
// Are we on the UI thread?
bool onUi = Dispatcher.CheckAccess();

// Post work to it (fire and forget, returns immediately).
// BeginInvoke takes a Delegate, so give the lambda an explicit type.
Dispatcher.BeginInvoke(new Action(() => status.Text = "Done"));
Dispatcher.InvokeAsync(() => status.Text = "Done");   // overload takes Action directly

// Post and await the result
var width = await Dispatcher.InvokeAsync(() => element.ActualWidth);

// Post and block until done — deadlock risk, avoid
Dispatcher.Invoke(() => status.Text = "Done");

// Run after layout has completed
Dispatcher.InvokeAsync(() => box.Focus(), DispatcherPriority.Loaded);

Priority matters more than people expect. DispatcherPriority.Background work runs only when the queue is otherwise idle, which is how you keep a busy UI responsive. DispatcherPriority.Render and Loaded are the hooks for "after this frame has been laid out" — the reliable way to focus a control that doesn't exist yet.

The rule you actually follow

With async/await, almost none of the above is needed day to day. await captures the SynchronizationContext, and WPF installs a DispatcherSynchronizationContext, so continuations come back to the UI thread automatically.

C# 
[RelayCommand]
private async Task LoadAsync(CancellationToken ct)
{
    // UI thread here.
    Status = "Loading…";

    var rows = await _repo.GetAllAsync(ct);          // off to the thread pool and back

    // UI thread again — safe to touch bound collections.
    Items.Clear();
    foreach (var r in rows) Items.Add(new TaskViewModel(r));
    Status = $"{Items.Count} tasks";
}
  • Don't use ConfigureAwait(false) in view models and UI code — you want the context back. Do use it in library and service code that never touches UI.
  • Don't call .Result or .Wait() on the UI thread. The continuation needs the UI thread, which you are blocking. That is a textbook deadlock and it is still the most common hang in WPF applications.
  • Do use Task.Run for genuinely CPU-bound work, and nothing else. Wrapping an already-async I/O call in Task.Run just burns a thread.
C# 
// CPU-bound: correct use of Task.Run
var report = await Task.Run(() => _engine.Recalculate(model), ct);

// I/O-bound: wrong
var rows = await Task.Run(() => _repo.GetAllAsync(ct));   // pointless thread hop
var rows = await _repo.GetAllAsync(ct);                   // correct

Progress reporting

C# 
[ObservableProperty] public partial double Progress { get; set; }

[RelayCommand]
private async Task ImportAsync(CancellationToken ct)
{
    // IProgress captures the current SynchronizationContext at construction,
    // so the callback runs on the UI thread automatically.
    var progress = new Progress<double>(p => Progress = p);

    await Task.Run(() => _importer.Run(_path, progress, ct), ct);
}

Freezables and cross-thread objects

Freezable — brushes, geometries, transforms, animations — can be made immutable with Freeze(). A frozen freezable loses thread affinity and can be created on a background thread and used on the UI thread. That's how you pre-build complex geometry off the UI thread:

C# 
var geometry = await Task.Run(() =>
{
    var g = BuildComplexPath(points);   // StreamGeometry, thousands of segments
    g.Freeze();                          // now thread-agnostic and faster to render
    return g;
});

path.Data = geometry;                    // UI thread, no marshalling needed

A second UI thread

Rarely needed, occasionally the right answer — a splash screen that must animate while the main thread blocks on startup, or a diagnostics window that must stay responsive when the main UI hangs:

C# 
var thread = new Thread(() =>
{
    var window = new SplashWindow();
    window.Show();
    Dispatcher.Run();                      // this thread now has its own message loop
});
thread.SetApartmentState(ApartmentState.STA);
thread.IsBackground = true;
thread.Start();

// To close it later, from anywhere:
window.Dispatcher.InvokeShutdown();

The two windows cannot share element instances, and they cannot be parent and child in the normal sense. Treat them as separate applications that happen to share a process.

GOTCHA

async void is correct for event handlers and for framework overrides like OnStartup, and wrong everywhere else. An unhandled exception in an async void method is rethrown on the synchronization context and takes the process down. Every async void body should be wrapped in try/catch, or be a one-liner delegating to a Task-returning method that handles its own errors.
