PART 17

Threading and async

Every WPF element, brush and animation belongs to the thread that created it, and touching it from any other thread throws, unless it is frozen.

Builds on Part 14, MVVM with the Community Toolkit ([RelayCommand] and [ObservableProperty]) and Part 8, resources (freezing brushes).

Without a model of threads, the first WPF bug you meet is usually one of two. Either the window turns white and says "Not Responding" while a file loads, or you move the load to a background thread and get InvalidOperationException: "The calling thread cannot access this object because a different thread owns it." This part explains both and the small set of rules that avoid them.

Precisely: every DispatcherObject, the base class of every element, every brush and every animation, remembers the thread that created it and throws if touched from another. That is thread affinity. Single-threaded apartment (STA) is the COM threading model the UI thread must use, which is why WPF's startup code marks the main thread with [STAThread].

IN PLAIN TERMS

The UI thread is a single cashier with one queue. Only the cashier may touch the till, which here means every element on screen (frozen objects, later in this part, are the exception). Other threads can do heavy work in the back room, but to change what the customer sees they must join the queue and hand the cashier a note. If the cashier is busy with one long job, the whole queue stops, and that is the "Not Responding" window.

The Dispatcher

One UI thread runs a message loop: it repeatedly takes the next piece of work (a click, a repaint, your code) and runs it. The Dispatcher is that loop's work queue, and it orders work by DispatcherPriority rather than strictly by arrival.

These are the ways to put work on that queue. Read the comments: they differ in whether you wait, and whether you can get a value back.

C# 
// Are we on the UI thread?
bool onUi = Dispatcher.CheckAccess();

// Post work to it (fire and forget, returns immediately).
// BeginInvoke takes a Delegate, so give the lambda an explicit type.
Dispatcher.BeginInvoke(new Action(() => status.Text = "Done"));
Dispatcher.InvokeAsync(() => status.Text = "Done");   // overload takes Action directly

// Post and await the result
var width = await Dispatcher.InvokeAsync(() => element.ActualWidth);

// Post and block until done: deadlock risk, avoid
Dispatcher.Invoke(() => status.Text = "Done");

// Run after layout has completed
Dispatcher.InvokeAsync(() => box.Focus(), DispatcherPriority.Loaded);

Priority matters more than people expect. DispatcherPriority.Background work runs only after input, rendering and normal work have been handled, which is how you keep a busy UI responsive. DispatcherPriority.Loaded is the hook for "after layout has run": work queued there runs once pending layout is done, which makes it the reliable way to focus a control that does not exist yet. Render is the priority layout itself runs at, so work queued at Render is not guaranteed to see the finished layout.

The rule you actually follow

With async/await, almost none of the above is needed day to day. await captures the current SynchronizationContext, an object that knows how to run code "back where you started". WPF installs a DispatcherSynchronizationContext on the UI thread, so the code after each await comes back to the UI thread automatically.

IN PLAIN TERMS

An await is like the cashier sending a slow order off to be prepared and keeping a ticket for it. Instead of standing and waiting, the cashier goes back to serving the queue. When the order is ready, the ticket (the rest of your method) joins the cashier's queue again, and the cashier finishes the order, not whoever prepared it. That is why the lines after await can touch the UI safely.

A typical command looks like this. The comments mark which thread each part runs on; notice that nothing in it mentions the dispatcher.

C# 
[RelayCommand]
private async Task LoadAsync(CancellationToken ct)
{
    // UI thread here.
    Status = "Loading…";

    var rows = await _repo.GetAllAsync(ct);          // UI thread is free while this waits

    // UI thread again: safe to touch bound collections.
    Items.Clear();
    foreach (var r in rows) Items.Add(new TaskViewModel(r));
    Status = $"{Items.Count} tasks";
}

While the repository call is in flight, the window stays responsive: the UI thread is free, not waiting. The three rules that keep this working:

  • Don't use ConfigureAwait(false) in view models and UI code. It tells the await not to come back to the captured context, and you want the context back. Do use it in library and service code that never touches UI.
  • Don't call .Result or .Wait() on the UI thread. The continuation needs the UI thread, which you are blocking while you wait for it. That is a textbook deadlock, two pieces of work each waiting for the other forever, and it is still the most common hang in WPF applications.
  • Do use Task.Run for genuinely CPU-bound work (work that keeps a processor busy, such as calculation), and nothing else. I/O-bound work (waiting on a disk, database or network) already frees the thread while it waits, so wrapping an async I/O call in Task.Run just burns a thread.
C# 
// CPU-bound: correct use of Task.Run
var report = await Task.Run(() => _engine.Recalculate(model), ct);

// I/O-bound: wrong
var rows = await Task.Run(() => _repo.GetAllAsync(ct));   // pointless thread hop
var rows = await _repo.GetAllAsync(ct);                   // correct

Progress reporting

Long work on a background thread usually needs to move a progress bar. Background code must not touch elements or bound collections. WPF forwards a plain property change from another thread, but not a collection change, unless you call BindingOperations.EnableCollectionSynchronization. Progress<T> gives the background code one safe channel: it remembers the context it was created on and posts every report back there.

C# 
[ObservableProperty] public partial double Progress { get; set; }

[RelayCommand]
private async Task ImportAsync(CancellationToken ct)
{
    // Progress<T> captures the current SynchronizationContext at construction,
    // so the callback runs on the UI thread automatically.
    var progress = new Progress<double>(p => Progress = p);

    await Task.Run(() => _importer.Run(_path, progress, ct), ct);
}

The importer only sees an IProgress<double> and calls Report; it knows nothing about WPF. Create the Progress<T> on the UI thread, as here; created on a background thread, its callbacks would run on the thread pool instead.

Freezables and cross-thread objects

Thread affinity has a cost: if a brush or a shape belongs to the UI thread, you cannot build a large one in the background. Freezing is the way out.

A Freezable is the kind of object brushes, geometries, transforms and animations are built on, and it can be made immutable with Freeze(). A frozen freezable loses thread affinity, so it can be created on a background thread and used on the UI thread. That is how you pre-build complex geometry off the UI thread:

C# 
var geometry = await Task.Run(() =>
{
    var g = BuildComplexPath(points);   // StreamGeometry, thousands of segments
    g.Freeze();                          // now thread-agnostic and faster to render
    return g;
});

path.Data = geometry;                    // UI thread, no marshalling needed

Freezing is one-way: to change a frozen object, clone it with Clone(), which gives you an unfrozen copy. A freezable with a binding or a running animation on it cannot be frozen; CanFreeze tells you before you try.

A second UI thread DEEPER

Rarely needed, occasionally the right answer: a splash screen that must animate while the main thread blocks on startup, or a diagnostics window that must stay responsive when the main UI hangs.

The code creates a thread, marks it STA, shows a window on it, and starts that thread's own dispatcher loop with Dispatcher.Run(). IsBackground = true means this thread will not keep the process alive after the main window closes. The main thread waits on ready until the window exists, so it has the splash thread's dispatcher in hand. splashDispatcher is a local here; in a real app, keep it in a field so other code can close the splash later.

C# 
Dispatcher? splashDispatcher = null;
using var ready = new ManualResetEventSlim();
var thread = new Thread(() =>
{
    var window = new SplashWindow();
    splashDispatcher = window.Dispatcher;
    window.Show();
    ready.Set();
    Dispatcher.Run();                      // this thread now has its own message loop
});
thread.SetApartmentState(ApartmentState.STA);
thread.IsBackground = true;
thread.Start();
ready.Wait();

// To close it later, from anywhere:
splashDispatcher!.InvokeShutdown();

The two windows cannot share element instances, and they cannot be parent and child in the normal sense. Treat them as separate applications that happen to share a process.

GOTCHA

async void is correct for event handlers and for framework overrides like OnStartup, and wrong everywhere else. Nobody can await an async void method, so nobody can catch its exceptions: an unhandled exception in one is rethrown on the synchronization context and takes the process down, unless a DispatcherUnhandledException handler marks it handled (Part 2). Every async void body should be wrapped in try/catch, or be a one-liner delegating to a Task-returning method that handles its own errors.

RECAP
  • Every WPF element, brush and animation belongs to the thread that created it, normally the UI thread.
  • The dispatcher is the UI thread's queue, and other threads hand work to it.
  • In view models, plain await brings you back to the UI thread; never block on .Result or .Wait().
  • Use Task.Run only for heavy computation, not to wrap calls that are already async.
  • Freeze brushes and geometry built on a background thread so the UI thread can use them.
  • Keep async void to event handlers and overrides, and catch errors inside it.
