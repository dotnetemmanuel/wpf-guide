PART 32

Windows integration and custom chrome

A WPF window works without any of this. What this part adds is the feeling that the app belongs on Windows: progress on the taskbar, recent files on right-click, an icon by the clock, a title bar that matches your design, and a window that reopens where the user left it.

Builds on Part 11, data binding, Part 14, MVVM with the Community Toolkit (commands), Part 16, navigation, windows, dialogs and, for the Mica section, Part 20, testing, packaging, interop.

Taskbar

A user starts a long import, switches to another app, and has no idea when it finishes unless they keep switching back. Windows already has a place to show this: the app's taskbar button can carry a progress bar, a small status badge, and buttons in the thumbnail preview that appears on hover.

WPF exposes all of that through TaskbarItemInfo, an object you attach to a window that describes what its taskbar button should show. Because its properties are dependency properties, you can bind them to your view model like anything else. In the block below, notice the four bound properties and the single thumbnail button, which runs a command exactly as an ordinary button would.

XAML 
<Window.TaskbarItemInfo>
  <TaskbarItemInfo ProgressState="{Binding TaskbarState}"
                   ProgressValue="{Binding Progress}"
                   Overlay="{Binding OverlayIcon}"
                   Description="{Binding Title}">
    <TaskbarItemInfo.ThumbButtonInfos>
      <ThumbButtonInfoCollection>
        <ThumbButtonInfo Description="Sync now"
                         ImageSource="/Assets/sync.png"
                         Command="{Binding SyncCommand}" />
      </ThumbButtonInfoCollection>
    </TaskbarItemInfo.ThumbButtonInfos>
  </TaskbarItemInfo>
</Window.TaskbarItemInfo>

ProgressState takes None, Normal, Paused, Error or Indeterminate, and ProgressValue runs from 0 to 1. Wiring it to a long-running import is a two-minute change that makes an app feel considerably more native.

Jump lists

A jump list is the menu that appears when the user right-clicks your taskbar button: recent files, common tasks, shortcuts straight into part of the app. Without one, reopening yesterday's project means launching the app and finding the file again.

Each entry in a jump list is a JumpTask: a recipe for starting a program with some command-line arguments. Clicking it does not talk to your running window. It starts your executable again with those arguments, so your startup code has to read them. The method below builds a list of up to ten recent projects under a custom heading, replacing Windows' own recent and frequent categories. Notice that it points each task at the app's own executable and passes the file path, quoted, as the argument.

C# 
public static void PublishRecent(IEnumerable<string> paths)
{
    var list = new JumpList { ShowRecentCategory = false, ShowFrequentCategory = false };

    foreach (string path in paths.Take(10))
    {
        list.JumpItems.Add(new JumpTask
        {
            Title = Path.GetFileNameWithoutExtension(path),
            Description = path,
            ApplicationPath = Environment.ProcessPath,
            Arguments = $"\"{path}\"",
            IconResourcePath = Environment.ProcessPath,
            CustomCategory = "Recent projects",
        });
    }

    JumpList.SetJumpList(Application.Current, list);
    list.Apply();
}

Once Apply has run, right-clicking the taskbar button shows a "Recent projects" heading with one entry per file, and the file's full path as the tooltip.

Tray icon and notifications

Apps that run in the background, such as sync clients or chat apps, usually live in the notification area (the tray): the row of small icons beside the clock. It lets the user close the main window while the app keeps working, and bring it back with a click.

WPF has no tray icon. Two options: reference WinForms for NotifyIcon, or use H.NotifyIcon.Wpf, which is XAML-native and better behaved. The XAML below uses the second. It declares the icon, its hover text, a command for a left click, and an ordinary WPF context menu for a right click.

XAML (H.NotifyIcon) 
xmlns:tb="clr-namespace:H.NotifyIcon;assembly=H.NotifyIcon.Wpf"

<tb:TaskbarIcon IconSource="/Assets/tray.ico"
                ToolTipText="Tasks"
                LeftClickCommand="{Binding ShowWindowCommand}">
  <tb:TaskbarIcon.ContextMenu>
    <ContextMenu>
      <MenuItem Header="Sync now" Command="{Binding SyncCommand}" />
      <Separator />
      <MenuItem Header="Exit"     Command="{Binding ExitCommand}" />
    </ContextMenu>
  </tb:TaskbarIcon.ContextMenu>
</tb:TaskbarIcon>

For real Windows toast notifications, target a Windows SDK TFM and use Microsoft.Toolkit.Uwp.Notifications / CommunityToolkit.WinUI.Notifications. A Windows SDK TFM is a target framework that names a Windows version, such as net10.0-windows10.0.19041.0, which gives your project access to Windows Runtime APIs.

Toasts need an app ID, the AUMID (Application User Model ID). An MSIX package supplies one. An unpackaged app still needs an app ID, but these libraries register one for it when they first run (ToastNotificationManagerCompat in the toolkit package above, or the Windows App SDK AppNotificationManager); you only set it up by hand if you call the raw Windows APIs.

IN PLAIN TERMS

An AUMID is your app's return address. A toast sits in the notification centre long after it appears, and when the user clicks it, Windows needs to know which app to hand the click to. An installed MSIX package comes with an address; a plain executable has none until the library registers one.

Custom window chrome

Many modern apps put their own content in the title bar: a search box, tabs, or simply colours that match the rest of the design. The part of a window that Windows normally draws (title bar, border, minimise, maximise and close buttons) is called the non-client area, or the window's chrome. WPF cannot draw into it by default.

The tempting shortcut is WindowStyle="None" (usually with AllowsTransparency="True") with a hand-made title bar. It looks right, but the window loses behaviour users expect: dragging to the screen edge to snap, resizing from the border, shaking the window to minimise others, double-clicking the title to maximise.

IN PLAIN TERMS

WindowChrome lets you repaint the frame of a window while Windows keeps owning how the frame behaves. You tell Windows "the top 36 pixels are the title bar, the outer 6 pixels are the resize border", then draw whatever you like in those areas. Windows still treats a drag there as moving the window. The consequence is that anything you place in the title bar is part of the drag handle too, unless you mark it as an exception.

The supported way to draw your own title bar while keeping snapping, resizing, Aero shake and maximise behaviour is below. Notice three things: CaptionHeight matches the height of the grid used as the title bar; ResizeBorderThickness sets the grab area for resizing; and the StackPanel of buttons sets WindowChrome.IsHitTestVisibleInChrome, without which clicks on the buttons would be taken as the start of a window drag.

XAML 
<Window x:Class="Tasks.Shell"
        WindowStyle="SingleBorderWindow"
        Background="{DynamicResource SurfaceBrush}">

  <WindowChrome.WindowChrome>
    <WindowChrome CaptionHeight="36"
                  ResizeBorderThickness="6"
                  CornerRadius="0"
                  GlassFrameThickness="0,0,0,1"
                  UseAeroCaptionButtons="False" />
  </WindowChrome.WindowChrome>

  <DockPanel>
    <Grid DockPanel.Dock="Top" Height="36" Background="{DynamicResource TitleBarBrush}">
      <Grid.ColumnDefinitions>
        <ColumnDefinition Width="*" />
        <ColumnDefinition Width="Auto" />
      </Grid.ColumnDefinitions>

      <TextBlock Text="{Binding Title}" Margin="12,0,0,0"
                 VerticalAlignment="Center" FontSize="12" />

      <!-- Buttons must opt out of the caption area or they aren't clickable -->
      <StackPanel Grid.Column="1" Orientation="Horizontal"
                  WindowChrome.IsHitTestVisibleInChrome="True">
        <Button Style="{StaticResource CaptionButton}" Content="─"
                Click="OnMinimise" />
        <Button Style="{StaticResource CaptionButton}" Content="◻"
                Click="OnMaximise" />
        <Button Style="{StaticResource CloseButton}"   Content="✕"
                Click="OnClose" />
      </StackPanel>
    </Grid>

    <ContentControl Content="{Binding Current}" />
  </DockPanel>
</Window>

The caption buttons need ordinary click handlers, because once you draw them yourself nothing else knows what they do:

C# 
private void OnMinimise(object s, RoutedEventArgs e) => WindowState = WindowState.Minimized;
private void OnClose(object s, RoutedEventArgs e) => Close();
private void OnMaximise(object s, RoutedEventArgs e) =>
    WindowState = WindowState == WindowState.Maximized
        ? WindowState.Normal : WindowState.Maximized;
GOTCHA

A maximised WindowChrome window overflows the screen by the resize-border thickness, hiding the top few pixels of your title bar. The figure above shows the result: roughly 8 pixels lost on every edge. The standard fix is to add a margin equal to SystemParameters.WindowResizeBorderThickness when WindowState == Maximized, via a trigger on the root element. Every custom-chrome implementation has this workaround in it somewhere.

Mica and dark title bars DEEPER

Windows 11 apps can have a translucent, tinted background called Mica, which picks up the colour of the desktop wallpaper, and a title bar that turns dark in dark mode. A WPF window that does neither looks slightly out of place next to them.

Both effects are drawn by the Desktop Window Manager (DWM), the part of Windows that composes every window on screen into the final image. WPF has no managed API for these attributes, so you ask DWM directly through P/Invoke, which is calling a native Windows function from C#.

IN PLAIN TERMS

Your app draws the inside of its window; DWM assembles all the windows on the screen and adds the frame effects. DwmSetWindowAttribute is a request slip handed to DWM: "use the dark title bar for this window", "put Mica behind this one". The numbers 20 and 38 are just which box on the slip you are ticking. If the running version of Windows does not recognise the box, the call returns an error code that this class ignores, so nothing visible happens.

The class below wraps the two requests. Each method gets the window's native handle (EnsureHandle creates it if the window has not been shown yet) and passes one integer value.

C# 
internal static class DwmWindow
{
    private const int UseImmersiveDarkMode = 20;
    private const int SystemBackdropType   = 38;

    [DllImport("dwmapi.dll")]
    private static extern int DwmSetWindowAttribute(
        IntPtr hwnd, int attribute, ref int value, int size);

    public static void ApplyDark(Window window, bool dark)
    {
        IntPtr hwnd = new WindowInteropHelper(window).EnsureHandle();
        int value = dark ? 1 : 0;
        DwmSetWindowAttribute(hwnd, UseImmersiveDarkMode, ref value, sizeof(int));
    }

    /// <summary>2 = Mica, 3 = Acrylic, 4 = Mica Alt. Windows 11 22H2+.</summary>
    public static void ApplyBackdrop(Window window, int type)
    {
        IntPtr hwnd = new WindowInteropHelper(window).EnsureHandle();
        DwmSetWindowAttribute(hwnd, SystemBackdropType, ref type, sizeof(int));
    }
}

For Mica to show through, the window background must be transparent and WindowChrome.GlassFrameThickness set to -1. It fails silently on Windows 10, so feature-detect. Windows 11 starts at build 22000, but the backdrop attribute used here arrived with 22H2 (build 22621), as the comment in the code says, so check Environment.OSVersion.Version.Build >= 22621 before calling ApplyBackdrop.

SINCE .NET 9

The built-in Fluent theme (ThemeMode, Part 8) handles the dark title bar and backdrop for you on supported Windows versions, so check whether you need this P/Invoke at all before writing it. .NET 11 previews fix Fluent backdrop and background defects specifically on Windows 10, another reason to feature-detect rather than assume.

Persisting window placement

Users expect a window to reopen at the size and position they left it. The obvious approach is to save Left, Top, Width, Height and whether it was maximised, then set them again at startup. The trap is that the monitor layout may have changed in between: a laptop undocked from its second screen, a projector unplugged.

The code below restores a saved placement. Notice the check at the top. It builds a rectangle covering the whole virtual screen (the combined area of every connected monitor) and only restores the saved position if the saved window rectangle overlaps it. Otherwise it centres the window.

C# 
public sealed record WindowPlacement(
    double Left, double Top, double Width, double Height, bool Maximised);

public static void Restore(Window window, WindowPlacement p)
{
    // Reject placements entirely outside the current monitor layout.
    var virt = new Rect(SystemParameters.VirtualScreenLeft,
                        SystemParameters.VirtualScreenTop,
                        SystemParameters.VirtualScreenWidth,
                        SystemParameters.VirtualScreenHeight);

    var target = new Rect(p.Left, p.Top, p.Width, p.Height);
    if (!virt.IntersectsWith(target))
    {
        window.WindowStartupLocation = WindowStartupLocation.CenterScreen;
        return;
    }

    window.WindowStartupLocation = WindowStartupLocation.Manual;
    window.Left = p.Left; window.Top = p.Top;
    window.Width = p.Width; window.Height = p.Height;
    if (p.Maximised) window.WindowState = WindowState.Maximized;
}

The intersection check is the part people skip, and it's why apps occasionally open on a monitor that is no longer plugged in. Call Restore before the window is shown, so it appears in the right place rather than jumping there.

RECAP
  • TaskbarItemInfo puts bindable progress, a badge and thumbnail buttons on the taskbar button.
  • A jump list entry starts your executable again with arguments, so startup code must handle them.
  • WPF has no tray icon of its own; use H.NotifyIcon.Wpf or the WinForms NotifyIcon.
  • WindowChrome lets you draw the title bar while keeping snapping and resizing, but buttons in it must opt in to clicks and a maximised window needs a margin fix.
  • Mica and dark title bars are DWM requests that fail silently on older Windows, so feature-detect, and try the Fluent theme first.
  • Only restore a saved window position if it still overlaps a connected monitor.
