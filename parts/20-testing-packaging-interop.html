PART 20

Testing, packaging, interop

Three things stand between an app that works on your machine and one you can hand to people: tests that tell you it still works, a way to install and update it, and occasionally a piece of older technology it has to host.

Builds on Part 14, MVVM with the Community Toolkit (generated commands), Part 15, dependency injection, Part 16, navigation, windows, dialogs (services behind interfaces) and Part 17, threading and async (STA threads).

Testing view models

Clicking through every screen after each change does not scale, and nobody does it consistently. Automated tests do, but only if the logic can run without a window.

IN PLAIN TERMS

A well-built view model is your app with the screen unplugged. Every button is a command you can execute from code, and every label is a property you can read. A test does exactly what a user would, pressing and reading, without anything being drawn.

The point of keeping System.Windows out of your view models is that this needs no special infrastructure. Each test builds the view model with a fake, a hand-written stand-in for a real dependency that keeps its data in memory, then drives the commands. sut is the usual name for the system under test, the object being tested.

The first test checks that adding a task trims the text, appends the item and clears the draft. The second starts a slow refresh, cancels it, and checks that the running task ends in cancellation with no items loaded. RefreshCancelCommand is the cancel command the toolkit generates from [RelayCommand(IncludeCancelCommand = true)].

C# 
[Fact]
public void Add_appends_and_clears_the_draft()
{
    var repo = new FakeTaskRepository();
    var sut  = new TaskListViewModel(repo) { Draft = "  Write tests  " };

    Assert.True(sut.AddCommand.CanExecute(null));
    sut.AddCommand.Execute(null);

    Assert.Equal("Write tests", Assert.Single(sut.Items).Title);
    Assert.Equal("", sut.Draft);
    Assert.False(sut.AddCommand.CanExecute(null));
}

[Fact]
public async Task Refresh_stops_when_cancelled()
{
    var repo = new SlowFakeRepository(delay: TimeSpan.FromSeconds(30));
    var sut  = new TaskListViewModel(repo);

    Task running = sut.RefreshCommand.ExecuteAsync(null);
    Assert.True(sut.RefreshCommand.IsRunning);

    sut.RefreshCancelCommand.Execute(null);
    await Assert.ThrowsAnyAsync<OperationCanceledException>(() => running);

    Assert.Empty(sut.Items);
}

Testing things that need a UI thread DEEPER

Converters, custom controls and anything constructing a DispatcherObject need an STA thread, and xUnit does not run tests on one, so you need a helper. This one runs your function on a new STA thread, waits for it, and rethrows any failure on the test thread, wrapped in an InvalidOperationException:

C# 
public static class Sta
{
    public static T Run<T>(Func<T> func)
    {
        T result = default!;
        Exception? error = null;

        var t = new Thread(() =>
        {
            try { result = func(); }
            catch (Exception ex) { error = ex; }
        });
        t.SetApartmentState(ApartmentState.STA);
        t.Start();
        t.Join();

        if (error is not null) throw new InvalidOperationException("STA work failed", error);
        return result;
    }
}

[Fact]
public void Pill_template_applies()
{
    var actual = Sta.Run(() =>
    {
        var button = new Button { Style = TestResources.PillButton };
        var host = new Border { Child = button };
        host.Measure(new Size(500, 500));
        host.Arrange(new Rect(0, 0, 500, 500));
        button.ApplyTemplate();
        return button.Template is not null;
    });

    Assert.True(actual);
}

The test forces the button through a real measure and arrange, as a window would, before checking the template. The helper starts no dispatcher loop, so work queued on the dispatcher (BeginInvoke, a DispatcherTimer) never runs. Code after an await does not come back to this thread either: it resumes on the thread pool, where touching a WPF object throws. Keep these tests synchronous.

The Xunit.StaFact package wraps this: [StaFact] runs a test on an STA thread, and [WpfFact] also runs a dispatcher for it, so awaits work there. For end-to-end UI automation, FlaUI is the maintained choice. It drives the app through UI Automation, the Windows accessibility interface that screen readers also use, which is another reason to set AutomationProperties.Name on your controls (Part 31).

Publishing

dotnet publish turns the project into a folder you can ship. The main decision is whether the user's machine must already have .NET.

A framework-dependent app contains only your code and needs the .NET desktop runtime installed. A self-contained app carries the runtime inside it, so it runs on any matching Windows machine with no prerequisite, at the cost of size. -r win-x64 names the runtime identifier, the operating system and processor you are publishing for.

IN PLAIN TERMS

Framework-dependent is like selling a film on disc: small and cheap to ship, but the buyer needs their own player. Self-contained puts a player in the box with every film. Nothing is required from the buyer, the box is much heavier, and each copy carries its own player that you, not the buyer, keep up to date.

bash 
# Framework-dependent: small, requires the .NET 10 desktop runtime installed
dotnet publish -c Release -r win-x64 --self-contained false

# Self-contained: ~150 MB, no runtime prerequisite
dotnet publish -c Release -r win-x64 --self-contained true \
  -p:PublishSingleFile=true \
  -p:IncludeNativeLibrariesForSelfExtract=true \
  -p:EnableCompressionInSingleFile=true \
  -p:PublishReadyToRun=true

The extra switches on the second command: PublishSingleFile bundles everything into one executable. IncludeNativeLibrariesForSelfExtract puts the native DLLs WPF needs inside that file too, extracted when the app starts, rather than leaving them beside it. EnableCompressionInSingleFile shrinks the bundle at a small cost in startup time. PublishReadyToRun precompiles your code to native code, so less is compiled while the app starts, at the cost of larger files.

GOTCHA

Do not enable PublishTrimmed or Native AOT. Trimming removes code the build believes is unused, and Native AOT (compiling the whole app to native code ahead of time) depends on trimming. WPF relies on reflection for XAML type resolution and binding paths, so the trimmer cannot see that those types are used and removes them. The SDK refuses the combination at build time with error NETSDK1168; if you suppress that check, the failures are run-time XamlParseExceptions in whichever screen you didn't test. PublishReadyToRun is safe and helps startup noticeably.

Distribution options, roughly in order of how much you'll enjoy them:

  • MSIX: the current Microsoft answer. Clean install and uninstall, automatic updates, Store or sideload. Needs signing, and the packaged-app identity changes how file paths and registry writes behave.
  • Velopack (successor to Squirrel and Clowd.Squirrel): delta updates, no admin rights, minimal ceremony. The pragmatic choice for internal tools.
  • ClickOnce: still supported for .NET 10, still awkward, still the path of least resistance in some enterprises.
  • An MSI via WiX: when IT requires it.

Settings and file locations

An installed app usually cannot write to its own folder, which is often under Program Files and read-only for normal users. Settings, databases and logs need a per-user location instead.

The old Properties.Settings/app.config system still works but is a dead end. Use IOptions<T> for read-only configuration (Part 15) and write user state yourself. The class below keeps every path in one place, under the user's local application data folder (%LOCALAPPDATA%):

C# 
public static class AppPaths
{
    private static string Root => Path.Combine(
        Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData), "Tasks");

    public static string Settings => Path.Combine(Root, "settings.json");
    public static string Database => Path.Combine(Root, "tasks.db");
    public static string Logs     => Path.Combine(Root, "logs");

    public static void EnsureCreated() => Directory.CreateDirectory(Root);
}

Call EnsureCreated() once at startup, before anything writes to these paths.

Interop DEEPER

Sometimes the control you need already exists in another technology: a WinForms PropertyGrid, or a web page. WPF can host both.

To follow the gotcha below you need one Windows term. An HWND is a Win32 window handle. In classic Windows UI, every control is its own small window with its own HWND. WPF instead draws the entire content of a window itself, inside a single HWND.

Hosting a WinForms control needs WinForms enabled in the project and two XML namespaces:

XAML: hosting a WinForms control 
<!-- csproj needs: <UseWindowsForms>true</UseWindowsForms> -->
xmlns:wfi="clr-namespace:System.Windows.Forms.Integration;assembly=WindowsFormsIntegration"
xmlns:wf="clr-namespace:System.Windows.Forms;assembly=System.Windows.Forms"

<wfi:WindowsFormsHost Height="300">
  <wf:PropertyGrid x:Name="Grid" />
</wfi:WindowsFormsHost>

Embedding a browser uses the WebView2 package, which renders with Microsoft Edge through the WebView2 Runtime installed on the machine:

XAML: embedding a browser 
<!-- PackageReference: Microsoft.Web.WebView2 -->
xmlns:wv2="clr-namespace:Microsoft.Web.WebView2.Wpf;assembly=Microsoft.Web.WebView2.Wpf"

<wv2:WebView2 Source="https://localhost:5001/report" />
IN PLAIN TERMS

A hosted control is like a television set into a painted wall. You can paint the wall however you like, but you cannot paint over the screen: anything you draw on the wall in that spot ends up behind the television. A WPF popup is different: it is a separate small window of its own, like a sign held up in front of the wall, so it can cover the screen.

GOTCHA

Both of these are airspace problems: they're HWND-based child windows rendered by a different system, so they always draw on top of the WPF content in their window, regardless of z-order. Adorners, overlay panels and in-window dialogs that should overlap them won't. Popups, menus and tooltips are the exception, because WPF shows them in windows of their own. Plan your layout so hosted content never needs WPF content floating above it. For web content, WebView2CompositionControl in the same package draws into WPF's own content and so avoids the airspace limit, at some cost in frame rate.

For Win32 proper, HwndHost hosts a native window and HwndSource hosts WPF content inside a native application. WindowInteropHelper gets you the HWND of a WPF window, which you need for most shell APIs and for DwmSetWindowAttribute if you want Mica or a custom title bar colour (Part 32).

RECAP
  • View models with no WPF types in them can be tested with plain unit tests and fakes.
  • Code that creates WPF objects needs an STA thread in tests.
  • Self-contained publishing ships the runtime with the app; framework-dependent needs it installed.
  • Never enable trimming or Native AOT for a WPF app; ReadyToRun is safe.
  • Write settings and data under the user's local application data folder, not beside the executable.
  • Hosted WinForms controls and the standard WebView2 control cover any WPF content drawn in the same window.
