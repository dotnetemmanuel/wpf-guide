PART 01

Where WPF stands today

WPF is a retained-mode, vector-based, resolution-independent UI framework. You describe a tree of elements; WPF composes it into a DirectX scene and re-renders what changed. Everything else in the framework follows from that one decision.

Each of those three terms answers a problem you would otherwise hit when building a desktop app.

  • Retained mode means WPF keeps your description of the screen in memory and redraws it itself. You never write "paint this rectangle now" code; you change an object in the tree and the screen follows.
  • Vector-based means shapes, text and borders are stored as geometry rather than as pixels, so they stay sharp when enlarged.
  • Resolution-independent means sizes are measured in units that follow the Windows display scaling setting rather than raw pixels, so a button keeps sensible proportions on a dense screen instead of shrinking.
IN PLAIN TERMS

Older Windows toolkits work like a whiteboard: whenever the window is uncovered or resized, your code is asked to draw everything again. WPF works like a scale model on a table: you place and move objects, and whenever something changes, a camera (DirectX) takes a fresh photograph of the model. Your job is to arrange the model, not to repaint the photograph.

WPF shipped in 2006 on .NET Framework 3.0 and moved to .NET Core 3.0 in 2019. It is now open source at dotnet/wpf and ships yearly with the rest of .NET. It is far from a museum piece: Visual Studio's shell is still WPF. So are large parts of Office's add-in surface, most industrial and defence line-of-business tooling on Windows, and a long tail of internal tools nobody is going to rewrite.

What that means practically:

  • It is Windows only. The TFM (target framework moniker, the value in your project file that names the .NET version and platform) is net10.0-windows. Your app runs only on Windows. The SDK can compile a WPF project elsewhere if you set EnableWindowsTargeting, which helps build servers, but you cannot run or debug it there. There is no Linux story and there never will be.
  • It is in maintenance-plus mode. Yearly releases contain performance work, accessibility fixes, and incremental Fluent styling. No new layout system, no new binding engine.
  • The core API surface is frozen, which is why a 2013 book still works. Dependency properties, routed events, templates and binding have not changed.
  • Trimming (the publish step that deletes code it believes is unused) and Native AOT (compiling the whole app ahead of time to machine code) are not supported. Both need to see every type use at build time, and WPF leans on reflection everywhere (binding paths, XAML type resolution). Publish self-contained or framework-dependent, not trimmed.
IN PLAIN TERMS

"Frozen" is good news for you as a learner. A book, blog post or Stack Overflow answer about bindings or templates from ten years ago still describes how WPF behaves today. What aged is the code around WPF: project files, how view models are written, how services are wired up. The list further down tells you exactly which parts to translate.

Choosing WPF over the alternatives

Several .NET UI frameworks overlap with WPF. The right one depends less on taste than on where the app has to run and who is building it.

PickWhen
WPFWindows-only desktop, rich data-heavy UI, dense forms, custom-drawn controls, an existing WPF codebase, or a team that already knows XAML. The deepest styling and templating system of anything in .NET.
WinUI 3You want the current Windows design language natively and can accept a smaller control set and a rockier tooling story.
AvaloniaYou want WPF-shaped XAML that also runs on Linux and macOS. Closest thing to a cross-platform WPF; different rendering stack.
.NET MAUIMobile is the actual requirement. Desktop is a side effect and the desktop control set shows it.
Blazor HybridYour team is a web team. Host a BlazorWebView and write Razor instead.

What actually changed since the books were written

Most of the best WPF material predates 2020. The framework in it is still accurate; the surrounding tooling and habits are not. Keep this list in your head while reading anything published before 2020, and translate as you go:

  • Project format. SDK-style .csproj (the short project file that lists only what differs from the defaults), no packages.config, no AssemblyInfo.cs, no app.config for settings.
  • MVVM plumbing. CommunityToolkit.Mvvm replaces the change-notification and command code that every old sample writes by hand. Its ObservableObject base class implements INotifyPropertyChanged, its source generators write the properties and command properties for you at compile time, and its RelayCommand class supplies the command logic.
  • Composition. Microsoft.Extensions.Hosting gives you dependency injection (DI), configuration and logging. The books construct view models with new.
  • Async. async/await existed by 2013 but the idioms did not. BackgroundWorker is gone from real code.
  • Theming. .NET 9 added a built-in Fluent theme and ThemeMode. The books' chapters on Aero and Luna theming are archaeology.
  • Gone entirely. XBAP and partial trust, WCF-as-default (HttpClient now), BinaryFormatter (removed in .NET 9, which breaks old clipboard and drag-drop code).
GOTCHA

WPF has no x:Bind. Compiled bindings are a UWP and WinUI feature, so tutorials for those platforms do not carry over here. Every binding in WPF is reflection-based and resolved at runtime, which is why a typo in a Path fails silently instead of failing to build: the app runs, and the field just stays empty. Part 11 covers how to make those failures loud.

RECAP
  • WPF keeps a tree of objects describing your UI and redraws it for you whenever something in the tree changes.
  • It runs only on Windows, and your project targets something like net10.0-windows.
  • The core concepts have not changed since the early books, so old explanations of bindings, templates and properties still hold.
  • The code around WPF has changed: SDK-style projects, the MVVM Toolkit, the generic host and async code replace the old habits.
  • Trimming and Native AOT do not work with WPF, because it discovers types by reflection at runtime.
  • A mistyped binding path does not fail the build; it silently shows nothing at runtime.
