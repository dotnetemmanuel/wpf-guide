PART 11

Data binding

The engine everything else leans on. A binding is an object that watches a source property and pushes values into a target dependency property, with optional conversion, validation and fallbacks.

Anatomy

XAML 
<TextBox Text="{Binding Path=Customer.Name,
                        Mode=TwoWay,
                        UpdateSourceTrigger=PropertyChanged,
                        Converter={StaticResource Trim},
                        ConverterParameter=NFC,
                        StringFormat='{}{0}',
                        FallbackValue='(unavailable)',
                        TargetNullValue='(none)',
                        Delay=300,
                        ValidatesOnDataErrors=True,
                        NotifyOnValidationError=True}" />
PartMeaning
PathDotted property path from the source. Path= is optional in first position.
ModeOneWay, TwoWay, OneWayToSource, OneTime, or Default (per-property metadata; TextBox.Text defaults to two-way).
UpdateSourceTriggerWhen the target pushes back: LostFocus (default for Text), PropertyChanged, Explicit.
FallbackValueUsed when the binding fails to resolve at all.
TargetNullValueUsed when the source resolves to null.
DelayMilliseconds to debounce source updates. Excellent on search boxes.

Where the source comes from

Exactly one of these, or none — in which case it's the inherited DataContext:

XAML 
<!-- 1. DataContext (inherited down the logical tree). The normal case. -->
<TextBlock Text="{Binding Title}" />

<!-- 2. ElementName: another named element in the same name scope -->
<Slider x:Name="Zoom" Minimum="0.5" Maximum="3" />
<TextBlock Text="{Binding Value, ElementName=Zoom, StringFormat={}{0:P0}}" />

<!-- 3. RelativeSource Self: this element -->
<TextBox ToolTip="{Binding Text, RelativeSource={RelativeSource Self}}" />

<!-- 4. RelativeSource AncestorType: walk up the visual tree -->
<Button Command="{Binding DataContext.DeleteCommand,
                          RelativeSource={RelativeSource AncestorType=DataGrid}}"
        CommandParameter="{Binding}" />

<!-- 5. RelativeSource TemplatedParent: inside a ControlTemplate -->
<TextBlock Text="{Binding Header, RelativeSource={RelativeSource TemplatedParent}}" />

<!-- 6. Source: an explicit object, usually a resource or a static -->
<TextBlock Text="{Binding Version, Source={x:Static app:BuildInfo.Current}}" />

AncestorLevel disambiguates nesting — {RelativeSource AncestorType=ListBox, AncestorLevel=2} skips the first ListBox and finds the one above it.

Path syntax

XAML 
{Binding Customer.Address.City}          <!-- nested -->
{Binding Items[0].Title}                 <!-- indexer -->
{Binding Tags[status]}                   <!-- string key, no quotes needed -->
{Binding .}                              <!-- the DataContext itself -->
{Binding}                                <!-- same thing, shorter -->
{Binding (Validation.HasError), RelativeSource={RelativeSource Self}}   <!-- attached prop -->
{Binding Path=(vm:Doc.Title)}            <!-- attached prop, qualified -->
{Binding Items/Title}                    <!-- current item of a collection view -->
GOTCHA

Attached properties in a Path must be parenthesised. {Binding Validation.HasError} looks for a property called Validation and fails silently; {Binding (Validation.HasError)} is correct.

Converters

C# 
[ValueConversion(typeof(bool), typeof(Visibility))]
public sealed class BoolToVisibilityConverter : IValueConverter
{
    public Visibility WhenFalse { get; set; } = Visibility.Collapsed;
    public bool Invert { get; set; }

    public object Convert(object? value, Type targetType, object? parameter, CultureInfo culture)
    {
        bool flag = value is true;
        if (Invert) flag = !flag;
        return flag ? Visibility.Visible : WhenFalse;
    }

    public object ConvertBack(object? value, Type targetType, object? parameter, CultureInfo culture)
        => throw new NotSupportedException();
}
XAML 
<Application.Resources>
  <conv:BoolToVisibilityConverter x:Key="BoolToVis" />
  <conv:BoolToVisibilityConverter x:Key="BoolToVisInverted" Invert="True" />
  <conv:BoolToVisibilityConverter x:Key="BoolToHidden" WhenFalse="Hidden" />
</Application.Resources>

<ProgressBar Visibility="{Binding IsBusy, Converter={StaticResource BoolToVis}}" />

Multi-value bindings combine several sources. The classic case is enabling a button on a conjunction of conditions:

C# 
public sealed class AllTrueConverter : IMultiValueConverter
{
    public object Convert(object[] values, Type t, object? p, CultureInfo c)
        => values.All(v => v is true);

    public object[] ConvertBack(object value, Type[] t, object? p, CultureInfo c)
        => throw new NotSupportedException();
}
XAML 
<Button Content="Submit">
  <Button.IsEnabled>
    <MultiBinding Converter="{StaticResource AllTrue}">
      <Binding Path="IsValid" />
      <Binding Path="IsConnected" />
      <Binding Path="HasPermission" />
    </MultiBinding>
  </Button.IsEnabled>
</Button>
RULE

Converters are presentation glue, not logic. A BoolToVisibility or a ByteCountToHumanString is fine. A converter that queries a database or decides business rules belongs on the view model as a computed property. If a converter needs a ConverterParameter to know what it's doing, that's usually a sign it should be two converters or one view-model property.

Making binding failures loud

Bindings fail silently by design. In development, don't accept that.

XAML 
<!-- Per binding: raises the trace level for this one binding only -->
xmlns:diag="clr-namespace:System.Diagnostics;assembly=WindowsBase"
<TextBlock Text="{Binding Whatever, diag:PresentationTraceSources.TraceLevel=High}" />
C# 
// App-wide, in Debug builds: turn every binding error into something you can't ignore.
#if DEBUG
PresentationTraceSources.Refresh();
PresentationTraceSources.DataBindingSource.Listeners.Add(new BindingErrorListener());
PresentationTraceSources.DataBindingSource.Switch.Level = SourceLevels.Error;
#endif

internal sealed class BindingErrorListener : TraceListener
{
    public override void Write(string? message) { }

    public override void WriteLine(string? message)
    {
        Debug.Fail("Binding error: " + message);   // breaks into the debugger
    }
}

Also set Tools → Options → Debugging → Output Window → WPF Trace Settings → Data Binding to Warning. Most "the value just doesn't show up" bugs are a misspelled path that has been printing an error to the output window the whole time.

Binding in code

C# 
var binding = new Binding(nameof(TaskViewModel.Title))
{
    Source = viewModel,
    Mode = BindingMode.TwoWay,
    UpdateSourceTrigger = UpdateSourceTrigger.PropertyChanged,
    Converter = new TrimConverter(),
};
BindingOperations.SetBinding(textBox, TextBox.TextProperty, binding);

// Later:
BindingOperations.ClearBinding(textBox, TextBox.TextProperty);

// Force a push/pull on an Explicit binding:
textBox.GetBindingExpression(TextBox.TextProperty)?.UpdateSource();
textBox.GetBindingExpression(TextBox.TextProperty)?.UpdateTarget();
