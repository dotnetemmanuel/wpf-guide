PART 11

Data binding

The engine everything else leans on.

Builds on Part 3, XAML precisely (markup extensions such as {Binding}), Part 5, dependency properties and Part 8, resources.

Without binding, you write code to copy a customer's name into a text box when the form opens, more code to copy it back when the user types, and more again whenever the name changes somewhere else. Every missed copy is a bug where the screen and the data disagree.

IN PLAIN TERMS

A binding is that copying done for you. Instead of a one-off assignment, you leave a standing instruction: "keep this box showing Customer.Name", and, if you ask, "write the user's edits back". The instruction stays in force until you replace or clear it. It can only react to changes the source announces, though, which is the job of INotifyPropertyChanged (or of a dependency property, when the source is another element).

Precisely: a binding is an object that watches a source property and pushes values into a target dependency property, with optional conversion, validation and fallbacks. The target is the property on the element that shows the value, such as TextBox.Text, and it must be a dependency property. The source is the object that owns the data, usually a view model.

Anatomy

Every binding follows the same route. Knowing the hops tells you where to look when a value does not appear.

Reading the figure left to right: the binding starts from a source object (by default the element's DataContext, explained in the next section), follows the Path to a property, optionally passes the value through a converter, and sets the target. INotifyPropertyChanged is a one-event interface a class implements to announce "this property just changed". Without it the binding picks up the value when it starts and misses every later change. For a two-way binding the value also travels back, from target to source, when the update trigger fires.

The markup below shows most of a binding's options at once; no real text box needs them all. The table explains the ones that change behaviour most.

XAML 
<TextBox Text="{Binding Path=Customer.Name,
                        Mode=TwoWay,
                        UpdateSourceTrigger=PropertyChanged,
                        Converter={StaticResource Trim},
                        ConverterParameter=NFC,
                        StringFormat='{}{0}',
                        FallbackValue='(unavailable)',
                        TargetNullValue='(none)',
                        Delay=300,
                        ValidatesOnDataErrors=True,
                        NotifyOnValidationError=True}" />
PartMeaning
PathDotted property path from the source. Path= is optional in first position.
ModeOneWay, TwoWay, OneWayToSource, OneTime, or Default (per-property metadata; TextBox.Text defaults to two-way).
UpdateSourceTriggerWhen the target pushes back: LostFocus (default for Text), PropertyChanged, Explicit.
FallbackValueUsed when the binding fails to resolve at all.
TargetNullValueUsed when the source resolves to null.
DelayMilliseconds to debounce source updates. Excellent on search boxes.

Two groups of settings in the example are not in the table. StringFormat applies a .NET format string, and only takes effect when the target property is a string; the leading {} stops XAML reading {0} as the start of a markup extension. Converter and ConverterParameter are covered under Converters below. ValidatesOnDataErrors turns on checks from the older IDataErrorInfo interface, and NotifyOnValidationError raises the Validation.Error event on the element; Part 13 covers validation and why new code uses INotifyDataErrorInfo instead.

Two settings cause most of the early surprises: Mode, which way values flow, and UpdateSourceTrigger, when a two-way binding writes back. With the defaults, a TextBox leaves your view model untouched while the user types, and writes the text only when focus leaves the box. Set PropertyChanged to write on every change, and add Delay to write once the user pauses.

Where the source comes from

A binding needs an object to read from. You can point it at one explicitly, but most bindings do not: they use the DataContext. DataContext is a property every element has, and its value is inherited by the elements inside it. Set it once on a window and every binding in the window reads from that object.

IN PLAIN TERMS

Setting DataContext on a window is like telling a team "unless I say otherwise, take your questions to Anna". Every control inside asks Anna. ElementName, RelativeSource and Source are the "unless I say otherwise": each points one binding at someone else without changing the default for anyone. Unlike a team rule, any element can set its own DataContext, and that changes the default for everything inside that element.

A binding uses exactly one of the sources below, or none, in which case it uses the inherited DataContext:

XAML 
<!-- 1. DataContext (inherited down the logical tree). The normal case. -->
<TextBlock Text="{Binding Title}" />

<!-- 2. ElementName: another named element in the same name scope -->
<Slider x:Name="Zoom" Minimum="0.5" Maximum="3" />
<TextBlock Text="{Binding Value, ElementName=Zoom, StringFormat={}{0:P0}}" />

<!-- 3. RelativeSource Self: this element -->
<TextBox ToolTip="{Binding Text, RelativeSource={RelativeSource Self}}" />

<!-- 4. RelativeSource AncestorType: walk up the visual tree -->
<Button Command="{Binding DataContext.DeleteCommand,
                          RelativeSource={RelativeSource AncestorType=DataGrid}}"
        CommandParameter="{Binding}" />

<!-- 5. RelativeSource TemplatedParent: inside a ControlTemplate -->
<TextBlock Text="{Binding Header, RelativeSource={RelativeSource TemplatedParent}}" />

<!-- 6. Source: an explicit object, usually a resource or a static -->
<TextBlock Text="{Binding Version, Source={x:Static app:BuildInfo.Current}}" />

A few terms from those comments. A name scope is the set of x:Names that can see each other, typically one window, user control or template. The visual tree is the full tree of elements that are actually drawn, including the parts inside control templates. TemplatedParent means the control that a ControlTemplate is drawing (Part 10).

Case 4 is the one you will write most after DataContext. A button inside a grid row has the row's item as its DataContext, but the delete command lives on the grid's view model. The binding walks up to the DataGrid, reads its DataContext, and CommandParameter="{Binding}" passes the row item itself.

AncestorLevel disambiguates nesting: {RelativeSource AncestorType=ListBox, AncestorLevel=2} skips the first ListBox and finds the one above it.

Path syntax

The Path is a small language of its own. Most bindings use only the first form, a dotted chain of property names; the others are here so you recognise them.

XAML 
{Binding Customer.Address.City}          <!-- nested -->
{Binding Items[0].Title}                 <!-- indexer -->
{Binding Tags[status]}                   <!-- string key, no quotes needed -->
{Binding .}                              <!-- the DataContext itself -->
{Binding}                                <!-- same thing, shorter -->
{Binding (Validation.HasError), RelativeSource={RelativeSource Self}}   <!-- attached prop -->
{Binding Path=(vm:Doc.Title)}            <!-- attached prop, qualified -->
{Binding Items/Title}                    <!-- current item of a collection view -->

An attached property (Part 5) is one defined by one class but set on elements of another, such as Grid.Row or Validation.HasError. The slash form in the last line reads a property of a collection view's current item, a concept from Part 12.

GOTCHA

Attached properties in a Path must be parenthesised. {Binding Validation.HasError} looks for a property called Validation and fails silently; {Binding (Validation.HasError)} is correct.

Converters

A view model exposes data in its own terms, for example a bool IsBusy. The element often wants something else: Visibility is an enum with Visible, Hidden and Collapsed, not a bool. A value converter is a small class implementing IValueConverter that translates between the two: Convert runs on the way to the target, ConvertBack on the way back to the source.

IN PLAIN TERMS

A converter is a travel plug adapter: the view model offers one shape, the element accepts another, and the adapter joins them without either side changing. Like an adapter, it should do nothing but make the connection fit. Deciding anything belongs to the view model, which is the rule at the end of this section.

The converter below turns a bool into a Visibility. Its two properties let one class cover three common cases. ConvertBack throws, which is the convention for a converter meant only for one-way bindings.

C# 
[ValueConversion(typeof(bool), typeof(Visibility))]
public sealed class BoolToVisibilityConverter : IValueConverter
{
    public Visibility WhenFalse { get; set; } = Visibility.Collapsed;
    public bool Invert { get; set; }

    public object Convert(object? value, Type targetType, object? parameter, CultureInfo culture)
    {
        bool flag = value is true;
        if (Invert) flag = !flag;
        return flag ? Visibility.Visible : WhenFalse;
    }

    public object ConvertBack(object? value, Type targetType, object? parameter, CultureInfo culture)
        => throw new NotSupportedException();
}
XAML 
<Application.Resources>
  <conv:BoolToVisibilityConverter x:Key="BoolToVis" />
  <conv:BoolToVisibilityConverter x:Key="BoolToVisInverted" Invert="True" />
  <conv:BoolToVisibilityConverter x:Key="BoolToHidden" WhenFalse="Hidden" />
</Application.Resources>

<ProgressBar Visibility="{Binding IsBusy, Converter={StaticResource BoolToVis}}" />

WPF already ships a BooleanToVisibilityConverter; the custom one earns its place with the Invert and WhenFalse options.

Multi-value bindings combine several sources. A MultiBinding feeds several child bindings into one converter, which implements IMultiValueConverter and receives all the current values as an array. The classic case is enabling a button on a conjunction of conditions:

C# 
public sealed class AllTrueConverter : IMultiValueConverter
{
    public object Convert(object[] values, Type t, object? p, CultureInfo c)
        => values.All(v => v is true);

    public object[] ConvertBack(object value, Type[] t, object? p, CultureInfo c)
        => throw new NotSupportedException();
}
XAML 
<Button Content="Submit">
  <Button.IsEnabled>
    <MultiBinding Converter="{StaticResource AllTrue}">
      <Binding Path="IsValid" />
      <Binding Path="IsConnected" />
      <Binding Path="HasPermission" />
    </MultiBinding>
  </Button.IsEnabled>
</Button>

Whenever any of the three source properties changes, the converter runs again with all three values. A child binding that fails to resolve passes DependencyProperty.UnsetValue rather than a bool, which v is true treats as false.

RULE

Converters are presentation glue, not logic. A BoolToVisibility or a ByteCountToHumanString is fine. A converter that queries a database or decides business rules belongs on the view model as a computed property. If a converter needs a ConverterParameter to know what it's doing, that's usually a sign it should be two converters or one view-model property.

Making binding failures loud

Bindings fail silently by design. A misspelled path does not stop the build and does not throw: WPF writes a message to the debug output and leaves the target at its fallback or default value, so the screen just shows nothing. In development, do not accept that.

To investigate one suspicious binding, raise its trace level. The output window then shows each step the binding took while resolving its path, including the one where it failed.

XAML 
<!-- Per binding: raises the trace level for this one binding only -->
xmlns:diag="clr-namespace:System.Diagnostics;assembly=WindowsBase"
<TextBlock Text="{Binding Whatever, diag:PresentationTraceSources.TraceLevel=High}" />

To catch every broken binding in the app, attach a listener once at startup, for example in the App constructor. In Debug builds each binding error is then written to the output with its message, which names the missing property and the type it was looked for on. It breaks into the debugger only when one is attached, so the app still runs normally outside Visual Studio.

C# 
// App-wide, in Debug builds: log every binding error, and break on it under a debugger.
#if DEBUG
PresentationTraceSources.Refresh();
PresentationTraceSources.DataBindingSource.Listeners.Add(new BindingErrorListener());
PresentationTraceSources.DataBindingSource.Switch.Level = SourceLevels.Error;
#endif

internal sealed class BindingErrorListener : TraceListener
{
    public override void Write(string? message) { }

    public override void WriteLine(string? message)
    {
        Debug.WriteLine("Binding error: " + message);
        if (Debugger.IsAttached) Debugger.Break();
    }
}

Also set Tools → Options → Debugging → Output Window → WPF Trace Settings → Data Binding to Warning. Most "the value just doesn't show up" bugs are a misspelled path that has been printing an error to the output window the whole time.

Binding in code DEEPER

Occasionally you need to create a binding at runtime, for example for columns generated from data. {Binding} in XAML creates an instance of this same Binding class, so every option above is a property you can set from C#.

C# 
var binding = new Binding(nameof(TaskViewModel.Title))
{
    Source = viewModel,
    Mode = BindingMode.TwoWay,
    UpdateSourceTrigger = UpdateSourceTrigger.PropertyChanged,
    Converter = new TrimConverter(),
};
BindingOperations.SetBinding(textBox, TextBox.TextProperty, binding);

// Later:
BindingOperations.ClearBinding(textBox, TextBox.TextProperty);

// Force a push/pull on an Explicit binding:
textBox.GetBindingExpression(TextBox.TextProperty)?.UpdateSource();
textBox.GetBindingExpression(TextBox.TextProperty)?.UpdateTarget();

A binding with UpdateSourceTrigger=Explicit never writes back on its own. Calling UpdateSource is how you commit it, which suits a dialog that should change nothing until the user presses OK. UpdateTarget goes the other way and re-reads the source.

RECAP
  • A binding keeps a property on an element in step with a property on a source object, so you stop writing copy code.
  • With no explicit source, a binding reads from the DataContext inherited from the elements around it.
  • The source must announce changes, through INotifyPropertyChanged or by being a dependency property such as a Slider's Value, or the screen shows the first value and never updates.
  • Mode decides which way values flow, and UpdateSourceTrigger decides when a text box writes back.
  • Converters change a value's type or shape for display; decisions belong in the view model.
  • A broken binding fails silently, so turn up binding trace output while you develop.
