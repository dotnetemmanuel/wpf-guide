PART 31

Accessibility

In much of Europe the EN 301 549 standard makes this a procurement requirement rather than a nice-to-have. WPF's automation support is good; the defaults are not.

Builds on Part 8, resources (dynamic resources), Part 9, styles and triggers, Part 23, input, focus and keyboard and, for the last section, Part 27, authoring custom controls.

Some of the people using your app cannot see the screen, cannot use a mouse, or need far more contrast than your design offers. They reach your app through assistive technology: a screen reader that speaks the interface aloud, a switch device, voice control. None of those tools can look at pixels. They ask Windows what is on the screen, and Windows asks your app.

The channel for those questions is UI Automation (UIA): the Windows API through which assistive technology, and automated UI tests, discover the controls in a window, read their names and values, and operate them. WPF answers UIA for you by building an automation tree, a parallel, simplified description of your visual tree that lists each meaningful element with its role (button, list, slider), its name and its current state.

IN PLAIN TERMS

Think of the automation tree as the spoken description of a room for someone who cannot see it. The visual tree is the room itself, with every trim, shadow and decorative border. The description lists only what matters: "a door on your left labelled Exit, a switch that is currently off". Your job is to make sure the description exists for everything that does something, uses the words a person would use, and leaves out the ornaments.

WPF builds this tree automatically for standard controls, which is why the support is good. But it can only describe what it can infer. A button whose content is an icon has no text to read, a label is not known to belong to its field unless you say so, and a decorative image is reported like any other image. That is why the defaults are not good enough.

The five things that cover most of it

Most of the work is setting attached properties from the AutomationProperties class: properties you can set on any element, which feed the automation tree without changing what is drawn. The block below shows the five that matter most. Notice what each one fixes:

  1. An icon-only button has no text, so a screen reader would announce just "button". AutomationProperties.Name gives it a spoken name. The matching ToolTip helps sighted mouse users with the same problem.
  2. A field needs to announce what it is for. Label.Target gives the label's access key (the underlined letter, from the _ in _Due date) a field to move focus to. It does not reliably reach the automation tree, so the field also sets AutomationProperties.LabeledBy, which tells the automation tree which element names the field. The label is given x:Name="DueLabel" so that binding can find it.
  3. Decoration clutters the description. A decorative image is announced like any meaningful one; setting AccessibilityView to Raw keeps it out of the views screen readers normally walk. Shapes such as Path need nothing: they create no automation peer, so they never appear in the tree.
  4. Text that changes on its own (a status line, a count) goes unnoticed unless it is marked as a live region, an element whose changes the screen reader announces. Polite waits for the reader to finish speaking; Assertive interrupts.
  5. Everything must be reachable from the keyboard. Access keys and IsDefault (Enter activates the button) are the cheapest part of that.
XAML 
<!-- 1. Name every control that has no visible text label -->
<Button Command="{Binding DeleteCommand}"
        AutomationProperties.Name="Delete task"
        ToolTip="Delete task">
  <Path Data="{StaticResource TrashGeometry}" />
</Button>

<!-- 2. Associate labels with fields -->
<Label x:Name="DueLabel" Content="_Due date" Target="{Binding ElementName=DueBox}" />
<DatePicker x:Name="DueBox"
            AutomationProperties.LabeledBy="{Binding ElementName=DueLabel}" />

<!-- 3. Hide decorative visuals from the automation tree -->
<Image Source="/Assets/divider.png"
       AutomationProperties.AccessibilityView="Raw" />

<!-- 4. Announce live changes -->
<TextBlock x:Name="StatusText"
           Text="{Binding StatusMessage, NotifyOnTargetUpdated=True}"
           TargetUpdated="OnStatusTargetUpdated"
           AutomationProperties.LiveSetting="Polite" />

<!-- 5. Give the user a keyboard path to everything -->
<Button Content="_Save" IsDefault="True" />

With these in place, Narrator reads the first button as "Delete task, button" instead of "button", and reads the date picker with the label's text rather than as an unnamed date picker.

IN PLAIN TERMS

A live region is like a colleague who glances at the dashboard and says "the import finished" out loud. Without it, the screen reader user only learns about the change if they happen to move back to that line and read it again. Mark too many elements as live and the colleague never stops talking, so reserve it for messages the user actually needs to hear.

Marking the element is only half of a live region. The screen reader announces it when the element raises a LiveRegionChanged automation event, and WPF does not raise that for you when the text changes. Raise it yourself after the change. Give the TextBlock x:Name="StatusText" and set NotifyOnTargetUpdated=True on its binding, as item 4 above does: the element then raises TargetUpdated each time a new value arrives from the view model, and its handler in code-behind raises the automation event:

C# 
private void OnStatusTargetUpdated(object? sender, DataTransferEventArgs e) => AnnounceStatus();

private void AnnounceStatus()
{
    AutomationPeer? peer = UIElementAutomationPeer.CreatePeerForElement(StatusText);
    peer?.RaiseAutomationEvent(AutomationEvents.LiveRegionChanged);
}

Testing it

You cannot judge accessibility by looking at the window, because the failures are invisible by definition. Use the tools that see what assistive technology sees:

  • Accessibility Insights for Windows: free from Microsoft. Live inspection of the automation tree plus automated checks. Run it before you ship.
  • Narrator (Win+Ctrl+Enter) or NVDA: actually listen to your screen. Ten minutes tells you more than any checklist.
  • Unplug the mouse and complete your main workflow. The fastest test there is.
  • High contrast: Win+Alt+PrintScreen. Anything using a hard-coded colour disappears.

High contrast

High contrast is a Windows setting that replaces every colour with a small user-chosen palette, often white or yellow text on black. People with low vision rely on it. Windows applies the palette to standard controls, but it cannot recolour your own brushes. A card drawn in a soft beige on a white window can vanish entirely, and text in your brand colour can become unreadable against the new background.

IN PLAIN TERMS

High contrast is the user saying "use my colours, not yours". SystemColors is where Windows publishes those colours. If your style reads its colours from there when high contrast is on, your app follows the user's choice; if it keeps its own palette, it is like a sign painted in the house style after the reader asked for large black print.

The style below shows the pattern. Normally the card uses your palette through dynamic resources. A DataTrigger checks SystemParameters.HighContrast and, when it is true, swaps the fill and border for the system window colours and adds a visible border, because in high contrast a fill difference alone no longer marks the card's edge. As written, the binding reads the setting once, so a user who turns high contrast on while the app runs sees the change only after a restart, as the figure notes. To follow live changes, bind with a property path instead, Binding="{Binding Path=(SystemParameters.HighContrast)}", which listens for the static property's change notification.

XAML 
<Style TargetType="Border" x:Key="Card">
  <Setter Property="Background" Value="{DynamicResource SurfaceBrush}" />
  <Setter Property="BorderBrush" Value="{DynamicResource BorderBrush}" />
  <Style.Triggers>
    <DataTrigger Binding="{Binding Source={x:Static SystemParameters.HighContrast}}"
                 Value="True">
      <Setter Property="Background"
              Value="{DynamicResource {x:Static SystemColors.WindowBrushKey}}" />
      <Setter Property="BorderBrush"
              Value="{DynamicResource {x:Static SystemColors.WindowTextBrushKey}}" />
      <Setter Property="BorderThickness" Value="1" />
    </DataTrigger>
  </Style.Triggers>
</Style>

The general rule: never convey information by colour alone, and in high contrast mode fall back to SystemColors keys rather than your palette. "Colour alone" means things like a red border as the only sign of a validation error, or green and grey as the only difference between done and not done. Add an icon, a text change or a pattern as well.

Custom controls need a custom peer DEEPER

The automation tree is not built from your controls directly. Each element creates an automation peer: a companion object that answers UIA's questions on the element's behalf ("what are you, what is your name, what can I do with you"). Every built-in control ships with a suitable peer, so a Slider reports itself as a slider with a value and a range.

IN PLAIN TERMS

The peer is the control's interpreter. The control itself speaks only in pixels and mouse events; the peer translates that into the terms a screen reader understands, such as "slider, 3 of 5". A control you wrote yourself has no interpreter of its own, so WPF sends a generic one that can only say "something is here".

If you write a lookless control, screen readers see a generic element unless you supply an AutomationPeer. The peer also exposes control patterns: small interfaces that describe what can be done with the element. IRangeValueProvider, for example, says "I have a value between a minimum and a maximum, and you can set it".

The code below gives a star-rating control a peer. Notice three things. OnCreateAutomationPeer is the hook WPF calls to get the peer. The peer reports itself as a Slider, the closest standard role, and returns itself for the RangeValue pattern. And the control raises a property-changed event through the peer when its value changes, which is what lets a screen reader announce the new rating.

C# 
public class RatingBar : Control
{
    protected override AutomationPeer OnCreateAutomationPeer() => new RatingBarPeer(this);

    internal void RaiseValueChanged(int oldValue, int newValue)
    {
        if (UIElementAutomationPeer.FromElement(this) is RatingBarPeer peer)
            peer.RaisePropertyChangedEvent(
                RangeValuePatternIdentifiers.ValueProperty,
                (double)oldValue, (double)newValue);
    }
}

public sealed class RatingBarPeer(RatingBar owner)
    : FrameworkElementAutomationPeer(owner), IRangeValueProvider
{
    protected override AutomationControlType GetAutomationControlType()
        => AutomationControlType.Slider;

    protected override string GetClassNameCore() => nameof(RatingBar);

    public override object? GetPattern(PatternInterface pattern)
        => pattern == PatternInterface.RangeValue ? this : base.GetPattern(pattern);

    // IRangeValueProvider
    public double Value => ((RatingBar)Owner).Value;
    public double Minimum => 0;
    public double Maximum => ((RatingBar)Owner).Maximum;
    public double SmallChange => 1;
    public double LargeChange => 1;
    public bool IsReadOnly => !Owner.IsEnabled;

    public void SetValue(double value) => ((RatingBar)Owner).Value = (int)Math.Round(value);
}

Run Accessibility Insights against a window holding this control and it now shows a slider named after the control, with a current value, a minimum and a maximum, instead of a bare custom element.

Implementing the right pattern (IInvokeProvider for things that are clicked, IToggleProvider for things that switch on and off, ISelectionProvider for things that hold a selection, IRangeValueProvider for a value in a range) is also what makes the control drivable by UI automation tests (Part 20), so the accessibility work pays for itself twice.

SINCE .NET 9 / .NET 10

Both releases contain substantial UI Automation fixes, including better NVDA compatibility and added RecognizesAccessKey on controls that were missing it in the Fluent theme. .NET 10 also improved automation performance by cutting allocations in the automation layer. If accessibility is contractual for you, target .NET 10.

RECAP
  • Screen readers and UI tests see your app through the automation tree, not through its pixels.
  • Give every control without visible text an AutomationProperties.Name, and link labels to their fields.
  • Hide decoration from the automation tree and mark status text as a live region so changes are announced.
  • Test with Accessibility Insights, a real screen reader, no mouse, and high contrast turned on.
  • In high contrast, take colours from SystemColors, and never use colour as the only signal.
  • A custom control needs its own automation peer, which also makes it testable by UI automation.
