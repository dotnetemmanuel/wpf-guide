PART 38

Projects: a route from first window to production

Eight projects, each one adding a layer. Every project names the parts it exercises, gives you a specification rather than a tutorial to copy, and ends with checkpoints you can honestly answer yes or no to. Do them in order; each assumes the last.

HOW TO USE THIS

Do not read the relevant parts first and then build. Start each project, get stuck, then go read. The parts are written to be searched, and the knowledge sticks when it arrives as an answer to a question you already have.

Sections marked DEEPER are stretch goals you can skip on a first pass.

Project 0 · The environment

Exercises: Part 2. Time: 30 minutes.

By the end you can run, debug, hot reload and inspect a WPF app, and you know where binding errors appear.

Before anything else, prove the loop works: edit, build, run, debug, hot reload. WPF fails quietly: a mistyped binding does not throw, the text box is simply empty. These tools are how you find the cause in minutes rather than an evening.

You need Windows, Visual Studio and the .NET 10 SDK (with the .NET 9 SDK, use -f net9.0-windows instead). The commands below create an empty app and run it. The last one, dotnet watch, runs it again with hot reload attached: C# edits are applied to the running process without restarting it.

bash 
dotnet new wpf -n Scratch -f net10.0-windows
cd Scratch
dotnet run

# Hot reload while running:
dotnet watch

Then, in order:

  1. Put a Button in the window. Handle Click in code-behind. Open the project in Visual Studio, set a breakpoint in the handler, start with F5, click the button, and confirm the debugger stops there.
  2. Stop debugging first (a running F5 session locks the exe and the build fails), then start the app with dotnet run instead, and in Visual Studio use Debug → Attach to Process to attach to Scratch.exe. Click the button: the same breakpoint stops.
  3. Back under F5, change a Background in XAML and watch XAML Hot Reload apply it live. That needs the Visual Studio debugger; dotnet watch covers only the C# half. Stop debugging first, then run dotnet watch, change a method body and watch that apply. Then change an existing field's type from int to long, or add an interface to the class: dotnet watch reports it cannot apply the edit and offers to restart. Knowing what hot reload cannot do saves you restarts later.
  4. Install Snoop (snoopwpf on GitHub). Attach it to your running app and walk the visual tree: the tree of every element actually on screen, including the pieces inside each control's template. Find the TextBlock inside your button's template. You wrote a button with some text; WPF built a border, a content presenter and a text block to draw it.
  5. Turn on binding trace output: Tools → Options → Debugging → Output Window → WPF Trace Settings → Data Binding → Warning. Add a deliberately broken binding, such as Text="{Binding NoSuchProperty, RelativeSource={RelativeSource AncestorType=Window}}", and find the error in the Output window. It names the property it could not find and the type it looked on. Visual Studio's XAML Binding Failures window lists the same failures while you debug. (A binding with no source at all, because nothing set a data context yet, stays silent at this level, so give it a real source to fail against.)

Checkpoints

  • You can attach a debugger to a running WPF app.
  • You can find any element in the visual tree with Snoop.
  • You know where binding errors print, and you have read one.

Project 1 · Unit converter

Exercises: Parts 3, 4, 11, 14. Time: an evening.

By the end you can lay out a form that survives resizing, bind controls to a view model instead of writing event handlers, and explain why a value set directly on a control beats a style.

New here: data binding and a view model, in the smallest thing that teaches layout and binding properly. Project 0 had one click handler; this project replaces handlers altogether.

Specification

  • Two text boxes and a category selector: length, mass, temperature.
  • Typing in either box updates the other as you type, not on focus loss.
  • Two combo boxes select the source and target unit within the category.
  • A swap button exchanges the two units and the two values.
  • Invalid input shows a message and does not clear what the user typed.

Build it twice

Lay the window out first, with a Grid and no fixed widths on the text boxes (Part 4), and resize it before writing any logic.

Then build it in code-behind: event handlers, double.TryParse, direct assignment to TextBox.Text. Get it working. Count the lines. In that version every handler reads one control and writes another, so the conversion logic cannot run, or be tested, without a window.

Then delete the code-behind and rebuild it with a view model. The second version is the lesson.

IN PLAIN TERMS

A view model is a plain C# class that holds what the screen shows, as properties, with no reference to any control. Think of a spreadsheet: the view model is the cells and their formulas, and the window is the formatting laid over them. ResultText below is a formula cell. The analogy breaks in one place: a spreadsheet notices dependencies by itself, whereas your view model must announce "this property changed" so bindings re-read it.

Before you start the second version:

  • Add the toolkit with dotnet add package CommunityToolkit.Mvvm. Its source generators write the property-changed plumbing for you (Part 14).
  • Create the view model in XAML, with <Window.DataContext><local:ConverterViewModel /></Window.DataContext>, so the code-behind stays empty. The data context is the object every binding in the window reads from unless told otherwise (Part 11).
  • Unit, UnitCategory, UnitTable and the TryConvert method are yours to write. Temperature is the interesting case: Celsius to Fahrenheit is not a multiplication, so store each unit as a conversion to and from a base unit rather than as a single factor.
C#: the shape to aim for 
public partial class ConverterViewModel : ObservableValidator
{
    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(Units))]
    public partial UnitCategory Category { get; set; }

    [ObservableProperty] public partial Unit? From { get; set; }
    [ObservableProperty] public partial Unit? To { get; set; }

    [ObservableProperty] public partial string SourceText { get; set; }

    public IReadOnlyList<Unit> Units => UnitTable.For(Category);

    public string ResultText => TryConvert(out double result)
        ? result.ToString("0.####", CultureInfo.CurrentCulture)
        : "";

    public ConverterViewModel()
    {
        SourceText = "";
        Category = UnitCategory.Length;
        From = Units[0];
        To = Units[1];
    }

    partial void OnSourceTextChanged(string value) => OnPropertyChanged(nameof(ResultText));
    partial void OnFromChanged(Unit? value)        => OnPropertyChanged(nameof(ResultText));
    partial void OnToChanged(Unit? value)          => OnPropertyChanged(nameof(ResultText));

    [RelayCommand]
    private void Swap() => (From, To) = (To, From);
}

SourceText is a string, not a number, on purpose. A string always accepts whatever was typed, so invalid input is never thrown away, and parsing happens in one place you control.

The sketch converts one way and swaps only units; finishing the specification is your job. When both boxes drive each other, never write back into the box the user is typing in, or the reformatted result rewrites their text (1.50 becomes 1.5). When it works, walk into the traps below one at a time.

Deliberate traps to walk into

  • Bind Text without UpdateSourceTrigger=PropertyChanged first, and notice it only updates on tab-out. A TextBox pushes its text to the source when it loses focus unless told otherwise.
  • Set Background="LightYellow" directly on a TextBox, then add a style trigger (Part 9) that changes the background when IsKeyboardFocused is true. Click into the box and watch the trigger lose. That is Part 5's precedence list, learned the memorable way.
  • Use StringFormat={0:N2} and see what a Swedish or German locale does to it: bindings format with US English by default, whatever the machine's culture, so the user sees a full stop where they expect a comma. Then apply the LanguageProperty.OverrideMetadata fix from Part 30.

Checkpoints

  • Zero lines in code-behind beyond InitializeComponent.
  • You can explain why a local value beat your trigger.
  • The layout still looks correct when the window is resized to 320×200 and to 1600×1200.

Project 2 · Markdown scratchpad

Exercises: Parts 6, 8, 9, 16, 17. Time: a weekend.

By the end you can build a document app: several commands with shortcuts, a window that can refuse to close, dialogs kept out of the view model, runtime themes and persisted settings.

New here: Project 1 had no files, no dialogs and nothing to lose when it closed. This one has all three.

Specification

  • A two-pane window: editor on the left, rendered preview on the right, a GridSplitter between them.
  • New, Open, Save, Save As, with the standard keyboard shortcuts, on a menu and a toolbar.
  • The window title shows the file name and an asterisk when there are unsaved changes.
  • Closing with unsaved changes prompts Save / Discard / Cancel, and Cancel actually cancels.
  • A recent-files list, persisted between runs.
  • Light and dark themes, switchable at runtime, remembered.

What this teaches

  • Commands and their CanExecute lifecycle. Menu item, toolbar button and KeyBinding share one command, so when Save has nothing to save the menu item and the toolbar button grey out and the shortcut does nothing (Part 6).
  • The async close-confirmation dance from Part 16: Closing cannot usefully await, so you cancel, ask, then close again if allowed.
  • An IDialogService so the view model never touches SaveFileDialog.
  • Runtime theme switching with a swapped merged dictionary (Part 8), which restyles every DynamicResource reference at once.
  • Debouncing the preview, because rendering markdown on every keystroke will feel bad.
  • Persistence of recent files and the theme in a settings file (Part 34).

The dialog service changes how the app starts. Project 1 created its view model in XAML, which only works with a parameterless constructor, and this view model needs the service passed in. Remove StartupUri from App.xaml, override OnStartup in App, and create the window there with new MainWindow { DataContext = new DocumentViewModel(new DialogService()) }.Show(); (Part 2). Your DialogService simply creates a SaveFileDialog itself; the one in Part 16 takes a container, which arrives in Project 3.

The core of the app is knowing whether the document has unsaved changes. In the sketch below, IsDirty drives two things through attributes: the window title, and whether SaveCommand can execute. Any change to Text sets it; a successful save clears it. _dialogs is the dialog service passed to the constructor, which the sketch omits.

C#: the dirty-tracking core 
public partial class DocumentViewModel : ObservableObject
{
    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayTitle))]
    [NotifyCanExecuteChangedFor(nameof(SaveCommand))]
    public partial bool IsDirty { get; set; }

    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayTitle))]
    public partial string? FilePath { get; set; }

    [ObservableProperty] public partial string Text { get; set; }

    public string DisplayTitle =>
        $"{Path.GetFileName(FilePath) ?? "Untitled"}{(IsDirty ? " *" : "")} - Scratchpad";

    partial void OnTextChanged(string value) => IsDirty = true;

    [RelayCommand(CanExecute = nameof(CanSave))]
    private async Task SaveAsync(CancellationToken ct)
    {
        string? path = FilePath ?? _dialogs.PickSaveFile("Markdown|*.md", "Untitled.md");
        if (path is null) return;

        await File.WriteAllTextAsync(path, Text, ct);
        FilePath = path;
        IsDirty = false;
    }

    private bool CanSave() => IsDirty;
}
GOTCHA

OnTextChanged fires on every assignment, including yours. Setting Text in the constructor or after opening a file marks the document dirty, and the title shows an asterisk before the user has typed anything. Clear IsDirty after any assignment that is not a user edit.

GOTCHA

Debounce the preview, not the editor. Bind the editor's Text with UpdateSourceTrigger=PropertyChanged and no Delay: with Delay=250 on that binding, a quick Ctrl+S saves the text without its last keystrokes, and Save may still be disabled. Instead, restart a short timer in the view model on each change: cancel the previous Task.Delay(250) and start a new one. In OnTextChanged that code becomes async void, and the cancelled delay throws, crashing the app on the second keystroke. Catch OperationCanceledException around the delay (Part 17 explains why async void needs it). Read Text after the delay, not before, so the last edit is always the one rendered, and do not add ConfigureAwait(false), so the method resumes on the UI thread.

Render the preview with Markdig to HTML in a WebView2, or with Markdig.Wpf straight to a FlowDocument. The FlowDocument route is more interesting: it exercises Part 21 and keeps everything in one rendering stack.

Steps, in this order

  1. The window layout, with nothing wired up.
  2. The startup in OnStartup and the document view model; bind the title and see the asterisk appear as you type.
  3. The file commands, dialog service and shortcuts.
  4. The close prompt. Test Cancel first.
  5. The preview, then its debounce; then themes and the settings file.

Stretch DEEPER

  • Synchronised scrolling between editor and preview.
  • A Find bar with highlighting, using adorners from Part 24.
  • Drag a .md file onto the window to open it (Part 25).

Checkpoints

  • Cancelling the close prompt keeps the window open and the document intact.
  • Save is disabled when there is nothing to save.
  • Switching theme does not restart the app or lose the document.

Project 3 · Task tracker with a database

Exercises: Parts 7, 10, 12, 13, 15, 33. Also leans on Part 19 for virtualisation, Part 20 for tests and Part 31 for the overdue styling. Time: a week of evenings.

By the end you can structure a layered solution started from a host, store data through EF Core, show it with templates and collection views, validate edits, and test view models without a window.

New here: this is the first project with real architecture: several projects in one solution, a database, a container that builds your objects, and tests. Until now everything fitted in one assembly and was created by hand.

Specification

  • SQLite via EF Core, migrated on startup, stored under %LOCALAPPDATA%.
  • Projects contain tasks. A tree or list on the left, tasks on the right.
  • Tasks have a title, notes, due date, priority, done flag and an optional assignee.
  • Sort by due date, priority or title; group by project; filter by a search box and a "hide completed" toggle.
  • Inline editing with validation: a title is required, a due date cannot be in the past for a new task.
  • Overdue tasks are visually distinct, and not by colour alone.
  • Everything is resolved from a DI container; the shell window is constructed by the host.

Structure to aim for

Split the solution so each layer can only see the ones below it. The domain knows nothing about storage; the data layer knows nothing about WPF; only the app project references WPF. Tasks.App.Tests references that WPF project, so it must target net10.0-windows too, even though its tests need no UI thread.

Solution layout 
Tasks.sln
├─ src/
│  ├─ Tasks.Domain/          # entities, value objects, no dependencies
│  ├─ Tasks.Data/            # DbContext, migrations, repositories
│  ├─ Tasks.App/             # WPF: Views/, ViewModels/, Services/, Themes/
│  └─ Tasks.App/Themes/      # Colors.xaml, Typography.xaml, Controls.xaml
└─ tests/
   ├─ Tasks.Data.Tests/
   └─ Tasks.App.Tests/       # view model tests, no UI thread needed

The important constraint: Tasks.App.ViewModels must not reference System.Windows. A view model that holds a Brush or a Visibility is tied to WPF, so its tests need WPF too, and the boundary erodes one convenient shortcut at a time. Enforce it with an architecture test so it stays true. The test below scans every type in the view model namespace and fails if any property, or any private instance field, has a type from a System.Windows namespace:

C#: a test that protects the boundary 
[Fact]
public void ViewModels_do_not_depend_on_WPF()
{
    var offenders = typeof(TaskListViewModel).Assembly
        .GetTypes()
        .Where(t => t.Namespace?.Contains(".ViewModels") == true)
        .SelectMany(t => t.GetProperties().Select(p => p.PropertyType)
                          .Concat(t.GetFields(BindingFlags.NonPublic | BindingFlags.Instance)
                                   .Select(f => f.FieldType)))
        .Where(t => t.Namespace?.StartsWith("System.Windows") == true)
        .Distinct()
        .ToList();

    Assert.Empty(offenders);
}
GOTCHA

The test matches on namespace, and ICommand lives in System.Windows.Input even though it ships with the base libraries, not WPF. Generated IRelayCommand properties pass; a hand-written ICommand property fails, so exclude that type. The test also ignores generic arguments and nullable wrappers (a Visibility? or List<Brush> property passes), method parameters and locals: it catches drift, not every violation.

Milestones, in this order

  1. Host and DI first. Empty window, resolved from the container, logging to a file. Do not skip ahead; retrofitting this is miserable, because every class that created its own dependencies has to be rewritten to receive them (Part 15).
  2. Domain and data. Entities, DbContext, a migration, a repository returning DTOs (data transfer objects: plain classes that carry values out of the data layer, so view models never hold EF Core entities). Test the repository against an in-memory or temp-file SQLite database.
  3. List and detail. A ListBox or ListView with an ItemTemplate, a ContentControl for the selected task, and implicit DataTemplates wiring view models to views (Part 10): put a view model in a ContentControl and WPF picks its view by type. Avoid a plain ItemsControl for the list: it creates an element for every task.
  4. Sorting, grouping, filtering via ICollectionView (Part 12). Grouping switches virtualisation off unless the list sets VirtualizingPanel.IsVirtualizingWhenGrouping="True" (Part 19). Debounce the search box.
  5. Validation with ObservableValidator and a proper Validation.ErrorTemplate (Part 13).
  6. Polish. Keyboard shortcuts, empty states, a busy indicator bound to Command.IsRunning.

Stretch DEEPER

  • Undo/redo with a command stack.
  • Multi-select with bulk complete and bulk delete (Part 26's IsSelected pattern).
  • Export the current filtered view to CSV and to a printed report (Part 29).

Checkpoints

  • Deleting the database file and restarting recreates it cleanly.
  • Every view model has a test.
  • No view model references a WPF type.
  • The app starts in under a second with 5,000 tasks in the database.

Project 4 · Log viewer

Exercises: Parts 12, 17, 19, 26. Time: a few evenings.

By the end you can keep a UI responsive while it reads, filters and displays far more data than you should hold in memory, arriving faster than anyone can read it.

New here: volume. This is the performance project: everything is about not falling over. Project 3 loaded thousands of rows once; here millions of lines arrive, some while the user scrolls. The architecture is simpler, the difficulty is timing and memory.

Specification

  • Open a log file of at least 500 MB, or tail one that is actively being written.
  • Scrolling stays smooth. Memory does not track file size.
  • Filter by level, by time range and by a substring, with results appearing as you type.
  • Click a line to see the full entry, including a stack trace, in a detail pane.
  • Colour and an icon per level, working in high contrast.

Test data comes first: a small console app that writes a 500 MB log with mixed levels and stack traces, or appends lines continuously for tailing.

The techniques it forces

  • Streaming parse. Read with StreamReader and IAsyncEnumerable, not File.ReadAllLines. ReadAllLines holds the entire file in memory before you show the first line.
  • Batched appends. Buffer incoming lines and flush on a PeriodicTimer every 100 ms, so the UI does its layout and rendering once per tick rather than once per line.
  • Adding from the UI thread, or EnableCollectionSynchronization. Two alternatives, below.
  • Data virtualisation, which the memory checkpoint requires: an IList implementation over a page cache with a line-offset index built on first read. Every entry held in an ObservableCollection costs memory in proportion to the file, so a 500 MB log cannot stay under 300 MB that way. Filter and sort in your own line index (a list of matching line offsets), not with ICollectionView.Filter, which reads every item. A DataGrid also sorts through its collection view when a header is clicked, which reads every item too, so turn off CanUserSortColumns or handle Sorting yourself (Part 26).
  • Once the list is virtualised, the pump appends line offsets to the index and your list raises the add notifications; the batching and lock rules stay the same.
  • Fixed row height and a flat item template, per Part 26.
IN PLAIN TERMS

Batching is how a postal service works. Letters are dropped in a postbox whenever people like, and a van collects them on a fixed round, rather than a courier driving each letter the moment it is posted. The Channel below is the postbox: the reader thread drops parsed entries into it and never touches the collection. The PeriodicTimer is the round: every 100 ms the pump empties the box, up to 2,000 entries, into the collection the grid is bound to.

Channel<T> appears nowhere else in the book: it is a thread-safe queue. PeriodicTimer drove the background service in Part 15; its WaitForNextTickAsync completes once per period, returns false once the timer is disposed, and throws OperationCanceledException when the token is cancelled.

C#: batched ingestion 
private readonly Channel<LogEntry> _incoming =
    Channel.CreateUnbounded<LogEntry>(new UnboundedChannelOptions { SingleReader = true });

private async Task PumpAsync(CancellationToken ct)
{
    var batch = new List<LogEntry>(512);
    using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(100));

    while (await timer.WaitForNextTickAsync(ct))
    {
        batch.Clear();
        while (batch.Count < 2000 && _incoming.Reader.TryRead(out var entry))
            batch.Add(entry);

        if (batch.Count == 0) continue;

        lock (_entriesLock)
            foreach (var entry in batch) Entries.Add(entry);
    }
}

Where the pump runs decides whether the lock matters. Start it from the UI thread and it resumes there after each await, so the adds need no lock. Or run it via Task.Run and register Entries with BindingOperations.EnableCollectionSynchronization, passing the same _entriesLock: a background thread can then append without marshalling every line, and the shared lock lets WPF read the collection safely while you add to it.

GOTCHA

Batching reduces how often the screen updates, not how many change notifications are raised. ObservableCollection<T> raises one event per Add, so 400 lines in a tick are still 400 notifications, handled in one pass. WPF's collection views reject a single notification describing several added items; the only single notification is a reset, and a reset makes the view re-read, re-sort and re-filter the whole list each tick and can drop the selection. For a large, growing log, the one-by-one adds are the right choice.

GOTCHA

A log file being tailed is open for writing by another process. Open it with FileShare.ReadWrite, or opening a live log fails with an IOException.

Steps, in this order

  1. Generate the test files.
  2. Show a small file in a DataGrid or ListView with a fixed row height. In Snoop, only the visible rows should exist.
  3. The streaming parse, the pump, then tailing.
  4. Data virtualisation, to meet the memory checkpoint.
  5. Filtering in the line index, the detail pane and level styling.

Checkpoints

  • Open a 500 MB file: time to first visible line under two seconds, memory under 300 MB.
  • Scroll from top to bottom with no stutter.
  • Tail a file receiving 10,000 lines a second without the UI freezing.

Project 5 · Photo organiser

Exercises: Parts 18, 22, 23, 24, 25. Time: a week.

By the end you can decode images off the UI thread, virtualise a layout WPF does not virtualise for you, implement drag and drop inside the app and from Explorer, and drive transforms from mouse wheel and touch.

New here: pixels and pointers. Each item is now expensive to produce, and users handle items directly rather than through commands.

Specification

  • Point it at a folder; it shows a virtualised thumbnail grid.
  • Thumbnails decode on background threads at the display size, never at full resolution.
  • Drag photos into albums in a sidebar. Drag files in from Explorer to import.
  • A full-screen viewer with pinch/wheel zoom and pan, plus arrow-key navigation.
  • Show EXIF: camera, date taken, exposure. Edit tags and write them back.
  • Non-destructive crop and rotate, stored as metadata, applied on export.

The parts that will hurt, and why that is the point

IN PLAIN TERMS

Most WPF objects belong to the thread that created them, like a whiteboard in one person's office: only that person may write on it or even read it. Calling Freeze() on a bitmap turns it into a printed page. Nobody can change it any more, so anyone, on any thread, can safely look at it. If you need to change a frozen object, you make a copy with Clone(), just as you would photocopy the page.

  • Decode off the UI thread and Freeze(). Part 22. Without freezing, every thumbnail must be created on the UI thread and the grid will jank. Decode with DecodePixelWidth set, and with CacheOption set to OnLoad so the file is closed after reading. Without OnLoad the file stays locked, which is what the last checkpoint tests.
  • WrapPanel does not virtualise. It creates an element for every photo in the folder, visible or not. Use a virtualising wrap panel from a library (the VirtualizingWrapPanel package, for example), or a virtualised ListBox whose rows each hold N thumbnails, recomputing N when the width changes; with rows, selection, dragging and arrow keys work per row rather than per photo until you handle them yourself.
  • A drag ghost is an adorner that follows the cursor. Part 24.
  • Zoom and pan is a MatrixTransform updated from MouseWheel and ManipulationDelta, with the zoom anchored at the cursor rather than the centre. Getting the anchor maths right is a genuine exercise. Manipulation events are raised only once IsManipulationEnabled="True" is set on the element (Part 23).

The handler below zooms 15% per wheel notch. GetPosition gives the cursor in the element's untransformed coordinates, and ScaleAtPrepend scales about that point before the existing transform, so the point under the cursor stays put. The clamp rejects a step below 10% or above 2,000%.

C#: cursor-anchored zoom 
private void OnMouseWheel(object sender, MouseWheelEventArgs e)
{
    var element = (FrameworkElement)sender;
    var transform = (MatrixTransform)element.RenderTransform;
    Matrix m = transform.Matrix;

    double factor = e.Delta > 0 ? 1.15 : 1 / 1.15;
    Point anchor = e.GetPosition(element);      // in unscaled element space

    m.ScaleAtPrepend(factor, factor, anchor.X, anchor.Y);

    // Clamp so the user can't zoom into oblivion
    double scale = Math.Sqrt(Math.Abs(m.M11 * m.M22 - m.M12 * m.M21));
    if (scale is < 0.1 or > 20) return;

    transform.Matrix = m;
    e.Handled = true;
}
GOTCHA

An element's default RenderTransform is the shared, frozen identity transform. The cast in the handler succeeds, but assigning transform.Matrix throws. Give the element its own transform first: <Image.RenderTransform><MatrixTransform /></Image.RenderTransform>.

Steps, in this order

  1. Thumbnails in a plain ListBox, decoded off the UI thread and frozen.
  2. A virtualising wrap layout (a library panel or rows of N), tested with 5,000 photos.
  3. The viewer: arrow keys, then wheel zoom, then pan and touch.
  4. EXIF and tags (Part 22 covers metadata), then albums and import, then crop and rotate.

Stretch DEEPER

  • Write your own virtualising wrap panel by deriving from VirtualizingPanel. It is expert work that no part walks through; read a library panel's source first.

Checkpoints

  • A folder of 5,000 photos scrolls smoothly and stays under 500 MB.
  • Thumbnails appear progressively rather than all at once after a freeze.
  • Deleting a photo from Explorer while the app is running does not crash it or lock the file.

Project 6 · A themed control library

Exercises: Parts 5, 9, 10, 27, 31, 36. Time: a week.

By the end you can write controls other developers restyle without breaking them: dependency and attached properties, template parts, visual states, automation peers, themes, and a NuGet package.

New here: producing rather than consuming, which is where templating stops being theory. Someone else uses your controls without reading the source, so every decision is a contract.

IN PLAIN TERMS

A lookless control keeps its behaviour in code and its appearance entirely in a replaceable template. Think of a light switch: the mechanism in the wall is the control, the faceplate is the template. Anyone can fit a different faceplate and the light still switches. A faceplate with no hole for the toggle is a template that omits a part, and your control must carry on without crashing, even if that feature then does nothing.

Specification

A NuGet-packable library with a coherent theme and at least these controls:

  • Card: a headered container with an optional footer. Three content slots.
  • Badge: a count that animates in and out, with an attached property so it can be applied to any element.
  • NumericBox: value, minimum, maximum, step, increment buttons, culture-correct parsing, paste handling.
  • SegmentedControl: a selector shaped like a set of joined buttons, derived from Selector (in System.Windows.Controls.Primitives: an ItemsControl with selection built in). SelectorAutomationPeer is abstract, so it needs its own automation peer.
  • InfoBar: severity, message, optional action, dismissible.
  • A Themes/Generic.xaml with light and dark variants, honouring the system accent colour.

Requirements that make it real

  • Every control is lookless: a consumer can replace the template without losing behaviour.
  • Every control declares [TemplatePart] and [TemplateVisualState], and tolerates a template that omits a part.
  • Every control has an AutomationPeer exposing the right pattern.
  • Every control works in high contrast.
  • A sample application in the solution demonstrates each control in light, dark and high contrast.

Start from dotnet new wpfcustomcontrollib. It sets up the three pieces a custom control needs, which Part 27 explains: the control class, whose static constructor calls DefaultStyleKeyProperty.OverrideMetadata to point WPF at its default style; that style in Themes/Generic.xaml; and the assembly-level ThemeInfo attribute that tells WPF to look there. Miss any of the three and a control derived from Control renders as nothing, without an error.

The sync design, because it is the hard part

IN PLAIN TERMS

An outbox is a technician's logbook of changes still to phone in. Each change is written in the logbook at the moment it is made, not remembered for later, and the logbook keeps one open line per job: a second change to the same job updates that line rather than starting a new one. When there is signal, the lines are phoned in oldest first and crossed off one by one as the office accepts them. If the technician amends a line while it is being phoned in, it is not crossed off, and the amendment goes out on the next call. If the office says "that job sheet was changed here since you last saw it", the line is not crossed off: that job waits until the technician has looked at both versions and decided, while other jobs carry on.

These rules are what keep a device from losing edits or conflicting with itself; each checkpoint below tests one of them.

  1. One pending entry per record. A new change folds into the record's existing entry and increments its Revision, because a second entry would carry the same stale BaseVersion and conflict with the device's own first edit. An update into a Create stays a Create; a Delete into a Create or an Update becomes a Delete (never just drop the entry: the Create may already be on its way).
  2. The server remembers, per entry Id, the last Revision it applied and the record version that produced. A repeat of an applied Revision gets back the version its first application produced, not the record's current version. A newer Revision of the same Id is accepted (a Create applied as an update) if the record is still at the version that Id last produced, whatever BaseVersion it carries, and a Delete of a record the server never received counts as applied.
  3. The push settles each answer in one conditional step. On acceptance, one transaction deletes the entry where Id and Revision match the Revision sent, and stores the returned version on the local record so the next edit's BaseVersion is current. If nothing was deleted, the entry changed in flight: one conditional update matching Id and the current Revision sets BaseVersion to the returned version and turns a Create into an Update only if the operation is still Create (or use Revision as a concurrency token and retry).
  4. A conflict parks the entry by setting ConflictAt, and later edits fold into it. Keeping the server's version removes the entry and replaces the local record with the server's copy and its version, so the screen stops showing the discarded edit and the next edit does not raise the same conflict. Keeping or merging the technician's edit rewrites PayloadJson and BaseVersion against the server's copy, clears ConflictAt and increments Revision. Either way the step matches the Revision the dialog showed, so an edit folded in while the dialog was open is not overwritten; if the Revision no longer matches, the app shows the dialog again with the newer edit.
  5. The pull never overwrites a local record that has a pending entry. It keeps the server's copy beside it for the conflict dialog only, and discards it when an acceptance deletes the entry, because it is older than the version just stored.

Sync engines fail in timing cases like these. Treat the checkpoints below as the minimum test list, and add a test for every new rule you write.

The sketch below shows the push loop only. It leaves out Revision and operation folding, and its comments ("writes an outbox record", "later edits to this entity wait") describe the simpler version without folding. It does show the two habits the rules rely on: it skips records with a parked conflict, and it saves after every server answer, so only the entry in flight can ever be resent.

C# 
// Every local mutation writes an outbox record in the same transaction as the change.
public sealed class OutboxEntry
{
    public long Id { get; set; }
    public required string EntityType { get; set; }
    public required string EntityId { get; set; }
    public required string Operation { get; set; }   // Create | Update | Delete
    public required string PayloadJson { get; set; }
    public DateTimeOffset QueuedAt { get; set; }
    public int Attempts { get; set; }
    public string? LastError { get; set; }
    public string? BaseVersion { get; set; }         // ETag or rowversion seen when editing
    public DateTimeOffset? ConflictAt { get; set; }  // set when parked; later edits to this entity wait
}

public async Task<SyncOutcome> PushAsync(CancellationToken ct)
{
    await using var db = await _factory.CreateDbContextAsync(ct);
    var pending = await db.Outbox
        .Where(o => !db.Outbox.Any(p => p.ConflictAt != null
                                     && p.EntityType == o.EntityType && p.EntityId == o.EntityId))
        .OrderBy(o => o.Id).Take(50).ToListAsync(ct);

    var conflicts = new List<Conflict>();
    var blocked = new HashSet<(string, string)>();

    foreach (var entry in pending)
    {
        if (blocked.Contains((entry.EntityType, entry.EntityId))) continue;
        try
        {
            var result = await _api.ApplyAsync(entry, ct);   // server dedupes on entry.Id
            if (result.IsConflict)
            {
                conflicts.Add(new Conflict(entry, result.ServerState!));
                entry.LastError = "Changed on the server";
                entry.ConflictAt = DateTimeOffset.UtcNow;
                blocked.Add((entry.EntityType, entry.EntityId));
            }
            else
            {
                db.Outbox.Remove(entry);
            }
            await db.SaveChangesAsync(CancellationToken.None);
        }
        catch (HttpRequestException ex)
        {
            entry.Attempts++;
            entry.LastError = ex.Message;
            await db.SaveChangesAsync(CancellationToken.None);
            break;
        }
    }
    return new SyncOutcome(pending.Count, conflicts);
}

Three rules that separate a sync implementation that works from one that loses data:

  • The outbox write is in the same transaction as the change. Otherwise a crash between the two silently drops an edit.
  • Send the version you edited from. Without it the server cannot detect a conflict and last-writer-wins quietly destroys someone's work.
  • Never auto-resolve. Show the user both versions and let them choose. Users forgive a conflict dialog; they do not forgive vanished data.

Where to go after DEEPER

Having built these, the remaining depth in WPF is in three directions, and each is worth a project of its own:

  • Custom rendering. A node-graph editor or a timeline, built on DrawingVisual with your own hit-testing, virtualisation and spatial index. This is where WPF outperforms every alternative in .NET and where the visual-layer APIs from Part 18 pay off.
  • Extensibility. A plugin host using AssemblyLoadContext, where plugins contribute views, commands and settings pages. Forces you to understand pack URIs, resource dictionaries across assemblies, and isolation.
  • Scale. Take an existing large WPF application and make its slowest screen fast. Profiling, virtualisation, binding audits and template flattening on somebody else's code teaches more about the framework than any amount of greenfield work.
