PART 38

Projects: a route from first window to production

Eight projects, each one adding a layer. Every project names the parts it exercises, gives you a specification rather than a tutorial to copy, and ends with checkpoints you can honestly answer yes or no to. Do them in order; each assumes the last.

HOW TO USE THIS

Do not read the relevant parts first and then build. Start each project, get stuck, then go read. The parts are written to be searched, and the knowledge sticks when it arrives as an answer to a question you already have.

Project 0 · The environment

Exercises: Part 2. Time: 30 minutes.

Before anything else, prove the loop works: edit, build, run, debug, hot reload.

bash 
dotnet new wpf -n Scratch -f net10.0-windows
cd Scratch
dotnet run

# Hot reload while running:
dotnet watch

Then, in order:

  1. Put a Button in the window. Handle Click in code-behind. Breakpoint the handler; confirm the debugger stops.
  2. With dotnet watch running, change a Background in XAML and watch it apply live. Then change a method body and watch that apply too. Then add a new field and watch hot reload refuse — knowing what it can't do saves you restarts.
  3. Install Snoop. Attach it to your running app and walk the visual tree. Find the TextBlock inside your button's template.
  4. Turn on binding trace output: Tools → Options → Debugging → Output Window → WPF Trace Settings → Data Binding → Warning. Add a deliberately broken binding and find the error in the output window.

Checkpoints. Can you attach a debugger to a running WPF app? Can you find any element in the visual tree with Snoop? Do you know where binding errors print?

Project 1 · Unit converter

Exercises: Parts 3, 4, 11, 14. Time: an evening.

The smallest thing that teaches layout and binding properly.

Specification

  • Two text boxes and a category selector: length, mass, temperature.
  • Typing in either box updates the other as you type, not on focus loss.
  • Two combo boxes select the source and target unit within the category.
  • A swap button exchanges the two units and the two values.
  • Invalid input shows a message and does not clear what the user typed.

Build it twice

First in code-behind: event handlers, double.TryParse, direct assignment to TextBox.Text. Get it working. Count the lines.

Then delete the code-behind and rebuild it with a view model. The second version is the lesson.

C# — the shape to aim for 
public partial class ConverterViewModel : ObservableValidator
{
    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(Units))]
    public partial UnitCategory Category { get; set; }

    [ObservableProperty] public partial Unit? From { get; set; }
    [ObservableProperty] public partial Unit? To { get; set; }

    [ObservableProperty] public partial string SourceText { get; set; }

    public IReadOnlyList<Unit> Units => UnitTable.For(Category);

    public string ResultText => TryConvert(out double result)
        ? result.ToString("0.####", CultureInfo.CurrentCulture)
        : "";

    public ConverterViewModel()
    {
        SourceText = "";
        Category = UnitCategory.Length;
        From = Units[0];
        To = Units[1];
    }

    partial void OnSourceTextChanged(string value) => OnPropertyChanged(nameof(ResultText));
    partial void OnFromChanged(Unit? value)        => OnPropertyChanged(nameof(ResultText));
    partial void OnToChanged(Unit? value)          => OnPropertyChanged(nameof(ResultText));

    [RelayCommand]
    private void Swap() => (From, To) = (To, From);
}

Deliberate traps to walk into

  • Bind Text without UpdateSourceTrigger=PropertyChanged first, and notice it only updates on tab-out.
  • Set Background="LightYellow" directly on a TextBox, then add a style trigger that tries to change the background on error. Watch the trigger lose. That is Part 5's precedence list, learned the memorable way.
  • Use StringFormat={0:N2} and see what a Swedish or German locale does to it. Then apply the LanguageProperty.OverrideMetadata fix from Part 30.

Checkpoints. Zero lines in code-behind beyond InitializeComponent. You can explain why a local value beat your trigger. The layout still looks correct when the window is resized to 320×200 and to 1600×1200.

Project 2 · Markdown scratchpad

Exercises: Parts 6, 8, 9, 16, 17. Time: a weekend.

Specification

  • A two-pane window: editor on the left, rendered preview on the right, a GridSplitter between them.
  • New, Open, Save, Save As, with the standard keyboard shortcuts, on a menu and a toolbar.
  • The window title shows the file name and an asterisk when there are unsaved changes.
  • Closing with unsaved changes prompts Save / Discard / Cancel, and Cancel actually cancels.
  • A recent-files list, persisted between runs.
  • Light and dark themes, switchable at runtime, remembered.

What this teaches

Commands and their CanExecute lifecycle; the async close-confirmation dance from Part 16; an IDialogService so the view model never touches SaveFileDialog; runtime theme switching with a swapped merged dictionary; and debouncing, because rendering markdown on every keystroke will feel bad until you add Delay=250.

C# — the dirty-tracking core 
public partial class DocumentViewModel : ObservableObject
{
    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayTitle))]
    [NotifyCanExecuteChangedFor(nameof(SaveCommand))]
    public partial bool IsDirty { get; set; }

    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayTitle))]
    public partial string? FilePath { get; set; }

    [ObservableProperty] public partial string Text { get; set; }

    public string DisplayTitle =>
        $"{Path.GetFileName(FilePath) ?? "Untitled"}{(IsDirty ? " *" : "")} — Scratchpad";

    partial void OnTextChanged(string value) => IsDirty = true;

    [RelayCommand(CanExecute = nameof(CanSave))]
    private async Task SaveAsync(CancellationToken ct)
    {
        string? path = FilePath ?? _dialogs.PickSaveFile("Markdown|*.md", "Untitled.md");
        if (path is null) return;

        await File.WriteAllTextAsync(path, Text, ct);
        FilePath = path;
        IsDirty = false;
    }

    private bool CanSave() => IsDirty;
}

Render the preview with Markdig to HTML in a WebView2, or with Markdig.Wpf straight to a FlowDocument. The FlowDocument route is more interesting: it exercises Part 21 and keeps everything in one rendering stack.

Stretch

  • Synchronised scrolling between editor and preview.
  • A Find bar with highlighting, using adorners from Part 24.
  • Drag a .md file onto the window to open it (Part 25).

Checkpoints. Cancelling the close prompt keeps the window open and the document intact. Save is disabled when there is nothing to save. Switching theme does not restart the app or lose the document.

Project 3 · Task tracker with a database

Exercises: Parts 7, 10, 12, 13, 15, 33. Time: a week of evenings.

This is the first project with real architecture. Everything after it is a variation.

Specification

  • SQLite via EF Core, migrated on startup, stored under %LOCALAPPDATA%.
  • Projects contain tasks. A tree or list on the left, tasks on the right.
  • Tasks have a title, notes, due date, priority, done flag and an optional assignee.
  • Sort by due date, priority or title; group by project; filter by a search box and a "hide completed" toggle.
  • Inline editing with validation: a title is required, a due date cannot be in the past for a new task.
  • Overdue tasks are visually distinct, and not by colour alone.
  • Everything is resolved from a DI container; the shell window is constructed by the host.

Structure to aim for

Solution layout 
Tasks.sln
├─ src/
│  ├─ Tasks.Domain/          # entities, value objects, no dependencies
│  ├─ Tasks.Data/            # DbContext, migrations, repositories
│  ├─ Tasks.App/             # WPF: Views/, ViewModels/, Services/, Themes/
│  └─ Tasks.App/Themes/      # Colors.xaml, Typography.xaml, Controls.xaml
└─ tests/
   ├─ Tasks.Data.Tests/
   └─ Tasks.App.Tests/       # view model tests, no UI thread needed

The important constraint: Tasks.App.ViewModels must not reference System.Windows. Enforce it with an architecture test so it stays true:

C# — a test that protects the boundary 
[Fact]
public void ViewModels_do_not_depend_on_WPF()
{
    var offenders = typeof(TaskListViewModel).Assembly
        .GetTypes()
        .Where(t => t.Namespace?.Contains(".ViewModels") == true)
        .SelectMany(t => t.GetProperties().Select(p => p.PropertyType)
                          .Concat(t.GetFields(BindingFlags.NonPublic | BindingFlags.Instance)
                                   .Select(f => f.FieldType)))
        .Where(t => t.Namespace?.StartsWith("System.Windows") == true)
        .Distinct()
        .ToList();

    Assert.Empty(offenders);
}

Milestones, in this order

  1. Host and DI first. Empty window, resolved from the container, logging to a file. Do not skip ahead; retrofitting this is miserable.
  2. Domain and data. Entities, DbContext, a migration, a repository returning DTOs. Test the repository against an in-memory or temp-file SQLite database.
  3. List and detail. An ItemsControl with an ItemTemplate, a ContentControl for the selected task, and implicit DataTemplates wiring view models to views.
  4. Sorting, grouping, filtering via ICollectionView. Debounce the search box.
  5. Validation with ObservableValidator and a proper Validation.ErrorTemplate.
  6. Polish. Keyboard shortcuts, empty states, a busy indicator bound to Command.IsRunning.

Stretch

  • Undo/redo with a command stack.
  • Multi-select with bulk complete and bulk delete (Part 26's IsSelected pattern).
  • Export the current filtered view to CSV and to a printed report (Part 29).

Checkpoints. Deleting the database file and restarting recreates it cleanly. Every view model has a test. No view model references a WPF type. The app starts in under a second with 5,000 tasks in the database.

Project 4 · Log viewer

Exercises: Parts 12, 17, 19, 26. Time: a few evenings.

The performance project. Everything here is about not falling over.

Specification

  • Open a log file of at least 500 MB, or tail one that is actively being written.
  • Scrolling stays smooth. Memory does not track file size.
  • Filter by level, by time range and by a substring, with results appearing as you type.
  • Click a line to see the full entry, including a stack trace, in a detail pane.
  • Colour and an icon per level, working in high contrast.

The techniques it forces

  • Streaming parse. Read with StreamReader and IAsyncEnumerable, not File.ReadAllLines.
  • EnableCollectionSynchronization so the tail thread can append without marshalling every line.
  • Batched appends. Buffer incoming lines and flush on a PeriodicTimer every 100 ms. One notification for 400 lines instead of 400 notifications.
  • Data virtualisation if you go past what an ObservableCollection can hold: an IList implementation over a page cache with a line-offset index built on first read.
  • Fixed row height and a flat item template, per Part 26.
C# — batched ingestion 
private readonly Channel<LogEntry> _incoming =
    Channel.CreateUnbounded<LogEntry>(new UnboundedChannelOptions { SingleReader = true });

private async Task PumpAsync(CancellationToken ct)
{
    var batch = new List<LogEntry>(512);
    using var timer = new PeriodicTimer(TimeSpan.FromMilliseconds(100));

    while (await timer.WaitForNextTickAsync(ct))
    {
        batch.Clear();
        while (batch.Count < 2000 && _incoming.Reader.TryRead(out var entry))
            batch.Add(entry);

        if (batch.Count == 0) continue;

        lock (_entriesLock)
            foreach (var entry in batch) Entries.Add(entry);
    }
}

Checkpoints. Open a 500 MB file: time to first visible line under two seconds, memory under 300 MB. Scroll from top to bottom with no stutter. Tail a file receiving 10,000 lines a second without the UI freezing.

Project 5 · Photo organiser

Exercises: Parts 18, 22, 23, 24, 25. Time: a week.

Specification

  • Point it at a folder; it shows a virtualised thumbnail grid.
  • Thumbnails decode on background threads at the display size, never at full resolution.
  • Drag photos into albums in a sidebar. Drag files in from Explorer to import.
  • A full-screen viewer with pinch/wheel zoom and pan, plus arrow-key navigation.
  • Show EXIF: camera, date taken, exposure. Edit tags and write them back.
  • Non-destructive crop and rotate, stored as metadata, applied on export.

The parts that will hurt, and why that's the point

  • Decode off the UI thread and Freeze(). Part 22. Without freezing, every thumbnail must be created on the UI thread and the grid will jank.
  • WrapPanel does not virtualise. You will need a virtualising wrap panel — write one by deriving from VirtualizingPanel, or take one from a library and read its source.
  • A drag ghost is an adorner that follows the cursor. Part 24.
  • Zoom and pan is a MatrixTransform updated from MouseWheel and ManipulationDelta, with the zoom anchored at the cursor rather than the centre. Getting the anchor maths right is a genuine exercise.
C# — cursor-anchored zoom 
private void OnMouseWheel(object sender, MouseWheelEventArgs e)
{
    var element = (FrameworkElement)sender;
    var transform = (MatrixTransform)element.RenderTransform;
    Matrix m = transform.Matrix;

    double factor = e.Delta > 0 ? 1.15 : 1 / 1.15;
    Point anchor = e.GetPosition(element);      // in unscaled element space

    m.ScaleAtPrepend(factor, factor, anchor.X, anchor.Y);

    // Clamp so the user can't zoom into oblivion
    double scale = Math.Sqrt(Math.Abs(m.M11 * m.M22 - m.M12 * m.M21));
    if (scale is < 0.1 or > 20) return;

    transform.Matrix = m;
    e.Handled = true;
}

Checkpoints. A folder of 5,000 photos scrolls smoothly and stays under 500 MB. Thumbnails appear progressively rather than all at once after a freeze. Deleting a photo from Explorer while the app is running does not crash it or lock the file.

Project 6 · A themed control library

Exercises: Parts 5, 9, 10, 27, 31. Time: a week.

Producing rather than consuming. This is where templating stops being theory.

Specification

A NuGet-packable library with a coherent theme and at least these controls:

  • Card — a headered container with an optional footer. Three content slots.
  • Badge — a count that animates in and out, with an attached property so it can be applied to any element.
  • NumericBox — value, minimum, maximum, step, increment buttons, culture-correct parsing, paste handling.
  • SegmentedControl — a selector shaped like a set of joined buttons, an ItemsControl under the hood.
  • InfoBar — severity, message, optional action, dismissible.
  • A Themes/Generic.xaml with light and dark variants, honouring the system accent colour.

Requirements that make it real

  • Every control is lookless: a consumer can replace the template without losing behaviour.
  • Every control declares [TemplatePart] and [TemplateVisualState], and tolerates a template that omits a part.
  • Every control has an AutomationPeer exposing the right pattern.
  • Every control works in high contrast.
  • A sample application in the solution demonstrates each control in light, dark and high contrast.

Checkpoints. Install your own package into a fresh WPF app from a local feed and use it without reading the source. Replace one control's template entirely in the consuming app and confirm the behaviour survives. Accessibility Insights reports no errors on the sample app.

The sync design, because it is the hard part

C# 
// Every local mutation writes an outbox record in the same transaction as the change.
public sealed class OutboxEntry
{
    public long Id { get; set; }
    public required string EntityType { get; set; }
    public required string EntityId { get; set; }
    public required string Operation { get; set; }   // Create | Update | Delete
    public required string PayloadJson { get; set; }
    public DateTimeOffset QueuedAt { get; set; }
    public int Attempts { get; set; }
    public string? LastError { get; set; }
    public string? BaseVersion { get; set; }         // ETag or rowversion seen when editing
}

public async Task<SyncOutcome> PushAsync(CancellationToken ct)
{
    await using var db = await _factory.CreateDbContextAsync(ct);
    var pending = await db.Outbox.OrderBy(o => o.Id).Take(50).ToListAsync(ct);

    var conflicts = new List<Conflict>();

    foreach (var entry in pending)
    {
        try
        {
            var result = await _api.ApplyAsync(entry, ct);
            if (result.IsConflict)
            {
                // Do NOT discard the user's work. Park it and let them decide.
                conflicts.Add(new Conflict(entry, result.ServerState!));
                entry.LastError = "Changed on the server";
                continue;
            }
            db.Outbox.Remove(entry);
        }
        catch (HttpRequestException)
        {
            entry.Attempts++;
            break;                     // stop the batch; we're offline
        }
    }

    await db.SaveChangesAsync(ct);
    return new SyncOutcome(pending.Count, conflicts);
}

Three rules that separate a sync implementation that works from one that loses data:

  • The outbox write is in the same transaction as the change. Otherwise a crash between the two silently drops an edit.
  • Send the version you edited from. Without it the server cannot detect a conflict and last-writer-wins quietly destroys someone's work.
  • Never auto-resolve. Show the user both versions and let them choose. Users forgive a conflict dialog; they do not forgive vanished data.

Where to go after

Having built these, the remaining depth in WPF is in three directions, and each is worth a project of its own:

  • Custom rendering. A node-graph editor or a timeline, built on DrawingVisual with your own hit-testing, virtualisation and spatial index. This is where WPF outperforms every alternative in .NET and where the visual-layer APIs from Part 18 pay off.
  • Extensibility. A plugin host using AssemblyLoadContext, where plugins contribute views, commands and settings pages. Forces you to understand pack URIs, resource dictionaries across assemblies, and isolation.
  • Scale. Take an existing large WPF application and make its slowest screen fast. Profiling, virtualisation, binding audits and template flattening on somebody else's code teaches more about the framework than any amount of greenfield work.
