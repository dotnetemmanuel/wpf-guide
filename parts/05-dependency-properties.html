PART 05

Dependency properties

The single most important idea in WPF, and the one with no equivalent in the rest of .NET.

Builds on Part 3, XAML precisely and Part 4, layout, where the custom panel's Radius was a first glimpse of one.

IN PLAIN TERMS

An ordinary C# property holds one value, and whoever set it last wins. In WPF, many parties have an opinion about a button's background: you, a style, the theme, a running animation. A dependency property keeps every one of those opinions and shows the highest-ranked one, like a thermostat where a manual override beats the weekly schedule, which beats the factory setting. Remove the override and the schedule is back in charge without anyone re-entering it.

Precisely: a dependency property is a property whose value is computed from many possible sources, ranked by a fixed order called precedence, and stored only when something actually sets it.

Why they exist

A Button has several hundred properties. Storing a field for each, on every button in a grid of ten thousand rows, would be ruinous. Instead, a dependency property is a static registration shared by the type, and values are stored per-instance in a sparse table: an entry exists only for properties that were actually set. A button that sets three properties pays for three.

Sparse storage is the cheap benefit. The real benefit is that the framework can participate in the value. Styles, templates, animations, inheritance from the parent element, and data bindings all set values without fighting each other, because each is a distinct source at a distinct precedence.

Declaring one

A dependency property has two halves. The identifier is a public static readonly DependencyProperty field, created once per type by DependencyProperty.Register; name it after the property plus Property, because designers and parts of the property system rely on that convention. The CLR wrapper is an ordinary C# property whose getter and setter just call GetValue and SetValue with that identifier, so your own C# code can write bar.Value = 3.

Registration also takes metadata: the default value, flags that tell WPF what a change affects, and optional callbacks. Here is a complete declaration for a rating control. Notice the flags (a change must repaint the control, and bindings to it are two-way unless told otherwise) and the three callbacks, which are covered straight after:

C# 
public class RatingBar : Control
{
    public static readonly DependencyProperty ValueProperty =
        DependencyProperty.Register(
            name:         nameof(Value),
            propertyType: typeof(int),
            ownerType:    typeof(RatingBar),
            typeMetadata: new FrameworkPropertyMetadata(
                defaultValue:     0,
                flags:            FrameworkPropertyMetadataOptions.AffectsRender |
                                  FrameworkPropertyMetadataOptions.BindsTwoWayByDefault,
                propertyChangedCallback: OnValueChanged,
                coerceValueCallback:     CoerceValue),
            validateValueCallback: v => v is int i && i >= 0);

    // The CLR wrapper is a convenience only. WPF NEVER calls it:
    // XAML and binding go straight to SetValue/GetValue.
    public int Value
    {
        get => (int)GetValue(ValueProperty);
        set => SetValue(ValueProperty, value);
    }

    private static void OnValueChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        var bar = (RatingBar)d;
        bar.RaiseEvent(new RoutedEventArgs(ValueChangedEvent, bar));
    }

    private static object CoerceValue(DependencyObject d, object baseValue)
    {
        var bar = (RatingBar)d;
        return Math.Clamp((int)baseValue, 0, bar.Maximum);
    }
}
GOTCHA

Never put logic in the CLR wrapper. Put it in the PropertyChangedCallback. The wrapper is bypassed entirely when the value is set from XAML, from a style, from an animation, or from a binding, which is most of the time.

The three callbacks fire in a fixed order and do different jobs:

  • ValidateValueCallback: static, no instance access, returns bool. Throws ArgumentException on false. Use for "no negative sizes ever".
  • CoerceValueCallback: has the instance, so it can clamp against another property. Use for "Value must not exceed Maximum". Call CoerceValue(ValueProperty) from Maximum's changed callback so the clamp re-runs.
  • PropertyChangedCallback: fires only when the effective value actually changed. Where your side effects go.
IN PLAIN TERMS

Validation is a form field that rejects a negative number outright: the value never gets in. Coercion is a speed limiter: ask for 150 with a limit of 120 and you get 120, but the car remembers you asked for 150. Raise the limit and re-run coercion, and you are back at 150 without asking again. The changed callback is the dashboard light that comes on only when the speed you are actually doing changes.

Value precedence

Precedence is what decides the winner when several sources set the same property. The figure shows the case that trips up almost everyone: two identical buttons with the same hover trigger (a rule in a style or template that sets a property while a condition holds, here while the mouse is over the button), where only one reacts.

Here is the full order, highest first. Memorise it; almost every "why isn't my style applying" question is answered here.

#Source
1Property system coercion
2Active animations, or a held animation
3Local value: SetValue, an attribute in XAML, or a Binding you wrote directly on the element
4TemplatedParent template properties (triggers in the template, then setters)
5Implicit style (a Style keyed by {x:Type}): this rank applies only to the Style property itself, picking which style the element gets; that style's triggers then rank at row 6 and its setters at row 8
6Style triggers
7Template triggers (from the ControlTemplate)
8Style setters
9Theme style triggers
10Theme style setters
11Property value inheritance (FontSize, DataContext, FlowDirection…)
12Default value from metadata

A few terms in that table: a local value is one set directly on this particular element rather than arriving from a style or template. Triggers, introduced above, are covered fully in Part 9. The theme style is the default look WPF ships for each control.

The practical consequences:

  • A local value beats every style and trigger. Set Background="Red" on a button and no IsMouseOver trigger will ever change it. This is the single most common WPF confusion. Fix it by moving the value into the style's setters.
  • An animation beats a local value and keeps beating it after the animation finishes, unless the animation has FillBehavior="Stop". Call BeginAnimation(prop, null) to release the hold.
  • Clearing is not setting to default. ClearValue(prop) removes the local value and lets the next source win; SetValue(prop, default) installs a local value that happens to equal the default and continues to block styles.

Attached properties

Some settings belong to a relationship rather than to an element. Which grid row a text box sits in means nothing to the text box; only the Grid around it cares. Giving TextBox a Row property, and a Dock property, and a Left property for every panel that might ever contain it, would not scale.

An attached property is a dependency property registered by one type and set on instances of another. Grid.Row is the canonical example: the Grid owns it, but you set it on the child.

IN PLAIN TERMS

An attached property is a sticky note. Grid.Row="2" sticks a note saying "row 2" on the text box. The text box carries the note around but never reads it; the Grid reads the notes on its children when it lays them out. Any element can carry notes from any owner, which is why one text box can have Grid.Row, ToolTipService.ShowDuration and your own notes at the same time.

Declaring your own looks like a normal dependency property, with RegisterAttached and a pair of static Get/Set methods in place of the wrapper. This one shows a watermark hint in any TextBox it is attached to; the changed callback is where it hooks into the text box's events:

C# 
public static class Watermark
{
    public static readonly DependencyProperty TextProperty =
        DependencyProperty.RegisterAttached(
            "Text", typeof(string), typeof(Watermark),
            new FrameworkPropertyMetadata(null, OnTextChanged));

    public static void SetText(DependencyObject element, string value)
        => element.SetValue(TextProperty, value);

    public static string GetText(DependencyObject element)
        => (string)element.GetValue(TextProperty);

    private static void OnTextChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not TextBox box) return;
        box.GotFocus  -= Repaint;  box.GotFocus  += Repaint;
        box.LostFocus -= Repaint;  box.LostFocus += Repaint;
        Repaint(box, EventArgs.Empty);
    }

    private static void Repaint(object? sender, EventArgs e) { /* swap an adorner in/out */ }
}

Using it from XAML is one attribute on the element:

XAML 
<TextBox local:Watermark.Text="Search tasks…" />

The Get/Set static methods are not optional: the XAML parser finds the property by convention from those names. This pattern is how you add behaviour to a sealed framework control without subclassing, and it is the basis of attached behaviours: attached properties whose changed callback subscribes to the element's events, so that setting the property switches a behaviour on.

Attached behaviours in practice DEEPER

This section leans on commands and routed events (Part 6), styles (Part 9) and bindings (Part 11). Come back to it once those are familiar.

A frequent need: give an untouchable third-party control a command-on-double-click. No subclass required. When the property is set, the callback subscribes to MouseDoubleClick; when the user double-clicks, the handler runs the command with the element's data as the parameter:

C# 
public static class DoubleClick
{
    public static readonly DependencyProperty CommandProperty =
        DependencyProperty.RegisterAttached(
            "Command", typeof(ICommand), typeof(DoubleClick),
            new PropertyMetadata(null, OnCommandChanged));

    public static void SetCommand(DependencyObject d, ICommand? v) => d.SetValue(CommandProperty, v);
    public static ICommand? GetCommand(DependencyObject d) => (ICommand?)d.GetValue(CommandProperty);

    private static void OnCommandChanged(DependencyObject d, DependencyPropertyChangedEventArgs e)
    {
        if (d is not Control c) return;
        c.MouseDoubleClick -= Handle;
        if (e.NewValue is not null) c.MouseDoubleClick += Handle;
    }

    private static void Handle(object sender, MouseButtonEventArgs e)
    {
        var c = (Control)sender;
        var command = GetCommand(c);
        var parameter = (c as FrameworkElement)?.DataContext;
        if (command?.CanExecute(parameter) == true) command.Execute(parameter);
    }
}

Set through a style, the property lands on every item container the list creates. The binding reaches up to the ListBox to find the command on the view model:

XAML 
<ListBox ItemsSource="{Binding Items}">
  <ListBox.ItemContainerStyle>
    <Style TargetType="ListBoxItem">
      <Setter Property="local:DoubleClick.Command"
              Value="{Binding DataContext.OpenCommand, RelativeSource={RelativeSource AncestorType=ListBox}}" />
    </Style>
  </ListBox.ItemContainerStyle>
</ListBox>

The packaged alternative is Microsoft.Xaml.Behaviors.Wpf, which gives you EventTrigger + InvokeCommandAction declaratively, turning any event into a command call without writing a class:

XAML 
xmlns:b="http://schemas.microsoft.com/xaml/behaviors"
...
<ListBox ItemsSource="{Binding Items}">
  <b:Interaction.Triggers>
    <b:EventTrigger EventName="SelectionChanged">
      <b:InvokeCommandAction Command="{Binding SelectionChangedCommand}"
                             PassEventArgsToCommand="True" />
    </b:EventTrigger>
  </b:Interaction.Triggers>
</ListBox>

Read-only and inherited properties

Two variations come up often. A read-only dependency property is one that outside code can read and bind to, but only the owning class can set, such as a busy indicator the control manages itself. An inherited property is one whose value flows down to every descendant element unless one of them sets its own.

For read-only, registration returns a DependencyPropertyKey. Keep the key private (it is the permission to write) and expose the ordinary identifier publicly. For inheritance, add the Inherits flag; registering it as attached lets the value pass reliably through elements of any type:

C# 
// Read-only: expose the key privately, the property publicly.
private static readonly DependencyPropertyKey IsBusyPropertyKey =
    DependencyProperty.RegisterReadOnly(
        nameof(IsBusy), typeof(bool), typeof(Shell), new PropertyMetadata(false));

public static readonly DependencyProperty IsBusyProperty = IsBusyPropertyKey.DependencyProperty;

public bool IsBusy
{
    get => (bool)GetValue(IsBusyProperty);
    private set => SetValue(IsBusyPropertyKey, value);   // note: the KEY
}

// Inheritable: flows down the logical tree to every descendant.
public static readonly DependencyProperty DensityProperty =
    DependencyProperty.RegisterAttached(
        "Density", typeof(Density), typeof(Theme),
        new FrameworkPropertyMetadata(
            Density.Comfortable,
            FrameworkPropertyMetadataOptions.Inherits));

Inheritance is how FontSize set on a Window reaches a TextBlock six levels down, and how DataContext reaches every binding in a subtree. It is not free, because inherited properties invalidate a whole subtree on change, so use the flag deliberately.

RECAP
  • A dependency property keeps values from many sources and shows the one with the highest precedence.
  • Its C# wrapper is skipped by XAML, styles, bindings and animations, so put logic in the changed callback, never in the wrapper.
  • A value set directly on an element beats every style and trigger; move it into the style if a trigger must change it.
  • ClearValue hands control back to styles, while setting the default value keeps blocking them.
  • Attached properties let a parent such as Grid store its settings on the child elements it lays out.
  • Inherited properties such as FontSize and DataContext flow down the tree until something sets its own value.
