PART 03

XAML, precisely

XAML is an object graph serialisation format. Every element is a type, every attribute is a property or an event, and the whole document is a constructor call tree. Once you see it that way the odd corners stop being odd.

Builds on Part 2, project setup and startup, which shows how the build turns a .xaml file into a class.

Markup is a way of writing objects

You could build every window in C#: create a panel, create a button, set its properties, add it to the panel. For a real screen that code becomes long, deeply nested and hard to read, and a designer tool cannot edit it. XAML exists so you can write the same object tree as nested markup instead.

Precisely, XAML is a serialisation format: a text form of objects that can be turned back into those objects. An element such as <Button> means "create an instance of the Button class"; an attribute such as Width="80" means "set its Width property"; nesting means "put this object inside that one". These two snippets produce identical objects:

XAML 
<StackPanel>
  <Button Content="Save" Width="80" />
</StackPanel>
C#, the same objects 
var panel = new StackPanel();
var button = new Button { Content = "Save", Width = 80 };
panel.Children.Add(button);
IN PLAIN TERMS

XAML is a recipe, not a picture. Nothing in it is drawn directly: each line is an instruction to create an object or set a value, carried out in order when the window loads. When some markup puzzles you, ask what C# it would turn into; the answer is almost always the explanation.

Namespaces

Markup only names types, such as Button, so the parser needs to know which Button you mean and in which assembly to find it. An XML namespace declaration (xmlns) answers that: it maps a prefix to a set of .NET namespaces. Every WPF file starts with a block of them on its root element:

XAML 
<Window
  xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
  xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
  xmlns:sys="clr-namespace:System;assembly=System.Runtime"
  xmlns:vm="clr-namespace:Tasks.ViewModels"
  xmlns:ctrl="clr-namespace:Tasks.Controls"
  xmlns:b="http://schemas.microsoft.com/xaml/behaviors"
  xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
  xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
  mc:Ignorable="d"
  d:DataContext="{d:DesignInstance vm:MainViewModel}">
  • The default namespace (the xmlns with no prefix) maps to every WPF UI assembly at once, via XmlnsDefinition attributes on those assemblies. That is why <Button> needs no prefix.
  • The x: namespace is the XAML language itself: x:Class, x:Name, x:Key, x:Type, x:Static, x:Array, x:Null.
  • clr-namespace: maps your own types. <vm:MainViewModel /> then means the class in Tasks.ViewModels. The ;assembly= part is only needed for types outside the current assembly.
  • d: and mc:Ignorable="d" are design-time only; the compiler strips them. d:DataContext gives the designer and IntelliSense a type to bind against, which is how you get autocomplete on binding paths.

Property syntax, three ways

Attributes are strings, but properties have real types: a margin is a Thickness, a background is a Brush. XAML gives you three ways to set a property, depending on whether the value fits in a short string, needs a whole object, or is the element's main content:

XAML 
<!-- 1. attribute syntax: value goes through a TypeConverter -->
<Button Background="SteelBlue" Margin="4,8" />

<!-- 2. property element syntax: for values that aren't expressible as a string -->
<Button>
  <Button.Background>
    <LinearGradientBrush StartPoint="0,0" EndPoint="0,1">
      <GradientStop Offset="0" Color="#3B6FD4" />
      <GradientStop Offset="1" Color="#22458A" />
    </LinearGradientBrush>
  </Button.Background>
</Button>

<!-- 3. content syntax: the type's [ContentProperty] takes the children implicitly -->
<Button>                         <!-- Button's ContentProperty is Content -->
  <StackPanel Orientation="Horizontal">
    <Path Data="M0,0 L8,4 L0,8 Z" Fill="White" Width="8" Height="8" />
    <TextBlock Text="Run" Margin="6,0,0,0" />
  </StackPanel>
</Button>

A type converter is a class that turns a string into a value of some type. "4,8" becoming a Thickness and "SteelBlue" becoming a SolidColorBrush are both TypeConverter work. Your own types get the same treatment if you attribute them with [TypeConverter(typeof(MyConverter))].

The third form relies on [ContentProperty], an attribute on the class that names which property receives child elements written directly inside it. For Button that is Content; for panels it is Children, which is why the StackPanel example at the top of this part needed no <StackPanel.Children> wrapper.

Markup extensions

A plain attribute value is fixed when you write it. Many values are not known then: a colour defined in a shared resource file, a value read from a static field, a property that should follow your view model as it changes. Markup extensions cover those cases.

Anything in braces is a markup extension: an object that is constructed at parse time and asked to provide a value for the property. They are not string interpolation.

IN PLAIN TERMS

Type =B2 into a spreadsheet cell and the cell does not store the text "=B2"; it asks for a value and shows that. Braces in XAML work the same way. Some extensions behave like pasting a value ({StaticResource} is looked up once and never again), while {Binding} behaves like a live formula that updates when its source changes. The comparison stops at recalculation: most extensions run once, and only the ones that create a binding or resource reference stay live.

The ones you will use constantly:

ExtensionDoes
{Binding}Creates a live binding to a source property. Part 11.
{StaticResource k}One-time lookup at load time. Fast. Fails hard if the key is missing.
{DynamicResource k}Live lookup that re-evaluates if the resource is replaced. Slower, and only valid on dependency properties.
{x:Static local:Config.Version}Reads a static field, property or enum member.
{x:Type Button}A Type object. Needed for TargetType, DataType.
{x:Null}Literal null: the only way to say "no brush" rather than "a brush named Null".
{TemplateBinding P}Inside a ControlTemplate, a fast one-way binding to the templated parent's P.
{RelativeSource ...}Not standalone: a binding source specifier. Part 11.

"Only valid on dependency properties" refers to WPF's special kind of property, explained in Part 5. Nearly every property you set on a control is one.

Writing your own markup extension DEEPER

Writing your own is a two-method job: a constructor that receives the text after the name, and ProvideValue, which returns the value. This one looks up a localised string by key, and because it runs in the designer as well as in the app, it shows real text at design time too:

C# 
[MarkupExtensionReturnType(typeof(string))]
public sealed class LocExtension : MarkupExtension
{
    public LocExtension() { }
    public LocExtension(string key) => Key = key;

    [ConstructorArgument("key")]
    public string Key { get; set; } = "";

    public override object ProvideValue(IServiceProvider serviceProvider)
    {
        // serviceProvider gives you IProvideValueTarget, IRootObjectProvider,
        // IXamlTypeResolver and friends if you need context.
        return Localisation.Current[Key] ?? $"!{Key}!";
    }
}

In markup, you drop the Extension suffix from the class name, just as with C# attributes. Commands.Save is passed to the constructor as the key:

XAML 
xmlns:loc="clr-namespace:Tasks.Localisation"
...
<Button Content="{loc:Loc Commands.Save}" />

x:Name versus Name, and escaping

You give an element a name so your code-behind can reach it as a field, or so other markup can refer to it. There are two ways to spell that, and they overlap.

Name is a real CLR property on FrameworkElement; x:Name is the XAML-level directive. On a FrameworkElement they do the same thing and you cannot set both. On an object with no Name property of its own, such as a RotateTransform or a SolidColorBrush you want to animate, only x:Name works. Default to x:Name and stop thinking about it.

Because braces, commas and whitespace mean something to the parser, some literal values need escaping. The escapes you will hit:

XAML 
<!-- literal braces: escape with an empty pair -->
<TextBlock Text="{}{not a binding}" />

<!-- comma inside a markup extension parameter: quote it -->
<TextBlock Text="{Binding Total, StringFormat='{}{0:N2} kr'}" />

<!-- whitespace preservation -->
<TextBlock xml:space="preserve">  indented  </TextBlock>

<!-- null, not an empty string: the TextBlock shows nothing -->
<TextBlock Text="{x:Null}" />
GOTCHA

StringFormat needs a leading {} whenever the format string itself starts with {, otherwise the parser sees a markup extension. StringFormat='{}{0:N2}' works; StringFormat='{0:N2}' throws at load.

Loading XAML at runtime DEEPER

Normally all XAML is compiled into your assembly. Sometimes the markup only exists once the app is running: user-supplied templates, or report layouts stored in a database. XamlReader.Parse turns such a string into objects on the spot.

Note the security exposure: XamlReader can instantiate arbitrary types, so never feed it markup from a source you do not trust. The example builds a list item template from a string and applies it:

C# 
const string markup = """
    <DataTemplate xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation">
      <TextBlock Text="{Binding Title}" FontWeight="SemiBold" />
    </DataTemplate>
    """;

var template = (DataTemplate)XamlReader.Parse(markup);
listBox.ItemTemplate = template;

The markup must declare its own namespaces, because it is parsed on its own with no surrounding file to inherit them from.

RECAP
  • Every XAML element creates an object and every attribute sets a property, exactly as the equivalent C# would.
  • Namespace declarations tell the parser where to find types; the unprefixed one covers all of WPF, and clr-namespace: covers your own code.
  • Simple values are converted from strings, complex values use property element syntax, and child elements go to the content property.
  • Anything in braces is a markup extension that supplies a value when the markup loads, and only some of them stay live afterwards.
  • Prefer x:Name over Name, and escape a leading brace with {}.
