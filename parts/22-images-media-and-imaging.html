PART 22

Images, media and imaging

Images are where WPF apps most often waste memory without anyone noticing. This part covers loading pictures at the size you show them, where image files belong in the project, producing and editing bitmaps in code, reading photo metadata, and playing sound and video.

Builds on Part 8, resources and Part 17, threading and async (freezable objects).

Loading images correctly

Picture a photo browser with a grid of two hundred thumbnails. It works on your test folder of small images, then a user points it at their camera roll and memory climbs past a gigabyte.

The cause is decoding. To decode an image is to unpack the compressed file (JPEG, PNG) into a grid of pixels in memory, four bytes per pixel. The naive <Image Source="photo.jpg" /> decodes at full resolution regardless of display size. For a 4000×3000 photo shown in a 120px thumbnail that is roughly 48 MB of pixels per image. DecodePixelWidth fixes it.

IN PLAIN TERMS

Showing a full-size photo in a thumbnail is like printing a wall poster and then looking at it from across the room: it looks the same as a postcard would, but you paid for the poster. Image scales the picture down for display, yet the memory holds every original pixel. DecodePixelWidth asks for the postcard-sized print in the first place.

The XAML below declares the bitmap explicitly so you can set its decoding options. Set the first two on almost every image from a file; add the third when the file at that path can change.

XAML 
<Image Width="120" Height="90">
  <Image.Source>
    <BitmapImage UriSource="{Binding PhotoPath}"
                 DecodePixelWidth="240"
                 CacheOption="OnLoad"
                 CreateOptions="IgnoreImageCache" />
  </Image.Source>
</Image>
SettingWhy
DecodePixelWidthDecode at this width only. Set it to roughly 2× the display size for high-DPI headroom. Set one dimension; the other follows.
CacheOption="OnLoad"Read the whole stream immediately and close the file. Without it the file stays locked and you cannot delete or overwrite it.
CreateOptions="IgnoreImageCache"Bypass WPF's URI-keyed cache. Needed when the file at a path changes and you want the new content.

In code, the same settings go between BeginInit and EndInit. This version reads from a stream you open and close yourself, so the file is not held open once the method returns. The last step is freezing the bitmap: Freeze() makes it permanently read-only, and a frozen object can be used from any thread. CacheOption = OnLoad is required here, not optional: the stream is closed as soon as the method returns, so the bitmap must have read every byte by then.

C#: loading from a stream without locking the file 
public static BitmapImage LoadThumbnail(string path, int width)
{
    using var stream = File.OpenRead(path);
    var bmp = new BitmapImage();
    bmp.BeginInit();
    bmp.CacheOption = BitmapCacheOption.OnLoad;
    bmp.DecodePixelWidth = width;
    bmp.StreamSource = stream;
    bmp.EndInit();
    bmp.Freeze();        // safe to hand to the UI thread from a background thread
    return bmp;
}

Because the result is frozen, this whole method can run on a thread-pool thread. That is how you build a responsive photo grid: decode in the background, hand the frozen bitmaps to the UI.

Build actions for images

An image you add to the project has to end up somewhere the running app can find it. The build action, set in the file's properties, decides where it goes: inside the compiled assembly, or as a loose file next to it. That in turn decides which pack URI reaches it; a pack URI is WPF's address format for files that belong to the application.

Build actionResultURI
ResourceEmbedded in the assembly. Default and usually right.pack://application:,,,/Assets/icon.png or /Assets/icon.png
Content + copyLoose file beside the exe.pack://application:,,,/Assets/icon.png (listed at build time), or pack://siteoforigin:,,,/Assets/icon.png for files added after the build
EmbeddedResourceCLR resource. Not reachable by pack URI: it needs GetManifestResourceStream. Avoid for images.No pack URI
IN PLAIN TERMS

Resource and EmbeddedResource both put the image inside the same DLL, which is why they are so easy to confuse. The difference is which compartment. Resource files go into the compartment WPF's pack URIs search; EmbeddedResource files go into the general .NET one, which WPF does not look in. The image is there either way, but only one of them can be found by Source="/Assets/icon.png".

Encoding, screenshots and pixel work DEEPER

Sometimes you need to produce an image rather than show one: export a chart, save a thumbnail, attach a screenshot of a form to a bug report. An encoder turns pixels in memory into a file format; a decoder does the reverse.

The method below renders any element into a RenderTargetBitmap, an off-screen bitmap you can draw a visual into, at the DPI you choose, then saves it as PNG. Pass 192 for a double-resolution image.

C#: render any element to a PNG 
public static void SaveElementAsPng(FrameworkElement element, string path, double dpi = 96)
{
    double scale = dpi / 96.0;
    var rtb = new RenderTargetBitmap(
        (int)Math.Ceiling(element.ActualWidth  * scale),
        (int)Math.Ceiling(element.ActualHeight * scale),
        dpi, dpi, PixelFormats.Pbgra32);

    // Render through a VisualBrush so element transforms and margins are respected.
    var visual = new DrawingVisual();
    using (var dc = visual.RenderOpen())
    {
        dc.DrawRectangle(new VisualBrush(element), null,
            new Rect(new Point(), new Size(element.ActualWidth, element.ActualHeight)));
    }
    rtb.Render(visual);

    var encoder = new PngBitmapEncoder();
    encoder.Frames.Add(BitmapFrame.Create(rtb));
    using var fs = File.Create(path);
    encoder.Save(fs);
}

Encoders available out of the box: PngBitmapEncoder, JpegBitmapEncoder (with QualityLevel), BmpBitmapEncoder, GifBitmapEncoder, TiffBitmapEncoder, WmpBitmapEncoder. Decoders mirror them, and BitmapDecoder.Create sniffs the format.

For generated images (a heat map, a waveform, a paint canvas) you want to set pixels yourself. WriteableBitmap gives you direct access to its memory. The pattern is always the same: lock, write into the back buffer, mark the changed area with AddDirtyRect, unlock.

IN PLAIN TERMS

A WriteableBitmap keeps two copies of its pixels: a back buffer you write into, and the copy the screen shows. It works like editing a draft while readers see the last published version. Lock gives you the draft, AddDirtyRect marks which part you changed, and Unlock publishes. Only the marked area is copied across, so a change outside it stays unseen until a later dirty rectangle covers it.

The loop fills every pixel with one colour. Each pixel is four bytes in blue, green, red, alpha order, and each row is BackBufferStride bytes long, which can be more than width times four.

C#: WriteableBitmap for direct pixel access 
var wb = new WriteableBitmap(width, height, 96, 96, PixelFormats.Bgra32, null);

wb.Lock();
try
{
    unsafe
    {
        var buffer = (byte*)wb.BackBuffer;
        int stride = wb.BackBufferStride;
        for (int y = 0; y < height; y++)
        for (int x = 0; x < width; x++)
        {
            int i = y * stride + x * 4;
            buffer[i + 0] = blue;
            buffer[i + 1] = green;
            buffer[i + 2] = red;
            buffer[i + 3] = 255;          // alpha: fully opaque
        }
    }
    wb.AddDirtyRect(new Int32Rect(0, 0, width, height));
}
finally { wb.Unlock(); }

Requires <AllowUnsafeBlocks>true</AllowUnsafeBlocks> in the project file. The safe alternative is wb.WritePixels(rect, array, stride, offset), which copies: fine for occasional updates, too slow for per-frame work.

Reading metadata DEEPER

A photo app that sorts by date taken or shows the camera model needs EXIF data: the facts a camera writes into the image file alongside the pixels. BitmapMetadata exposes the common fields as properties. For anything else, GetQuery takes a path into the metadata; 34855 is the EXIF tag number for ISO speed.

The creation and cache options ask the decoder to do no work up front, which keeps reading metadata cheap. Note that DateTaken is a string, hence the parse.

C# 
using var fs = File.OpenRead(path);
var decoder = BitmapDecoder.Create(fs, BitmapCreateOptions.DelayCreation,
                                       BitmapCacheOption.OnDemand);
var frame = decoder.Frames[0];

if (frame.Metadata is BitmapMetadata meta)
{
    string? camera = meta.CameraModel;
    DateTime? taken = DateTime.TryParse(meta.DateTaken, out var d) ? d : null;
    var tags = meta.Keywords;
    // Raw EXIF by path:
    object? iso = meta.GetQuery("/app1/ifd/exif/subifd:{uint=34855}");
}

Audio and video

MediaElement plays audio and video files. Declare it in XAML, then drive it from code or leave it to play on its own. Setting LoadedBehavior="Manual" is what hands control to your code, and the three events tell you when the media is ready, finished or broken.

XAML 
<MediaElement x:Name="Player"
              Source="{Binding VideoPath}"
              LoadedBehavior="Manual"
              UnloadedBehavior="Stop"
              ScrubbingEnabled="True"
              Stretch="Uniform"
              MediaOpened="OnOpened"
              MediaEnded="OnEnded"
              MediaFailed="OnFailed" />

With that in place, playback is a few calls. NaturalDuration is only known once the media has opened, which is why the code checks HasTimeSpan.

C# 
Player.Play();
Player.Pause();
Player.Position = TimeSpan.FromSeconds(30);
double seconds = Player.NaturalDuration.HasTimeSpan
    ? Player.NaturalDuration.TimeSpan.TotalSeconds : 0;
GOTCHA

Set LoadedBehavior to Manual before you drive playback with Play(), Pause() or Position. With the default, Play, the element runs the media itself and does not take instructions: Play(), Pause() and Stop() throw NotSupportedException unless LoadedBehavior or UnloadedBehavior is Manual. MediaElement also wraps Windows Media Player codecs, so format support depends on the machine and there is no error until MediaFailed fires. For anything serious, host LibVLCSharp.WPF or a WebView2 instead.

For short UI sounds, skip MediaElement entirely:

C# 
SystemSounds.Exclamation.Play();                      // system sounds
new SoundPlayer(@"Assets\ding.wav").Play();           // WAV only, fire and forget
RECAP
  • Set DecodePixelWidth on images shown smaller than their real size, or each one costs its full resolution in memory.
  • Use CacheOption="OnLoad" so loading an image does not lock the file.
  • Frozen bitmaps can be decoded on a background thread and handed to the UI.
  • Give image files the Resource build action; EmbeddedResource cannot be reached by a pack URI.
  • MediaElement needs LoadedBehavior="Manual" before code can control playback.
