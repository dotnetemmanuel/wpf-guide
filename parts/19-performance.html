PART 19

Performance

WPF is fast until you accidentally turn off the thing making it fast. Most performance work is removing mistakes rather than adding optimisations.

Builds on Part 11, data binding, Part 12, collections and views, Part 17, threading and async (freezables) and Part 18, graphics and animation.

Virtualisation: the six ways to break it

Bind a list to 40,000 rows and, done right, it opens instantly and scrolls smoothly. Done wrong, the window takes seconds to appear and uses hundreds of megabytes, because WPF has built every row, including the 39,988 nobody can see.

Each row in a ListBox is wrapped in a container, a ListBoxItem holding that row's expanded template. Virtualisation means creating containers only for the rows in view, plus a small margin, and creating or reusing more as you scroll. A container that exists is said to be realised.

IN PLAIN TERMS

A virtualised list is like a station departure board with a dozen slots. Scrolling changes what the slots say; nobody builds a board for every train of the year. The trick depends on the board knowing how many slots fit. Give it unlimited height, as a StackPanel does, and it concludes every row is visible and builds them all.

A ListBox virtualises by default: only visible containers exist. Each of these silently disables it, or never turns it on:

  1. Putting the list inside a StackPanel (or any container that gives infinite space in the scroll direction). The list gets as tall as its content and never scrolls, so everything is "visible".
  2. Replacing ItemsPanel with a non-virtualising panel: StackPanel, WrapPanel, UniformGrid.
  3. Setting ScrollViewer.CanContentScroll="False", which switches to pixel-based scrolling and materialises everything.
  4. Grouping without VirtualizingPanel.IsVirtualizingWhenGrouping="True".
  5. Using a plain ItemsControl. Its default panel is a StackPanel, its template has no ScrollViewer, and content scrolling is off, so it never virtualises until you give it a VirtualizingStackPanel, a ScrollViewer in its template and ScrollViewer.CanContentScroll="True".
  6. Filling the list with UI elements, such as ListBoxItems written out in XAML or added to Items. Each one is its own container, so all of them exist from the start and none can be recycled.

A source that is not an IList still virtualises containers, but WPF copies every item into its own list first.

The safest habit is to state every setting explicitly, so a later change to a style or template cannot quietly undo it:

XAML: explicit and correct 
<ListBox ItemsSource="{Binding Rows}"
         VirtualizingPanel.IsVirtualizing="True"
         VirtualizingPanel.VirtualizationMode="Recycling"
         VirtualizingPanel.ScrollUnit="Pixel"
         VirtualizingPanel.CacheLength="1,2"
         VirtualizingPanel.CacheLengthUnit="Page"
         VirtualizingPanel.IsVirtualizingWhenGrouping="True"
         ScrollViewer.IsDeferredScrollingEnabled="False">
  <ListBox.ItemsPanel>
    <ItemsPanelTemplate>
      <VirtualizingStackPanel />
    </ItemsPanelTemplate>
  </ListBox.ItemsPanel>
</ListBox>

What each line asks for: virtualisation on; containers reused rather than rebuilt; smooth scrolling by pixels while still virtualising; one page of containers kept ready above the view and two below (CacheLength is before, after); virtualisation kept when grouping; the content updated live while the scroll thumb is dragged, rather than only when it is released; and VirtualizingStackPanel as the panel, already the default, stated so that a style cannot swap in one that does not virtualise.

VirtualizationMode="Recycling" reuses containers instead of creating and discarding them, which is the single biggest win. In the default Standard mode, a row scrolled out of view has its container thrown away and a new one built for the row coming in. Recycling is not the default for historical compatibility reasons, so set it explicitly every time.

The other common costs

Once lists virtualise, the remaining costs are usually one of these. The visual tree in them means every element actually created on screen, with all templates expanded.

  • Unfrozen freezables. Every unfrozen brush carries change tracking so it can notify whatever uses it. Freeze all static brushes, pens and geometries.
  • Deep visual trees. A template with eight nested Borders multiplied across 5,000 rows is 40,000 elements. Flatten templates used in item containers ruthlessly.
  • Binding to properties without change notification. WPF falls back to PropertyDescriptor subscriptions, which leak and are slow. If the source is a plain CLR object with no INotifyPropertyChanged, either add it or set Mode=OneTime.
  • DynamicResource everywhere. Each one keeps a live lookup. Use it only where the value actually changes.
  • Layout thrash, meaning layout forced to run again and again over large parts of the tree. Changing an inherited property (FontSize) on a root element invalidates the whole tree. Changing Visibility from Collapsed to Visible forces measure on the whole subtree. Opacity and IsHitTestVisible are cheaper if you just want it hidden, though keyboard focus can still reach an element hidden that way.
  • Text rendering. TextOptions.TextFormattingMode="Display" makes small text crisper at 100% DPI; Ideal (the default) is better at high DPI. TextRenderingMode="ClearType" vs Grayscale matters over remote desktop.

Some content is expensive to draw but rarely changes, such as a detailed diagram behind an interactive layer. You can ask WPF to rasterise it, turning its vector drawing into a bitmap, once, and reuse the bitmap until the content changes:

XAML: caching an expensive static subtree 
<Canvas>
  <Canvas.CacheMode>
    <BitmapCache RenderAtScale="1" SnapsToDevicePixels="True" />
  </Canvas.CacheMode>
  <!-- a complex, rarely-changing diagram -->
</Canvas>

BitmapCache rasterises a subtree once and reuses the bitmap. Excellent for static decoration that is transformed or scrolled; harmful for anything that redraws, since you pay for re-rasterising every frame.

Memory leaks

.NET collects objects nobody references, so a WPF leak is always something still holding a reference you forgot about. You notice it as memory that climbs every time a screen is opened and closed. Three sources, in order of frequency:

  1. Event handlers on long-lived objects. A view model subscribing to a singleton service's event is never collected. Use WeakReferenceMessenger, or unsubscribe in a dispose or deactivate hook.
  2. Bindings to non-INotifyPropertyChanged sources. The PropertyDescriptor fallback roots the source object for the application's lifetime.
  3. DataContext retained by a cached Window. Windows you Hide() instead of Close() keep their whole view model graph alive.
IN PLAIN TERMS

Subscribing to an event hands the publisher your phone number. As long as the publisher keeps that number, the garbage collector sees your object as still in use, even after its screen is gone. A service that lives as long as the app is a publisher that never throws a number away. A weak event subscription lets the publisher still call you, without holding your number counting as a reason to keep you alive.

When you cannot unsubscribe at the right moment and cannot change the publisher, subscribe through WeakEventManager:

C# 
// The weak event pattern, for when you can't control the publisher's lifetime.
WeakEventManager<ITaskRepository, TaskChangedEventArgs>
    .AddHandler(_repo, nameof(ITaskRepository.TaskChanged), OnTaskChanged);

Measuring

Guessing at performance problems wastes time; these tools show you where the cost is.

  • Visual Studio's WPF Tree Visualizer and the live visual tree, for element counts and "why is that 400px wide".
  • Snoop, the community tool that has outlived every alternative. Inspect and edit any running WPF app's visual tree, watch binding errors live, profile the visual tree size.
  • PerfView or dotnet-trace for allocation and JIT.
  • RenderCapability.Tier, checked at startup and logged (shift it right by 16 to get 0, 1 or 2, as Part 18 explains), so you know when a user is on software rendering.
RECAP
  • A virtualised list builds only the rows you can see, and one placed in a StackPanel builds them all.
  • Set VirtualizationMode="Recycling" on every large list, because it is not the default.
  • Freeze static brushes and geometries, and keep item templates shallow.
  • Bind only to objects that raise change notifications, or bind them one time.
  • Most leaks are event subscriptions to objects that outlive the screen.
  • Measure with the live visual tree, Snoop or a profiler before changing anything.
