PART 24

Popups, menus, tooltips and adorners

Dropdowns, flyouts, context menus and tooltips all float above the window. Most are built on one primitive, Popup, and most of their surprises come from the fact that each one lives in a window of its own. Adorners are the other way to draw on top: inside the same window, in a layer above the content.

Builds on Part 6, routed events and commands, Part 9, styles and triggers and Part 11, data binding.

Popup: the primitive under everything floating

A filter dropdown near the bottom of a small window is useless if it is cut off at the window's edge. WPF avoids that by giving every popup its own operating-system window.

Popup creates a separate top-level HWND, the Win32 handle of a real window. That is why it can extend past the window edge. It is also why it ignores window clipping, and stays put when the window moves. Its DataContext can also fail to reach it in some situations: when the popup is not in the element tree, because it was created in code or set as a property value. The gotcha below covers the fix.

IN PLAIN TERMS

A popup is a sticky note stuck on the glass of your monitor rather than something drawn on the page underneath. Because it is on the glass, it can hang over the edge of the window and nothing on the page clips it. It is also why dragging the window away leaves the note where it was: it was never attached to the page.

The example is a Filters toggle button that opens a small panel of check boxes. IsOpen is bound two-way to the button's IsChecked, so clicking the button opens the popup, and a click outside that closes it also unchecks the button.

XAML 
<ToggleButton x:Name="Toggle" Content="Filters" />

<Popup IsOpen="{Binding IsChecked, ElementName=Toggle, Mode=TwoWay}"
       PlacementTarget="{Binding ElementName=Toggle}"
       Placement="Bottom"
       HorizontalOffset="0" VerticalOffset="4"
       StaysOpen="False"
       AllowsTransparency="True"
       PopupAnimation="Fade"
       Focusable="False">
  <Border Background="{DynamicResource SurfaceBrush}"
          BorderBrush="{DynamicResource BorderBrush}" BorderThickness="1"
          CornerRadius="6" Padding="12"
          Effect="{StaticResource PopupShadow}">
    <StackPanel>
      <CheckBox Content="Only open" IsChecked="{Binding OnlyOpen}" />
      <CheckBox Content="Assigned to me" IsChecked="{Binding Mine}" />
    </StackPanel>
  </Border>
</Popup>
PropertyWhy it matters
StaysOpen="False"Closes on an outside click. Without it the popup is sticky and users hate it.
AllowsTransparency="True"Required for rounded corners, shadows, or any non-rectangular shape.
PlacementBottom, Right, Mouse, Relative, Custom. Custom takes a CustomPopupPlacementCallback for flip-and-fit logic.
Focusable="False"Keeps keyboard focus on the opener, which is usually what a filter or picker flyout wants.
GOTCHA

A Popup is not a visual child of the element you declared it under, so it inherits DataContext through the logical tree only. If your bindings inside a popup resolve to nothing, set the DataContext explicitly: DataContext="{Binding PlacementTarget.DataContext, RelativeSource={RelativeSource Self}}". Popups also stay behind when the window moves, in every placement mode, because moving a window triggers no layout pass. Close the popup when the window moves, or in the window's LocationChanged handler change HorizontalOffset and set it back, which forces the popup to reposition.

Context menus

A right-click menu on each row of a list, with Open and Delete running commands on your view model, is one of the most common requests in WPF, and one of the most common binding failures.

A ContextMenu is shown in a popup, so it is not part of the visual tree of the element you right-clicked. Bindings that search upward for an ancestor, or name an element elsewhere in the window, find nothing. The menu does receive the clicked element's DataContext, so a plain {Binding} inside it sees the item. Its one link back to the window is its PlacementTarget: the element it was opened for.

IN PLAIN TERMS

Most bindings find their data by walking up the tree of elements, from child to parent, until they reach what they need. A context menu sits in its own small tree, so that walk stops at the menu. WPF does hand the menu the clicked item's data, so a plain binding to the item still works. Anything beyond the item, such as the list's view model, has to be fetched across the one link back, PlacementTarget.

Here the menu is set per item through the item container style, and the commands live on the list's view model, not on each item. The style first copies the ListBox's DataContext into each item's Tag. Inside the menu, the RelativeSource finds the ContextMenu, and PlacementTarget.Tag steps across to the clicked ListBoxItem and reads that view model. CommandParameter="{Binding}" needs no hop: the menu already has the item as its data.

XAML 
<ListBox ItemsSource="{Binding Items}">
  <ListBox.ItemContainerStyle>
    <Style TargetType="ListBoxItem">
      <Setter Property="Tag"
              Value="{Binding DataContext, RelativeSource={RelativeSource AncestorType=ListBox}}" />
      <Setter Property="ContextMenu">
        <Setter.Value>
          <ContextMenu>
            <MenuItem Header="_Open"
                      Command="{Binding PlacementTarget.Tag.OpenCommand,
                                        RelativeSource={RelativeSource AncestorType=ContextMenu}}"
                      CommandParameter="{Binding}" />
            <Separator />
            <MenuItem Header="_Delete"
                      Command="{Binding PlacementTarget.Tag.DeleteCommand,
                                        RelativeSource={RelativeSource AncestorType=ContextMenu}}"
                      CommandParameter="{Binding}"
                      InputGestureText="Del" />
          </ContextMenu>
        </Setter.Value>
      </Setter>
    </Style>
  </ListBox.ItemContainerStyle>
</ListBox>

The PlacementTarget hop is the standard escape from a context menu's separate visual tree. Tag is a spare property every element has, which makes it a convenient carrier: here it holds the ListBox's DataContext, and the menu reaches it through PlacementTarget.Tag.

InputGestureText is display-only. It prints the shortcut in the menu but does not bind it; you still need an InputBinding.

Menus driven by data DEEPER

Plugin systems, recent-file lists and user-configurable toolbars need menus built from data rather than written in XAML. You bind ItemsSource to a list of menu view models, each with a header, children and a command, and map those onto the generated MenuItems with a style. A trigger turns items flagged as separators into a plain line.

XAML 
<Menu ItemsSource="{Binding MenuItems}">
  <Menu.ItemContainerStyle>
    <Style TargetType="MenuItem">
      <Setter Property="Header"           Value="{Binding Header}" />
      <Setter Property="ItemsSource"      Value="{Binding Children}" />
      <Setter Property="Command"          Value="{Binding Command}" />
      <Setter Property="CommandParameter" Value="{Binding Parameter}" />
      <Setter Property="IsCheckable"      Value="{Binding IsCheckable}" />
      <Setter Property="IsChecked"        Value="{Binding IsChecked, Mode=TwoWay}" />
      <Style.Triggers>
        <DataTrigger Binding="{Binding IsSeparator}" Value="True">
          <Setter Property="Template">
            <Setter.Value>
              <ControlTemplate><Separator /></ControlTemplate>
            </Setter.Value>
          </Setter>
        </DataTrigger>
      </Style.Triggers>
    </Style>
  </Menu.ItemContainerStyle>
</Menu>

Using ItemContainerStyle rather than ItemTemplate is deliberate here. For each data item, the menu generates a MenuItem as its container, the element that wraps the item. The style sets properties on that container; a template would only fill its header. A MenuItem must be the container for submenus and keyboard navigation to work. Templating the content instead produces a menu item containing a menu item, which behaves oddly.

Tooltips

A tooltip that appears too slowly, vanishes while someone is still reading, or never shows on a disabled button is worse than none. The ToolTipService attached properties tune all of that per element, and the tooltip itself can hold any content, not only a string.

XAML 
<Button Content="Export"
        ToolTipService.InitialShowDelay="400"
        ToolTipService.ShowDuration="20000"
        ToolTipService.BetweenShowDelay="0"
        ToolTipService.ShowOnDisabled="True"
        ToolTipService.Placement="Bottom">
  <Button.ToolTip>
    <ToolTip>
      <StackPanel MaxWidth="260">
        <TextBlock Text="Export to CSV" FontWeight="SemiBold" />
        <TextBlock TextWrapping="Wrap" Opacity=".8"
                   Text="Writes the current filtered view, not the whole table." />
      </StackPanel>
    </ToolTip>
  </Button.ToolTip>
</Button>

ShowOnDisabled="True" is the useful one: a disabled button that explains why it's disabled is worth a dozen support tickets.

Adorners

Sometimes you need to draw on top of a control without moving anything around it: a red border on a field with an error, a count badge on an icon, resize handles on a selected shape. Putting those in the layout would push neighbouring controls aside.

An adorner is a visual drawn in a separate layer on top of its adorned element. It does not participate in layout, so it can overflow without changing anything. Validation error visuals, drag ghosts, resize handles and focus rectangles are all adorners. The layer that holds them is the adorner layer, supplied by an AdornerDecorator somewhere above the element.

IN PLAIN TERMS

An adorner layer is a sheet of tracing paper laid over a form. You can draw a red badge that pokes past the edge of a text box, and the form underneath does not shift at all. The analogy has one catch: the tracing paper covers everything under that decorator, so what you draw sits above every control there, not just the one you meant to mark.

The adorner below draws a red badge with a label at the top-right corner of its element. OnRender is called with a drawing context, and IsHitTestVisible = false lets clicks pass through the badge to the control.

C# 
public sealed class BadgeAdorner : Adorner
{
    private readonly string _text;
    private readonly Brush _fill = Brushes.Firebrick;
    private readonly Typeface _face = new("Segoe UI");

    public BadgeAdorner(UIElement adorned, string text) : base(adorned)
    {
        _text = text;
        IsHitTestVisible = false;    // let clicks through to the control underneath
    }

    protected override void OnRender(DrawingContext dc)
    {
        var size = AdornedElement.RenderSize;

        var text = new FormattedText(_text, CultureInfo.CurrentUICulture,
            FlowDirection.LeftToRight, _face, 10, Brushes.White,
            VisualTreeHelper.GetDpi(this).PixelsPerDip);

        double r = Math.Max(8, text.Width / 2 + 6);
        var centre = new Point(size.Width - 2, 2);

        dc.DrawEllipse(_fill, null, centre, r, 8);
        dc.DrawText(text, new Point(centre.X - text.Width / 2, centre.Y - text.Height / 2));
    }
}

To show it, find the element's adorner layer, remove any badge already there so they do not stack, and add a new one.

C#: attaching and removing 
public static void ShowBadge(UIElement element, string text)
{
    var layer = AdornerLayer.GetAdornerLayer(element);
    if (layer is null) return;                       // no AdornerDecorator in the tree

    foreach (var existing in layer.GetAdorners(element)?.OfType<BadgeAdorner>() ?? [])
        layer.Remove(existing);

    layer.Add(new BadgeAdorner(element, text));
}
GOTCHA

AdornerLayer.GetAdornerLayer returns null when there is no AdornerDecorator above the element. A Window's default template has one; Popup, ToolTip, ContextMenu and custom window templates often do not. If adorners vanish inside a flyout, wrap its content in <AdornerDecorator>. Adorners also do not clip to the adorned element and are rendered above everything in that layer, including content you'd expect to be on top.

RECAP
  • A Popup is its own window, so it can overflow the main window but does not move with it.
  • Set StaysOpen="False" so a popup closes when the user clicks elsewhere.
  • Inside a context menu, a plain binding sees the clicked item; anything beyond it, such as the list's view model, goes through PlacementTarget.
  • InputGestureText only displays a shortcut; an InputBinding makes it work.
  • Set ToolTipService.ShowOnDisabled so disabled controls can explain themselves.
  • Adorners draw above an element without affecting layout, and need an AdornerDecorator above them.
