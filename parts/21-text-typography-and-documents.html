PART 21

Text, typography and documents

Most of any screen is text. WPF gives you a few text controls of very different weight, a typography engine that most of .NET lacks, and a document model for anything longer than a sentence. This part shows which to use, and the handful of details that make text look wrong when you miss them.

Builds on Part 7, the control content model, Part 8, resources and Part 9, styles and triggers.

TextBlock, Label, TextBox: which and why

WPF has several controls that show text, and they are not interchangeable. Use the heavy one everywhere and a long list carries a template and extra elements for every caption. Use the light one where a user needs to copy a value and they cannot select it. The table sorts them by job.

ControlBaseUse for
TextBlockFrameworkElementRead-only text. Lightest of the three: no template, no content model. The default choice.
LabelContentControlText with an access key that focuses another control (Target). Heavier; use it only when you need _Access keys.
TextBoxControlEditable. Set IsReadOnly rather than using a TextBlock when you want selectable text.
AccessTextFrameworkElementInside templates, renders _ as an underlined mnemonic.

An access key (also called a mnemonic) is the underlined letter that lets a keyboard user jump to a control with Alt plus that letter. You mark it with an underscore before the letter in the text.

A TextBlock is also more than a string. Its content is a collection of inlines: pieces of text that flow along the same lines but each carry their own formatting. A Run is a stretch of plain text, Span groups runs under shared formatting, LineBreak ends a line and Hyperlink is a clickable span.

IN PLAIN TERMS

Think of a sentence in a word processor where you made one word bold and another a link. It is still one sentence that wraps as a whole, but inside it are stretches of text with different formatting. Inlines are those stretches. What it does not hold is controls laid out the way a panel lays them out: a button sits in the sentence wrapped in an InlineUIContainer (XAML adds the wrapper for you when you put a control directly inside), where it flows like one oversized word.

The snippet shows both ideas. The Label's underscore makes R its access key, and Target says which control receives focus. The TextBlock mixes a bound bold run, a line break, a link and an italic span. LineStackingStrategy="BlockLineHeight" makes every line exactly the LineHeight you set, instead of growing to fit the tallest piece of text on it.

XAML 
<!-- Label with a mnemonic that focuses the box -->
<Label Content="_Registration number" Target="{Binding ElementName=RegBox}" />
<TextBox x:Name="RegBox" />

<!-- TextBlock's content property is Inlines: runs and spans; a control is wrapped in an InlineUIContainer -->
<TextBlock TextWrapping="Wrap" LineHeight="20" LineStackingStrategy="BlockLineHeight">
  <Run Text="Saved to " />
  <Run Text="{Binding FileName}" FontWeight="SemiBold" />
  <LineBreak />
  <Hyperlink NavigateUri="{Binding FolderUri}" RequestNavigate="OnNavigate">
    Open containing folder
  </Hyperlink>
  <Span FontStyle="Italic" Foreground="{DynamicResource MutedBrush}">
    <Run Text=" (read only)" />
  </Span>
</TextBlock>

Hyperlink does not open a browser by itself: it only raises RequestNavigate, and outside a navigation host nobody answers. Handle the event and start the browser yourself. UseShellExecute = true is what lets Windows pick the default browser for a URL; on modern .NET it defaults to false, and starting a URL without it fails.

C# 
private void OnNavigate(object sender, RequestNavigateEventArgs e)
{
    Process.Start(new ProcessStartInfo(e.Uri.AbsoluteUri) { UseShellExecute = true });
    e.Handled = true;
}
GOTCHA

Run.Text is bindable, but the whitespace between <Run> elements is significant and easy to lose. Writing each Run on its own line collapses the newline to a single space. That is usually what you want, occasionally not. Use xml:space="preserve" on the TextBlock if exact spacing matters.

Typography

A column of prices only lines up if every digit has the same width. Body text reads better with ligatures and proper fractions. Good fonts carry these alternatives inside the font file as OpenType features: optional variants of the letters and figures that an app has to ask for by name. WPF exposes the full OpenType feature set, which almost nothing else in .NET does.

The first TextBlock below switches features on through the Typography attached properties. The second sets TextOptions, which control how glyphs (the drawn shapes of the letters) are rendered, including where they land on the pixel grid and how their edges are anti-aliased, rather than which glyphs are chosen.

XAML 
<TextBlock FontFamily="Cambria" FontSize="15"
           Typography.NumeralStyle="OldStyle"
           Typography.NumeralAlignment="Tabular"
           Typography.StandardLigatures="True"
           Typography.DiscretionaryLigatures="False"
           Typography.Kerning="True"
           Typography.Fraction="Slashed"
           Text="1/2 kg, 1 234,50 kr" />

<!-- Rendering hints that matter for small UI text -->
<TextBlock TextOptions.TextFormattingMode="Display"
           TextOptions.TextRenderingMode="ClearType"
           TextOptions.TextHintingMode="Fixed"
           Text="Dense grid label" />

TextFormattingMode="Display" snaps glyph metrics to whole pixels. That is sharper for small text on 100% DPI displays, and worse for scaling and animation. Ideal, the default, keeps sub-pixel metrics and is correct on high-DPI screens. If your users are on 1080p at 100%, switch to Display app-wide and the UI immediately looks less blurry.

IN PLAIN TERMS

Ideal places each letter exactly where the font designer intended, even when that falls a third of the way between two pixels. The screen then shades both pixels, which reads as soft edges on small text at low resolution. Display nudges each letter onto whole pixels: crisper, but the spacing moves slightly. Text that grows or slides then visibly jumps from pixel to pixel instead of moving smoothly.

Embedding a font

Your users will not have your chosen font installed. Ship it inside the assembly: give the font files the Resource build action, point a FontFamily at them with a pack URI, and set it on the window. Keep the FontFamily resource in App.xaml: a StaticResource in the window's own attributes is resolved before the window's Resources are read, so it could not see a key defined there.

csproj + XAML 
<ItemGroup>
  <Resource Include="Assets\Fonts\Inter-Regular.ttf" />
  <Resource Include="Assets\Fonts\Inter-SemiBold.ttf" />
</ItemGroup>

<!-- App.xaml, inside Application.Resources -->
<!-- The # is followed by the font's FAMILY name, not the file name -->
<FontFamily x:Key="UiFont">pack://application:,,,/Assets/Fonts/#Inter</FontFamily>

<!-- MainWindow.xaml: FontFamily is inherited by everything inside the window -->
<Window x:Class="Tasks.MainWindow" FontFamily="{StaticResource UiFont}">
  ...
</Window>

The trailing slash before # is required and the name after it is the family name recorded inside the file, which is often not the filename. If the font doesn't appear, that mismatch is almost always why.

IN PLAIN TERMS

A font file has a filename, like Inter-SemiBold.ttf, and inside it a family name, like Inter, much as a music file can be called track07.mp3 while its tags name the album. The part before # tells WPF which folder to search; the part after it is the family name WPF compares with what each file says inside. Several files can share one family name, which is how Regular and SemiBold become one family with two weights.

The snippet sets the font on the <Window> element itself, not through a Window style. An implicit style applies only to elements of exactly its target type, and your window's real type is MainWindow, so a style for Window never reaches it (a style for Control misses Button and TextBox the same way). FontFamily is inherited: everything inside the window picks it up unless something overrides it. The theme styles for Menu, ContextMenu, ToolTip and StatusBar do override it with the system font, so give those their own style.

FlowDocument: rich text and reading views

A TextBlock is fine for a sentence. Release notes with headings, a bulleted list and a table, or an invoice someone may print, need text that rewraps when the window resizes and can be cut into pages.

A FlowDocument is WPF's model for that: a paginated, reflowable document built from headings, paragraphs, lists, tables, figures and floaters. It is the right tool for release notes, help pages, generated reports and anything print-shaped. Its content is made of blocks, elements that stack vertically (Paragraph, List, Table), and the blocks contain the same inlines a TextBlock uses.

IN PLAIN TERMS

A FlowDocument is closer to a web page than to a PDF. You describe the content in order (a heading, a paragraph, a list) and the viewer decides where lines and pages break, based on the space it has. Narrow the window and the text rewraps; switch the viewer to page mode and the same content is cut into pages. Unlike a PDF, nothing about the final positions is fixed until it is shown.

You always show a FlowDocument inside a host. Three hosts display one, and RichTextBox edits one:

HostBehaviour
FlowDocumentScrollViewerContinuous scroll. The one you usually want in an app.
FlowDocumentPageViewerPaginated, one page at a time.
FlowDocumentReaderLets the user switch between one page, two pages side by side and continuous scroll, plus a search bar and zoom. Heavy.
RichTextBoxEditable FlowDocument.

The example builds release notes in XAML. Notice that every piece of text sits in a Paragraph, even inside a list item or a table cell: list items and cells hold blocks, not bare text.

XAML 
<FlowDocumentScrollViewer VerticalScrollBarVisibility="Auto">
  <FlowDocument ColumnWidth="400" FontFamily="Georgia" FontSize="14">
    <Paragraph FontSize="20" FontWeight="Bold" Margin="0,0,0,8">
      Release 4.2
    </Paragraph>
    <Paragraph>
      The importer now streams rather than buffering. See
      <Hyperlink NavigateUri="https://example.invalid/notes">the notes</Hyperlink>.
    </Paragraph>
    <List MarkerStyle="Disc">
      <ListItem><Paragraph>Fixed clipboard on .NET 9</Paragraph></ListItem>
      <ListItem><Paragraph>Added dark theme</Paragraph></ListItem>
    </List>
    <Table CellSpacing="0">
      <Table.Columns>
        <TableColumn Width="2*" /><TableColumn Width="*" />
      </Table.Columns>
      <TableRowGroup>
        <TableRow Background="#EEE">
          <TableCell><Paragraph>Setting</Paragraph></TableCell>
          <TableCell><Paragraph>Default</Paragraph></TableCell>
        </TableRow>
      </TableRowGroup>
    </Table>
  </FlowDocument>
</FlowDocumentScrollViewer>
GOTCHA

FlowDocument is not a FrameworkElement and its content is not bindable the way element trees are. There is no ItemsSource. To generate one from data you build it in code, or bind the viewer's Document property to a FlowDocument your view model produced. That technically drags a presentation type (a class that belongs to the UI layer) into the view model, so most teams put the builder in a service returning FlowDocument.

Here is such a builder. It takes plain data and returns a finished document: a heading paragraph, then a two-column table with one row per invoice line. ColumnWidth = double.PositiveInfinity matters when the document is paginated or printed; left at its default, a wide page is split into several narrow newspaper-style columns.

C#: building one from data 
public static FlowDocument BuildInvoice(Invoice invoice)
{
    var doc = new FlowDocument
    {
        FontFamily = new FontFamily("Segoe UI"),
        FontSize = 12,
        PagePadding = new Thickness(48),
        ColumnWidth = double.PositiveInfinity,   // single column
    };

    doc.Blocks.Add(new Paragraph(new Run($"Invoice {invoice.Number}"))
    {
        FontSize = 22, FontWeight = FontWeights.Bold, Margin = new Thickness(0, 0, 0, 16)
    });

    var table = new Table { CellSpacing = 0 };
    table.Columns.Add(new TableColumn { Width = new GridLength(3, GridUnitType.Star) });
    table.Columns.Add(new TableColumn { Width = new GridLength(1, GridUnitType.Star) });

    var body = new TableRowGroup();
    foreach (var line in invoice.Lines)
    {
        var row = new TableRow();
        row.Cells.Add(new TableCell(new Paragraph(new Run(line.Description))));
        row.Cells.Add(new TableCell(new Paragraph(new Run(line.Amount.ToString("C", invoice.Culture))))
        {
            TextAlignment = TextAlignment.Right
        });
        body.Rows.Add(row);
    }
    table.RowGroups.Add(body);
    doc.Blocks.Add(table);

    return doc;
}

RichTextBox and persisting formatted text DEEPER

A RichTextBox lets users write formatted text, and sooner or later you need to save what they wrote and load it back. Both go through a TextRange: a stretch of the document between two positions. ContentStart to ContentEnd covers everything; Selection is the range the user has highlighted.

The code saves and loads the whole document as XAML, reads the selected text and makes the selection bold. XAML keeps every WPF formatting detail. Pass DataFormats.Rtf instead when the text has to open in other programs such as Word.

C# 
// Save the whole document as XAML (lossless) or RTF (portable)
public static string ToXaml(RichTextBox box)
{
    var range = new TextRange(box.Document.ContentStart, box.Document.ContentEnd);
    using var ms = new MemoryStream();
    range.Save(ms, DataFormats.Xaml);
    return Encoding.UTF8.GetString(ms.ToArray());
}

public static void LoadXaml(RichTextBox box, string xaml)
{
    var range = new TextRange(box.Document.ContentStart, box.Document.ContentEnd);
    using var ms = new MemoryStream(Encoding.UTF8.GetBytes(xaml));
    range.Load(ms, DataFormats.Xaml);
}

// Plain text of the current selection
string selected = box.Selection.Text;

// Apply formatting to the selection
box.Selection.ApplyPropertyValue(TextElement.FontWeightProperty, FontWeights.Bold);

DataFormats.XamlPackage is the third option: XAML plus embedded images in a single container. Use it when users paste screenshots.

RECAP
  • Use TextBlock for read-only text, Label only when you need an access key, and a read-only TextBox when users must select the text.
  • A TextBlock holds inlines, so one block of text can mix bold runs, line breaks and links.
  • A Hyperlink opens nothing until you handle RequestNavigate.
  • For an embedded font, the name after # is the family name inside the file, not the filename.
  • Use a FlowDocument for long, structured, reflowing text, and build it in code when it comes from data.
  • Save RichTextBox content through a TextRange as XAML, RTF or XamlPackage.
