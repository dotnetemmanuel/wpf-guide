PART 13

Validation

Two places a rule can live, and one way to show what they find. Pick the mechanism that matches where the rule belongs.

Builds on Part 11, data binding, Part 9, styles and triggers and Part 10, templates.

A form that accepts anything and complains only when you press Save is frustrating: people want to know which field is wrong, next to that field, while they are filling it in. WPF's validation system keeps track of which bindings currently hold an error and gives every control a way to show it. The mechanisms differ in where the rule is written and what it can see.

IN PLAIN TERMS

Picture two desks. A ValidationRule is the front desk checking that a form is legible before it goes anywhere: "that is not a date". INotifyDataErrorInfo is the back office that knows the business: "a task needs a title". Both send their complaints to the same place, the error display on the control. The difference that matters: a form the front desk rejects normally never reaches the back office, while the back office has already filed the form by the time it complains.

1. ValidationRule: rules about the input

A ValidationRule is a class attached to one binding. By default it runs on the binding before conversion, on the raw value the user typed, and either accepts it or returns an error message. At that default step a rejected value never reaches your view model; the rule's ValidationStep property can move it later in the pipeline. That makes it right for rules about the input itself, such as "this must parse as a date".

This rule rejects empty or whitespace text. FieldName is an ordinary property, so each use in XAML can set it:

C# 
public sealed class RequiredRule : ValidationRule
{
    public string FieldName { get; set; } = "Value";

    public override ValidationResult Validate(object? value, CultureInfo culture)
        => string.IsNullOrWhiteSpace(value as string)
            ? new ValidationResult(false, $"{FieldName} is required.")
            : ValidationResult.ValidResult;
}
XAML 
<TextBox>
  <TextBox.Text>
    <Binding Path="Title" UpdateSourceTrigger="PropertyChanged">
      <Binding.ValidationRules>
        <rules:RequiredRule FieldName="Title" />
      </Binding.ValidationRules>
    </Binding>
  </TextBox.Text>
</TextBox>

Attaching a rule needs the long, property-element form of the binding, because ValidationRules is a collection and cannot be filled in inside {Binding ...} braces. With UpdateSourceTrigger=PropertyChanged, clearing the box shows the error at once rather than when focus leaves.

2. INotifyDataErrorInfo: rules about the model

Most rules are about your data rather than about keystrokes: a task needs a title, progress is a percentage, an end date follows a start date. Those rules belong with the data, where a unit test can reach them and the Save command can check them.

INotifyDataErrorInfo is the interface a source object implements to report such errors: a HasErrors flag, a GetErrors method that returns the errors for one property, and an ErrorsChanged event that bindings listen to. It is the modern interface, and the one you want by default. It is async-friendly, and supports multiple errors per property and object-level errors. IDataErrorInfo is its older predecessor (WPF has supported it since .NET Framework 3.5): synchronous, one error per property. Do not start new work with it.

You rarely implement it by hand. The Community Toolkit's ObservableValidator base class (the toolkit is covered in Part 14) implements it, driven by the standard attributes from System.ComponentModel.DataAnnotations. [NotifyDataErrorInfo] makes the generated setter validate the property each time it is set.

C# 
// CommunityToolkit.Mvvm implements INotifyDataErrorInfo for you.
public partial class TaskEditorViewModel : ObservableValidator
{
    [ObservableProperty]
    [NotifyDataErrorInfo]
    [Required(ErrorMessage = "Give the task a title.")]
    [MinLength(3, ErrorMessage = "At least three characters.")]
    public partial string Title { get; set; }

    [ObservableProperty]
    [NotifyDataErrorInfo]
    [Range(0, 100, ErrorMessage = "Progress is a percentage.")]
    public partial int Progress { get; set; }

    [RelayCommand(CanExecute = nameof(CanSave))]
    private async Task SaveAsync(CancellationToken ct) { /* … */ }

    private bool CanSave() => !HasErrors;

    public TaskEditorViewModel()
    {
        ErrorsChanged += (_, _) => SaveCommand.NotifyCanExecuteChanged();
    }
}

Look at the last three members together. CanSave asks HasErrors, and the constructor tells the command to ask again whenever the set of errors changes, so the Save button greys out while any field is invalid. One consequence of validating in the setter: a property nobody has set has not been checked, so a fresh form reports no errors. The last section of this part deals with that.

Bind with ValidatesOnNotifyDataErrors=True, which is the default when the source implements the interface. No extra markup is needed:

XAML 
<TextBox Text="{Binding Title, UpdateSourceTrigger=PropertyChanged}" />

3. Showing the errors

The default error visual is a red border and nothing else: no message. Replace Validation.ErrorTemplate to do better. The error template is shown as an adorner, a visual drawn in a separate layer on top of an element (Part 24 covers adorners in general).

IN PLAIN TERMS

The error template is a sticky note on a sheet of glass in front of the form. It can frame the field or hang a message under it, but it never pushes the other fields along. So a message placed below a text box overlaps whatever sits below it: leave room with a margin.

The style below gives every TextBox an error template with a rounded border and the first error message underneath. Its trigger also puts that message in the tooltip while the box has an error.

XAML 
<Style TargetType="TextBox">
  <Setter Property="Validation.ErrorTemplate">
    <Setter.Value>
      <ControlTemplate>
        <StackPanel>
          <Border BorderBrush="{StaticResource DangerBrush}" BorderThickness="1"
                  CornerRadius="4">
            <AdornedElementPlaceholder x:Name="Adorned" />
          </Border>
          <TextBlock Margin="2,3,0,0" FontSize="11"
                     Foreground="{StaticResource DangerBrush}"
                     Text="{Binding [0].ErrorContent}" />
        </StackPanel>
      </ControlTemplate>
    </Setter.Value>
  </Setter>

  <Style.Triggers>
    <Trigger Property="Validation.HasError" Value="True">
      <Setter Property="ToolTip"
              Value="{Binding (Validation.Errors)[0].ErrorContent,
                              RelativeSource={RelativeSource Self}}" />
    </Trigger>
  </Style.Triggers>
</Style>

AdornedElementPlaceholder is where the original control is rendered, so the border wraps the real text box. Inside the error template, the DataContext is the control's list of errors, a ReadOnlyObservableCollection<ValidationError>; hence [0].ErrorContent, the message of the first error.

GOTCHA

Error adorners are drawn in the AdornerLayer, which is created by the nearest AdornerDecorator. A Window's default template has one; a Popup, a ToolTip and some custom templates do not. If your error visuals vanish inside a popup, add an <AdornerDecorator> around its content.

Validating the whole form before save

Errors appear only for values that have been checked, and values are checked when they change. Someone who opens a blank form and presses Save straight away has changed nothing, so nothing has reported an error yet. Check everything explicitly before saving.

With ObservableValidator, ValidateAllProperties runs every rule on every property and raises the errors that were waiting. If your rules are ValidationRules, the view model cannot see them, so you have to ask the view: the helper below walks the element tree and fails if any element has an error.

C# 
// View model side (ObservableValidator):
ValidateAllProperties();
if (HasErrors) return;

// If you must check the view's bindings (ValidationRules case):
public static bool IsValid(DependencyObject node)
{
    if (Validation.GetHasError(node)) return false;
    return LogicalTreeHelper.GetChildren(node)
        .OfType<DependencyObject>()
        .All(IsValid);
}

The walk follows the logical tree, so it does not look inside control templates. It also finds only errors that already exist: a ValidationRule runs when a value moves towards the source, or also when the binding first loads if you set the rule's ValidatesOnTargetUpdated to true.

RECAP
  • Use a ValidationRule for rules about what the user typed; at its default step a rejected value never reaches the view model.
  • Put rules about your data in the view model through INotifyDataErrorInfo, which ObservableValidator implements for you.
  • Bindings show INotifyDataErrorInfo errors with no extra markup.
  • The default error visual is a red border with no message; replace Validation.ErrorTemplate to show the text.
  • Error templates are adorners: they take no layout space and need an AdornerDecorator above them.
  • Call ValidateAllProperties before saving, because fields the user never touched have not been checked.
