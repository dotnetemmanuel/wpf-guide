PART 12

Collections and views

A list on screen is a live view of a collection.

Builds on Part 11, data binding and Part 10, templates (item templates).

The notification contract

Controls that show many items, such as ListBox, ComboBox and DataGrid, have an ItemsSource property you bind to a collection. Bind it to a plain List<T> and the items appear once. Add an item afterwards and the screen does not change, because a List<T> has no way to tell anyone it changed.

For a bound list to update itself, two interfaces matter and they do different jobs:

  • INotifyCollectionChanged announces that the collection changed: items added, removed, moved, or reset (the whole contents replaced at once, which is what Clear raises). ObservableCollection<T> implements it.
  • INotifyPropertyChanged announces that an item changed. Your item type must implement this itself; ObservableCollection does nothing for you here.

A list of plain records inside an ObservableCollection will update when you add or remove, and will never update when you edit a field. This surprises people weekly.

IN PLAIN TERMS

Picture a noticeboard. INotifyCollectionChanged is the board calling out "a notice was pinned up" or "a notice was taken down". INotifyPropertyChanged is a single notice calling out "my text was just edited". ObservableCollection<T> gives the board a voice, but it cannot give the notices one: each item class has to announce its own changes.

CollectionView: sorting, filtering, grouping

Users want the task list sorted by due date, narrowed to what they typed and grouped by project. You could keep a second, sorted and filtered copy of the collection, but then every add, remove and edit has to update both. WPF puts a layer between the collection and the control instead.

A collection view (ICollectionView) is a sorted, filtered and grouped way of looking at a collection, plus a current item, a position marker that list controls can keep in step with their selection. The collection itself is never reordered.

IN PLAIN TERMS

A collection view works like a saved search in an email client. The mailbox keeps every message in arrival order; the saved search shows only unread mail from one sender, newest first. Deleting the saved search deletes no mail, and a new message that matches shows up in it. Where the comparison breaks: by default, editing an existing item does not re-filter or re-sort it until you call Refresh (live shaping, below, changes that).

Every ItemsSource binding is silently wrapped in an ICollectionView. That automatic one is the collection's default view: there is one per collection, shared by every control bound to it. You can get at it, or declare your own with a CollectionViewSource, a XAML-friendly object that creates a separate view over its Source.

The markup below sorts by due date, then by title, and groups by project. SortDescription lives in a CLR namespace that XAML does not map by default, hence the scm prefix and the xmlns comment in the middle. The GroupStyle gives each group a header; inside its template the DataContext is the group, whose Name is the value being grouped on.

XAML 
<Window.Resources>
  <CollectionViewSource x:Key="SortedTasks" Source="{Binding Tasks}">
    <CollectionViewSource.SortDescriptions>
      <scm:SortDescription PropertyName="DueDate" Direction="Ascending" />
      <scm:SortDescription PropertyName="Title"   Direction="Ascending" />
    </CollectionViewSource.SortDescriptions>
    <CollectionViewSource.GroupDescriptions>
      <PropertyGroupDescription PropertyName="Project" />
    </CollectionViewSource.GroupDescriptions>
  </CollectionViewSource>
</Window.Resources>

<!-- xmlns:scm="clr-namespace:System.ComponentModel;assembly=WindowsBase" -->

<ListBox ItemsSource="{Binding Source={StaticResource SortedTasks}}">
  <ListBox.GroupStyle>
    <GroupStyle>
      <GroupStyle.HeaderTemplate>
        <DataTemplate>
          <TextBlock Text="{Binding Name}" FontWeight="SemiBold"
                     Margin="0,10,0,4" Opacity=".7" />
        </DataTemplate>
      </GroupStyle.HeaderTemplate>
    </GroupStyle>
  </ListBox.GroupStyle>
</ListBox>

Run as written, the groups come out right but every row shows a type name. The figure shows why, and the one-attribute fix.

From the view model, the same thing with a live filter that follows a search box. The class uses the Community Toolkit's [ObservableProperty], covered in Part 14: read it as a Search property that raises change notifications and calls OnSearchChanged whenever its value changes.

C# 
public partial class TaskListViewModel : ObservableObject
{
    public ObservableCollection<TaskViewModel> Tasks { get; } = [];
    public ICollectionView View { get; }

    [ObservableProperty]
    public partial string Search { get; set; }

    public TaskListViewModel()
    {
        View = CollectionViewSource.GetDefaultView(Tasks);
        View.SortDescriptions.Add(new SortDescription(nameof(TaskViewModel.DueDate),
                                                      ListSortDirection.Ascending));
        View.Filter = o => o is TaskViewModel t &&
            (Search.Length == 0 ||
             t.Title.Contains(Search, StringComparison.OrdinalIgnoreCase));
        Search = "";
    }

    partial void OnSearchChanged(string value) => View.Refresh();
}

View.Filter is a predicate: return true to keep an item. The view cannot know that the predicate reads Search, so OnSearchChanged calls Refresh to run it again. That is also why Search is set last in the constructor: setting it calls OnSearchChanged, which needs View. Bind the list with ItemsSource="{Binding View}" and a text box to Search with UpdateSourceTrigger=PropertyChanged, and the list narrows as the user types.

GOTCHA

View.Refresh() re-evaluates the filter over the whole collection and resets selection. On a large list, debounce it: a Delay=300 on the search box binding, or a timer. And note that GetDefaultView returns a shared view: two ListBoxes bound to the same collection share sorting, filtering and current item. Use separate CollectionViewSource instances when you need them independent.

Live shaping DEEPER

By default a view places an item when it is added, not when it is edited: rename a task and it keeps its old sort position, and stays visible even if it no longer matches the filter. ListCollectionView, the view WPF creates over an ObservableCollection, implements ICollectionViewLiveShaping to fix that. On a CollectionViewSource, set IsLiveFilteringRequested and IsLiveSortingRequested to true and list the properties to watch in LiveFilteringProperties and LiveSortingProperties. Grouping has the matching IsLiveGroupingRequested and LiveGroupingProperties.

For a view created in code, cast the result of GetDefaultView to ICollectionViewLiveShaping, check CanChangeLiveFiltering, then set IsLiveFiltering to true and add property names to LiveFilteringProperties (sorting has the matching members). Either way, edits to those properties then re-filter and re-sort without Refresh, provided the items raise PropertyChanged; a DataGrid needs none of this for its own edits, because committing a row edit re-positions that row in a sorted or filtered view.

Large lists DEEPER

Beyond roughly 10,000 items, ObservableCollection plus a filter starts to hurt, because every change notification walks the view. Options, in order of effort:

  • Virtualise properly. Virtualisation means the list creates visual rows only for the items on screen, and Recycling reuses those rows as you scroll instead of building new ones. Grouping turns virtualisation off unless you also set VirtualizingPanel.IsVirtualizingWhenGrouping="True". Confirm VirtualizationMode="Recycling" and that you have not disabled virtualisation by accident (Part 19 lists the ways).
  • Filter at the source. Query the database or the in-memory index and replace the collection, rather than filtering a view over everything.
  • Batch. ObservableCollection raises one event per Add. Build the list first, then assign, or use a collection that supports range operations.
  • Data virtualisation. Implement IList over a paged, lazily-loaded backing store so only the visible window is materialised. Non-trivial; only do it when you must.

Cross-thread collection updates

Loading data on a background thread keeps the window responsive, but adding to a bound ObservableCollection from a background thread throws a NotSupportedException. A bound collection is effectively part of the screen, and only the UI thread may change the screen (Part 17 covers the threading model).

IN PLAIN TERMS

Think of a whiteboard in a room where only one person, the UI thread, may redraw anything. Fix A passes that person a note for each change. Fix B puts a single key on the table: any thread may change the list while holding the key, and WPF takes the same key whenever it reads the list. The redrawing still happens only on the UI thread: WPF forwards each change notice there itself.

Two fixes. In A, the Dispatcher is the UI thread's work queue, and InvokeAsync puts a piece of work on it:

C# 
// A. Marshal to the UI thread (fine for occasional updates).
await Application.Current.Dispatcher.InvokeAsync(() => Tasks.Add(item));

// B. Enable collection synchronisation (better for high-frequency streams).
private readonly object _lock = new();

public TaskListViewModel()
{
    BindingOperations.EnableCollectionSynchronization(Tasks, _lock);
}

// Then from any thread:
lock (_lock) { Tasks.Add(item); }

Option B lets WPF take the same lock while it reads the collection during layout, so background producers don't have to hop threads for every item. It is the right answer for telemetry feeds and log tails.

RECAP
  • ObservableCollection<T> tells the list when items are added or removed, but each item must raise PropertyChanged for edits to show.
  • Every bound collection is shown through a collection view, which sorts, filters and groups without changing the collection.
  • The default view is shared by every control bound to the same collection; use a CollectionViewSource when two lists need independent views.
  • After changing what a filter depends on, call Refresh, and debounce it on large lists.
  • Only the UI thread may change a bound collection, unless you enable collection synchronisation with a lock.
