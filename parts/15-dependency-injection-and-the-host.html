PART 15

Dependency injection and the host

WPF predates Microsoft.Extensions.* by a decade, so nothing is wired up for you. Fifty lines gets you the same composition root you'd have in an ASP.NET Core app.

Builds on Part 2, project setup and startup and Part 14, MVVM with the Community Toolkit.

A task list view model needs a repository; the repository needs a connection string from configuration; the API client needs a base address and a logger. If each class creates what it needs with new, the app is wired together in a hundred places, changing one constructor ripples through all of them, and a test cannot swap the real database for a fake.

Dependency injection (DI) turns that around. A class lists what it needs as constructor parameters and never creates those things itself. A container builds objects on request, filling in the parameters from a list of registrations that say which concrete class to use for each type. The one place where you write all the registrations is the composition root.

IN PLAIN TERMS

The container is a restaurant kitchen and the registrations are its recipes. Order a TaskListViewModel and the kitchen sees that it needs a repository, which needs a connection, and assembles the whole plate. The composition root places the order; dishes never order each other. Because a dish takes its ingredients rather than fetching them, a test can hand it fake ones.

The generic host (IHost, from Microsoft.Extensions.Hosting) wraps that container together with configuration, logging and background services, and gives them all a start and a stop. ASP.NET Core is built on it, and nothing stops a WPF app from using it too.

The wiring

The whole composition root lives in App.xaml.cs. Read it in three steps. The constructor reads configuration, sets up logging, registers every service and builds the host. OnStartup starts the host and asks it for the main window. StartAsync runs through Task.Run so no background service starts on the UI thread (see Background work below). OnExit stops the host, so background work and log files shut down cleanly. Besides Microsoft.Extensions.Hosting, the listing uses the Microsoft.Extensions.Http, Serilog.Extensions.Hosting, Serilog.Settings.Configuration and Serilog.Sinks.File packages.

App.xaml.cs 
public partial class App : Application
{
    private readonly IHost _host;

    public App()
    {
        var builder = Host.CreateApplicationBuilder(new HostApplicationBuilderSettings
        {
            ContentRootPath = AppContext.BaseDirectory
        });

        builder.Configuration
            .AddJsonFile("appsettings.json", optional: false)
            .AddJsonFile($"appsettings.{builder.Environment.EnvironmentName}.json", optional: true)
            .AddEnvironmentVariables("TASKS_")
            .AddUserSecrets<App>(optional: true);

        builder.Logging.ClearProviders();
        builder.Services.AddSerilog((_, cfg) => cfg
            .ReadFrom.Configuration(builder.Configuration)
            .WriteTo.File(
                Path.Combine(Environment.GetFolderPath(Environment.SpecialFolder.LocalApplicationData),
                             "Tasks", "logs", "log-.txt"),
                rollingInterval: RollingInterval.Day));

        builder.Services.Configure<ApiOptions>(builder.Configuration.GetSection("Api"));

        // Infrastructure
        builder.Services.AddSingleton<IClock, SystemClock>();
        builder.Services.AddSingleton<ITaskRepository, SqliteTaskRepository>();
        builder.Services.AddHttpClient<ITaskApi, TaskApi>((sp, http) =>
        {
            var o = sp.GetRequiredService<IOptions<ApiOptions>>().Value;
            http.BaseAddress = new Uri(o.BaseUrl);
        });

        // UI services
        builder.Services.AddSingleton<IDialogService, DialogService>();
        builder.Services.AddSingleton<INavigationService, NavigationService>();

        // Windows are singletons, page/dialog view models are transient
        builder.Services.AddSingleton<MainWindow>();
        builder.Services.AddSingleton<ShellViewModel>();
        builder.Services.AddTransient<TaskListViewModel>();
        builder.Services.AddTransient<TaskEditorViewModel>();

        _host = builder.Build();
    }

    protected override async void OnStartup(StartupEventArgs e)
    {
        try
        {
            base.OnStartup(e);
            await Task.Run(() => _host.StartAsync());

            var window = _host.Services.GetRequiredService<MainWindow>();
            window.DataContext = _host.Services.GetRequiredService<ShellViewModel>();
            window.Show();
        }
        catch (Exception ex)
        {
            MessageBox.Show(ex.ToString(), "Startup failed");
            Shutdown(1);
        }
    }

    protected override void OnExit(ExitEventArgs e)
    {
        using (_host)
        {
            Task.Run(() => _host.StopAsync(TimeSpan.FromSeconds(5))).GetAwaiter().GetResult();
        }
        base.OnExit(e);
    }
}

Setting ContentRootPath to the executable's folder matters because appsettings.json is looked up relative to the content root, which otherwise is the working folder: launched from a shortcut with a different "Start in" folder, the app would not find its settings.

WPF does not wait for OnExit to finish, so an async version could let the process end halfway through shutdown. The stop has to block, and running it through Task.Run keeps its awaits from needing the UI thread while that thread is blocked.

Nothing is created while you register. AddSingleton, AddTransient and AddHttpClient only record what to build. GetRequiredService is the moment of building: it constructs MainWindow and everything its constructor asks for, or throws if something is not registered. The try/catch matters because OnStartup is async void: an exception escaping it would surface as an unhandled dispatcher exception rather than a readable message.

Delete StartupUri (the attribute that tells WPF which window to open at launch) from App.xaml, or the framework will construct a second, unwired window behind the one you showed.

Lifetimes, translated to desktop

Every registration also says how long an instance lives and who shares it: its lifetime. The names come from web servers, where a scope is one HTTP request. A desktop app has no requests, so each lifetime needs translating.

IN PLAIN TERMS

A singleton is the office printer: one for everybody, for as long as the building is open. A transient is a paper cup: a fresh one every time anyone asks. A scoped service is the pen handed out with a visitor badge: everyone working on that visit shares it, and it is collected when the visit ends. In a desktop app you decide what counts as a visit, typically one dialog.

LifetimeDesktop meaning
SingletonLives as long as the process. Repositories, the shell view model, settings, the main window.
TransientNew instance per resolve. Dialog view models, page view models, anything holding per-screen state.
ScopedNo ambient scope exists in a desktop app. Create one explicitly per window or per unit of work; this is exactly how you get a per-dialog DbContext.

If you resolve a scoped service outside any scope, straight from _host.Services, it silently lives as long as the app, like a singleton. The host only catches that mistake when its environment is Development (set by the DOTNET_ENVIRONMENT variable; the default is Production), where it turns on scope validation and throws instead.

The method below opens an editor dialog with its own scope. Everything the editor's view model pulls in as scoped, such as a DbContext, is created fresh for this dialog and disposed when the method returns. Because ShowDialog blocks until the dialog closes, that is right after the user closes it.

C# 
// A scope per editor window, disposed when the window closes.
public async Task<bool> EditAsync(int taskId)
{
    using var scope = _services.CreateScope();
    var vm = scope.ServiceProvider.GetRequiredService<TaskEditorViewModel>();
    await vm.LoadAsync(taskId);

    var window = new TaskEditorWindow { DataContext = vm, Owner = _shell };
    return window.ShowDialog() == true;
}
GOTCHA

Never inject IServiceProvider into a view model so it can resolve things later. That is the service locator anti-pattern, and it hides your dependency graph: the constructor no longer shows what the class needs, so a missing registration only surfaces when some later code path runs. Inject a typed factory instead. Microsoft.Extensions.DependencyInjection does not supply a Func<TaskEditorViewModel> by itself, so either register one or define a small ITaskEditorFactory. The one place a container reference is legitimate is your navigation service, which is by definition a locator.

Background work with the host DEEPER

Because you started a real host, IHostedService works. A hosted service is a class the host starts when it starts and stops when it stops. This is a clean home for sync loops, file watchers and cache warmers. BackgroundService is the convenient base class: you override ExecuteAsync with a long-running loop, and the host cancels its token at shutdown.

This one pulls remote changes every five minutes, merges them into the local store and announces the result with the messenger from Part 14. The when filter logs and retries every failure, including an HTTP timeout, which surfaces as a cancellation exception too. Only a cancellation caused by the stopping token, at shutdown, ends the loop.

C# 
public sealed class SyncService : BackgroundService
{
    private readonly ITaskApi _api;
    private readonly ITaskRepository _repo;
    private readonly ILogger<SyncService> _log;

    public SyncService(ITaskApi api, ITaskRepository repo, ILogger<SyncService> log)
        => (_api, _repo, _log) = (api, repo, log);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
        while (await timer.WaitForNextTickAsync(stoppingToken))
        {
            try
            {
                var remote = await _api.GetChangesAsync(stoppingToken);
                await _repo.MergeAsync(remote, stoppingToken);
                WeakReferenceMessenger.Default.Send(new SyncCompleted(remote.Count));
            }
            catch (Exception ex) when (!stoppingToken.IsCancellationRequested)
            {
                _log.LogWarning(ex, "Sync failed; will retry");
            }
        }
    }
}

Register with builder.Services.AddHostedService<SyncService>(). It starts with _host.StartAsync() and stops cleanly on exit.

Do not assume which thread it runs on. On .NET 10 the host runs all of ExecuteAsync on a thread-pool thread. On .NET 9 the part before its first await runs on whichever thread called StartAsync, which is why OnStartup calls it through Task.Run: otherwise that part, and every later await, would run on the UI thread, and shutdown would wait out its full timeout. Either way, anything touching bound collections needs the marshalling from Part 12. That includes the message it sends: messenger recipients run on the sending thread, so a message from a background service arrives off the UI thread.

RECAP
  • Classes ask for what they need in their constructor, and the container builds them from registrations kept in one place, App.xaml.cs.
  • The generic host adds configuration, logging and background services around the container, as in ASP.NET Core.
  • Remove StartupUri and show the main window yourself, resolved from the host.
  • A singleton lives for the whole app, a transient is new every time, and a scoped service needs a scope you create, typically one per dialog.
  • Inject specific services or a factory, never IServiceProvider itself.
  • A background service's thread is not guaranteed, so marshal any change to a bound collection.
