PART 30

Globalisation and localisation

Your users do not all write numbers, dates and sentences the way you do. WPF has one surprising default here that every app has to fix, and a plain but workable toolset for the rest.

Builds on Part 5, dependency properties, Part 11, data binding and Part 3, XAML precisely.

Two words, two jobs. Globalisation means the app formats numbers, dates and currency, and lays out text direction, correctly for wherever the user is. Localisation means it shows its text in the user's language. Both start from a culture: a .NET CultureInfo such as sv-SE, which bundles the rules for one language in one region, from the decimal separator to the date order.

The culture bug everyone hits

IN PLAIN TERMS

Your app has two separate answers to "where is the user?". .NET's CultureInfo.CurrentCulture is filled in from the user's Windows region settings. WPF's Language property, on every element, is filled in with American English. Bindings read the second one. It is like a hotel where reception knows you are Swedish but nobody told the restaurant, so every bill comes printed the American way.

GOTCHA

WPF does not use CultureInfo.CurrentCulture for binding conversions. It uses the Language property of the element, which defaults to en-US regardless of the machine's settings. So a Swedish user sees 1,234.50 where they expect 1 234,50, and a date StringFormat produces American ordering. This has been the behaviour since 2006 and it will not change.

The fix goes in App.OnStartup, before any window exists. It first makes the user's formatting culture and their UI language the defaults for every thread, including ones started later. The two stay separate, because a user can format in one culture and read the interface in another. Then it calls OverrideMetadata, which changes the default value a dependency property has for a type. Because Language is inherited down the element tree, changing its default on FrameworkElement changes it everywhere. The call can only be made once per process: a second override for the same type throws.

C#: fix it once, at startup 
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    var culture = CultureInfo.CurrentCulture;       // or a user preference
    CultureInfo.DefaultThreadCurrentCulture   = culture;
    CultureInfo.DefaultThreadCurrentUICulture = CultureInfo.CurrentUICulture;

    // Make every FrameworkElement inherit the real culture.
    FrameworkElement.LanguageProperty.OverrideMetadata(
        typeof(FrameworkElement),
        new FrameworkPropertyMetadata(
            XmlLanguage.GetLanguage(culture.IetfLanguageTag)));
}

That single OverrideMetadata call fixes number, date and currency formatting across the entire application, with one loss. It passes only the culture's name, such as sv-SE, so customisations the user made in the Windows region settings, such as a different decimal symbol, are not carried over: WPF formats with the standard rules for that name.

Resx strings

A button that says Content="Save" in XAML can never say "Spara". To translate an app, every visible string has to move out of the markup into a table that can be swapped per language. A .resx file is that table: an XML list of names and values. You keep a neutral Strings.resx and add one file per language, such as Strings.sv-SE.resx. The build compiles each language into a satellite assembly in a folder named after the culture, and at runtime ResourceManager picks the closest match, falling back from sv-SE to sv to the neutral file.

The straightforward approach, and still the best supported one:

Strings.resx / Strings.sv-SE.resx 
<data name="Commands_Save"><value>Save</value></data>
<data name="Tasks_Count"><value>{0} tasks</value></data>
IN PLAIN TERMS

.NET keeps two culture settings, and they answer different questions. CurrentCulture decides how values are formatted: 1 234,50 or 1,234.50. CurrentUICulture decides which language the strings come from. A Swede who prefers an English interface has sv-SE for the first and en-US for the second, which is why the string lookup below uses CurrentUICulture.

To let the user switch language while the app runs, wrap the resources in one shared object that bindings can watch. Loc exposes an indexer, so a binding path of [Commands_Save] looks up that key. A missing key comes back as !Commands_Save!, which makes gaps easy to spot on screen. SetCulture changes the UI culture and then announces that every indexer value has changed.

C#: a bindable, switchable wrapper 
public sealed class Loc : INotifyPropertyChanged
{
    public static Loc Instance { get; } = new();

    // Indexer binding: {Binding Source={x:Static loc:Loc.Instance}, Path=[Commands_Save]}
    public string this[string key] => Strings.ResourceManager
        .GetString(key, CultureInfo.CurrentUICulture) ?? $"!{key}!";

    public void SetCulture(CultureInfo culture)
    {
        CultureInfo.CurrentUICulture = culture;
        CultureInfo.DefaultThreadCurrentUICulture = culture;
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs("Item[]"));
    }

    public event PropertyChangedEventHandler? PropertyChanged;
}
XAML 
xmlns:loc="clr-namespace:Tasks.Localisation"

<Button Content="{Binding Source={x:Static loc:Loc.Instance}, Path=[Commands_Save]}" />

Raising PropertyChanged for "Item[]" is the magic string that tells WPF every indexer binding on that object is stale (Binding.IndexerName holds the same string). That is how the whole UI re-reads its strings when the user switches language, with no restart. Switching this way changes strings only: number and date formatting still follow the Language fixed at startup.

The markup extension from Part 3 is nicer to read but does not update live, because ProvideValue runs once. If live switching matters, use the indexer binding; if it doesn't, use the extension.

Right-to-left

Arabic and Hebrew are read from right to left, and users of those languages expect the whole window to follow: the first column on the right, scroll bars on the left, text aligned to the right edge.

IN PLAIN TERMS

Setting FlowDirection to RightToLeft is like holding the layout up to a mirror, with one difference: WPF keeps the text itself readable instead of printing it backwards. The mirror is also selective: an Image does not pick up the flip from its container, so a picture stays the way it was drawn.

As with Language, overriding the default of the inherited FlowDirection property at startup flips the entire app in one call:

C# 
// Mirrors layout, scrollbars, text alignment and flow for the whole tree.
var flow = culture.TextInfo.IsRightToLeft ? FlowDirection.RightToLeft
                                          : FlowDirection.LeftToRight;

FrameworkElement.FlowDirectionProperty.OverrideMetadata(
    typeof(FrameworkElement), new FrameworkPropertyMetadata(flow));

RTL mirrors almost everything automatically, which is one of WPF's genuine strengths. That includes hard-coded Margin values and Canvas.Left, which then counts from the right edge. Images are the exception: they keep their drawn direction, so an arrow bitmap meaning "forward" still points right. Set FlowDirection="LeftToRight" locally on anything whose geometry must not flip, such as a phone number field, a code editor, a chart or a map.

SINCE .NET 10

.NET 10 fixed right-to-left layout defects in MenuItem, Expander and TreeViewItem under the Fluent theme. If you are targeting .NET 9 and shipping an RTL locale, test these three specifically or stay on the classic theme.

Formatting values

With the startup fix in place, a StringFormat in a binding follows the user's culture. C formats currency and d a short date. ConverterCulture pins one binding to a specific culture whatever the user's settings.

XAML 
<!-- Follows the element's Language after the OverrideMetadata fix above -->
<TextBlock Text="{Binding Amount, StringFormat={}{0:C}}" />
<TextBlock Text="{Binding Due, StringFormat={}{0:d}}" />

<!-- Force a specific culture for one binding -->
<TextBlock Text="{Binding Amount, StringFormat={}{0:C}, ConverterCulture=sv-SE}" />

Use standard format specifiers (d, D, C, N, P), which mean "this culture's own pattern", rather than custom ones (dd/MM/yyyy), which spell out one fixed pattern. Custom patterns look right in your locale and wrong in every other. With d, the same date shows as 2026-09-13 in Sweden and 9/13/2026 in the United States.

C changes only the presentation: 100 shows as 100,00 kr in Sweden and $100.00 in the United States. No money is converted, so if the currency matters, store it with the amount.

Pluralisation and beyond DEEPER

Resx has no plural support. "{0} tasks" reads badly at 1 and is outright wrong in languages with more than two plural forms: English needs two forms of "tasks", Polish three and Arabic six. If your product ships in Slavic or Arabic locales, move to MessageFormat-style resources (Jeffijoe.MessageFormat) or Mozilla Fluent (Linguini) rather than fighting resx. Both let a translator write each plural form as part of the string itself.

RECAP
  • WPF formats bindings as American English until you override the Language default once at startup.
  • CurrentCulture controls formatting and CurrentUICulture controls which language strings load.
  • Keep strings in .resx files, one per language, and bind through an indexer if the user must switch language live.
  • Right-to-left layout is one FlowDirection setting, but check images, which do not flip, and anything drawn to exact positions that must not flip.
  • Use standard format specifiers such as d and C, never hand-written date patterns.
