PART 30

Globalisation and localisation

The culture bug everyone hits

GOTCHA

WPF does not use CultureInfo.CurrentCulture for binding conversions. It uses the Language property of the element, which defaults to en-US regardless of the machine's settings. So a Swedish user sees 1,234.50 where they expect 1 234,50, and a date StringFormat produces American ordering. This has been the behaviour since 2006 and it will not change.

C# — fix it once, at startup 
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    var culture = CultureInfo.CurrentCulture;       // or a user preference
    CultureInfo.DefaultThreadCurrentCulture   = culture;
    CultureInfo.DefaultThreadCurrentUICulture = culture;

    // Make every FrameworkElement inherit the real culture.
    FrameworkElement.LanguageProperty.OverrideMetadata(
        typeof(FrameworkElement),
        new FrameworkPropertyMetadata(
            XmlLanguage.GetLanguage(culture.IetfLanguageTag)));
}

That single OverrideMetadata call fixes number, date and currency formatting across the entire application.

Resx strings

The straightforward approach, and still the best supported one:

Strings.resx / Strings.sv-SE.resx 
<data name="Commands_Save"><value>Save</value></data>
<data name="Tasks_Count"><value>{0} tasks</value></data>
C# — a bindable, switchable wrapper 
public sealed class Loc : INotifyPropertyChanged
{
    public static Loc Instance { get; } = new();

    // Indexer binding: {Binding Source={x:Static loc:Loc.Instance}, Path=[Commands_Save]}
    public string this[string key] => Strings.ResourceManager
        .GetString(key, CultureInfo.CurrentUICulture) ?? $"!{key}!";

    public void SetCulture(CultureInfo culture)
    {
        CultureInfo.CurrentUICulture = culture;
        CultureInfo.DefaultThreadCurrentUICulture = culture;
        PropertyChanged?.Invoke(this, new PropertyChangedEventArgs("Item[]"));
    }

    public event PropertyChangedEventHandler? PropertyChanged;
}
XAML 
xmlns:loc="clr-namespace:Tasks.Localisation"

<Button Content="{Binding Source={x:Static loc:Loc.Instance}, Path=[Commands_Save]}" />

Raising PropertyChanged for "Item[]" is the magic string that tells WPF every indexer binding on that object is stale — which is how the whole UI re-reads its strings when the user switches language, with no restart.

The markup extension from Part 3 is nicer to read but does not update live, because ProvideValue runs once. If live switching matters, use the indexer binding; if it doesn't, use the extension.

Right-to-left

C# 
// Mirrors layout, scrollbars, text alignment and flow for the whole tree.
var flow = culture.TextInfo.IsRightToLeft ? FlowDirection.RightToLeft
                                          : FlowDirection.LeftToRight;

FrameworkElement.FlowDirectionProperty.OverrideMetadata(
    typeof(FrameworkElement), new FrameworkPropertyMetadata(flow));

RTL mirrors almost everything automatically, which is one of WPF's genuine strengths. Things it does not mirror: images with directional meaning (arrows), hard-coded Margin values that assume left-to-right, and Canvas.Left positioning. Use symmetric margins where you can, and FlowDirection="LeftToRight" locally on anything that must not flip, such as a phone number field or a code editor.

SINCE .NET 10

.NET 10 fixed right-to-left layout defects in MenuItem, Expander and TreeViewItem under the Fluent theme. If you are targeting .NET 9 and shipping an RTL locale, test these three specifically or stay on the classic theme.

Formatting values

XAML 
<!-- Follows the element's Language after the OverrideMetadata fix above -->
<TextBlock Text="{Binding Amount, StringFormat={}{0:C}}" />
<TextBlock Text="{Binding Due, StringFormat={}{0:d}}" />

<!-- Force a specific culture for one binding -->
<TextBlock Text="{Binding Amount, StringFormat={}{0:C}, ConverterCulture=sv-SE}" />

Use standard format specifiers (d, D, C, N, P) rather than custom ones (dd/MM/yyyy). Custom patterns look right in your locale and wrong in every other.

Pluralisation and beyond

Resx has no plural support. "{0} tasks" reads badly at 1 and is outright wrong in languages with more than two plural forms. If your product ships in Slavic or Arabic locales, move to MessageFormat-style resources (Jeffijoe.MessageFormat) or Mozilla Fluent (Linguini) rather than fighting resx.
