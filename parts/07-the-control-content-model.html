PART 07

The control content model

WPF has fewer control types than you would expect because most controls are one of three shapes, and the shape tells you what you can put inside.

Builds on Part 3, XAML precisely and Part 4, layout (panels such as StackPanel and Grid). Styles, resources and templates appear briefly here; Parts 8 to 10 explain them.

The three shapes

In many UI toolkits a button holds a caption and perhaps an icon. If you want a button with a spinner and two lines of text, you need a different control or a custom-drawn one. WPF avoids that by separating what a control does from what it contains. The rule for what a control can contain is its content model, and nearly every control follows one of three.

IN PLAIN TERMS

A ContentControl is a picture frame: the frame decides the border and how it reacts when pressed, and you can put any picture in it. A HeaderedContentControl is a frame with a caption plate. An ItemsControl is a photo album: it holds many pictures and decides how they are laid out. Where the analogy stops: a real frame never looks at its picture, whereas WPF inspects the content to decide how to draw it, as the next paragraph shows.

BaseKey propertyExamples
ContentControlContent: one object of any typeButton, Label, CheckBox, ScrollViewer, Window, UserControl
HeaderedContentControlHeader + ContentGroupBox, Expander, TabItem
ItemsControlItems / ItemsSourceListBox, ComboBox, TreeView, Menu, DataGrid, TabControl

Content being object is the whole trick. WPF decides how to draw it by looking at what you gave it:

  • A string becomes a TextBlock.
  • A UIElement (anything that can draw itself, such as a panel or another control) is rendered as it is.
  • Anything else, say a Customer, makes WPF look for a DataTemplate whose DataType matches, and failing that call ToString(). A DataTemplate is a piece of XAML describing how to draw objects of one type (Part 10).

The three cases side by side:

XAML 
<Button Content="Save" />                      <!-- string  → TextBlock -->

<Button>                                        <!-- element → rendered as-is -->
  <StackPanel Orientation="Horizontal">
    <ctrl:Spinner Width="14" Height="14" />
    <TextBlock Text="Saving…" Margin="6,0,0,0" />
  </StackPanel>
</Button>

<ContentControl Content="{Binding SelectedCustomer}" />  <!-- object → DataTemplate lookup -->

ItemsControl and containers

A list of tasks needs each row to be selectable, highlighted on hover and reachable with the arrow keys. Your TaskViewModel knows nothing about selection, and should not. So the list wraps each item in a container: a control created per item that carries selection, focus and hover behaviour, and draws your item inside it.

IN PLAIN TERMS

Think of a cloakroom. You hand over a coat (the item), the attendant puts it on a hanger (the container), and the hangers go on a rail (the panel). How the coat is displayed, how every hanger behaves, which rail they hang on, and what the counter looks like are four separate decisions. Where the analogy stops: a long list usually makes hangers only for the coats currently in view (virtualisation, defined below).

This is the mechanism behind every list in WPF. For each item in ItemsSource, the control runs through a few overridable methods that each list control customises:

  1. Checks IsItemItsOwnContainerOverride: if the item is already a ListBoxItem, use it directly.
  2. Otherwise calls GetContainerForItemOverride to create one (ListBoxItem, ComboBoxItem, TreeViewItem, DataGridRow…).
  3. Sets the container's Content to the item and its DataContext to the item.
  4. Applies ItemTemplate as the container's ContentTemplate.

Which is why there are four separate template hooks and each does a different job. The ListBox below sets all four; the numbered comments match the four hooks named in the figure caption. Style and DataTrigger are explained in Part 9 and ControlTemplate in Part 10; for now, notice only which layer each hook reaches.

XAML 
<ListBox ItemsSource="{Binding Tasks}">

  <!-- 1. How each ITEM looks -->
  <ListBox.ItemTemplate>
    <DataTemplate DataType="{x:Type vm:TaskViewModel}">
      <Grid>
        <Grid.ColumnDefinitions>
          <ColumnDefinition Width="Auto" />
          <ColumnDefinition Width="*" />
        </Grid.ColumnDefinitions>
        <CheckBox IsChecked="{Binding IsDone}" VerticalAlignment="Center" />
        <TextBlock Grid.Column="1" Text="{Binding Title}" Margin="8,0,0,0" />
      </Grid>
    </DataTemplate>
  </ListBox.ItemTemplate>

  <!-- 2. How each CONTAINER behaves: selection, spacing, bindings to the item -->
  <ListBox.ItemContainerStyle>
    <Style TargetType="ListBoxItem">
      <Setter Property="Padding" Value="6,4" />
      <Setter Property="HorizontalContentAlignment" Value="Stretch" />
      <Style.Triggers>
        <DataTrigger Binding="{Binding IsOverdue}" Value="True">
          <Setter Property="Foreground" Value="{DynamicResource DangerBrush}" />
        </DataTrigger>
      </Style.Triggers>
    </Style>
  </ListBox.ItemContainerStyle>

  <!-- 3. What PANEL lays the containers out -->
  <ListBox.ItemsPanel>
    <ItemsPanelTemplate>
      <VirtualizingStackPanel />
    </ItemsPanelTemplate>
  </ListBox.ItemsPanel>

  <!-- 4. The CHROME around the whole control -->
  <ListBox.Template>
    <ControlTemplate TargetType="ListBox">
      <Border BorderBrush="{TemplateBinding BorderBrush}"
              BorderThickness="{TemplateBinding BorderThickness}"
              CornerRadius="4">
        <ScrollViewer>
          <ItemsPresenter />
        </ScrollViewer>
      </Border>
    </ControlTemplate>
  </ListBox.Template>

</ListBox>
GOTCHA

Inside an ItemTemplate the DataContext is the item, not the parent view model. To bind a per-item button to a command on the list's view model, hop out with RelativeSource, which finds a binding source by walking up the tree: {Binding DataContext.DeleteCommand, RelativeSource={RelativeSource AncestorType=ListBox}}, with CommandParameter="{Binding}" to pass the item.

Choosing a list control

Pick the lightest control that does the job; the table says what each one adds over a bare ItemsControl. One term first: virtualisation means creating containers only for the rows currently on screen, which is what keeps a list of 100,000 items fast.

ControlAdds
ItemsControlNothing. No selection, no scrolling, no virtualisation by default. Perfect for rendering a read-only repeated block.
ListBoxSelection, keyboard navigation, a ScrollViewer, virtualisation.
ListViewA ListBox with a pluggable View, in practice GridView. Mostly superseded by DataGrid.
DataGridColumns, sorting, in-place editing, row headers, frozen columns. Heavy: reach for it when you need editing, not just a table.
TreeViewHierarchy, via HierarchicalDataTemplate.
TabControlYes, really an ItemsControl. Bind ItemsSource to a collection of documents and template ItemTemplate (the tab header) and ContentTemplate (the page).

Hierarchies

A folder tree has items that contain items. A plain DataTemplate describes one level. A HierarchicalDataTemplate is a DataTemplate that also says where each item's children are, through its own ItemsSource, so the TreeView can keep going down.

In the example, folders and files are different view-model types. Each gets a template in the TreeView's resources, keyed by type, so WPF picks the right one per node. The container style then connects each TreeViewItem to its view model.

XAML 
<TreeView ItemsSource="{Binding RootFolders}">
  <TreeView.Resources>
    <HierarchicalDataTemplate DataType="{x:Type vm:FolderViewModel}"
                              ItemsSource="{Binding Children}">
      <StackPanel Orientation="Horizontal">
        <Path Data="{StaticResource FolderGeometry}" Fill="{DynamicResource IconBrush}"
              Width="14" Height="14" Stretch="Uniform" />
        <TextBlock Text="{Binding Name}" Margin="6,0,0,0" />
      </StackPanel>
    </HierarchicalDataTemplate>

    <DataTemplate DataType="{x:Type vm:FileViewModel}">
      <TextBlock Text="{Binding Name}" Opacity=".8" />
    </DataTemplate>
  </TreeView.Resources>

  <TreeView.ItemContainerStyle>
    <Style TargetType="TreeViewItem">
      <Setter Property="IsExpanded" Value="{Binding IsExpanded, Mode=TwoWay}" />
      <Setter Property="IsSelected" Value="{Binding IsSelected, Mode=TwoWay}" />
    </Style>
  </TreeView.ItemContainerStyle>
</TreeView>

Binding IsExpanded and IsSelected back to the view model is the standard way to control a TreeView from MVVM. TreeView.SelectedItem is read-only, so there is no other route.

Logical tree versus visual tree

WPF keeps two trees for the same window, and each feature follows one or the other. Mixing them up is behind many "why is this null" questions.

The logical tree is what you wrote in XAML: window → panel → button → string. It carries DataContext, resource lookup, and property value inheritance.

The visual tree is the expansion after templates are applied: window → border → panel → button → chrome border → content presenter → text block. It is what gets rendered and hit-tested, and what routed events travel (Part 6).

IN PLAIN TERMS

Your XAML is the floor plan: a window, a panel, a button. The visual tree is the finished building, with every wall, frame and fitting the builder added to realise that plan, such as the border and text block inside the button. Settings that flow from room to room, like DataContext, follow the plan; drawing, hit-testing and routed events work on the building. The fittings inside each control are only added when its template is applied, which is why they are missing in a constructor.

Walking the visual tree from code DEEPER

Occasionally you need an element that only exists in the visual tree, such as the container around the item that was clicked. VisualTreeHelper exposes parents and children; these two helpers wrap it. FindAncestor walks up from an element, and FindDescendants yields every matching element below one.

C# 
public static class TreeSearch
{
public static T? FindAncestor<T>(DependencyObject start) where T : DependencyObject
{
    for (var d = start; d is not null; d = VisualTreeHelper.GetParent(d))
        if (d is T match) return match;
    return null;
}

public static IEnumerable<T> FindDescendants<T>(DependencyObject root) where T : DependencyObject
{
    for (int i = 0; i < VisualTreeHelper.GetChildrenCount(root); i++)
    {
        var child = VisualTreeHelper.GetChild(root, i);
        if (child is T match) yield return match;
        foreach (var nested in FindDescendants<T>(child)) yield return nested;
    }
}
}
GOTCHA

Template parts do not exist until the template has been applied. After InitializeComponent the panels and controls you wrote are there, but the elements inside each control's template are not, so VisualTreeHelper cannot find them in a constructor. Do this work in OnApplyTemplate for a custom control, or in the Loaded event otherwise. And if you find yourself walking the visual tree in application code rather than control code, there is usually a binding that would do the job instead.

RECAP
  • A ContentControl holds one thing, a HeaderedContentControl holds a header and one thing, and an ItemsControl holds a collection.
  • Content can be any object: strings become text, elements draw themselves, and other objects are drawn by a matching DataTemplate or shown with ToString().
  • A list wraps each item in a container, and ItemTemplate, ItemContainerStyle, ItemsPanel and Template each customise a different layer.
  • Inside an item template the DataContext is the item, not the list's view model.
  • The logical tree is what you wrote; the visual tree is what gets drawn, and the elements inside each control's template only appear once that template is applied.
