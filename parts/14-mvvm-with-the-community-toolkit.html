PART 14

MVVM with the Community Toolkit

This is the part that has changed most since the books. Everything below replaces roughly two hundred lines of hand-written boilerplate in every old sample you'll read.

Builds on Part 11, data binding, Part 6, routed events and commands and Part 10, templates.

What MVVM actually buys you

Put a screen's logic in its event handlers and it works, until you want to test it without opening a window, give it a different layout, or find which of forty handlers changed a value. MVVM (Model, View, ViewModel) is a way of splitting each screen so that the XAML only displays state and forwards input, while an ordinary C# class holds the state and the actions.

IN PLAIN TERMS

A view model is the screen with the pixels taken out: what the title says, whether Save is available, which task is selected, what happens when Delete is pressed. The XAML draws that state and passes the user's typing and clicks to it through bindings and commands. Because the view model is plain C#, a unit test can press Delete on it without a window ever existing.

Testability is part of the payoff, but not all of it: WPF's binding and templating engine is designed around this split. An implicit DataTemplate (one with a DataType and no key) chooses visuals by the type of the data object, which pays off once every screen and every row is a view model type. Triggers only reach state that is bound. Fight MVVM and you fight the framework.

The division:

  • Model: domain types and services. Knows nothing about WPF.
  • ViewModel: state and commands for one screen or one item. Knows nothing about WPF types, though it may know about abstractions like IDialogService. No using System.Windows; the usual exception is the collection view from Part 12 (CollectionViewSource lives in System.Windows.Data), which you either accept or wrap behind your own interface.
  • View: XAML plus, ideally, an empty code-behind, the .xaml.cs file paired with the XAML. Not zero code-behind as a religion; view-only concerns (focus management, animations, drag adorners) legitimately live there.

Observable properties

For the screen to follow a property, the property has to raise PropertyChanged (Part 11). Written by hand, that means a backing field and a setter with an equality check and a notification call, repeated for every property, plus extra notifications for any property computed from it. This is what every property looks like in older samples:

The old way 
public class TaskViewModel : INotifyPropertyChanged
{
    private string _title = "";
    public string Title
    {
        get => _title;
        set
        {
            if (_title == value) return;
            _title = value;
            OnPropertyChanged();
            OnPropertyChanged(nameof(DisplayName));
        }
    }

    public event PropertyChangedEventHandler? PropertyChanged;
    protected void OnPropertyChanged([CallerMemberName] string? n = null)
        => PropertyChanged?.Invoke(this, new PropertyChangedEventArgs(n));
}

The CommunityToolkit.Mvvm package produces all of that from attributes. It uses a source generator, a compiler plug-in that writes extra C# into your class during the build. That is why the class and the property are marked partial: you write one half, the generator writes the other. The class derives from ObservableObject, the toolkit's base class that implements INotifyPropertyChanged for you.

The current way 
using CommunityToolkit.Mvvm.ComponentModel;

public partial class TaskViewModel : ObservableObject
{
    public int Id { get; init; }

    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayName))]
    public partial string Title { get; set; }

    [ObservableProperty]
    [NotifyPropertyChangedFor(nameof(DisplayName))]
    public partial bool IsDone { get; set; }

    public string DisplayName => IsDone ? $"\u2713 {Title}" : Title;

    public TaskViewModel() => Title = "";   // see the note below
}

[NotifyPropertyChangedFor] makes the generated setters for Title and IsDone also announce DisplayName, which is computed from both.

GOTCHA

A partial property declaration cannot have an initialiser. public partial string Title { get; set; } = ""; does not compile, because the generator supplies the implementing declaration and that is where an auto-property initialiser would have to live. Set defaults in the constructor, or mark the property required. This is the one place the new syntax is less convenient than the old field form, and it catches everyone once.

The source generator writes the backing field, the setter with its equality check, the OnPropertyChanged call, and the dependent notifications. Two optional partial hooks let you intercept. A partial method hook is one the generated setter calls if you implement it; if you do not, the call is compiled away.

C# 
partial void OnTitleChanging(string oldValue, string newValue)
{
    // runs before the field is assigned; throw here to veto
}

partial void OnTitleChanged(string value)
{
    _logger.LogDebug("Title is now {Title}", value);
    IsDirty = true;
}
SINCE C# 13 / TOOLKIT 8.4

The public partial string Title { get; set; } form replaces the old [ObservableProperty] private string title; field syntax. Partial properties mean the generated member is the one you declared, so XML docs, attributes, nullability and IntelliSense all work properly. The field form still compiles; new code should use partial properties.

Commands

A button needs something to run when clicked, and a way to know whether it is allowed right now. WPF's answer is ICommand (Part 6): Execute does the work, CanExecute says whether it may, and the CanExecuteChanged event tells the button to ask again. Writing a command class per action is tedious, so [RelayCommand] generates a command property from an ordinary method.

IN PLAIN TERMS

A command is a job card with a status light: what to do, and whether it can be done now. A button bound to it greys itself out while the light is off. The button only looks at the light again when told it may have changed. WPF's routed commands are re-asked after almost any keyboard or mouse activity; the toolkit's commands are asked again only when you say so.

[NotifyCanExecuteChangedFor] is how you say so: whenever Draft or Selected changes, the matching command raises CanExecuteChanged and its button checks again. The listing shows the three shapes you will write most: synchronous with a guard, async with cancellation, and async with a parameter. Watch how each method name becomes a generated property. This TaskListViewModel and its TaskViewModel are separate, simpler versions of the ones in Part 12.

C# 
using CommunityToolkit.Mvvm.Input;

public partial class TaskListViewModel : ObservableObject
{
    private readonly ITaskRepository _repo;

    public TaskListViewModel(ITaskRepository repo) => _repo = repo;

    public ObservableCollection<TaskViewModel> Items { get; } = [];

    [ObservableProperty]
    [NotifyCanExecuteChangedFor(nameof(AddCommand))]
    public partial string Draft { get; set; }

    [ObservableProperty]
    [NotifyCanExecuteChangedFor(nameof(DeleteCommand))]
    public partial TaskViewModel? Selected { get; set; }

    // Synchronous, with a CanExecute guard
    [RelayCommand(CanExecute = nameof(CanAdd))]
    private void Add()
    {
        Items.Add(new TaskViewModel { Title = Draft.Trim() });
        Draft = "";
    }

    private bool CanAdd() => !string.IsNullOrWhiteSpace(Draft);

    // Async, cancellable, with automatic re-entrancy blocking
    [RelayCommand(IncludeCancelCommand = true, AllowConcurrentExecutions = false)]
    private async Task RefreshAsync(CancellationToken ct)
    {
        var rows = await _repo.GetAllAsync(ct);
        Items.Clear();
        foreach (var r in rows) Items.Add(new TaskViewModel { Id = r.Id, Title = r.Title, IsDone = r.IsDone });
    }

    // Parameterised
    [RelayCommand(CanExecute = nameof(CanDelete))]
    private async Task DeleteAsync(TaskViewModel item, CancellationToken ct)
    {
        await _repo.DeleteAsync(item.Id, ct);
        Items.Remove(item);
    }

    private bool CanDelete(TaskViewModel? item) => item is not null;
}

The generator produces AddCommand, RefreshCommand, RefreshCancelCommand and DeleteCommand: the method name without its Async suffix, plus Command. IncludeCancelCommand adds RefreshCancelCommand, which cancels the token passed to RefreshAsync. The async ones are IAsyncRelayCommand, which exposes IsRunning: bind a progress indicator straight to {Binding RefreshCommand.IsRunning} and delete your IsBusy property.

XAML 
<Button Content="Refresh" Command="{Binding RefreshCommand}" />
<Button Content="Cancel"  Command="{Binding RefreshCancelCommand}" />
<ProgressBar IsIndeterminate="True" Height="2"
             Visibility="{Binding RefreshCommand.IsRunning,
                          Converter={StaticResource BoolToVis}}" />

The converter is the BoolToVisibilityConverter from Part 11. The figure shows the two states you would see.

GOTCHA

AllowConcurrentExecutions = false is the default and it is what you want: it stops a user double-clicking Refresh into two overlapping requests. But it also means CanExecute returns false while running, so the button greys out. If the button shouldn't grey out, either allow concurrency and guard yourself, or bind IsEnabled separately.

Messaging between view models DEEPER

Sometimes two view models that do not know each other need to talk: a settings dialog telling the shell the theme changed, a save completing and a list needing a nudge. Handing each a reference to the other ties them together. A messenger gives you loose coupling instead: one side sends a message object, and any side registered for that message type receives it, with neither holding a reference to the other.

IN PLAIN TERMS

A messenger is a building's public address system. The sender announces "task 42 saved" without knowing who is listening, and only those who asked to hear that kind of announcement react. The same property is the cost: reading the code that reacts, you cannot see who made the announcement, or when. That is why it should stay an occasional tool, not the default way view models talk.

C# 
using CommunityToolkit.Mvvm.Input;
using CommunityToolkit.Mvvm.Messaging;

public sealed record TaskSaved(int Id);

// Publisher
WeakReferenceMessenger.Default.Send(new TaskSaved(task.Id));

// Subscriber: ObservableRecipient auto-registers/unregisters with IsActive
public partial class SidebarViewModel : ObservableRecipient, IRecipient<TaskSaved>
{
    public void Receive(TaskSaved message) => RefreshCommand.Execute(null);

    [RelayCommand]
    private void Refresh() { /* reload the sidebar's counts */ }
}

ObservableRecipient registers every IRecipient<T> handler when you set its IsActive to true, and unregisters them when you set it back to false. WeakReferenceMessenger holds weak references (references that do not keep the recipient alive), so a forgotten unregister leaks nothing. StrongReferenceMessenger is faster and will leak if you forget. Default to the weak one.

There is also a request/response shape, useful for "does anyone want to veto this close?":

C# 
public sealed class HasUnsavedChangesRequest : CollectionRequestMessage<bool> { }

// Ask:
bool dirty = WeakReferenceMessenger.Default.Send<HasUnsavedChangesRequest>().Any(r => r);

// Answer:
public void Receive(HasUnsavedChangesRequest m) => m.Reply(IsDirty);

The request derives from CollectionRequestMessage<T> (in CommunityToolkit.Mvvm.Messaging.Messages) because several open editors may answer: it collects every reply, and Any asks whether any of them has unsaved changes. A plain RequestMessage<T> accepts exactly one reply and throws on a second.

A view model base worth having DEEPER

Most pages in an app need the same few things: a title, a moment to load their data when shown, and a chance to object before the user navigates away. A small base class gives every page those hooks in the same shape.

C# 
public abstract partial class PageViewModel : ObservableObject
{
    [ObservableProperty] public partial string Title { get; set; }
    [ObservableProperty] public partial bool IsLoaded { get; set; }

    protected PageViewModel(string title) => Title = title;

    /// <summary>Called once when the page becomes visible.</summary>
    public virtual Task LoadAsync(CancellationToken ct) => Task.CompletedTask;

    /// <summary>Return false to veto navigation away.</summary>
    public virtual Task<bool> CanLeaveAsync() => Task.FromResult(true);
}

Resist the urge to grow this into a framework. A base class with Title, a load hook and a leave hook covers almost everything; anything more is usually a service in disguise.

Design-time data DEEPER

The Visual Studio XAML designer draws your view without running the app, so no view model exists and every bound value is blank. Design-time data gives the designer a view model of its own. It is worth five minutes of setup, because it turns the XAML designer from useless into useful. First, a view model subclass filled with sample content:

C# 
public sealed class DesignTaskListViewModel : TaskListViewModel
{
    public DesignTaskListViewModel() : base(new FakeRepository())
    {
        Items.Add(new TaskViewModel { Title = "Read the value precedence list" });
        Items.Add(new TaskViewModel { Title = "Freeze the theme brushes", IsDone = true });
        Selected = Items[0];
    }
}

Then point the view at it. Attributes with the d: prefix are for the designer only: mc:Ignorable="d" tells the compiler and the runtime XAML reader to skip them; only the designer reads them, so the real DataContext is untouched.

XAML 
<UserControl ...
  xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
  xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
  mc:Ignorable="d"
  d:DataContext="{d:DesignInstance design:DesignTaskListViewModel, IsDesignTimeCreatable=True}">

IsDesignTimeCreatable=True actually constructs the object, so you see real content. Without it you get type information only: still enough for binding IntelliSense, which is most of the value.

RECAP
  • A view model is a plain C# class holding a screen's state and actions; the XAML only draws it and forwards input through bindings and commands.
  • [ObservableProperty] on a partial property generates the change notification you used to write by hand.
  • A partial property cannot have an initialiser, so set defaults in the constructor.
  • [RelayCommand] turns a method into a command, and [NotifyCanExecuteChangedFor] tells its button when to check again.
  • Async commands expose IsRunning and, by default, refuse to start again until the current run finishes.
  • Use the messenger for occasional announcements between unrelated view models, not as the main way they talk.
